# start-step

参数：节号（如 `2.3`）。没给编号时，读学习者的进度分支 `<名字>-main` 上已经有哪些 `tests/test_X_Y.py`，推断下一步，并向学习者确认。

节号永远指路线图的节。一节内部的任务叫任务 A / B / C，不用数字。

## 1. 准备环境

学习者的进度分支是 `<名字>-main`（维护者的是 `kyrie-main`）。这一节从它上面切出来：

```bash
git status --short                       # 有未提交的改动就先停下，问学习者怎么处理
git checkout <名字>-main
git fetch upstream && git merge upstream/main     # 文档和 skill 始终用最新版；main 上没有实现，不会冲突
git checkout -b learn/<节>
git submodule update --init reference/DeepInfer
```

- 还没有 `<名字>-main` 的（第一次用）：`git checkout -b <名字>-main main && git push -u origin <名字>-main`，再切 `learn/<节>`。
- 上一节还没做完就想跳到这一节：`git fetch upstream --tags && git checkout <上一节>-done -- nanovllm tests bench`，把维护者的实现拿过来当起点，并说明这一点。tag 不存在就只能从当前进度往下做。
- 如果 `reference/DeepInfer` 是空的或没有 `upstream`，运行 `bash scripts/setup_reference.sh`。
- **跑实验的地方**：本机有 GPU 就直接跑；没有就用 `modal run scripts/modal_run.py --cmd "<命令>"`（用法在文件头）。第一次用 Modal 之前，让学习者先在 Usage & Billing 页面设好 budget $30、spend limit $0。文档里的命令都是本机形式，在 Modal 上跑就包一层 `--cmd`。

## 2. 读材料

- `doc/<节>-*.md`：这一步的文档。开头那张表（问题 / 实验 / 硬件 / 学到 / 时长）先念给学习者，让他知道要投入什么、换回什么。文档还没写的，用 `doc/README.md` 路线图里这一步的描述，再到 `reference/DeepInfer` 里找到对应代码，现场备课（结构参照 `doc/_template.md`）。
- 上一步的卡片（`doc/cards/`），用来做衔接。
- `nanovllm/` 里要改的文件，先自己读一遍，确认行号。

## 3. 发现问题（这一步最重要，不要赶）

学习者是新手，**要给方向，但结论让他自己说**。

1. 用一两句话交代背景：上一步解决了什么，现在的引擎处在什么状态。
2. 告诉他这一步要关注哪一类问题（比如"看看长 prompt 进来时 decode 怎么样"），然后给出文档"发现问题"里的实验命令（负载场景加指标）。文档还没写的，按路线图里"现象"一列现场设计一个实验。
3. **先请学习者预测**：跑之前，他觉得会看到什么？
4. 学习者跑完后，问他：哪个数字不对劲？和你的预测差在哪？
5. 学习者没看出来时，逐步缩小范围：先提示看哪个指标，再提示看哪段时间，最后提示看哪一个请求。

问题没有被复现出来之前，不进入下一节。这是两个必须等他回答的地方之一。

## 4. 分析问题

从现象一层层追问到本质，每次只问一个问题，让学习者自己回答：

1. 这个现象是哪段代码造成的？带他去读 `nanovllm/` 里的对应位置，粒度按 `.claude/skills/learn-codebase/SKILL.md`。
2. 根本原因是什么？卡在哪种资源上？**根本原因要他自己说出来**，这是第二个必须等的地方。
3. **这时候才引出理论**：这个现象在哪篇论文里讨论过（优先从 `reference/gpu-perf-engineering-resources/` 里找），用三到五句话说清楚。
4. 量化：用一个简单算式估一下，这个问题吃掉了多少吞吐或延迟，和实测数字对一对。算式让他算，数字对不上时一起找哪一项漏了（1.1 里漏乘 batch、单位换错，都是这样抓出来的）。

其余的问题都是思考题：放在一段讲解的末尾，他想答就答，不答就直接给下一步。

## 5. 看 DeepInfer 怎么解决，备好脚手架，布置任务

1. 先请学习者想一想可以怎么解决，然后带他读 DeepInfer 的做法（`reference/DeepInfer/...`），讲清楚它为什么这样选。**实现方向以 DeepInfer 为准**，其他方案只用来做对比。
2. **把任务收成最多三个**，每个约 20 分钟。文档里已经分好的照文档；没分好的，按"每个任务对应分析里的一个结论"来切。
3. **先写脚手架，再布置任务。** 样板代码、CLI、IO、报告格式、数据类的字段、测试，都在这一步写进文件。只把承载 why 的函数体留成 `TODO(<节>)` + 签名 + 一行说明。每个任务留给学习者的量在 50 行上下，按逻辑密度调整。
4. `tests/test_<节>.py`（点换下划线）不存在就写，把"发现问题"的实验写成断言，纯 Python 的部分不依赖 GPU。**跑一遍，确认它在当前代码上是失败的**，把失败信息给学习者看。
5. **布置任务**，每个任务讲四样：
   - 目标：做完手上多了什么
   - 思路：数据从哪来、流到哪去、为什么这样拆，对回分析里的结论
   - 已备好 / 你写什么：哪些文件已经写好，哪几个函数体是他的；最容易写错的那一两处先点出来
   - 预估：约 20 分钟、约 N 行
6. 告诉学习者：写完之后用 `check-step <节>` 验收。

## 6. 实现过程中

遵守 `AGENTS.md` 里的导师模式：提示分层给（方向 → 位置 → 伪代码 → 答案）。学习者要答案时，代码贴在对话里逐段讲解，由他自己抄进文件；他说"直接写进去"才动文件。他抄完让你检查时，逐处指出错在哪、为什么错；他说"帮我改"再改。
