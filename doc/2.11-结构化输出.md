# 2.11：一个 JSON 请求拖慢所有人

> 起点：2.10 做完的代码　硬件：1×H100，Qwen3-8B　预计改动：300–450 行　轴：7 采样 / 1 调度

## 1. 发现问题

**关注什么**：带语法约束（JSON schema / 正则 / EBNF）的请求混进普通流量后，谁的延迟变了。

先用最直接的方式实现一版：每步采样前，对每个 SO 请求在 CPU 上算出允许的 token 集合，做成 `[V]` 的位掩码，`logits[~mask] = -inf`。然后：

```bash
python -m bench.run --scenario steady_decode          # 混入 10% 的 JSON schema 请求（workloads 里加一个 so_ratio）
```

**先预测**：10% 的请求带 schema，另外 90% 的 TBT 会变吗？schema 第一次出现时发生了什么？

**现象**：

- 新 schema 第一次出现的那一步，`cpu_schedule`（或你放编译的那一段）跳到几百毫秒：grammar 编译是重活。**所有** 256 个请求在这一步停住。
- 之后每步 `cpu_*` 里多了一块：逐 SO 请求推进自动机、生成 `[V]` 位掩码、H2D。十几个 SO 请求就是几毫秒，又回到 2.5 的状况。
- 2.8 的投机解码下，draft token 也要过语法：一步要推进 `nextn+1` 次，再回退。

## 2. 分析问题

- **追问链**：所有人变慢 → 编译在主循环里同步做 → 应该异步编译，没编译好的请求不入队。每步变慢 → 掩码生成和拷贝在关键路径上 → 放到侧 stream，和 forward 重叠。投机解码下 → 自动机要能 rollback。
- **本质**：SO 的工作有两种时间尺度：编译一次（百毫秒级，CPU）和每步推进（微秒到毫秒，CPU），两者都不该挡住 GPU。
- **理论**：`reference/gpu-perf-engineering-resources/` §4 Structured decoding：Outlines 的 FSM 索引（把正则编译成"状态 → 允许 token 集"的表）、XGrammar（带上下文无关文法的快速引擎）、"Guiding LLMs the Right Way"（约束不改变期望分布）。
- **DeepInfer 怎么做**（`deepinfer/structure_output/`，595 行；`sampler.py:302-408`）：
  - **编译异步**：`SOMatcherBuilder`（`so_matcher_builder.py`）线程池绑在空闲 CPU 上，`submit`（`:97`）提交编译，`pump`（`:109`）每步在 `pre_sampler_sync` 里轮询，编译好的请求才 `add_sequence`。超时 `DEEPINFER_XGRAMMAR_TIMEOUT`（20 s）→ matcher 标 aborted → 请求 `FINISHED_SO_FAILED`。编译结果有缓存（10 GiB 上限）。
  - **每步推进**：driver 上逐请求 `_get_so_mask`（`sampler.py:302`）：先把上一步接受的 token 回放进 matcher，填第 0 步的位掩码；然后对每个 draft token 试探性接受、填第 1..k 步的掩码，再 `rollback`（`matcher.py:206`，最多 `nextn+2` 步）。掩码写进 pinned buffer，**侧 stream** H2D，采样 kernel 等这个 stream 的 event。
  - **kernel 内应用**：`apply_token_bitmask_by_step_inplace`（`tilelang_ops/structure_output.py`），位掩码 `[total_q, V/32]`，在 fused_sample 之前就地把 logits 置 -inf。
  - **状态账本**：`so_status` 0 未开始 / 1 刚开始（最后一个 prefill chunk 设，`llm_engine.py:910-928`）/ 2 进行中 / -1 出错 → `FINISHED_SO_FAILED`。
  - SO 请求**不能被抢占重算**（`scheduler.hpp:770-780`），直接结束；fork 时 `copy_without_status`。
  - 触发 token：`trigger_token_ids`，在出现某个序列之前自由生成（比如先 think 再输出 JSON）。

## 3. 要做什么

### 3.1 编译器和 matcher

**新建** `nanovllm/structure_output/`：`compiler.py`、`matcher.py`、`builder.py`。

- 用 xgrammar：`GrammarCompiler` 编译 JSON schema / regex / EBNF 到 `CompiledGrammar`，带缓存；`GrammarMatcher` 做推进、`fill_next_token_bitmask`、`rollback`。
- `Matcher` 包装：`advance(token)`、`fill_mask(out[V/32])`、`rollback(n)`、`is_terminated`、`copy_without_status`（2.4 的 fork 用）。

### 3.2 异步编译和入队

**改哪里**：`llm_engine.py` 的 `add_request`，`SamplingParams` 加 `so_args`。

- 有 `so_args` 的请求先 `builder.submit(seq, so_args)`，不入调度器；每步 `builder.pump()` 把编译完成的入队，超时的标 `FINISHED_SO_FAILED`（2.1 的状态机加这一个值，`finish_reason = "xgrammar runtime errors or timeout"`）。
- `pump()` 放在 2.7 的 post-process 之后、GPU 忙的时候。

### 3.3 每步掩码

**改哪里**：`layers/sampler.py`、`model_runner.py`。

- driver 上对每个 SO 请求：回放上一步接受的 token → 填第 0 步掩码；2.8 开着时对每个 draft token 试探 `advance` 填后续掩码，然后 `rollback`。
- 掩码写进预分配的 pinned `[max_total_q, V/32]`，用一个**侧 stream** H2D，记 event；采样 kernel 所在 stream `wait_event`。
- 2.10 的 fused_sample 之前加一个 Triton kernel：按位掩码把 logits 置 -inf（或并进 fused_sample）。
- 不是 SO 的请求行不填、不传。

### 3.4 状态账本和边角

- `Sequence.so_status`：0 / 1 / 2 / -1，最后一个 prefill chunk 时置 1；采样时 -1 直接跳过并在 post-process 标 `FINISHED_SO_FAILED`。
- 2.3 的抢占：SO 请求走 `stop_preempted_request` 路径。
- 2.4 的 fork：复制 matcher。
- `Config.so_builder_threads`，默认按空闲 CPU 数。

## 4. 验收

同一个实验重跑（10% SO 请求）：

1. 非 SO 请求的 TBT p50 / p99 和没有 SO 请求时一致（目标：差异 < 5%）。
2. 新 schema 出现的那一步不再有几百毫秒的停顿；SO 请求的 TTFT 包含编译时间，写进报告。
3. SO 请求的输出 100% 符合 schema（用 `jsonschema` 校验）；带投机解码时同样。
4. 一个编译不出来的 schema（或人为把超时设成 1 ms）：请求以 `xgrammar runtime errors or timeout` 结束，别的请求不受影响。
5. `tests/test_2_11.py`：(a) 掩码 kernel 和 `logits[~mask] = -inf` 一致；(b) 试探 + rollback 后 matcher 状态不变；(c) 超时路径；(d) fork 后两个分支各自独立推进；(e) 2.1–2.10 全过。

**新浮现的问题**：同一个 prompt 放进不同大小的 batch 里，logprob 不一样。这是 2.12。

## 常见坑

- xgrammar 的 matcher 不是线程安全的，推进只在 driver 线程做；编译才用线程池。
- 位掩码的 `V` 要按 tokenizer 的真实词表大小对齐到 32，和 2.10 的强制 top-K 空间要协调：掩码要在 top-K 之前应用，否则允许的 token 可能已经被截掉。
- 投机解码下 draft 被拒绝时，matcher 已经 rollback，但 2.8 的 pool 里下一步的 draft 还是按旧状态生成的，没关系，验证时会再过一遍掩码。
- 侧 stream 的 event 一定要等，否则采样读到上一步的掩码，错得很隐蔽。
