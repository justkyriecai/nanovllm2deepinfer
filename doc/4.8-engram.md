# 4.8：n-gram 表比显存大，每层查一次

> 起点：4.7 做完的代码　硬件：1×B200（单卡先做本地版本）　预计改动：600–900 行　轴：2 显存 / 3 访存 / 4 模型结构

## 1. 发现问题

**关注什么**：config 里的 `engram_layer_ids`、`engram_max_ngram_size`、`engram_vocab_size`、`engram_n_heads`、`engram_head_dim`、`engram_compressed_vocab_size`，和 HF 权重里 `engram_embedding.embedding [rows, head_dim]` 这些巨大的表。

先算一道题，再做一个朴素实现：

```bash
python - <<'EOF'
import json; c = json.load(open("config.json"))["text_config"]
n_tables = c["engram_max_ngram_size"] - 1
rows = n_tables * c["engram_n_heads"] * c["engram_vocab_size"]     # 每层，素数取整后略大
print(len(c["engram_layer_ids"]), "layers ×", rows, "rows ×", c["engram_head_dim"], "× 1 B (fp8) =", len(c["engram_layer_ids"]) * rows * c["engram_head_dim"] / 2**30, "GiB")
EOF
```

朴素实现：表放 GPU（放不下就放 host pinned 内存），每个 engram 层 forward 时按 token 的 n-gram 哈希 `index_select`，投影，加进残差。

```bash
nsys profile python -m tests.v4.harness --layers 0..K --decode --batch 64   # K 要覆盖至少一个 engram 层
```

**先预测**：表总共多大？放 host 的话，每个 engram 层一次 gather 要等多久？能不能在算前面几层的时候就把表查好？

**现象**：

- 表的总大小按 config 算出来是几十 GiB 的量级（具体数字写进报告），和权重加 KV 抢显存；多卡时还要分片。
- 放 host 时每个 engram 层前面有一段 H2D gather 的等待，GPU 空转；放 GPU 时 KV 预算被挤掉一大块。
- 查表的 key 不是原始 token id：HF 的实现先把 token 过一个"压缩 tokenizer"（大小写、空白归一化），再对最近 `n` 个压缩 id 做哈希。2.7 的 ZOS 下，上一步采样的 token 还在 GPU 上，CPU 拼不出这一步的 n-gram。

## 2. 分析问题

- **追问链**：表太大 → 不能全放 GPU → 放 host（多卡时分片到各 rank 的 host 内存）→ 每层同步取太慢 → 整个 forward 的 n-gram 哈希在第 0 层之前就能算出来（只依赖 token id）→ 所有 engram 层的 fetch 在层循环之前一起发出去，异步，第 i 层用到时才等 → 取回来的 embedding 过一个投影，按门控加进四路残差（在 4.7 的 post 之后、pre 之前）→ ZOS 下 n-gram 的 token 在 GPU 上，哈希的输入要在 GPU 上 gather。
- **本质**：engram 是一个"条件记忆"：用 n-gram 哈希做 key 的稀疏查表，容量大但每 token 只碰几行。它的推理问题是经典的 embedding 表问题：容量放 host / 远端，延迟靠预取隐藏。
- **量化**：每 token 每层取 `(max_ngram − 1) × n_heads` 行，每行 `head_dim` 字节（fp8）+ scale；batch 256 一步所有 engram 层加起来几 MB，PCIe / RDMA 一次几十微秒。预取后这个时间和前面几层的计算重叠。
- **理论**：DeepSeek 的 Engram 报告（不在清单里）：n-gram 哈希嵌入作为 attention 之外的记忆通道。`reference/gpu-perf-engineering-resources/` §5 的 DeepEP 是 DeepInfer 实际用的传输层（RDMA 读 host 表）。
- **DeepInfer 怎么做**（`models/v4_modules/engram*.py`）：
  - **压缩 tokenizer**：`CompressedVocabulary`（`engram_metadata.py:16`）用 HF tokenizers 的 normalizer（NFKC、去重音、小写、空白合并）把每个原始 token 的文本归一化，再映射到压缩 id；运行时是一张 `lookup_table [vocab] int32`。
  - **表布局**：`EngramLayout`（`:59`）：每层、每个 n（2..max）、每个头一张表，大小取**互不相同的素数**（`nextprime`），哈希 `(Σ multiplier_k × id_k) mod prime` 落进各自的表；`NgramHashMapping`（`:98`）按层 seed 生成 multipliers；`engram_hash` kernel（`deepseek.py:180`）一次算出所有层所有 token 的表内行号。
  - **参数**：`NgramEmbeddingParameters`（`engram_parameters.py:16`）按 engram 并行组分片，行数 pad 到 `lcm(256, size)`，FP8 + UE8M0 scale。
  - **存储和取数**：`EngramRuntime.allocate`（`engram.py:171`）→ `userbuffer.allocate_engram`（`userbuffer.py:127`）建 DeepEP 的 `EngramBuffer`：GPU 一小块 staging，表本体默认放 **host**（`use_cpu_rdma_storage`，`DEEPINFER_ENGRAM_FORCE_GPU_STORAGE` 可改），RDMA 读；`initialize`（`:195`）把本 rank 的分片写进去后释放原参数。`fetch(hashes)`（`:214`）**一次发出所有层的取数**，返回 `{layer_id: hook}`，hook 调用时才等待并返回 `[total_q, (max_ngram−1) × n_heads × head_dim]`。
  - **层内**：`Engram.forward`（`:139`）：`fused_kv_projection(embed_hook())` 投影到 `(hc_mult + 1) × H`，`engram_gate_fwd` 按门控把它融进四路 trunk（`inplace=True`）。挂在 `hc_post_intervention`（`decoder_layer.py:111-118`）：4.7 的 post 之后、pre 之前，所以 engram 层**不能用** `mega_mhc`（`hc.py:195`）。
  - **输入**：`ngram_token_ids [total_q, max_ngram_size]` 由 C++ 填（`prepare_tensor_input_base.cpp:126-132`，用压缩后的历史 + draft token）；ZOS 下 `gather_engram_tokens_zos`（`tilelang_ops/gather_engram_tokens_zos.py:10`）在 GPU 上按 `remap` 从上一步的采样 / draft 结果里取、过 `lookup_table` 压缩、拼上 CPU 建好的窗口（`zos.cpp:53-74`）。
  - **多卡**：表按 `engram_parallel_size` 分片，可以跨多个 DP 副本（`config.py:172`）；5.x 再做。

## 3. 要做什么

### 3.1 压缩 tokenizer 和哈希

**新建** `nanovllm/layers/engram.py`、`nanovllm/utils/engram_vocab.py`。

- 启动时建 `lookup_table`：照 `engram_metadata.py:24-50` 的 normalizer 序列，逐 token 解码、归一化、去重得到压缩 id。
- `EngramLayout`：素数表大小（`sympy.nextprime`，全局去重），multipliers 按层 seed；`engram_hash` 先 PyTorch（int64 乘加取模），再 Triton。
- C++ 填 `ngram_token_ids [total_q, max_ngram]`：每个 query 位置往前取 `max_ngram` 个压缩 id（跨 chunk 用序列的历史，draft 位置用 draft token），不足补 pad。

### 3.2 表和取数（单卡本地版）

- 表放 host pinned 内存（放得下就放 GPU，`Config.engram_storage = "cpu" | "cuda"`），FP8 + scale。
- `EngramRuntime.fetch(hashes) -> {layer_id: hook}`：在层循环之前，对所有 engram 层发出异步 gather（host 表：用一个侧 stream 做 `index_select` 到 pinned 再 H2D，或 UVA 直接 gather；GPU 表：侧 stream `index_select`），记 event；hook 调用时 `wait_event` 返回。接口和 DeepInfer 的 `EngramBuffer.fetch` 一致，5.x 换 DeepEP RDMA 时只换实现。

### 3.3 层内融合

- `fused_kv_projection`：FP8 linear（3.3），输出 `(hc_mult + 1) × H`，拆成 `hc_mult` 份 value 和 1 份 gate。
- `engram_gate`：先 PyTorch（照 HF modeling 的门控公式，`eps`、`clamp_value`），再 Triton，原地写 trunk。
- 4.7 的 `attn_norm_forward` 加 `hc_post_intervention` 参数；engram 层走非融合路径（post → 干预 → pre）。

### 3.4 ZOS

- `gather_engram_tokens_zos`（Triton）：按 `remap` 从上一步的 `sampled / predict` 取、`lookup_table` 压缩、拼 CPU 建的窗口 `win_compressed [n_seq, nextn + max_ngram − 1]`，被拒绝的 draft 按 `num_accepted` 跳过。

## 4. 验收

1. 同一个实验重跑：engram 层前面的 H2D 等待消失（fetch 在第 0 层前发出，Nsight 里看到 gather 和前面层的计算重叠）；表放 host 时 KV 预算不变。
2. harness：engram 层的输出和 DeepInfer 一致（prefill、decode、decode 带 draft）。
3. `tests/test_4_8.py`：(a) `lookup_table` 和 DeepInfer 的 `CompressedVocabulary` 逐 id 一致；(b) 哈希和 `NgramHashMapping` 一致（同 seed）；(c) `ngram_token_ids` 的 C++ 填法和 Python 参考一致，含 chunk 边界和 draft；(d) ZOS gather kernel 和 `gather_engram_tokens_zos_ref` 一致；(e) 门控 kernel 和 PyTorch 参考一致；(f) 前面全过。

**新浮现的问题**：V4.1 一层的其它部分都对上了，MoE 用的还是 3.3 的 FP8 专家和十几个 kernel 的链。B200 上 config 要求专家是 FP4，而且 DeepInfer 的 MoE 是一个 kernel。这是 4.9。

## DeepInfer 对照

| 这一节 | DeepInfer | 差异和原因 |
|---|---|---|
| 压缩 tokenizer | `CompressedVocabulary`（`engram_metadata.py:16`） | 一致 |
| 素数表 + 哈希 | `EngramLayout / NgramHashMapping`（`:59 / :98`） | 一致 |
| host 表 + 侧 stream gather | DeepEP `EngramBuffer`，RDMA（`userbuffer.py:127`） | 5.x 换 |
| 层前一次 fetch，hook 延迟等待 | `EngramRuntime.fetch`（`engram.py:214`）、`deepseek.py:188` | 一致 |
| 门控融合作为 post 干预 | `decoder_layer.py:111-118`、`engram.py:139` | 一致 |
| ZOS gather | `gather_engram_tokens_zos.py:10` | 一致 |
| 单卡不分片 | 按 `engram_parallel_size` 分片 | 5.x |

## 常见坑

- 压缩 tokenizer 的 normalizer 顺序和 sentinel 处理要和 DeepInfer 完全一样，否则哈希全错但不报错；先对 `lookup_table`。
- 素数要**全局**去重（跨层跨头），`EngramLayout` 用一个 `seen` 集合。
- `ngram_token_ids` 的 pad 用 `engram_pad_token_id` 的压缩 id，不是 0。
- engram 层不能走 4.7 的融合路径，`use_mega_mhc` 要按层关。
- host 表的 gather 要在侧 stream，并且 pinned；用普通 pageable 内存 `index_select` 再 `.cuda()` 会同步。
