# 4.8：n-gram 表比显存大，每层查一次

> 起点：4.7 做完的代码　轴：2 显存 / 3 访存 / 4 模型结构

| | |
|---|---|
| **问题** | engram 的表按 config 算是几十 GiB，放 GPU 挤掉一大块 KV 预算，放 host 则每个 engram 层前面有一段 H2D gather 的等待、GPU 空转；而且查表的 key 不是原始 token id，ZOS 下上一步的 token 还在 GPU 上，CPU 拼不出 n-gram。本质是经典的大 embedding 表问题：key 只依赖 token id，整个 forward 的哈希在第 0 层之前就能算出来，所有层的取数一次发出去、用前面几层的计算把延迟藏起来 |
| **实验** | `nsys profile -t cuda,nvtx,osrt --sample=none --cpuctxsw=none -o out/v4-engram python -m tests.v4.harness --layers 0..K --decode --batch 64`（K 覆盖至少一个 engram 层），盯 engram 层前面那段 H2D gather 等待 |
| **硬件 / 费用** | 1×B200（单卡先做本地版本）+ V4.1-Flash 前几层权重，Modal 约 $6.25/h；表放 host pinned 内存；发现实验加对拍约 3 小时，约 $20 |
| **学到** | n-gram 哈希的输入只有 token id，所以所有 engram 层的 fetch 可以在层循环之前一起发出去、第 i 层用到时才等，这是"容量放 host、延迟靠预取隐藏"的 embedding 表套路；查表的 key 是压缩 tokenizer 归一化之后的 id，normalizer 顺序和 sentinel 处理错一点哈希全错但不报错，所以先对 `lookup_table`；取回来的 embedding 按门控加进四路残差要插在 4.7 的 post 之后、pre 之前，所以 engram 层不能走 `mega_mhc` |
| **时长** | 发现 + 分析约 2 小时；任务 A 约 40 分钟、任务 B 约 30 分钟、任务 C 约 20 分钟；验收约 1 小时。改动约 600–900 行 |

## 发现问题

**关注什么**：config 里的 `engram_layer_ids`、`engram_max_ngram_size`、`engram_vocab_size`、`engram_n_heads`、`engram_head_dim`、`engram_compressed_vocab_size`，和 HF 权重里 `engram_embedding.embedding [rows, head_dim]` 这些巨大的表。

先算一道题，再做一个朴素实现：

```bash
python - <<'EOF'
import json; c = json.load(open("config.json"))["text_config"]
n_tables = c["engram_max_ngram_size"] - 1
rows = n_tables * c["engram_n_heads"] * c["engram_vocab_size"]     # 每层，素数取整后略大
print(len(c["engram_layer_ids"]), "layers ×", rows, "rows ×", c["engram_head_dim"], "× 1 B (fp8) =", len(c["engram_layer_ids"]) * rows * c["engram_head_dim"] / 2**30, "GiB")
EOF
```

朴素实现：表放 GPU（放不下就放 host pinned 内存），每个 engram 层 forward 时按 token 的 n-gram 哈希 `index_select`，投影，加进残差。

```bash
nsys profile -t cuda,nvtx,osrt --sample=none --cpuctxsw=none -o out/v4-engram python -m tests.v4.harness --layers 0..K --decode --batch 64   # K 要覆盖至少一个 engram 层
```

**先预测**：表总共多大？放 host 的话，每个 engram 层一次 gather 要等多久？能不能在算前面几层的时候就把表查好？

**现象**：

- 表的总大小按 config 算出来是几十 GiB 的量级（具体数字写进报告），和权重加 KV 抢显存；多卡时还要分片。
- 放 host 时每个 engram 层前面有一段 H2D gather 的等待，GPU 空转；放 GPU 时 KV 预算被挤掉一大块。
- 查表的 key 不是原始 token id：HF 的实现先把 token 过一个"压缩 tokenizer"（大小写、空白归一化），再对最近 `n` 个压缩 id 做哈希。2.7 的 ZOS 下，上一步采样的 token 还在 GPU 上，CPU 拼不出这一步的 n-gram。

## 分析问题

- **追问链**：表太大 → 不能全放 GPU → 放 host（多卡时分片到各 rank 的 host 内存）→ 每层同步取太慢 → 整个 forward 的 n-gram 哈希在第 0 层之前就能算出来（只依赖 token id）→ 所有 engram 层的 fetch 在层循环之前一起发出去，异步，第 i 层用到时才等 → 取回来的 embedding 过一个投影，按门控加进四路残差（在 4.7 的 post 之后、pre 之前）→ ZOS 下 n-gram 的 token 在 GPU 上，哈希的输入要在 GPU 上 gather。
- **本质**：engram 是一个"条件记忆"：用 n-gram 哈希做 key 的稀疏查表，容量大但每 token 只碰几行。它的推理问题是经典的 embedding 表问题：容量放 host / 远端，延迟靠预取隐藏。
- **量化**：每 token 每层取 `(max_ngram − 1) × n_heads` 行，每行 `head_dim` 字节（fp8）+ scale；batch 256 一步所有 engram 层加起来几 MB，PCIe / RDMA 一次几十微秒。预取后这个时间和前面几层的计算重叠。
- **理论**：DeepSeek 的 Engram 报告（不在清单里）：n-gram 哈希嵌入作为 attention 之外的记忆通道。`reference/gpu-perf-engineering-resources/` §5 的 DeepEP 是 DeepInfer 实际用的传输层（RDMA 读 host 表）。
- **DeepInfer 怎么做**（`models/v4_modules/engram*.py`）：
  - **压缩 tokenizer**：`CompressedVocabulary`（`engram_metadata.py:16`）用 HF tokenizers 的 normalizer（NFKC、去重音、小写、空白合并）把每个原始 token 的文本归一化，再映射到压缩 id；运行时是一张 `lookup_table [vocab] int32`。
  - **表布局**：`EngramLayout`（`:59`）：每层、每个 n（2..max）、每个头一张表，大小取**互不相同的素数**（`nextprime`），哈希 `(Σ multiplier_k × id_k) mod prime` 落进各自的表；`NgramHashMapping`（`:98`）按层 seed 生成 multipliers；`engram_hash` kernel（`deepseek.py:180`）一次算出所有层所有 token 的表内行号。
  - **参数**：`NgramEmbeddingParameters`（`engram_parameters.py:16`）按 engram 并行组分片，行数 pad 到 `lcm(256, size)`，FP8 + UE8M0 scale。
  - **存储和取数**：`EngramRuntime.allocate`（`engram.py:171`）→ `userbuffer.allocate_engram`（`userbuffer.py:127`）建 DeepEP 的 `EngramBuffer`：GPU 一小块 staging，表本体默认放 **host**（`use_cpu_rdma_storage`，`DEEPINFER_ENGRAM_FORCE_GPU_STORAGE` 可改），RDMA 读；`initialize`（`:195`）把本 rank 的分片写进去后释放原参数。`fetch(hashes)`（`:214`）**一次发出所有层的取数**，返回 `{layer_id: hook}`，hook 调用时才等待并返回 `[total_q, (max_ngram−1) × n_heads × head_dim]`。
  - **层内**：`Engram.forward`（`:139`）：`fused_kv_projection(embed_hook())` 投影到 `(hc_mult + 1) × H`，`engram_gate_fwd` 按门控把它融进四路 trunk（`inplace=True`）。挂在 `hc_post_intervention`（`decoder_layer.py:111-118`）：4.7 的 post 之后、pre 之前，所以 engram 层**不能用** `mega_mhc`（`hc.py:195`）。
  - **输入**：`ngram_token_ids [total_q, max_ngram_size]` 由 C++ 填（`prepare_tensor_input_base.cpp:126-132`，用压缩后的历史 + draft token）；ZOS 下 `gather_engram_tokens_zos`（`tilelang_ops/gather_engram_tokens_zos.py:10`）在 GPU 上按 `remap` 从上一步的采样 / draft 结果里取、过 `lookup_table` 压缩、拼上 CPU 建好的窗口（`zos.cpp:53-74`）。
  - **多卡**：表按 `engram_parallel_size` 分片，可以跨多个 DP 副本（`config.py:172`）；5.x 再做。

**思考题**：按 config 算 batch 256 一步所有 engram 层要取多少字节；再和第 0 层到第一个 engram 层之间的 decode 时间比一比，预取能不能把这段取数完全藏住？如果第一个 engram 层就是第 0 层呢？

## 解决问题

三个任务对应分析里的三段：key 怎么来（压缩 tokenizer、哈希、ZOS 下在 GPU 上拼 n-gram）、表放哪取数怎么藏延迟、取回来的 embedding 怎么进残差。

### 任务 A：压缩 tokenizer、哈希和 n-gram 输入（约 40 分钟，你写约 150 行）

- **目标**：`lookup_table` 和 DeepInfer 的 `CompressedVocabulary` 逐 id 一致；哈希和 `NgramHashMapping` 同 seed 一致；`ngram_token_ids [total_q, max_ngram]` 在普通路径由 C++ 填、ZOS 下由 GPU kernel 拼，两者都和 Python 参考一致。
- **思路**：启动时照 `engram_metadata.py:24-50` 的 normalizer 序列逐 token 解码、归一化、去重得到压缩 id，建成 `lookup_table`。`EngramLayout` 给每层每个 n 每个头一张素数大小的表（`sympy.nextprime`，全局去重），multipliers 按层 seed；`engram_hash` 先 PyTorch（int64 乘加取模），再 Triton。C++ 填 `ngram_token_ids`：每个 query 位置往前取 `max_ngram` 个压缩 id（跨 chunk 用序列的历史，draft 位置用 draft token），不足补 pad。ZOS 下 `gather_engram_tokens_zos`（Triton）按 `remap` 从上一步的 `sampled / predict` 取、`lookup_table` 压缩、拼 CPU 建的窗口 `win_compressed [n_seq, nextn + max_ngram − 1]`，被拒绝的 draft 按 `num_accepted` 跳过。对应分析里"哈希只依赖 token id，第 0 层之前就能算；ZOS 下输入要在 GPU 上 gather"。
- **已备好**：**新建**的 `nanovllm/utils/engram_vocab.py` 和 `nanovllm/layers/engram.py` 的函数签名；HF tokenizers 的 normalizer 构造；C++ 侧 `ngram_token_ids` 的张量分配和 pybind；ZOS gather kernel 的 launch 包装；`tests/test_4_8.py` (a)(b)(c)(d) 的用例壳和 `gather_engram_tokens_zos_ref`。
- **你写什么**：`lookup_table` 的构建、`EngramLayout` 和哈希、C++ 的 n-gram 窗口填法、ZOS gather kernel 的函数体。最容易写错的三处：normalizer 顺序和 sentinel 处理要和 DeepInfer 完全一样，否则哈希全错但不报错，先对 `lookup_table` 再往下；素数要**全局**去重（跨层跨头），用一个 `seen` 集合；`ngram_token_ids` 的 pad 用 `engram_pad_token_id` 的压缩 id，不是 0。
- **改哪里**：

  | 文件 | 函数 | 做什么 |
  |---|---|---|
  | `nanovllm/utils/engram_vocab.py` | `build_lookup_table` | normalizer 序列，压缩 id |
  | `nanovllm/layers/engram.py` | `EngramLayout`、`engram_hash` | 素数表大小、multipliers、哈希（PyTorch → Triton） |
  | `csrc/prepare_input.cpp` | `ngram_token_ids` 填充 | 往前取 `max_ngram` 个压缩 id，跨 chunk / draft / pad |
  | `nanovllm/layers/engram.py` | `gather_engram_tokens_zos` | ZOS 下在 GPU 上拼 n-gram |

### 任务 B：表和取数（约 30 分钟，你写约 80 行）

- **目标**：`EngramRuntime.fetch(hashes) -> {layer_id: hook}`：在层循环之前对所有 engram 层发出异步 gather，hook 调用时才等；Nsight 里 engram 层前面的 H2D 等待消失，表放 host 时 KV 预算不变。
- **思路**：表放 host pinned 内存（放得下就放 GPU，`Config.engram_storage = "cpu" | "cuda"`），FP8 + scale。host 表：用一个侧 stream 做 `index_select` 到 pinned 再 H2D，或 UVA 直接 gather；GPU 表：侧 stream `index_select`；每层记一个 event，hook 调用时 `wait_event` 返回。接口和 DeepInfer 的 `EngramBuffer.fetch` 一致，5.x 换 DeepEP RDMA 时只换实现。对应分析里"所有层的 fetch 在层循环之前一起发出去，第 i 层用到时才等"。
- **已备好**：`Config.engram_storage` 的传递；表的装载（FP8 + scale，pinned 分配）；`EngramRuntime` 的类骨架和模型 `forward` 里"层循环之前调 `fetch`、层内调 hook"的两行。
- **你写什么**：`fetch` 的函数体（侧 stream、gather、event、hook 闭包）。最容易写错的一处：host 表的 gather 要在侧 stream，并且 pinned；用普通 pageable 内存 `index_select` 再 `.cuda()` 会同步，等待就又回到 engram 层前面。
- **改哪里**：

  | 文件 | 函数 | 做什么 |
  |---|---|---|
  | `nanovllm/layers/engram.py` | `EngramRuntime.fetch` | 侧 stream 异步 gather，`{layer_id: hook}` |
  | `nanovllm/models/deepseek_v4.py` | 模型 `forward` | 层循环之前 `engram_hash` + `fetch` |

### 任务 C：层内融合（约 20 分钟，你写约 60 行）

- **目标**：engram 层的输出和 DeepInfer 一致（prefill、decode、decode 带 draft）；门控 kernel 和 PyTorch 参考一致。
- **思路**：`fused_kv_projection`：FP8 linear（3.3），输出 `(hc_mult + 1) × H`，拆成 `hc_mult` 份 value 和 1 份 gate；`engram_gate`：先 PyTorch（照 HF modeling 的门控公式，`eps`、`clamp_value`），再 Triton，原地写 trunk。挂在 4.7 的 `attn_norm_forward` 新加的 `hc_post_intervention` 参数上：engram 层走非融合路径（post → 干预 → pre）。对应分析里"按门控加进四路残差，在 post 之后、pre 之前"。
- **已备好**：`hc_post_intervention` 参数的透传；`use_mega_mhc` 按层关闭的判断；`tests/test_4_8.py` (e) 的用例。
- **你写什么**：`fused_kv_projection` 的拆分、`engram_gate` 的 PyTorch 版和 Triton 版。最容易写错的一处：engram 层不能走 4.7 的融合路径，`use_mega_mhc` 要按层关，否则干预被跳过、数值对不上但不报错。
- **改哪里**：

  | 文件 | 函数 | 做什么 |
  |---|---|---|
  | `nanovllm/layers/engram.py` | `fused_kv_projection`、`engram_gate` | 投影拆分；门控原地写 trunk |
  | `nanovllm/models/deepseek_v4.py` | `attn_norm_forward` | 加 `hc_post_intervention`，engram 层走 post → 干预 → pre |

## 验收

1. 同一个实验重跑：engram 层前面的 H2D 等待消失（fetch 在第 0 层前发出，Nsight 里看到 gather 和前面层的计算重叠）；表放 host 时 KV 预算不变。
2. harness：engram 层的输出和 DeepInfer 一致（prefill、decode、decode 带 draft）。
3. `tests/test_4_8.py`：(a) `lookup_table` 和 DeepInfer 的 `CompressedVocabulary` 逐 id 一致；(b) 哈希和 `NgramHashMapping` 一致（同 seed）；(c) `ngram_token_ids` 的 C++ 填法和 Python 参考一致，含 chunk 边界和 draft；(d) ZOS gather kernel 和 `gather_engram_tokens_zos_ref` 一致；(e) 门控 kernel 和 PyTorch 参考一致；(f) 前面全过。
4. **解释**（由你说）：Nsight 里 H2D 等待消失了，取数本身的时间去了哪里？如果把 `fetch` 挪到第一个 engram 层的前一层才发，等待会回来多少？表放 host 之后 KV 预算不变，代价付在了哪里？

**新浮现的问题**：V4.1 一层的其它部分都对上了，MoE 用的还是 3.3 的 FP8 专家和十几个 kernel 的链。B200 上 config 要求专家是 FP4，而且 DeepInfer 的 MoE 是一个 kernel。这是 4.9。

## 常见坑

- 压缩 tokenizer 的 normalizer 顺序和 sentinel 处理要和 DeepInfer 完全一样，否则哈希全错但不报错；先对 `lookup_table`。
- 素数要**全局**去重（跨层跨头），`EngramLayout` 用一个 `seen` 集合。
- `ngram_token_ids` 的 pad 用 `engram_pad_token_id` 的压缩 id，不是 0。
- engram 层不能走 4.7 的融合路径，`use_mega_mhc` 要按层关。
- host 表的 gather 要在侧 stream，并且 pinned；用普通 pageable 内存 `index_select` 再 `.cuda()` 会同步。
