# 4.9：MoE 还是十几个 kernel，专家还是 FP8

> 起点：4.8 做完的代码　硬件：1×B200　预计改动：500–800 行　轴：5 kernel / 3 访存

## 1. 发现问题

**关注什么**：V4.1 的 MoE。config 的 `quantization_config.expert_dtype = fp4`，HF 权重里专家是打包的 FP4（`[E, N, K/2]` int8 + UE8M0 scale）。3.2 / 3.3 的实现是 gate → permute → grouped GEMM → SwiGLU → grouped GEMM → shared → unpermute，十几个 kernel，专家 FP8。

```bash
nsys profile python -m tests.v4.harness --layers 0..K --decode --batch 256
python -m tests.v4.harness --layers 0..K --decode --batch 256 --report moe-bytes
```

**先预测**：B200 上 decode batch 256，一层 MoE 的 kernel 之间有多少空隙？中间结果（dispatch 后的 x、GEMM1 的输出、SwiGLU 的输出）各往返 HBM 几次？专家权重 FP8 → FP4 省多少字节？

**现象**：

- 十几个 kernel 之间的 launch 空隙加起来和 kernel 本身一个量级（B200 快，kernel 短，空隙显得更大）。
- 中间结果：`x_fp8 → 排序后的 x → GEMM1 输出 bf16 [T×k, 2I] → SwiGLU 输出 fp8 [T×k, I] → GEMM2 输出 → 加权求和`，每一步写一遍读一遍 HBM。
- 专家权重按 FP8 存是 config 要求的两倍；decode 访存的大头是专家权重（3.2 的结论），FP4 直接砍一半。
- DeepInfer 的 `DeepseekMoE.forward`（`mlp.py:565`）在 B200 上只走 `mega_moe_forward`（`:528`）：**一个 kernel**。

## 2. 分析问题

- **追问链**：kernel 多 → 中间结果走 HBM → 把 dispatch、GEMM1、SwiGLU、GEMM2、combine 放进一个持久 kernel，中间结果留在 SMEM / 寄存器 → 输入要按 kernel 要求的布局预先放好（对称内存 buffer 里的 `x / x_sf / topk_idx / topk_weights`）→ 上游的 norm 和 gate 直接写进这个 buffer，连 copy 都省 → 专家权重 FP4 要在装载时变成 kernel 要的打包布局 → 多卡时同一个 kernel 顺便做 NVLink 通信（5.2），单卡时 EP = 1 就是本地。
- **本质**：MoE 在 decode 是访存瓶颈（3.2），B200 上 kernel 之间的空隙和中间结果的 HBM 往返成了主要成本；融合成一个 kernel 是唯一的出路，FP4 专家把权重访存再砍半。
- **量化**：按 config 算一层专家权重的字节：FP8 `E × (2I + I) × H × 1 B`，FP4 一半再加 scale（每 32 个元素 1 B）。decode batch 256 的一步读所有专家，FP4 让这部分访存减半。
- **理论**：`reference/gpu-perf-engineering-resources/` §2 "Tensor cores and low precision"：OCP MX 规范（MXFP4 = E2M1 + 每 32 个一个 UE8M0 scale）、NVIDIA 的 NVFP4 介绍（Blackwell 的 4 位微块缩放）、`tcgen05 for dummies`（Blackwell GEMM 的持久调度和 tensor memory，mega kernel 的基础）；§5 MegaScale-Infer（MoE 推理的通信计算重叠）；DeepGEMM README 的 Mega MoE 一节（`vendor/DeepGEMM/README.md:112`）。
- **DeepInfer 怎么做**（`models/v4_modules/mlp.py`）：
  - **权重**：HF 的 FP4 专家由 `materialize_hf_parameter(packed_fp4=True)`（`containers.py:62`）直接分配成 `[E, N, K/2]` int8 + 列主序 UE8M0 scale（`:70-86`）；`process_moe_weight`（`mlp.py:41`）的 `use_fp4` 分支是给 dummy 权重用的转换；`post_load_weights`（`:259`）调 `_convert_mega_moe_weight`（`:93`）→ `deep_gemm.transform_weights_for_mega_moe` 转成 mega kernel 的布局，shared expert 也转。
  - **buffer**：`allocate_userbuffer`（`:303`）→ `userbuffer.allocate_sym_buffer` → `deep_gemm.get_symm_buffer_for_mega_moe(group, E, max_tokens, k, H, I, mma_type)`，`SymmBuffer` 里有 `x / x_sf / topk_idx / topk_weights / shared_l1_acts_sf`。
  - **上游直接写 buffer**：`fused_norm_cast_kwargs`（`:274`）把 `out=(sym_buffer.x, sym_buffer.x_sf)` 和 `extra_sf_out = shared_l1_acts_sf` 交给 norm（3.3 的 `norm` kernel 或 4.7 的 `mega_mhc`，`hc.py:52 / :258`），norm 的 FP8 输出直接落在 buffer 里（`:543-545` 断言指针相等）；gate 用 `out=(sym_buffer.topk_idx, topk_weights)`（`:538-541`）直接写。
  - **一个 kernel**：`deep_gemm.fp8_fp4_mega_moe(out, (l1, l1_sf), (l2, l2_sf), sym_buffer, shared_l1_weights=…, shared_l2_weights=…, cumulative_local_expert_recv_stats=…, activation="swiglu", activation_clamp=…, fast_math=True)`（`:548-558`）。shared expert 融合在里面（`fuse_shared`），否则 `shared_forward(out_acc=out)` 累加（`:561`）。EPLB 的统计指针也传进去（5.4）。
  - **条件**：`use_mega_moe = PLATFORM.is_gpu and mma_type ∈ {fp8xfp4, fp8xfp8, bf16xbf16} and EP 组在 NVLink 域内`（`:184-188`）。
  - **gate**：`bf16_mega_gate`（`:398`）在 B200 上也是 DeepGEMM 的 kernel：sqrtsoftplus + noaux_tc + bias + EPLB 映射。

## 3. 要做什么

### 3.1 FP4 专家装载

**改哪里**：`nanovllm/utils/loader.py`、`nanovllm/layers/moe.py`。

- HF 的打包 FP4 权重和 scale 直接装进 `[E, N, K/2]` int8 + 列主序 UE8M0 scale（照 `containers.py:70-86` 的形状和 stride）。
- `transform_weights_for_mega_moe` 转布局（vendor 函数），转完释放原张量。
- 3.3 的 FP8 路径保留（V2-Lite 还要跑）。

### 3.2 gate 换 V4 的

- `select_experts` 加 `sqrtsoftplus` + `noaux_tc` + `e_score_correction_bias` + `norm_topk_prob` + `routed_scaling_factor`（3.2 留的参数），先 PyTorch 对拍，再换 `deep_gemm.bf16_mega_gate`。

### 3.3 SymmBuffer 和 mega kernel

- `allocate_sym_buffer`（EP = 1 时 group 就是单进程组；DeepGEMM 要求多进程启动 + 对称内存，单卡用 world size 1 的进程组，照 `vendor/DeepGEMM/tests/test_mega_moe.py` 的启动方式）。
- norm（3.3 的 Triton norm 或 4.7 的融合 kernel）加 `out=(x, x_sf)` 参数，直接写 buffer；sf 布局按 `fused_norm_cast_kwargs` 的要求（row-major packed UE8M0，`extra_sf_layout="mega_moe"` 给 shared）。
- gate 写 `topk_idx / topk_weights` 进 buffer。
- `fp8_fp4_mega_moe` 一个调用；shared expert 融合进去。
- `Config.use_mega_moe`，关掉时走 3.3 的链（对拍和 H100 用）。

### 3.4 对拍

- MoE 模块级：同一个 hidden，DeepInfer 的 `DeepseekMoE` 和我们的输出一致（FP4 下容差按格式定）。
- 整层：4.7 的整层对拍重跑。

## 4. 验收

1. 同一个实验重跑：一层 MoE 从十几个 kernel 变成 gate + mega 两个（加上 norm），decode batch 256 下 MoE 时间下降，报告里给 Nsight 前后对比和专家权重字节数前后对比。
2. harness：MoE 输出和 DeepInfer 一致；整层一致。
3. 关掉 `use_mega_moe`，走 3.3 的链 + FP4 grouped GEMM（`m_grouped_fp8_fp4_gemm_nt_contiguous`）结果一致，时间回到 3.3 的水平。
4. `tests/test_4_9.py`：(a) FP4 权重装载后反量化和 HF 的 dequant 参考一致；(b) V4 gate 的 PyTorch 版和 `bf16_mega_gate` 一致；(c) norm 直接写 buffer 的 sf 布局和 `tilelang_ops/norm.py` 的 `_shared_sf_ref`（`:328`）一致；(d) mega 和非融合链一致；(e) 前面全过。

**新浮现的问题**：主模型的层全对上了。2.8 的 draft 头是 Qwen3 的 EAGLE-3，V4.1 用不了；而且它每步要跑 `nextn` 次小 forward、没有置信度输出，2.9 只能用接受率近似。HF 权重里有 `num_nextn_predict_layers` 个 DFlash 层。这是 4.10。

## 常见坑

- FP4 scale 是列主序、按 `fp8_sf_type`（int32）打包 4 个 UE8M0，`containers.py:78-86` 的 `.mT` 不是装饰，装错了 kernel 读到的 scale 全错但不崩。
- `SymmBuffer` 要求 PyTorch ≥ 2.9（DeepGEMM README）；单进程也要 `dist.init_process_group`。
- norm 写进 buffer 的 `x` 必须和 kernel 读的是同一块内存（DeepInfer 用 `data_ptr` 断言，`mlp.py:543`），不要在中间 `.contiguous()`。
- `fast_math=True` 让 mega kernel 的结果和非融合链有 bf16 量级的差异，对拍容差要放到这个级别；2.12 的 batch-invariant 模式下要看 DeepGEMM 的确定性开关。
- V2-Lite 的 gate 是 softmax / greedy，V4 是 sqrtsoftplus / noaux_tc，3.2 留的参数化这里要全部填上，别让一条路径覆盖另一条。
