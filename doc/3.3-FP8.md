# 3.3：decode 贴着带宽上限，prefill 贴着算力上限

> 起点：3.2 做完的代码　轴：5 kernel 与精度

| | |
|---|---|
| **问题** | 并发 256 的 decode `gpu_forward` 12 ms、下限 10 ms，访存到顶；16k prefill 的 GEMM MFU 50–60%，算力到顶。两边碰到的都是 bf16 这种数据类型的上限：每个权重 2 字节，每次乘加用 bf16 tensor core。FP8 同时打两个瓶颈，代价是 scale 的管理：权重离线按 128×128 块算 scale，激活每步在线按 1×128 算，所以 cast 要融进产生这个激活的 kernel |
| **实验** | `python -m bench.run --scenario steady_decode --model deepseek-ai/DeepSeek-V2-Lite --max-num-seqs 256` 和 `--scenario mixed_long_short`，盯 decode `gpu_forward` 和"读一遍权重"下限的差，以及 prefill 步 GEMM 的 MFU |
| **硬件 / 费用** | 1×H100 + DeepSeek-V2-Lite（自己离线量化成 FP8），Modal $3.95/h；量化、对 HF 算 KL、反复验收约 4 小时，约 $16 |
| **学到** | FP8 权重字节减半打 decode 的访存、FP8 tensor core 吞吐翻倍打 prefill 的算力，一种精度同时碰两个 roofline；E4M3 只有 3 位尾数、动态范围 ±448，必须分块缩放，权重的 scale 可以离线算、激活的 scale 每步在线算，这就是 cast 要融进 norm / SwiGLU / attention epilogue 而不是单独一个 kernel 的原因；gate、lm_head、norm 统计、sink 这些地方保持 bf16 / fp32，精度损失用 KL 量化，`greedy_match` 不再要求 100% |
| **时长** | 发现 + 分析约 2 小时；任务 A 约 20 分钟、B 约 20 分钟、C 约 40 分钟；验收约 1 小时。改动约 600–900 行（含离线量化脚本） |

## 发现问题

**关注什么**：decode 和 prefill 各自的 roofline。3.2 之后 MoE 的 kernel 已经收拾干净，看一步的时间离硬件极限还有多远。

```bash
python -m bench.run --scenario steady_decode --model deepseek-ai/DeepSeek-V2-Lite --max-num-seqs 256
python -m bench.run --scenario mixed_long_short --model deepseek-ai/DeepSeek-V2-Lite   # 看 prefill 步
```

**先预测**：并发 256 的 decode 一步至少要读多少字节？按 H100 的 3.35 TB/s 算下限是几毫秒？一个 16k token 的 prefill 要多少 FLOP，按 bf16 tensor core 的 990 TFLOPS 算下限是几毫秒？

**现象**：

- decode：`gpu_forward` 在 12 ms 上下，下限（读 31 GB bf16 权重 + 256 个请求的 latent cache）约 10 ms。已经是**访存瓶颈**，kernel 层面没有多少可榨了。
- prefill：16k token 的一步，GEMM 占了大头，MFU 50–60%，贴近 bf16 的实际可达峰值。**算力瓶颈**。
- 两边都碰到了 bf16 这种数据类型本身的上限：每个权重 2 字节，每次乘加用 bf16 tensor core。

## 分析问题

- **追问链**：decode 访存到顶 → 权重字节数减半才能再快 → FP8 权重；prefill 算力到顶 → H100 的 FP8 tensor core 峰值是 bf16 的两倍 → 激活也要 FP8 → 激活是运行时算出来的，要**在线量化**，每次量化本身要读写一遍激活 → 把量化融进产生这个激活的 kernel（norm、SwiGLU、attention 的 epilogue），GEMM 直接吃 FP8 → 精度损失要能量化，哪些层不能动（gate、lm_head、norm 的统计）。
- **本质**：FP8 同时打两个瓶颈：权重字节减半（decode），tensor core 吞吐翻倍（prefill）。代价是精度和**scale 的管理**：E4M3 只有 3 位尾数、动态范围 ±448，必须分块缩放。权重可以离线算 scale，激活的 scale 要每步在线算，这就是"cast kernel"要融合的原因。
- **量化格式**：DeepSeek-V3 的配方：权重 **128×128 块**一个 fp32 scale（`weight_scale_inv`），激活 **1×128**（每 token 每 128 个通道）一个 scale，GEMM 内部按块反量化累加到 fp32。`reference/gpu-perf-engineering-resources/` §2 "Tensor cores and low precision"：OCP FP8 规范（E4M3 / E5M2）、OCP MX 规范（共享 scale 的微块格式，UE8M0 就是 MX 的 2 的幂 scale）、Transformer Engine（scaling 策略）；§4 "Quantization"：SmoothQuant（为什么激活比权重难量化）；§2 DeepGEMM（Hopper FP8 GEMM 的实现，细粒度 scale 的两级累加）。
- **DeepInfer 怎么做**（V4 全程 FP8 激活 + FP8 / FP4 权重，B200 上用 per-32 UE8M0 scale；Hopper 上同样的结构换成 128 块 + fp32 scale）：
  - **哪些是 FP8**：`prepare_meta_fp8`（`v4_modules/containers.py:113`）把所有 `use_fp8_gemm=True` 的 linear 声明成 `float8_e4m3fn` 权重 + `sf` fp32 scale，形状 `ceil(dim / block)`；**跳过 `tok_emb` 和 `head`**；gate 永远 bf16（`moe.py:40`）；`SoftmaxAPEGatedColumnParallelLora` 的 A / Gate 也是 bf16（`mla_attn.py:63`）。两个开关 `fp8_attn`、`fp8_mlp`（`mla_attn.py:197` / `moe.py:84`）。
  - **GEMM 入口统一** `ReplicatedLinear.apply_weight_fp8`（`layers/linear.py:140`）：输入要么是 bf16 张量（当场 `tile_kernels.quant.per_token_cast`，`:150`），要么**已经是 `(fp8, sf)` 二元组**，直接 `deep_gemm.fp8_fp4_gemm_nt(x, weight, out, out_acc, recipe=(1, 1, 32))`（`:165`）。整个模型里，大部分 GEMM 收到的是二元组：cast 在上一个 kernel 里做完了。`out_acc` 让 GEMM 直接累加进残差。
  - **cast 融进 norm**：`tilelang_ops/norm.py:65` 的 `norm(x, weight, residual, fmt="e4m3", num_per_channels=32, ...)`：residual 加、RMSNorm 统计、输出 FP8 + scale，一个 kernel；`return_bf16=True` 时再额外给一份 bf16（gate 要用）。MoE 层 attention 后的 norm 直接写进 DeepEP / mega MoE 的 buffer（`mlp.py:274` `fused_norm_cast_kwargs`）。
  - **cast 融进 SwiGLU**：`swiglu_forward_and_per_token_cast`（`mlp.py:19` 引入，`:435` 调用）：SiLU × up × topk_weight → FP8，`down_proj` 直接吃。
  - **cast 融进 attention epilogue**：`fused_norm_rope_attn_rope_cast`（`attention_backend.py:2`）把 q 的 norm + RoPE、attention、输出的 RoPE 反旋转和 FP8 cast 全融在 FlashMLA 的 kernel 里，输出 `(fp8, sf)` 给 `fp8_einsum`（`attn.py:215`）。
  - **grouped GEMM FP8**：`_grouped_gemm`（`mlp.py:109`）`m_grouped_fp8_fp4_gemm_nt_contiguous`，`recipe_a=(1, 32)`、`recipe_b=(1, 32)`。
  - **scale 布局**：权重 `sf` 装载后经 `deep_gemm.transform_sf_into_required_layout`（`layers/linear.py:70`、`mlp.py:81`）转成 kernel 要的布局（B200 上是 packed UE8M0 int32，`PLATFORM.fp8_sf_type`）；激活 scale 由 cast kernel 按 `get_fp8_cast_params()`（`linear.py:17`：`round_sf`、`use_packed_ue8m0`、`use_tma_aligned_col_major_sf`）直接写成对齐布局，GEMM 不再搬。
  - **哪里保持高精度**：gate 和 lm_head 的 GEMM bf16 权重、fp32 输出（2.10 的 `bf16_gemm_nt`）；norm 的统计 fp32；`e_score_correction_bias`、attention sink fp32；`einsum_out_clamp_value` 对 FP8 einsum 的输出做截断防溢出（`attn.py:222`）。
  - **精度验收**：`tests/models/test_kl.py` 的 `Case.max_kl`（`:30`）是 FP8 路径对参考 logprob 的 KL 上界；`offline_decode_ppl.json` 是逐样本 PPL 的黄金值。

**思考题**：权重 FP8 之后一步 decode 读 16 GB，latent cache 还是 bf16 的 31 KB/token。并发 256 时上下文多长，KV 的读量就追上权重？这个数说明 4.3 为什么还要把 cache 也量化。

## 解决问题

### 任务 A：离线量化（约 20 分钟，你写约 50 行）

- **目标**：`scripts/quantize_fp8.py` 把 V2-Lite 的 bf16 checkpoint 写成 DeepSeek-V3 格式的 FP8 safetensors，反量化后和原权重的相对误差在 E4M3 的理论范围内。
- **思路**：对回分析里的"权重可以离线算 scale"。每个 `use_fp8` 的 linear 权重按 128×128 块算 `amax / 448` 当 scale，存 `float8_e4m3fn` 的 `weight` 和 fp32 的 `weight_scale_inv [ceil(N/128), ceil(K/128)]`。跳过精度敏感的层：`embed_tokens`、`lm_head`、`mlp.gate`、所有 norm、`kv_a_proj_with_mqa`（DeepInfer 的 `Wkv.A` 是 FP8，但 V2-Lite 的 latent 投影很小，先保守留 bf16，验收时再试 FP8 看 KL 变化）。
- **已备好**：脚本的 CLI、safetensors 读写、输出目录带 `quantization_config` 的 `config.json`（`loader.py` 按它决定走哪条装载路径）；跳过列表。
- **你写什么**：分块算 scale 和 cast 的那段。最容易错的两处：E4M3 没有 inf，最大 448，amax 为 0 的块要特殊处理否则除零；`weight_scale_inv` 是"反量化乘的数"（`w_bf16 ≈ w_fp8 × scale_inv`），HF 格式的命名容易弄反。
- **改哪里**：

  | 文件 | 函数 | 做什么 |
  |---|---|---|
  | `scripts/quantize_fp8.py`（新建） | 分块量化 | 128×128 块 scale，写新 checkpoint |

### 任务 B：FP8 linear 和 scale 布局（约 20 分钟，你写约 60 行）

- **目标**：`LinearBase` 加 `use_fp8`，`forward(x)` 接受 bf16 张量或 `(fp8, sf)` 二元组，走 `deep_gemm.fp8_gemm_nt`；FP8 GEMM 和 `F.linear(dequant(w))` 的误差在 bf16 累加误差量级；`Config.fp8_attn` / `fp8_mlp` 关掉时走 3.2 的 bf16 路径。
- **思路**：对回 DeepInfer 的"GEMM 入口统一"：一个 linear 既能吃 bf16（当场 per-token cast），也能吃上一个 kernel 直接产出的 `(fp8, sf)`，任务 C 的融合才有地方接。装载时把 `weight_scale_inv` 转成 DeepGEMM 要的布局（TMA 对齐的 column-major），做一次、存起来。`out_acc` 允许 GEMM 直接加到残差上（`o_proj` 和 `down_proj` 用），省一次 `[T, H]` 的读写。
- **已备好**：`Config.fp8_attn` / `fp8_mlp` 两个开关和它们到各层的传递（验收要对比）；保持高精度的地方：gate 的 bf16 权重、fp32 logits（3.2 已经是），lm_head 的 bf16 权重、fp32 logits（2.10 已经是），残差流 bf16；`loader.py` 按 `quantization_config` 选装载路径。
- **你写什么**：`use_fp8` 的 forward：bf16 时当场 per-token cast，然后 `deep_gemm.fp8_gemm_nt((x, x_sf), (w, w_sf), out)`，Hopper 用 `(1, 128) / (128, 128)` 配方，fp32 scale（按你装的 DeepGEMM 版本的 README 核对 SM90 支持的 recipe 和 scale 布局；UE8M0 packed 是 SM100 的）；装载时的 scale 布局转换；`out_acc`。最容易错的两处：激活 per-token 1×128 的 scale 要在 fp32 里算，输入是 bf16 先转 fp32 再算 amax；DeepGEMM 对 `M`、`N`、`K` 的对齐和 scale 张量的布局有硬要求，不满足时报错不直观，先用它自带的 `tests/` 里的小例子确认环境。
- **改哪里**：

  | 文件 | 函数 | 做什么 |
  |---|---|---|
  | `nanovllm/layers/linear.py` | `LinearBase.forward`、装载 | `use_fp8`、`(fp8, sf)` 输入、scale 布局、`out_acc` |
  | `nanovllm/config.py` | `fp8_attn`、`fp8_mlp` | 已备好 |

### 任务 C：cast 融合（约 40 分钟，你写约 120 行）

- **目标**：一层里除了 gate 和 attention core，每个 GEMM 的输入都是上一个 kernel 直接产出的 `(fp8, sf)`，**没有独立的 cast kernel**。用 Nsight 数一层的 kernel 数来验证。
- **思路**：对回分析里的"激活的 scale 要每步在线算，所以 cast 要融进产生它的 kernel"。三处：norm 出 FP8 给 attention 和 MLP 的第一个 GEMM；SwiGLU 出 FP8 给 `down_proj`；attention 输出 cast 后给 `W_UV` 和 `o_proj`。grouped GEMM 换 `m_grouped_fp8_gemm_nt_contiguous`。V4 的 `fused_norm_rope_attn_rope_cast` 是 FlashMLA 内置的，这里不做。
- **已备好**：Triton kernel 的壳和签名；`tests/test_3_3.py` 里反量化对拍和"数 kernel 名"的测试。
- **你写什么**：RMSNorm 改成 Triton kernel：输入 bf16 x（+ residual），输出 `(fp8 [T, H], sf [T, H/128])` 和 bf16 的 residual，加 `return_bf16` 给 gate 用，替换掉 `torch.compile` 的版本（2.12 的 batch-invariant 要求整行一个 program，正好）；SwiGLU kernel 加 FP8 输出（SiLU × up × topk_weight → cast），`down_proj` 的 grouped GEMM 吃它；MLA 的 `W_UV` einsum 和 `o_proj`：attention 输出 `[T, heads, 512]` 先 per-token cast，`W_UV` 用 FP8 batched GEMM（`torch.bmm` 没有 FP8，用 DeepGEMM 的 `fp8_einsum` 或先把 heads 维并进 M 做普通 FP8 GEMM），然后 `o_proj` FP8。最容易错的一处：norm 的统计要在 fp32 做，只有输出才降到 FP8。
- **改哪里**：

  | 文件 | 函数 | 做什么 |

  | `nanovllm/layers/moe.py` | SwiGLU kernel、grouped GEMM | FP8 输出；`m_grouped_fp8_gemm_nt_contiguous` |

## 验收

同一个实验重跑：

1. decode 并发 256：`gpu_forward` 从 12 ms 量级降到 7 ms 量级（权重 31 GB → 16 GB，下限 5 ms）；吞吐提升写进报告。
2. prefill 16k：GEMM 时间接近减半；MFU 按 FP8 峰值重新算。
3. 精度：`tests/kl.py` 对 bf16 HF 的 KL 从 1e-3 量级升到 1e-2 以下，**具体数字写进报告**；`greedy_match` 允许有少量不一致（记下比例）；黄金文件按 FP8 重新生成一份 `deepseek_v2_lite_fp8.json`，之后的回归对它。`fp8_attn` 和 `fp8_mlp` 各自单独开，报告两者各贡献多少 KL。
4. 关掉两个开关，数字回到 3.2。
5. `tests/test_3_3.py`：(a) 量化脚本：反量化后和原权重的相对误差在 E4M3 的理论范围内；(b) FP8 GEMM 和 `F.linear(dequant(w))` 的误差在 bf16 累加误差量级；(c) 融合 norm 的 `(fp8, sf)` 反量化后和 PyTorch RMSNorm 一致；(d) SwiGLU + cast 同样；(e) 一层里没有独立的 cast kernel（用 `torch.profiler` 数 kernel 名）；(f) 3.1、3.2 和第 2 章全过（Qwen3 路径不受影响）。
6. **解释**（由你说）：decode 为什么停在 7 ms 而不是下限 5 ms，剩下的 2 ms 在读什么；`fp8_attn` 和 `fp8_mlp` 各贡献的 KL 为什么不一样大；`greedy_match` 不再是 100% 为什么不算错。

**新浮现的问题**：V2-Lite 到此跑完，P1 之后的模型结构部分也和 DeepInfer 的骨架对上。但 V4.1-Flash 的每一层都比 V2 多了东西：cache 不止一种、SWA 环、压缩 KV、稀疏索引、YoCo、mHC、engram、FP4 专家。第 4 章换到 B200，一层一层对拍。第一个问题是：nano-vllm 的一个大 KV 张量放不下 V4 每层不同的 cache 类型。这是 4.1。

## 常见坑

- E4M3 没有 inf，最大 448；scale 算 `amax / 448` 时 amax 为 0 的块要特殊处理，否则除零。
- `weight_scale_inv` 是"反量化乘的数"（`w_bf16 ≈ w_fp8 × scale_inv`），HF 格式的命名容易弄反。
- 激活 per-token 1×128 的 scale 要在 fp32 里算；cast kernel 输入是 bf16，先转 fp32 再算 amax。
- DeepGEMM 对 `M`、`N`、`K` 的对齐和 scale 张量的布局有硬要求（TMA 对齐），不满足时报错信息不直观；先用它自带的 `tests/` 里的小例子确认环境。
- 2.12 的 batch-invariant 开关要覆盖 FP8 GEMM（`deep_gemm.use_deterministic_algorithms`，`runtime_config.py:68`）；FP8 下归约顺序对结果的影响更大。
- 量化后 `greedy_match` 不再是 100%，不要为了过旧黄金文件把精度调回 bf16；黄金文件按 FP8 重做，KL 是主要指标。
- `torch.float8_e4m3fn` 张量不能直接 `.sum()`、`.abs()`，对拍时先 `.float()`。
