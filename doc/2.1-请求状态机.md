# 2.1：边界请求会把引擎弄死

> 起点：1.1 做完的代码　轴：1 调度与请求状态机

| | |
|---|---|
| **问题** | 一个比 KV cache 总容量还大的 prompt 让 `assert scheduled_seqs` 崩掉整个引擎；取消请求没有接口，从 `running` 里硬 remove 会漏 block；prompt 恰好等于 `max_model_len` 时 decode 第一步越界。根因是 `Sequence` 只有三个状态、`can_allocate` 只有一种失败，引擎分不清"暂时放不下"和"永远放不下"，也分不清"正常结束"和"被取消 / 被拒绝 / 被抢占" |
| **实验** | `LLM(model, max_model_len=4096, max_num_seqs=8)` 下发三个边界请求：超容量 prompt、跑到一半取消、prompt 恰好 `max_model_len`。盯引擎崩不崩，以及跑完之后 `len(free_block_ids)` 是不是等于 `num_blocks` |
| **硬件 / 费用** | 1×H100 + Qwen3-8B（$3.95/h）；调度逻辑 L4 即可（$0.80/h），H100 更接近文档数字。验收大半是假 `Config` 的纯 CPU 测试，GPU 只开约 1 小时跑边界实验和重跑 1.1 的四个场景，约 $4 |
| **学到** | 请求的生命周期不是一条直线，每种结局（停止、截断、取消、拒绝、抢占）要有自己的终态和 `finish_reason`，否则要么崩要么漏；资源判断要三态，`NEVER` 立刻拒绝、`LATER` 才等，不然一个永远放不下的请求会把队列卡死；abort 只标记不动队列，判定结束、出队、释放 block 分三处，因为 GPU 可能还在读那些 block，这是 2.7 ZOS 的前提 |
| **时长** | 发现 + 分析约 1.5 小时；任务 A / B 各约 20 分钟，任务 C 约 30 分钟；验收约 30 分钟。改动约 150–250 行 |

## 发现问题

**关注什么**：引擎在"不正常的请求"面前站不站得住。1.1 之后你有了观测工具，先拿它去撞边界。

三个实验（用 `bench.run` 的驱动或者直接写几行脚本）：

```python
llm = LLM(model, max_model_len=4096, max_num_seqs=8)
# (a) 一个比 KV cache 总容量还大的 prompt：prompt_len > num_kvcache_blocks * block_size
# (b) 正常请求跑到一半，想取消其中一个（nano-vllm 没有 abort 接口，先想想该怎么做）
# (c) 一个 prompt 恰好等于 max_model_len，max_tokens=1
```

**先预测**：(a) 会报错、卡住、还是被默默跳过？(b) 没有接口，你会直接从 `scheduler.running` 里 remove 吗？会出什么问题？(c) 能生成那 1 个 token 吗？

**现象**：

- (a) `can_allocate` 返回 -1，`schedule()` 在 prefill 分支 `break`，队列里没有别的请求时走到 decode 分支，`assert scheduled_seqs` 断言失败，整个引擎崩。有别的请求时它们先跑完，然后同样崩。这个请求**永远**放不下，但引擎只知道"现在放不下"。
- (b) 从 `running` 里 remove 之后 block 没有释放，`block_manager.used_block_ids` 漏了；如果它正好在本步被调度，`postprocess` 会拿到它的 token 继续 `append_token`。没有一个状态表示"被取消"。
- (c) `may_append` 在 decode 第一步要再分配一个 block（`len(seq) % block_size == 1`），而 `max_model_len` 不是这样算的。要么越界，要么 CUDA graph 的 `block_tables` 列数不够。

## 分析问题

- **追问链**：三个现象 → 共同点是 `Sequence` 只有 `WAITING / RUNNING / FINISHED` 三个状态，`BlockManager.can_allocate` 只有 -1 一种失败 → 引擎分不清"暂时放不下"和"永远放不下"、分不清"正常结束"和"被取消 / 被拒绝 / 被抢占" → 这些情况下要么崩、要么资源泄漏。
- **本质**：请求的生命周期不是一条直线。生产流量里有超长 prompt、客户端断开、超时、资源不足，每一种都要有一个明确的终态和一条干净的退出路径。
- **卡在哪种资源**：不是性能问题，是正确性和资源回收。但它决定了后面所有调度策略能不能安全地做。
- **理论**：`reference/gpu-perf-engineering-resources/` §4 的 vLLM 论文 4.5 节讲抢占时顺带定义了请求的三类结局（完成、抢占后重算、换出）。生产引擎在此之上还要处理 abort 和 ignore。
- **DeepInfer 怎么做**：
  - `SequenceStatus` 有 10 个值（`csrc/engine/sequence.hpp:30`）：`WAITING, RUNNING, SWAPPED, FINISHED_STOPPED, FINISHED_LENGTH_CAPPED, FINISHED_ABORTED, FINISHED_IGNORED, FINISHED_PREEMPTED, FINISHED_SO_FAILED, FINISHED_VE_FAILED`，`is_finished = status >= FINISHED_STOPPED`。每个终态对应一个 `finish_reason` 字符串回给调用方。
  - 资源判断三态：`can_allocate_nolock` 返回 `OK / LATER / NEVER`（`csrc/engine/block_manager.hpp:128`）。`NEVER`（需要的 block 数 ≥ 总数）→ 标 `FINISHED_IGNORED`，`continue` 看下一个请求；`LATER` → `break`。
  - abort 只**标记**不动队列（`scheduler.hpp:144` `abort_sequence`），下一次 `_schedule_decode` 开头统一清理（`:562-577`）。原因：ZOS 下这个请求可能还在 GPU 上跑。
  - "判定结束"、"移出队列"、"释放 block"分三处：`_check_stop`（`:1035`）只改状态；`free_finished_seqs`（`:752`）只出队；`free_seq`（`:738`）才还 block，由 `pre_sampler_sync` 在下一步 forward 发射之后调用（`llm_engine.py:830-846`）。
  - 长度检查提前到入队：`prompt_limit`（`scheduler.hpp:112`）和 `runtime_max_model_len`（`config.py:11-16`，给 draft token 和 ZOS 的 inflight 留余量）。

**思考题**：`NEVER` 的条件是 `num_new_blocks >= num_blocks`，用的是 `>=` 而不是 `>`。一个 prompt 恰好占满全部 block 的请求，如果放它进来，会在哪一步、因为什么出问题？和现象 (c) 是同一个问题吗？

## 解决问题

三个任务，照 DeepInfer 的拆法：先把终态补齐，再把资源判断改成三态，最后把 abort 和"判定 / 出队 / 释放"的三处分离一起做。枚举骨架、接口签名、测试由 `start-step` 先写好。

### 任务 A：状态和结束原因（约 20 分钟，你写约 40 行）

- **目标**：`SequenceStatus` 有 7 个值，每个终态能回一个 `finish_reason` 字符串；`is_finished` 对所有 `FINISHED_*` 为真。
- **思路**：对回分析里的第一个结论：三个现象的共同点是状态太少。先把终态补齐，任务 B、C 才有东西可标。照 DeepInfer 的枚举（`sequence.hpp:30`）缩成 7 个，去掉这一节用不到的 `SWAPPED`、`SO_FAILED`、`VE_FAILED`。顺手埋两颗架构种子（路线图第 6 节）。
- **已备好**：枚举的骨架、`finish_reason` 的字符串表、`tests/test_2_1.py` 里和状态相关的断言。
- **你写什么**：
  - `SequenceStatus` 扩成：`WAITING, RUNNING, FINISHED_STOPPED, FINISHED_LENGTH_CAPPED, FINISHED_ABORTED, FINISHED_IGNORED, FINISHED_PREEMPTED`。保持 `is_finished` 语义：所有 `FINISHED_*` 都算结束。
  - `finish_reason` 属性，返回 `"stop" / "length" / "abort" / "prompt_length_exceeded" / "insufficient_system_resource"`，照 DeepInfer 的字符串。
  - 预留两个字段，这一节不用但后面要：`total_inflight_tokens: int = 0`（2.7）、`num_preemptions`（1.1 已有）。`num_blocks` 的计算改成 `(num_tokens + total_inflight_tokens + block_size - 1) // block_size`，现在 inflight 恒为 0，行为不变。

  最容易写错的一处：`is_finished` 照 DeepInfer 用序比较 `status >= FINISHED_STOPPED`，那么枚举里所有终态必须排在 `RUNNING` 之后，中间不能插非终态。
- **改哪里**：

  | 文件 | 函数 | 做什么 |
  |---|---|---|
  | `nanovllm/engine/sequence.py` | `SequenceStatus`、`is_finished`、`finish_reason`、`num_blocks` | 7 个状态、结束原因、两个预留字段 |

### 任务 B：三态资源判断（约 20 分钟，你写约 40 行）

- **目标**：超过总容量的 prompt 入队即被标 `FINISHED_IGNORED`，`finish_reason == "prompt_length_exceeded"`；队列里其他请求照常完成，引擎不崩。
- **思路**：对回"分不清暂时放不下和永远放不下"。`can_allocate` 从返回 -1 改成返回 `(status, num_cached_blocks)`，`status ∈ {OK, LATER, NEVER}`；调度器对 `NEVER` `continue`、对 `LATER` `break`。长度检查照 DeepInfer 的 `prompt_limit` 提前到入队。
- **已备好**：`OK / LATER / NEVER` 的枚举、`tests/test_2_1.py` 的测试 1、2、6。
- **你写什么**：
  - `can_allocate` 的三态判断。`NEVER` 的条件：`num_new_blocks >= num_blocks`（和 DeepInfer 一样用 `>=`，因为 decode 至少还要一块）。
  - 调度器 prefill 分支：`NEVER` → `seq.status = FINISHED_IGNORED`，出队，记进本步的 `ignored`，`continue`；`LATER` → `break`。
  - 入队时检查 `prompt_len > max_model_len - 1` 也直接 `FINISHED_IGNORED`（给 decode 留至少 1 个位置）。

  最容易写错的两处：`>=` 写成 `>`，恰好占满的请求会在 decode 第一步 `may_append` 时无块可分；`FINISHED_IGNORED` 的请求从来没分配过 block，它走任务 C 的释放路径时 `block_table` 是空的，释放代码要能处理。
- **改哪里**：

  | 文件 | 函数 | 做什么 |
  |---|---|---|
  | `nanovllm/engine/block_manager.py` | `can_allocate` | 返回 `(status, num_cached_blocks)` |
  | `nanovllm/engine/scheduler.py` | `schedule` 的 prefill 分支 | `NEVER` 出队 `continue`，`LATER` `break` |
  | `nanovllm/engine/scheduler.py` | `add` | 入队时的长度检查 |

### 任务 C：abort，以及判定、出队、释放分三处（约 30 分钟，你写约 80 行）

- **目标**：`LLMEngine.abort_request(seq_ids)` 能取消 `running` 或 `waiting` 里的请求，下一步它不在 `scheduled_ids` 里，它的 block 全部回到 `free_block_ids`；所有终态走同一条出队和释放路径，`step()` 返回的 outputs 带 `finish_reason`。
- **思路**：对回"没有一个状态表示被取消"和"资源泄漏"。照 DeepInfer 把三件事拆开：`postprocess` 只改状态（对应 `_check_stop`）、`schedule()` 开头只出队（对应 `free_finished_seqs`）、`step()` 在 `run` 返回之后才释放 block（对应 `free_seq`）。abort 只是多一个把状态改成 `FINISHED_ABORTED` 的入口，之后走和 EOS、截断完全相同的路。
- **已备好**：`abort_request` / `abort` 的签名和 seq_id 查找；`step()` 返回 outputs 带 `finish_reason`、1.1 的 `RequestRecord` 记 `finish_reason` 的字段；`tests/test_2_1.py` 的测试 3、4、5。
- **你写什么**：
  - `abort`：只把状态改成 `FINISHED_ABORTED`，不动 `waiting / running`，不释放 block。
  - `postprocess`：命中 EOS → `FINISHED_STOPPED`；`num_completion_tokens == max_tokens` 或 `num_tokens >= max_model_len` → `FINISHED_LENGTH_CAPPED`。**只改状态，不 deallocate，不 remove。** 遇到已经 `is_finished` 的 seq 跳过（它本步可能被调度过了）。
  - `schedule()` 开头统一清理：`running` 里 `is_finished` 的移到本步的 `finished` 列表；`waiting` 里 `is_finished` 的移出。两处都只出队。
  - `step()`：拿到 `finished` 列表后，在 `model_runner.call("run")` **返回之后**再对它们 `deallocate`。现在这样做看起来多此一举，2.7 做 ZOS 时你会需要这个顺序：GPU 可能还在读这些 block。

  最容易写错的两处：`postprocess` 不跳过已终态的 seq，abort 和它同一步发生时（abort 在 `step()` 之外被调用），被取消的请求本步又被 `append_token`；`deallocate` 顺手写在 `run` 之前，现在测试抓不到，2.7 才会炸。
- **改哪里**：

  | 文件 | 函数 | 做什么 |
  |---|---|---|
  | `nanovllm/engine/llm_engine.py` | `abort_request` | 转给 `scheduler.abort` |
  | `nanovllm/engine/scheduler.py` | `abort` | 只标记 |
  | `nanovllm/engine/scheduler.py` | `postprocess` | 只改状态；跳过已终态的 |
  | `nanovllm/engine/scheduler.py` | `schedule` | 开头统一出队，收 `finished` 列表 |
  | `nanovllm/engine/llm_engine.py` | `step` | `run` 返回之后 `deallocate`；outputs 带 `finish_reason` |

写完用 `check-step 2.1` 验收。

## 验收

`tests/test_2_1.py`，纯 CPU 可以用一个假的 `Config`（`num_kvcache_blocks` 手工指定）直接测 `Scheduler`：

1. 超过总容量的 prompt：状态 `FINISHED_IGNORED`，`finish_reason == "prompt_length_exceeded"`，队列里其他请求照常完成，引擎不崩。
2. 暂时放不下的 prompt：等前面的请求结束后被调度，最终 `FINISHED_STOPPED` 或 `LENGTH_CAPPED`。
3. abort 一个 `running` 的请求：下一步它不在 `scheduled_ids` 里；它的 block 全部回到 `free_block_ids`；`used_block_ids` 和 `free_block_ids` 的并集始终等于全集。
4. abort 一个 `waiting` 的请求：同上。
5. 任何测试结束时 `len(free_block_ids) == num_blocks`（没有泄漏）。
6. prompt 长度 `max_model_len - 1`、`max_tokens=1` 能正常生成 1 个 token。

重跑 1.1 的四个场景，数字应该和 1.1 一样（这一节不改性能）。

## 常见坑

- `running.remove(seq)` 是 O(n)，而且 `deque.remove` 按相等比较。这一节先不管，2.5 会算这笔账。
- abort 和 postprocess 同一步发生：abort 在 `step()` 之外被调用，postprocess 要能容忍 seq 已经是终态。
- `FINISHED_IGNORED` 的请求从来没分配过 block，释放路径要能处理空 `block_table`。
- 别忘了 1.1 的 `RequestRecord` 要在所有终态下都生成，否则 `summarize_requests` 会少算请求。
