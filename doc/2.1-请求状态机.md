# 2.1：边界请求会把引擎弄死

> 起点：1.1 做完的代码　轴：1 调度与请求状态机

| | |
|---|---|
| **问题** | 一个比 KV cache 总容量还大的 prompt 让 `assert scheduled_seqs` 崩掉整个引擎；取消请求没有接口，从 `running` 里硬 remove 会漏 block；prompt 恰好等于 `max_model_len` 时 decode 第一步越界。根因是 `Sequence` 只有三个状态、`can_allocate` 只有一种失败，引擎分不清"暂时放不下"和"永远放不下"，也分不清"正常结束"和"被取消 / 被拒绝 / 被抢占" |
| **实验** | `LLM(model, max_model_len=4096, max_num_seqs=8)` 下发三个边界请求：超容量 prompt、跑到一半取消、prompt 恰好 `max_model_len`。盯引擎崩不崩，以及跑完之后 `len(free_block_ids)` 是不是等于 `num_blocks` |
| **硬件 / 费用** | 1×H100 + Qwen3-8B（$3.95/h）；调度逻辑 L4 即可（$0.80/h），H100 更接近文档数字。验收大半是假 `Config` 的纯 CPU 测试，GPU 只开约 1 小时跑边界实验和重跑 1.1 的四个场景，约 $4 |
| **学到** | 请求的生命周期不是一条直线，每种结局（停止、截断、取消、拒绝、抢占）要有自己的终态和 `finish_reason`，否则要么崩要么漏；资源判断要三态，`NEVER` 立刻拒绝、`LATER` 才等，不然一个永远放不下的请求会把队列卡死；abort 只标记不动队列，判定结束、出队、释放 block 分三处，因为 GPU 可能还在读那些 block，这是 2.7 ZOS 的前提 |
| **时长** | 发现 + 分析约 1.5 小时；任务 A / B / C 各约 20 分钟；验收约 30 分钟。改动约 150–250 行 |

## 发现问题

**关注什么**：引擎在"不正常的请求"面前站不站得住。1.1 之后你有了观测工具，先拿它去撞边界。

三个实验，`start-step` 会备好 `bench/edge.py`，每个 case 一个进程（崩了不连累别的），每步打印调度了谁、谁结束了，最后打印 `waiting / running / free_blocks / used`：

```bash
python -m bench.edge --case a                  # 短请求、比 KV cache 总容量大 1 个 token 的请求、短请求
python -m bench.edge --case b                  # 三个请求跑到第 4 步，running.remove 掉一个（没有 abort 接口）
python -m bench.edge --case c --max-tokens 1   # prompt 恰好等于 max_model_len=4096
python -m bench.edge --case c --max-tokens 2
```

**先预测**：(a) 会报错、卡住、还是被默默跳过？第三个短请求的结局是什么？(b) remove 之后 `free_blocks` 回得到总数吗？(c) `max_tokens=1` 和 `2` 哪个能跑通？

**现象**：

- (a) `can_allocate` 返回 -1，`schedule()` 在 prefill 分支 `break`。排在它**后面**的短请求一步都跑不了（队头阻塞）；前面已经在跑的先跑完，然后走到 decode 分支，`assert scheduled_seqs` 断言失败，整个引擎崩。崩的那一刻 `free_blocks` 是满的。这个请求**永远**放不下，但引擎只知道"现在放不下"。
- (b) 从 `running` 里 remove 之后 block 没有释放，`block_manager.used_block_ids` 漏了；如果它正好在本步被调度，`postprocess` 会拿到它的 token 继续 `append_token`。没有一个状态表示"被取消"。
- (c) `max_tokens=1` 能跑通：prefill 本身就产出第 1 个 token，`postprocess` 当场结束，从不进 decode。`max_tokens=2` 崩：decode 第一步 `len(seq) = 4097`，`may_append` 要第 17 个 block（`len(seq) % block_size == 1`），而 CUDA graph 的 `block_tables` 按 `max_model_len` 只 capture 了 16 列，`model_runner.py` 里拷 `block_tables` 时 `RuntimeError`。入队时没人检查 prompt 长度和 `max_model_len` 的关系。

L4 + Qwen3-0.6B（650 块 × 256）实测：(a) 第一个短请求跑完后 `AssertionError`，第三个短请求从没被调度；(b) 跑完 `free_blocks=648/650`，被 remove 的那个请求的 2 块永远回不来；(c) `max_tokens=1` 正常结束，`max_tokens=2` 在 step 1 报 `expanded size of the tensor (16) must match the existing size (17)`。

## 分析问题

- **追问链**：三个现象 → 共同点是 `Sequence` 只有 `WAITING / RUNNING / FINISHED` 三个状态，`BlockManager.can_allocate` 只有 -1 一种失败 → 引擎分不清"暂时放不下"和"永远放不下"、分不清"正常结束"和"被取消 / 被拒绝 / 被抢占" → 这些情况下要么崩、要么资源泄漏。
- **本质**：请求的生命周期不是一条直线。生产流量里有超长 prompt、客户端断开、超时、资源不足，每一种都要有一个明确的终态和一条干净的退出路径。
- **卡在哪种资源**：不是性能问题，是正确性和资源回收。但它决定了后面所有调度策略能不能安全地做。
- **理论**：`reference/gpu-perf-engineering-resources/` §4 的 vLLM 论文 4.5 节讲抢占时顺带定义了请求的三类结局（完成、抢占后重算、换出）。生产引擎在此之上还要处理 abort 和 ignore。
- **DeepInfer 怎么做**：
  - `SequenceStatus` 有 10 个值（`csrc/engine/sequence.hpp:30`）：`WAITING, RUNNING, SWAPPED, FINISHED_STOPPED, FINISHED_LENGTH_CAPPED, FINISHED_ABORTED, FINISHED_IGNORED, FINISHED_PREEMPTED, FINISHED_SO_FAILED, FINISHED_VE_FAILED`，`is_finished = status >= FINISHED_STOPPED`。每个终态对应一个 `finish_reason` 字符串回给调用方。
  - 资源判断三态：`can_allocate_nolock` 返回 `OK / LATER / NEVER`（`csrc/engine/block_manager.hpp:128`）。`NEVER`（需要的 block 数 ≥ 总数）→ 标 `FINISHED_IGNORED`，`continue` 看下一个请求；`LATER` → `break`。
  - abort 只**标记**不动队列（`scheduler.hpp:144` `abort_sequence`），下一次 `_schedule_decode` 开头统一清理（`:562-577`）。原因：ZOS 下这个请求可能还在 GPU 上跑。
  - "判定结束"、"移出队列"、"释放 block"分三处：`_check_stop`（`:1035`）只改状态；`free_finished_seqs`（`:752`）只出队；`free_seq`（`:738`）才还 block，由 `pre_sampler_sync` 在下一步 forward 发射之后调用（`llm_engine.py:830-846`）。
  - 长度检查提前到入队：`prompt_limit`（`scheduler.hpp:112`）和 `runtime_max_model_len`（`config.py:11-16`，给 draft token 和 ZOS 的 inflight 留余量）。

**思考题**：`NEVER` 的条件是 `seq.num_blocks >= num_blocks`，用的是 `>=` 而不是 `>`。一个 prompt 恰好占满全部 block 的请求，如果放它进来，会在哪一步、因为什么出问题？和现象 (c) 是同一个问题吗？

## 解决问题

三个任务，照 DeepInfer 的拆法：先加一组状态类型，再把"判定 / 出队 / 释放"拆到三处，让所有终态走同一条出口，最后让每个入口按类型打状态。B 做完，C 的每个入口就只剩"打一个状态"。

### 任务 A：一组状态类型（约 20 分钟，你写约 30 行）

- **目标**：`SequenceStatus` 有 7 个值，每个终态能回一个 `finish_reason`；`is_finished` 对所有 `FINISHED_*` 为真；`BlockManager` 有 `OK / LATER / NEVER` 三态。这一步只加类型，引擎行为不变。
- **思路**：对回分析里的第一个结论：三个现象的共同点是状态太少，引擎分不清"暂时放不下"和"永远放不下"，也分不清"正常结束"和"被取消 / 被拒绝"。先把类型补齐，任务 B、C 才有东西可用。照 DeepInfer 的枚举（`sequence.hpp:30`）缩成 7 个，去掉这一节用不到的 `SWAPPED`、`SO_FAILED`、`VE_FAILED`；三态照 `block_manager.hpp:128`。顺手埋一颗架构种子（路线图第 6 节）。
- **你写什么**：
  - `SequenceStatus` 改成 `IntEnum`：`WAITING, RUNNING, FINISHED_STOPPED, FINISHED_LENGTH_CAPPED, FINISHED_ABORTED, FINISHED_IGNORED, FINISHED_PREEMPTED`。`is_finished` 照 DeepInfer 用序比较：`status >= FINISHED_STOPPED`。
  - 终态到结束原因的表，和 `finish_reason` 属性：`"stop" / "length" / "abort" / "prompt_length_exceeded" / "insufficient_system_resource"`，照 DeepInfer 的字符串；非终态返回 `None`。
  - 预留 `total_inflight_tokens = 0`（2.7 用），`num_blocks` 改成 `(num_tokens + total_inflight_tokens + block_size - 1) // block_size`。现在 inflight 恒为 0，行为不变。
  - `block_manager.py` 里的 `AllocStatus`：`OK`（现在放得下）、`LATER`（现在放不下，别人结束后能放下）、`NEVER`（空的 cache 也放不下）。
  - 旧代码里唯一一处 `SequenceStatus.FINISHED`（`postprocess`）先换成 `FINISHED_STOPPED`，让代码能跑；任务 B 再把它分开。

  最容易写错的一处：用序比较，枚举里所有终态必须排在 `RUNNING` 之后，中间不能插非终态；用普通 `Enum` 根本比不了大小。
- **改哪里**：

  | 文件 | 函数 | 做什么 |
  |---|---|---|
  | `nanovllm/engine/sequence.py` | `SequenceStatus`、`is_finished`、`finish_reason`、`num_blocks` | 7 个状态、结束原因、预留字段 |
  | `nanovllm/engine/block_manager.py` | `AllocStatus` | 三态 |

### 任务 B：判定、出队、释放分三处（约 20 分钟，你写约 40 行）

- **目标**：所有终态走同一条出口。`postprocess` 只把状态改成终态；`schedule()` 开头把终态的请求移出队列；`step()` 在 `run` 返回之后才释放它们的 block，并把它们作为 outputs 返回，带 `finish_reason`。EOS 和 `max_tokens` 两种结局改走这条路，跑完 `len(free_block_ids) == num_blocks`。
- **思路**：对回"资源泄漏"和"只有正常结束才有路可走"。nano-vllm 在 `postprocess` 里一口气做完判定、出队、释放，所以只有 EOS 和 `max_tokens` 能结束一个请求；取消、拒绝都没有出口，硬从 `running` 里 remove 就漏 block。照 DeepInfer 把三件事拆开：`postprocess` 只判定（对应 `_check_stop`）、`schedule()` 开头只出队（对应 `free_finished_seqs`）、`step()` 在 `run` 返回之后释放（对应 `free_seq`）。拆开之后，任何地方只要把状态改成终态，后面的路都一样。
- **你写什么**：
  - `postprocess`：EOS → `FINISHED_STOPPED`，`num_completion_tokens == max_tokens` → `FINISHED_LENGTH_CAPPED`。删掉 `deallocate`、`running.remove`、`finished.append`，**只改状态**。
  - `schedule()` 开头：`running` 和 `waiting` 里 `is_finished` 的移进 `self.finished`，两个队列只留活的。只出队，不释放。
  - 清完之后可能什么都排不出（比如全被取消了）：prefill 分支没排出、`running` 又为空时，返回空步，不要掉进 decode 分支的 `assert`。
  - `step()`：`schedule()` 之后先取走 `self.finished`；`seqs` 非空才 `run`、`postprocess`、记 `StepRecord`；然后对取走的每个 seq `deallocate`、写 `RequestRecord`（带 `finish_reason`）；outputs 改成 `(seq_id, token_ids, finish_reason)`，只包含这一步出队的。

  最容易写错的两处：`deallocate` 顺手写在 `run` 之前，现在测试抓不到，2.7 做 ZOS 时 GPU 可能还在读这些 block，那时才会炸；最后一批请求在第 N 步判定结束，第 N+1 步才出队，这一步 `schedule()` 清完是空的，空步也要走释放和返回，否则 `generate()` 拿不到最后一批输出。
- **改哪里**：

  | 文件 | 函数 | 做什么 |
  |---|---|---|
  | `nanovllm/engine/scheduler.py` | `postprocess` | 只改状态 |
  | `nanovllm/engine/scheduler.py` | `schedule` | 开头统一出队；排不出且 `running` 为空时返回空步 |
  | `nanovllm/engine/llm_engine.py` | `step` | `run` 返回之后 `deallocate`；空步也释放；outputs 带 `finish_reason` |

### 任务 C：各入口按类型打状态（约 20 分钟，你写约 30 行）

- **目标**：超过总容量的 prompt 被标 `FINISHED_IGNORED`、`finish_reason == "prompt_length_exceeded"`，排在它后面的请求照常完成；暂时放不下的等前面的结束；`abort_request` 能取消 `running` 或 `waiting` 里的请求，下一步它不在 `scheduled_ids` 里，block 全部回到 `free_block_ids`；长到 `max_model_len` 就截断。验收 1–6 全绿。
- **思路**：对回"分不清暂时放不下和永远放不下"和"没有一个状态表示被取消"。有了任务 A 的类型和任务 B 的统一出口，每个入口只做一件事：判断属于哪种情况，打上对应的状态，剩下的交给出口。`can_allocate` 从返回 -1 改成返回 `(status, num_cached_blocks)`；调度器对 `NEVER` 拒绝、对 `LATER` 等；长度检查照 DeepInfer 的 `prompt_limit` 提前到入队；abort 只是多一个打 `FINISHED_ABORTED` 的入口（`scheduler.hpp:144`）。
- **你写什么**：
  - `add`：`num_prompt_tokens > max_model_len - 1` 直接 `FINISHED_IGNORED`（给 decode 留至少 1 个位置），照样入队，由任务 B 的出口带走。
  - `can_allocate`：`NEVER` 的条件是 `seq.num_blocks >= len(self.blocks)`（和 DeepInfer 一样用 `>=`，因为 decode 至少还要一块）。用请求需要的**总**块数，不是扣掉前缀缓存命中之后的 `num_new_blocks`：命中的块也占 cache，DeepInfer 用的也是 `get_num_blocks()`。空闲块不够是 `LATER`。
  - prefill 分支：`NEVER` → `FINISHED_IGNORED`，从 `waiting` 弹出放进 `self.finished`，`continue`；`LATER` → `break`。
  - `postprocess`：已经 `is_finished` 的跳过；`num_tokens >= max_model_len` 也算 `FINISHED_LENGTH_CAPPED`。
  - `abort`：在 `waiting` 和 `running` 里找到这些 `seq_id`，还没结束的改成 `FINISHED_ABORTED`。不动队列，不释放 block。

  最容易写错的三处：`>=` 写成 `>`，恰好占满的请求会在 decode 第一步 `may_append` 时无块可分；`postprocess` 不跳过已终态的 seq，abort 在 `step()` 之外被调用，落在 `schedule()` 选中它之后时，被取消的请求本步又被 `append_token`；`FINISHED_IGNORED` 的请求从来没分配过 block，走任务 B 的释放路径时 `block_table` 是空的，确认 `deallocate` 能处理。
- **改哪里**：

  | 文件 | 函数 | 做什么 |
  |---|---|---|
  | `nanovllm/engine/block_manager.py` | `can_allocate` | 返回 `(status, num_cached_blocks)` |
  | `nanovllm/engine/scheduler.py` | `add` | 入队时的长度检查 |
  | `nanovllm/engine/scheduler.py` | `schedule` 的 prefill 分支 | `NEVER` 出队 `continue`，`LATER` `break` |
  | `nanovllm/engine/scheduler.py` | `postprocess` | 跳过已终态的；`max_model_len` 截断 |
  | `nanovllm/engine/scheduler.py` | `abort` | 只标记 |

## 验收

`tests/test_2_1.py`，纯 CPU 可以用一个假的 `Config`（`num_kvcache_blocks` 手工指定）直接测 `Scheduler`：

1. 超过总容量的 prompt：状态 `FINISHED_IGNORED`，`finish_reason == "prompt_length_exceeded"`，队列里其他请求照常完成，引擎不崩。
2. 暂时放不下的 prompt：等前面的请求结束后被调度，最终 `FINISHED_STOPPED` 或 `LENGTH_CAPPED`。
3. abort 一个 `running` 的请求：下一步它不在 `scheduled_ids` 里；它的 block 全部回到 `free_block_ids`；`used_block_ids` 和 `free_block_ids` 的并集始终等于全集。
4. abort 一个 `waiting` 的请求：同上。
5. 任何测试结束时 `len(free_block_ids) == num_blocks`（没有泄漏）。
6. prompt 长度 `max_model_len - 1`、`max_tokens=1` 能正常生成 1 个 token。

## 常见坑

- `running.remove(seq)` 是 O(n)，而且 `deque.remove` 按相等比较。这一节先不管，2.5 会算这笔账。
- abort 和 postprocess 同一步发生：abort 在 `step()` 之外被调用，postprocess 要能容忍 seq 已经是终态。
- `FINISHED_IGNORED` 的请求从来没分配过 block，释放路径要能处理空 `block_table`。
- 别忘了 1.1 的 `RequestRecord` 要在所有终态下都生成，否则 `summarize_requests` 会少算请求。
