# 2.1：边界请求会把引擎弄死

> 起点：1.1 做完的代码　硬件：1×GPU　预计改动：150–250 行　轴：1 调度与请求状态机

## 1. 发现问题

**关注什么**：引擎在"不正常的请求"面前站不站得住。1.1 之后你有了观测工具，先拿它去撞边界。

三个实验（用 `bench.run` 的驱动或者直接写几行脚本）：

```python
llm = LLM(model, max_model_len=4096, max_num_seqs=8)
# (a) 一个比 KV cache 总容量还大的 prompt：prompt_len > num_kvcache_blocks * block_size
# (b) 正常请求跑到一半，想取消其中一个（nano-vllm 没有 abort 接口，先想想该怎么做）
# (c) 一个 prompt 恰好等于 max_model_len，max_tokens=1
```

**先预测**：(a) 会报错、卡住、还是被默默跳过？(b) 没有接口，你会直接从 `scheduler.running` 里 remove 吗？会出什么问题？(c) 能生成那 1 个 token 吗？

**现象**：

- (a) `can_allocate` 返回 -1，`schedule()` 在 prefill 分支 `break`，队列里没有别的请求时走到 decode 分支，`assert scheduled_seqs` 断言失败，整个引擎崩。有别的请求时它们先跑完，然后同样崩。这个请求**永远**放不下，但引擎只知道"现在放不下"。
- (b) 从 `running` 里 remove 之后 block 没有释放，`block_manager.used_block_ids` 漏了；如果它正好在本步被调度，`postprocess` 会拿到它的 token 继续 `append_token`。没有一个状态表示"被取消"。
- (c) `may_append` 在 decode 第一步要再分配一个 block（`len(seq) % block_size == 1`），而 `max_model_len` 不是这样算的。要么越界，要么 CUDA graph 的 `block_tables` 列数不够。

## 2. 分析问题

- **追问链**：三个现象 → 共同点是 `Sequence` 只有 `WAITING / RUNNING / FINISHED` 三个状态，`BlockManager.can_allocate` 只有 -1 一种失败 → 引擎分不清"暂时放不下"和"永远放不下"、分不清"正常结束"和"被取消 / 被拒绝 / 被抢占" → 这些情况下要么崩、要么资源泄漏。
- **本质**：请求的生命周期不是一条直线。生产流量里有超长 prompt、客户端断开、超时、资源不足，每一种都要有一个明确的终态和一条干净的退出路径。
- **卡在哪种资源**：不是性能问题，是正确性和资源回收。但它决定了后面所有调度策略能不能安全地做。
- **理论**：`reference/gpu-perf-engineering-resources/` §4 的 vLLM 论文 4.5 节讲抢占时顺带定义了请求的三类结局（完成、抢占后重算、换出）。生产引擎在此之上还要处理 abort 和 ignore。
- **DeepInfer 怎么做**：
  - `SequenceStatus` 有 10 个值（`csrc/engine/sequence.hpp:30`）：`WAITING, RUNNING, SWAPPED, FINISHED_STOPPED, FINISHED_LENGTH_CAPPED, FINISHED_ABORTED, FINISHED_IGNORED, FINISHED_PREEMPTED, FINISHED_SO_FAILED, FINISHED_VE_FAILED`，`is_finished = status >= FINISHED_STOPPED`。每个终态对应一个 `finish_reason` 字符串回给调用方。
  - 资源判断三态：`can_allocate_nolock` 返回 `OK / LATER / NEVER`（`csrc/engine/block_manager.hpp:128`）。`NEVER`（需要的 block 数 ≥ 总数）→ 标 `FINISHED_IGNORED`，`continue` 看下一个请求；`LATER` → `break`。
  - abort 只**标记**不动队列（`scheduler.hpp:144` `abort_sequence`），下一次 `_schedule_decode` 开头统一清理（`:562-577`）。原因：ZOS 下这个请求可能还在 GPU 上跑。
  - "判定结束"、"移出队列"、"释放 block"分三处：`_check_stop`（`:1035`）只改状态；`free_finished_seqs`（`:752`）只出队；`free_seq`（`:738`）才还 block，由 `pre_sampler_sync` 在下一步 forward 发射之后调用（`llm_engine.py:830-846`）。
  - 长度检查提前到入队：`prompt_limit`（`scheduler.hpp:112`）和 `runtime_max_model_len`（`config.py:11-16`，给 draft token 和 ZOS 的 inflight 留余量）。

## 3. 要做什么

### 3.1 状态和结束原因

**改哪里**：`nanovllm/engine/sequence.py`。

- `SequenceStatus` 扩成：`WAITING, RUNNING, FINISHED_STOPPED, FINISHED_LENGTH_CAPPED, FINISHED_ABORTED, FINISHED_IGNORED, FINISHED_PREEMPTED`。保持 `is_finished` 语义：所有 `FINISHED_*` 都算结束。
- 加 `finish_reason` 属性，返回 `"stop" / "length" / "abort" / "prompt_length_exceeded" / "insufficient_system_resource"`，照 DeepInfer 的字符串。
- 预留两个字段，这一节不用但后面要：`total_inflight_tokens: int = 0`（2.7）、`num_preemptions`（1.1 已有）。`num_blocks` 的计算改成 `(num_tokens + total_inflight_tokens + block_size - 1) // block_size`，现在 inflight 恒为 0，行为不变。这是路线图第 6 节的"架构种子"。

### 3.2 三态资源判断

**改哪里**：`nanovllm/engine/block_manager.py` 的 `can_allocate`，`nanovllm/engine/scheduler.py` 的 prefill 分支。

- `can_allocate` 返回 `(status, num_cached_blocks)`，`status ∈ {OK, LATER, NEVER}`。`NEVER` 的条件：`num_new_blocks >= num_blocks`（和 DeepInfer 一样用 `>=`，因为 decode 至少还要一块）。
- 调度器：`NEVER` → `seq.status = FINISHED_IGNORED`，出队，记进本步的 `ignored`，`continue`；`LATER` → `break`。
- 入队时检查 `prompt_len > max_model_len - 1` 也直接 `FINISHED_IGNORED`（给 decode 留至少 1 个位置）。

### 3.3 abort

**改哪里**：`nanovllm/engine/llm_engine.py` 加 `abort_request(seq_ids)`，`scheduler.py` 加 `abort(seq_ids)`。

- `abort` 只把状态改成 `FINISHED_ABORTED`，不动 `waiting / running`，不释放 block。
- `schedule()` 开头统一清理：`running` 里 `is_finished` 的移出；`waiting` 里 `is_finished` 的移出。两处都只出队，释放放到 3.4。
- `postprocess` 遇到已经 `is_finished` 的 seq 跳过（它本步可能被调度过了）。

### 3.4 判定、出队、释放分三处

**改哪里**：`scheduler.py` 的 `postprocess` 和 `schedule`，`llm_engine.py` 的 `step`。

- `postprocess`：命中 EOS → `FINISHED_STOPPED`；`num_completion_tokens == max_tokens` 或 `num_tokens >= max_model_len` → `FINISHED_LENGTH_CAPPED`。**只改状态，不 deallocate，不 remove。**
- `schedule()` 开头：把 `running` 里 `is_finished` 的移到本步的 `finished` 列表（和 3.3 合并成一处）。
- `step()`：拿到 `finished` 列表后，在 `model_runner.call("run")` **返回之后**再对它们 `deallocate`。现在这样做看起来多此一举，2.7 做 ZOS 时你会需要这个顺序：GPU 可能还在读这些 block。
- `step()` 返回的 outputs 里带上 `finish_reason`；1.1 的 `RequestRecord` 也记上。

## 4. 验收

`tests/test_2_1.py`，纯 CPU 可以用一个假的 `Config`（`num_kvcache_blocks` 手工指定）直接测 `Scheduler`：

1. 超过总容量的 prompt：状态 `FINISHED_IGNORED`，`finish_reason == "prompt_length_exceeded"`，队列里其他请求照常完成，引擎不崩。
2. 暂时放不下的 prompt：等前面的请求结束后被调度，最终 `FINISHED_STOPPED` 或 `LENGTH_CAPPED`。
3. abort 一个 `running` 的请求：下一步它不在 `scheduled_ids` 里；它的 block 全部回到 `free_block_ids`；`used_block_ids` 和 `free_block_ids` 的并集始终等于全集。
4. abort 一个 `waiting` 的请求：同上。
5. 任何测试结束时 `len(free_block_ids) == num_blocks`（没有泄漏）。
6. prompt 长度 `max_model_len - 1`、`max_tokens=1` 能正常生成 1 个 token。

重跑 1.1 的四个场景，数字应该和 1.1 一样（这一节不改性能）。

## DeepInfer 对照

| 这一节 | DeepInfer | 差异和原因 |
|---|---|---|
| 7 个状态 | 10 个（`sequence.hpp:30`） | 少了 `SWAPPED`（它自己也没用）、`SO_FAILED`（2.11）、`VE_FAILED`（多模态） |
| `OK / LATER / NEVER` | `block_manager.hpp:128` | 一致 |
| abort 只标记，下次调度清理 | `scheduler.hpp:144`、`:562-577` | 一致。DeepInfer 还要清 waiting 里的死请求，否则 DP 投票会被一个只剩死请求的 rank 卡住（5.3） |
| 释放放在 `run` 返回之后 | `pre_sampler_sync` 在下一步 forward 发射之后才 `free_seq`（`llm_engine.py:846`） | 同一思想，DeepInfer 晚得更多，因为 ZOS 下 post-process 本身就晚一步 |
| 入队时查长度 | `prompt_limit`、`runtime_max_model_len` | DeepInfer 还要给 draft token 和 inflight 留余量，2.7、2.8 会遇到 |
| 没有 | `prompted` 队列、`fork` | 2.4 |

## 常见坑

- `running.remove(seq)` 是 O(n)，而且 `deque.remove` 按相等比较。这一节先不管，2.5 会算这笔账。
- abort 和 postprocess 同一步发生：abort 在 `step()` 之外被调用，postprocess 要能容忍 seq 已经是终态。
- `FINISHED_IGNORED` 的请求从来没分配过 block，释放路径要能处理空 `block_table`。
- 别忘了 1.1 的 `RequestRecord` 要在所有终态下都生成，否则 `summarize_requests` 会少算请求。
