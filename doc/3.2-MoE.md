# 3.2：2.4B 激活参数，跑得和 8B 一样慢

> 起点：3.1 做完的代码　轴：4 模型结构 / 5 kernel

| | |

## 发现问题

**关注什么**：V2-Lite 每个 token 只经过 6 + 2 个专家（2.4B 参数），理论上一步 decode 的计算量是 Qwen3-8B 的三分之一。看看实际的 `gpu_forward` 是多少，时间花在哪。

```bash
for n in 1 16 64 256; do python -m bench.run --scenario steady_decode --model deepseek-ai/DeepSeek-V2-Lite --max-num-seqs $n; done
nsys profile -o out/v2lite-decode python -m bench.run --scenario steady_decode --model deepseek-ai/DeepSeek-V2-Lite --max-num-seqs 256 --num-steps 50
```

**先预测**：并发 1 时 `gpu_forward` 应该比 Qwen3-8B 快多少？并发 256 时呢？一步 decode 要读多少字节的权重？

**现象**：

- 并发 1：`gpu_forward` 不比 Qwen3-8B 快，甚至更慢。Nsight 里一层 MoE 是 64 个专家 × (`index_select` + 2 个小 GEMM + SiLU + `index_add`) 串成一排，**一层几百个 kernel，26 层上万个**，每个几微秒，GPU 大部分时间在等 launch。2.7 的 ZOS 隐藏不了这个：这是 GPU 自己的 launch 间隙，不是 CPU 没跟上。
- 并发 256：`gpu_forward` 比 Qwen3-8B 的同并发慢。每层 64 个专家每个分到 256 × 6 / 64 = 24 个 token 的 GEMM，`M = 24`，tensor core 利用率个位数。
- 算一下访存：256 个 token 每层会命中几乎全部 64 个专家，一步要把 **15.7B 参数（31 GB）全读一遍**，和 dense 模型一样。按 3.35 TB/s 算下限 9 ms，实测远不止。"每 token 只算 2.4B" 省的是算力，不是访存。

## 分析问题

- **追问链**：慢 → MoE 层是逐专家的 Python 循环 → 每个专家一个小 GEMM，launch 多、`M` 小 → 把 64 个专家的 GEMM 合成一个 kernel（grouped GEMM），token 按专家排好序连续放，kernel 按分组读 → 排序和还原本身就是 dispatch / combine 的单卡版本 → 做完之后每个专家的 `M` 仍然只有 24，访存仍然是读全部权重 → 这是单卡解决不了的，专家要分到多卡上（5.1）。
- **本质**：MoE 的 decode 成本结构和 dense 不同：算力按激活参数算，访存按**本步被命中的专家总量**算。batch 大了所有专家都命中，访存就是全模型。单卡上能做的是把 kernel 数压到最少、让每个专家的 GEMM 形状对 tensor core 友好；真正降低每卡访存要靠 EP。
- **量化**：V2-Lite 一层 MoE 的 GEMM 总量是 `256 × 6 × 2 × (2048 × 2816 + 1408 × 2048)` ≈ 26 GFLOP，H100 上 30 µs 就能算完；而 64 个专家的权重 64 × 2 × 2048 × 2816 × 2 B ≈ 1.5 GB，读一遍 450 µs。所以 decode 的 MoE 层**完全是访存瓶颈**，目标是让 kernel 时间逼近 450 µs，而不是现在的几毫秒。
- **理论**：`reference/gpu-perf-engineering-resources/` §5 "Mixture-of-experts serving"：GShard（dispatch / combine 的定义，capacity）、DeepSeek-V3（routed + shared 专家、无辅助损失的负载均衡偏置 `e_score_correction_bias`、`routed_scaling_factor`）；§2 "Matrix multiplication"：DeepGEMM（grouped GEMM 的 contiguous 和 masked 两种布局）。
- **DeepInfer 怎么做**（`models/v4_modules/mlp.py`，`DeepseekMoE`）：
  - **gate** `gate_forward`（`mlp.py:359`）：gate 投影是 bf16 权重、**fp32 输出**（`use_fp32_output=True`，`:222`；`moe.py:40` 注释"gate 永远不参与 FP8"），然后 `moe_topk_gate`（TileKernels，`:400`）一个 kernel 做 scoring（V4 是 `sqrtsoftplus`）、加 `e_score_correction_bias` 选 top-k（`noaux_tc`）、按原始分数归一化、乘 `routed_scaling_factor`，输出 `topk_idx [T, k]`、`topk_weights [T, k]`。EPLB 的 `logical_to_physical_map` 也在这个 kernel 里做（5.4）。
  - **权重布局** `process_moe_weight`（`mlp.py:41`）：HF 的逐专家 `[h_out, h_in]` 打包成 `[E, N, K]` 一个连续张量（`gate_up` 合并成一个 `[E, 2×1408, 2048]`），FP8 时每个专家带自己的 scale。打包后原权重 `untyped_storage().resize_(0)` 立刻释放。
  - **dispatch / combine**：`dispatch`（`:461`）和 `combine`（`:493`）调 DeepEP 的 `EPBuffer`，单卡时等价于"按 `topk_idx` 把 token 复制 k 份并按专家排序"和"按 `topk_weights` 加权求和放回原位"。返回 `psum_num_recv_tokens_per_expert`（每个专家的 token 前缀和）给 grouped GEMM 当分组边界。
  - **专家计算** `routed_experts_forward`（`:406`）：`_grouped_gemm`（`:109`）→ `swiglu_forward_and_per_token_cast`（TileKernels，SiLU×up 和下一层的 FP8 cast 融合，`topk_weights` 也在这里乘进去）→ `_grouped_gemm`。两个 grouped GEMM 是 DeepGEMM 的 `m_grouped_*_gemm_nt_contiguous`，`use_psum_layout=True` 直接吃前缀和，**不要求每个专家的 token 数是 tile 的整数倍**。
  - **shared expert** `shared_forward`（`:513`）：两个 shared expert 合并成一个 `[2816×2, 2048]` 的普通 linear；多卡时放在被限制 SM 数的 stream 上和 combine 并行，输出作为 combine 的 `bias` 加进去（5.2）。
  - **forward**（`:565`）：gate → dispatch → routed → shared → combine。B200 上整条链是一个 `mega_moe` kernel（`:528`，4.9）。
  - V4 的 MoE 层里 attention 之后的 norm 输出直接就是 FP8（3.3）。

**思考题**：并发 256 时一步要读全部 64 个专家的权重。并发降到 16、4、1 时，每层平均命中几个专家、读多少字节？并发多少以下，MoE 层的访存才真的按 2.4B 激活参数算？

## 解决问题

### 任务 A：gate 和权重打包（约 20 分钟，你写约 60 行）

- **目标**：`select_experts` 的 `topk_idx`、`topk_weights` 和 HF `MoEGate` 完全一致；64 个专家的权重装进 `[E, N, K]` 两个连续张量，shared expert 合成一个普通 MLP，装完显存里没有 HF 原形状的副本。
- **思路**：对回分析里的 gate 和权重布局两条。gate 用 bf16 权重、输出 fp32 logits，选专家先用 PyTorch 写（`softmax → topk`），把 `sqrtsoftplus` / `noaux_tc` / bias 留成参数，4.9 给 V4 用。权重打包是 grouped GEMM 的前提：kernel 要按分组读，专家权重就得在一个连续张量里。
- **已备好**：`nanovllm/layers/moe.py` 的文件和 `select_experts(logits, k, scoring_func, bias, norm_topk_prob, routed_scaling_factor) -> topk_idx, topk_weights` 的签名；`loader.py` 的 `packed_modules_mapping` 把 `experts.{i}.gate_proj` 映射到第 i 个分组的前半；`tests/test_3_2.py` 的测试壳。
- **你写什么**：`select_experts` 的函数体（V2-Lite 是 `scoring_func="softmax"`、`topk_method="greedy"`、`norm_topk_prob=False`、`routed_scaling_factor=1.0`，按 `config.json` 核对）；打包：64 个专家的 `gate_proj` + `up_proj` 装进一个 `[E, 2×1408, 2048]`，`down_proj` 装进 `[E, 2048, 1408]`；两个 shared expert 合并成一个 `[2×2816, 2048]` + `[2048, 2×1408]` 的普通 MLP（HF 的 `shared_experts` 本来就是一个 `intermediate = 2 × 1408` 的 MLP）。最容易错的两处：HF 的 `topk_weights` 在 `norm_topk_prob=False` 时就是 softmax 后的原值，不要擅自归一化；`gate_proj` 和 `up_proj` 在 HF 里是分开的两个张量，合并顺序（先 gate 后 up）要和任务 C 的 SwiGLU kernel 的 chunk 顺序一致。装完检查显存：不要让 HF 原形状和打包后的形状同时存在。

### 任务 B：单卡 dispatch / combine（约 20 分钟，你写约 50 行）

- **目标**：`permute` / `unpermute` 两个函数，`permute → unpermute` 在权重全 1 时是恒等；输出 `psum` 给任务 C 当分组边界。
- **思路**：对回分析里的"排序和还原就是 dispatch / combine 的单卡版本"。`permute(x [T, H], topk_idx [T, k]) -> x_sorted [T×k, H], psum [E], inv_index [T×k]`：按专家 id 稳定排序（`argsort`），`psum` 是每个专家的 token 数前缀和；`unpermute(y_sorted [T×k, H], inv_index, topk_weights) -> y [T, H]`：加权求和回原位。接口和 DeepEP 单卡的语义一致，5.2 换成 DeepEP 时只换实现。
- **已备好**：两个函数的签名；`tests/test_3_2.py` 里恒等测试。

## 验收

同一个实验重跑：

1. 并发 1：`gpu_forward` 明显低于 3.1（launch 从上万个降到几百个），低于 Qwen3-8B 的同并发。
2. 并发 256：MoE 层的 GPU 时间逼近"读一遍专家权重"的下限（450 µs 量级，Nsight 里看 grouped GEMM 的时间），整步 `gpu_forward` 低于 Qwen3-8B。
3. 正确性：`tests/kl.py` 对 HF 的 KL 和 3.1 基线一致（grouped GEMM 的归约顺序和逐专家 GEMM 不同，bf16 下允许微小差异）；`greedy_match` 和黄金文件一致。
4. `tests/test_3_2.py`：(a) `select_experts` 和 HF `MoEGate` 一致；(b) `permute → unpermute` 是恒等（权重全 1 时）；(c) grouped GEMM 和逐专家 `F.linear` 一致，包括某些专家 0 个 token 的情况；(d) 并发 1 和 256 的 MoE 输出一致（专家分组不同不影响结果，2.12 的 batch-invariant 要覆盖 MoE）；(e) 3.1 和第 2 章全过。
5. 报告：一步 decode 读的权重字节数、MoE 层每个专家的 token 数分布（为 5.1 和 5.4 留底）。
6. **解释**（由你说）：并发 1 和并发 256 各卡在什么上（launch 还是访存），为什么同一个 grouped GEMM 对两边都有效；MoE 层逼近 450 µs 之后为什么单卡再也压不下去。

**新浮现的问题**：并发 256 的 decode 已经贴近"读一遍 31 GB bf16 权重"的下限，再往下只能让权重变小；prefill 大 batch 时 GEMM 贴近 bf16 tensor core 的峰值。两条路都指向更低的精度。这是 3.3。

## 常见坑

- V2-Lite 第 0 层是 dense MLP（`first_k_dense_replace = 1`），别把它当 MoE 装。
- HF 的 `topk_weights` 在 `norm_topk_prob=False` 时就是 softmax 后的原值，不要擅自归一化；V3/V4 才归一化并乘 `routed_scaling_factor`。
- `permute` 要用**稳定**排序，否则同一专家内 token 的顺序和 batch 有关，2.12 的 batch-invariant 会挂。
- grouped GEMM 的 `psum` 布局下有些专家 0 个 token 是正常的，kernel 要处理空分组；对拍时专门造这种 case。
- `index_add_` 在 bf16 上的原子加是不确定的，`unpermute` 的参考实现用 fp32 累加再转回。
- 打包权重时 64 个专家的 `gate_proj` 和 `up_proj` 在 HF 里是分开的两个张量，合并顺序（先 gate 后 up）要和 SwiGLU kernel 的 chunk 顺序一致。
