# 2.12：同一个 prompt，换个 batch 答案就变

> 起点：2.11 做完的代码　轴：7 采样与确定性

| | |
|---|---|
| **问题** | 同一个请求，单独跑和混在 64 个请求里跑，logprob 不一样，输出会分叉。根因是同一个数学运算在不同 batch 形状下选了不同的归约顺序，浮点加法不满足结合律 |
| **实验** | 同一 prompt 单发 vs 64 并发，逐 token 比 logprob，找第一个分叉的位置 |
| **硬件 / 费用** | 1×H100 + Qwen3-8B，Modal 约 $3.95/h；定位和反复验证约 3 小时，约 $12 |
| **学到** | batch-invariant = 每个归约的顺序只是位置的函数，不是 batch 的函数；哪些算子的归约和 batch 相关（split-K、split-KV、分块 norm、MoE 分组）；做到了逐位相等，正确性检查才能从"带容差"升级成 DeepInfer 的"逐位相等黄金文件 + decode / prefill 自洽" |
| **时长** | 发现 + 定位约 3 小时（本节最花时间的部分）；任务 A / B / C 各约 20 分钟；验收约 1 小时 |

## 发现问题

**关注什么**：同一个请求，单独跑和在 64 个请求里跑，输出是否逐 token、逐 logprob 相同。

```python
# 固定 seed，temperature=0（2.10 之后允许贪心）
out_single = llm.generate([p], sp)
out_batch  = llm.generate([p] + 63 个别的 prompt, sp)[0]
# 比较 token_ids 和每个 token 的 logprob
```

**先预测**：2.10 之后随机数已经是位置的函数了，两次结果会一样吗？如果不一样，差在哪一步？

**现象**：前几十个 token 一样，之后某个位置 logprob 差了 1e-3 量级，再往后 argmax 翻转，输出分叉。把每一层的输出 dump 出来对：差异从第一层的 RMSNorm 或者 attention 就开始了，量级 1e-6，逐层放大。差异的来源不是随机数，是**同一个数学运算在不同 batch 形状下的浮点归约顺序不同**。

## 分析问题

- **追问链**：logprob 不同 → 某层的输出不同 → 同一个 kernel 在 batch=1 和 batch=64 时选了不同的 tile / split 策略 → 浮点加法不满足结合律，归约顺序不同结果就不同 → 和 batch 组成相关的归约有：GEMM 的 split-K、attention 的 split-KV、RMSNorm 的分块归约、MoE 的 token 分组。
- **本质**：batch-invariant = 每个归约的顺序只是**位置**的函数，不是 batch 的函数。这是训推一致（训练时的 logprob 和推理时按位相同）和可复现调试的前提。
- **理论**：`reference/gpu-perf-engineering-resources/` §2 "Defeating Nondeterminism in LLM Inference"（Thinking Machines）：原因分析和 batch-invariant 的 RMSNorm / matmul / attention 实现。
- **DeepInfer 怎么做**（`DEEPINFER_BATCH_INVARIANT`，`environ.py:197`）：
  - `deep_gemm.use_deterministic_algorithms(True)` 和 `tile_kernels.use_deterministic_algorithms(True)`（`runtime_config.py:68-69`）：GEMM 和 kernel 固定 split 和归约顺序。
  - FlashMLA decode 传 `enable_batch_invariant=True`（`attention_backend.py:141`）：固定 split-KV 的归约。
  - 关闭融合的 norm-rope-attn 路径（`attn.py:87-92`），因为它的归约和 batch 相关。
  - EPLB 开启时关 DeepEP 的多重归约（`userbuffer.py:79`），否则 combine 的求和顺序取决于动态的专家放置。
  - 它是**每 rank 内**的性质，不跨 DP；确定性采样还要求 `DEEPINFER_ENABLE_MTP_VARLEN=0` 加固定 `seq_seed`（README）。
- **DeepInfer 的正确性检查建立在这个性质上**，这是 1.1 留下的那条线的终点：
  - `tests/models/test_batch_invariant.py:100-105`：同一 prompt 在 batch 里生成一次，把它生成的 token 作为 `golden_token_ids` 单独再跑一次，`assert result_batched == result_single`，token、logprob、top-k 完全一致。
  - `tests/models/test_kl.py:95-160`：第一遍用 `golden_token_ids` 在引擎里做 teacher forcing，拿到逐步 decode 的 logprob；第二遍把生成的 token 折进 prompt、开 `prompt_logprobs`，用一次 prefill 算整条序列的 logprob；两边用 `deepinfer/testing.py:4` 的 `cal_diff` 比，`max_kl = 0.0`。**decode 路径和 prefill 路径是两套 kernel，算同一个位置必须逐位一样**，这本身就是 batch-invariant 的一种。
  - `tests/models/offline_decode_ppl.json`：逐样本 decode PPL 黄金文件，`test_offline_inference.py:156-160` 要求 `actual == expected`，没有容差。黄金文件按平台、长短上下文、DP rank 分开存，并行配置一变就重新测。
  - 没有 HF。它的目标模型 HF 跑不动，靠"自己和自己比"加历史基线。

**思考题**：确定性和 batch-invariant 是两回事：同一 batch 跑两次一样叫确定性，换 batch 也一样才是 batch-invariant。一个有确定性但不 batch-invariant 的引擎，`test_kl` 的两遍会一样吗？

## 解决问题

### 任务 A：定位（约 20 分钟写工具，跑和看约 2 小时，你写约 40 行）

- **目标**：知道第一个不一致的层和算子是哪个。
- **思路**：对同一 prompt 在 batch=1 和 batch=64 下逐层保存 hidden，从第一层往后找第一个 `torch.equal` 为假的位置，再往里拆到算子。候选：`F.linear`（cuBLAS 按形状选算法，split-K 不同）、flash-attn 的 split-KV（`flash_attn_with_kvcache` 对短序列会 split）、`RMSNorm`（nano 的 Triton 实现如果按 block 分块归约）、2.10 的 top-K（并列值的顺序）。
- **已备好**：`bench/dump.py` 的 CLI 和保存 / 对比的框架，`tests/test_2_12.py` 的测试壳。
- **你写什么**：挂 forward hook 逐层存 hidden 的那段，和"找第一个不相等的层"的比较。最容易错的一处：batch=64 时要取出**同一个请求**的那几行再比，位置要按 `cu_seqlens` 切。

### 任务 B：固定归约顺序，带开关（约 20 分钟，你写约 60 行）

- **目标**：`Config.batch_invariant=True` 时，单发和 64 并发逐位一致；`False` 时走原来的快路径，两者吞吐差写进报告。
- **思路**：每个和 batch 相关的归约都换成只依赖位置的版本。GEMM：先试 `torch.use_deterministic_algorithms(True)` + `CUBLAS_WORKSPACE_CONFIG=:4096:8`，不够就用一个固定 tile 的 Triton GEMM（§2 的文章给了实现）。attention：decode 分支显式传 `num_splits=1`，prefill 不受 batch 影响。RMSNorm：一行一个 program，整行在一个 block 内归约。2.10 的 top-K：并列时按 id 稳定排序。2.9 的变长验证和确定性采样冲突（分配依赖运行时测量），开确定性采样时强制定长。
- **已备好**：`Config.batch_invariant` 字段和它到各层的传递；`tests/test_2_12.py` 里"关掉开关测试必须失败"那一条。
- **你写什么**：`nanovllm/layers/linear.py`、`attention.py`、`layernorm.py` 里按开关切路径的那几处。最容易错的一处：CUDA graph 捕获的 kernel 和 eager 跑的 kernel 可能选了不同算法，`enforce_eager=True/False` 都要测。

### 任务 C：正确性升级到 DeepInfer 的形式（约 20 分钟，你写约 50 行）

- **目标**：1.1 的 `bench.correctness` 从"HF 当裁判、按均值带容差"升级成 DeepInfer 的两道检查：逐位相等的黄金文件，和 decode / prefill 自洽。HF 退到新模型第一次接入时做外部背书（3.1 会用）。
- **思路**：
  1. **引擎自己算 logprob**。sampler 返回每个 token 的 logprob（2.10 的 fp32 logits 已经在了），`RequestRecord` 记下来。`SamplingParams` 加 `golden_token_ids`：给了就不采样、直接走这串 token，只算它们的 logprob。这是 DeepInfer 做 teacher forcing 的方式（`sampling_params.py:60`）。
  2. **黄金文件逐位相等**。`bench.correctness --write` 存每个 prompt 逐 token 的 logprob（或 PPL），`--golden` 要求 `==`，不再按均值带容差；黄金文件名带上硬件和模型，换卡重新生成。
  3. **decode / prefill 自洽**。`tests/kl.py`：第一遍正常生成拿 token 和逐步 logprob；第二遍把生成的 token 折进 prompt、`golden_token_ids` 指向它们，一次 prefill 算整条的 logprob；两边 `cal_diff`，开 `batch_invariant` 时 KL 必须是 0，关掉时记下它有多大。
- **已备好**：`bench/correctness.py` 的 `--exact` 开关和黄金文件的新格式；`tests/kl.py` 的两遍调用和 `cal_diff`（抄 `deepinfer/testing.py:4`）。
- **你写什么**：sampler 返回 logprob 并沿 `RequestRecord` 传出；`golden_token_ids` 在 sampler 里的分支；`compare` 的精确模式。最容易错的一处：prefill 路径算 logprob 的位置对齐，和 1.1 任务 C 的 `teacher_forced_nll` 是同一个坑，位置 t 的 logits 预测 t+1。

1. `tests/test_2_12.py`：固定 seed、`temperature=0`，同一 prompt 单发 vs 64 并发（并发里混不同长度），token、logprob、top-5 完全一致；`temperature=1` 加固定 seed 同样一致；开投机解码（定长）同样一致；`enforce_eager=True/False` 都过；2.1–2.11 全过。
2. 关掉开关，测试失败（证明开关真的在起作用）。
3. 吞吐损失写进报告（预期几个百分点）。

5. 黄金文件按精确模式重新生成，`--golden` 逐位相等通过；1.1 的破坏实验（prefill `causal=False`）照样被抓住，而且现在改一个 bit 就抓得住。
6. **解释**（由你说）：为什么做到 batch-invariant 之后才能要求逐位相等？decode / prefill 自洽和 batch-invariant 是什么关系？

**新浮现的问题**：第 2 章到此结束，引擎控制面和 DeepInfer 对齐（P1）。把 1.1 的 KV 容量数字换算到 70B 级 dense 模型：每 token KV 太大，batch 开不起来。这是第 3 章的起点。3.1 换模型时，黄金文件和 `tests/kl.py` 要为新模型重做一遍，第一次接入用 HF 背书。

## 常见坑

- `torch.use_deterministic_algorithms(True)` 会让一些算子直接报错而不是变慢；逐个处理。
- 确定性 ≠ batch-invariant：同一 batch 跑两次一样叫确定性；换 batch 也一样才是 batch-invariant。两个都要测。
- CUDA graph 捕获的 kernel 和 eager 跑的 kernel 可能选了不同算法，测试要同时覆盖 `enforce_eager=True/False`。
- 这一节的吞吐损失是真实代价，不要为了过测试把快路径也改慢；开关要保留。
- 黄金文件逐位相等意味着换一张卡、换一个 torch 版本就要重新生成。文件名里带上这些信息，`--golden` 对不上时先看是不是环境变了，再怀疑代码。
- 1.1 的 `nll` 容差版不要删，新模型第一次接入（3.1）还要靠它做外部背书。
