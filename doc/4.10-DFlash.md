# 4.10：draft 头是 Qwen3 的，V4 用不了

> 起点：4.9 做完的代码　轴：3 解码加速 / 4 模型结构

| | |
|---|---|

## 发现问题

**关注什么**：2.8 的投机解码在 V4.1 上怎么办。HF 权重里有 `num_nextn_predict_layers` 个 DFlash 层（每层是一个完整的 MoE decoder block，专家数按 `dspark_n_routed_experts`），加 `projection`、`project_norm`、`markov_w1 / w2`、`confidence_head.proj`、`shared_head.norm`。config 里 `dspark_target_layer_ids`、`dspark_block_size`、`dspark_markov_rank`、`dspark_noise_token_id`。

```bash
python -m bench.run --scenario steady_decode --model <V4.1 前 K 层 + DFlash> --max-num-seqs 1   # 2.8 的 EAGLE-3 头接不上，先跑不起来
```

**先预测**：DFlash 一步要跑几次 forward 才能产出 `nextn` 个 draft？它的输入是什么？2.9 的变长验证用的"置信度"从哪来？

**现象**：

- 2.8 的接口假设 draft 是**自回归**的：`nextn` 次小 forward，每次一个 token。DFlash 不是：它一次 forward 产出一整块 `nextn` 个 draft（block-parallel），输入是 `[上一步接受的 token, noise, noise, …]`。
- 它的"特征"不是 EAGLE-3 的三层 hidden 拼接，而是指定几层（`dspark_target_layer_ids`）attention 输入处的 hidden（四路残差取平均），经过 `projection` 变成 draft 层的 K。
- 它自带一个**置信度头**：每个 draft 位置输出一个接受概率，2.9 的 GPU 重分就是等这个。
- 2.8 的 draft 走的是一个小的 paged KV；DFlash 的 draft 层用的是 4.2 的 SWA 环布局，主 token 的 K 由主模型 forward 顺便写进去。

## 分析问题

- **追问链**：draft 头换成 DFlash → 它的结构是 `nextn` 个 V4 decoder 层（带 mHC、MoE）→ draft 层的 attention 看两样：主模型最近 `window` 个 token 的 K（从 target 特征投影，**主 forward 时就写好**）和本块内的 draft token → 一步一个 forward，`nextn` 个位置一起算 → lm_head 对 `nextn` 个位置一次算 logits，再逐位置采样（第 `i` 个位置的 Markov 头依赖第 `i−1` 个采出的 token，所以采样是串行的，但 forward 不是）→ 置信度头给每个位置一个接受概率 → 写进 2.8 的 pool，2.9 的 GPU 重分用它 → 整个 draft forward + 采样捕进一个 CUDA graph。
- **本质**：DFlash 把 draft 从"小模型自回归"变成"一个 block 的并行解码"：一次 forward 的代价换 `nextn` 个 draft；它和主模型共享 cache 布局（SWA 环）和层结构（mHC + MoE），所以第 4 章前面的所有模块在这里复用。
- **量化**：2.8 的 EAGLE-3 一步 `nextn` 次 forward 各读一遍 draft 权重；DFlash 一步读一遍 `num_nextn_predict_layers` 层的权重。接受率的数字写进报告和 2.8 比。
- **理论**：`reference/gpu-perf-engineering-resources/` §4 Speculative decoding：Leviathan（精确性）、EAGLE（吃特征的 draft）；DFlash（block-parallel draft，不在清单里）。
- **DeepInfer 怎么做**（`models/mtp/dflash.py`）：
  - **结构**：`DFlash`（`:82`）：`layers` 是 `num_nextn_predict_layers` 个 `DFlashDecoderLayer`（`decoder_layer.py:178`，attention 是 `DFlashAttention`，MoE 可以和主模型不同构，`builder.py:107-121`）；`projection`（`H × num_targets → H`）+ `projection_norm`；`main_kv_proj`（所有 DFlash 层的 `Wkv.A` 合并成一个 GEMM）；`markov_w1`（embedding）/ `markov_w2`（`rank → vocab`，fp32 输出）；`confidence_head`（`:46`，`sigmoid((hidden ‖ markov_emb) · w / T)`，`tilelang_ops/dflash.py:10`，温度按步可不同）；`post_norm`；`hc_head`。
  - **target 特征**：主模型 `decoder_layer.py:144-145`：target 层在 attn-norm 之后把残差（四路平均，`dflash_input_store`，`tilelang_ops/dflash.py:130`）写进 `dflash_input [n, H × num_targets]` 的对应段；YoCo compact 时行数跟着切（`deepseek.py:199-206`）。
  - **主 token 的 K**：`update_main_cache`（`dflash.py:198`）在主模型 forward **末尾**（`deepseek.py:223`，decode 时在主模型的 CUDA graph 里）：`projection_norm(projection(dflash_input))` → `main_kv_proj` → 每层一份 `[n, qk_head_dim]` → `DFlashAttention.update_main_cache`（`attn.py:928`）norm + RoPE + FP8 + 存到该层的 `swa_cache`，slot 用主模型的 `slot_mapping_store_swa`。被拒绝的 draft 位置也会写，但 `forward_drafts` 随后会覆盖它们（docstring）。
  - **draft forward**：`run_drafts`（`:347`）：`build_dflash_input`（`input_metadata/dflash.py:36`）从主 metadata 生成固定步长的 draft 元数据：每请求 `dflash_block_size` 行，`positions`、`dflash_newx_slot_mapping_store`（draft K 写到环里的哪些槽）、`dflash_kv_index`（每个 draft 位置看的槽：主 token 的窗口 + 本块前面的 draft）、`valid_token_mask`、`gate_force_random`，用一个融合 kernel 算；`_embed_draft_init_tokens`（`:230`）：`[golden, noise, …]`；`forward_drafts`（`:241`）：每层 `attn_norm → DFlashAttention.forward_drafts（:963，q 投影、draft K 写环、decode_mla_mqa_sparse 用 "DFlash" 的调度元数据）→ ffn_norm → MoE`，mHC 照 4.7，末尾 `hc_post` + shifted 混合。
  - **采样**：`sample_drafts`（`:279`）：`post_norm` → `get_logits` 一次算 `[req × nextn, V]` → 逐 step：`logits[step::nextn]` 加 Markov 头（`markov_w2(markov_w1(上一个 draft), out_acc=logits)`）→ 置信度头写 `confidence_rates[:, step]` → `process_sampling(tag="mtp")`（2.10 的 hash RNG，位置 `sample_positions + step + last_valid_offset`）→ 下一 step 的 Markov 输入。结果 `MTPPredictInfo(token_ids, confidence_rates)` 存进 `MTPInfoPool`（`:339`）。
  - **CUDA graph**：`DFlashCudaGraphRunner`（`worker/dflash_cuda_graph_runner.py:31`）按 batch 桶捕获整个 `run_drafts`（含采样和 pool 写入，`:42`），`replay`（`:84`）先把本步的 `MTPDecodeInput` 拷进固定 buffer。`decode_forward`（`dflash.py:379`）选 graph 或直跑。
  - **接口**：`MTPDecodeInput.driver`（`golden_tokens`、`last_valid_offset`、采样输入）来自 2.7 的 ZOS 路径；CP 下 follower rank 只跑 forward 不采样（`:359-364`）。

**思考题**：`nextn = 6` 时 `sample_drafts` 要做几次 lm_head GEMM、几次 Markov 的小 GEMM？forward 是并行的、采样是串行的，如果把 Markov 头也去掉让采样并行，draft 丢掉了什么信息？

## 解决问题

三个任务按数据流走：先把 DFlash 的层和权重建起来、把 2.8 的 drafter 接口改成"主 forward 末尾写主 K + 一次 run_drafts"（任务 A）；再让主模型在 forward 里把 target 特征和主 K 顺便写好（任务 B）；最后写 draft forward、串行采样、置信度进 pool，整个捕进 CUDA graph（任务 C）。任务 C 最大，老实按一个半小时排。

## 验收

1. harness：同一份 target 特征和 golden token，draft token（贪心）和置信度和 DeepInfer 一致；主 K 写进环的字节一致。
2. 同一个实验重跑（并发 1 / 16 / 64 / 256 的 `steady_decode`）：接受率写进报告；低并发吞吐提升和 2.8 比；2.9 的变长分配用置信度后高并发不退化。
3. 正确性：固定 seed 下开 / 关 DFlash 的输出分布一致（拒绝采样精确）；`greedy_match` 和黄金文件一致。
4. `tests/test_4_10.py`：(a) `build_dflash_input` 和 PyTorch 参考一致（含 padding 请求、`last_valid_offset` 各种值）；(b) 置信度 kernel 和 `confidence_head_fused_ref`（`tilelang_ops/dflash.py:54`）一致；(c) `dflash_input_store` 和 `_ref`（`:158`）一致；(d) Markov 头的串行依赖：第 `i` 步的 logits 用了第 `i−1` 步采出的 token；(e) 被拒绝的 draft 槽下一步被主 K 覆盖；(f) 前面全过。
5. **解释**（由你说）：并发 1 的吞吐为什么比 2.8 高，是 draft 便宜了还是接受率高了，用报告里的两个数拆开；并发 256 时提升为什么小甚至为零；2.9 用真正的置信度之后，高并发"不退化"是靠什么保证的。

**新浮现的问题**：一层 V4.1 的大 kernel 都是 vendor 的，但 Nsight 里它们之间还夹着不少我们自己用 torch 拼的小算子（cat、index_select、分开的 norm / rope / cast）。这是 4.11。

## 常见坑

- draft 层的 `window_size` 必须和主模型一致（`dflash.py:144`），否则 SWA 环布局对不上。
- `main_kv_proj` 是所有 DFlash 层的 `Wkv.A` 合并后的一个 GEMM，输出按层 `unflatten`；DFlash 层的权重 K 会保留两份（主 / draft 投影布局不同）。
- 主 K 在 decode 时是在**主模型的 CUDA graph 里**写的，此时接受结果还没出来，所有位置都写；靠 `forward_drafts` 覆盖拒绝位置，不要试图按接受结果屏蔽。
- 置信度头的温度 `DEEPINFER_DFLASH_CONFIDENCE_HEAD_TEMPERATURE` 可以按步不同（`environ.py:135`），对拍时要传同样的值。
- 采样位置 `sample_positions + step + last_valid_offset`：2.10 的 hash RNG 对位置敏感，错一位就对不上。
