# 2.10：同一个 seed 两次结果不一样

> 起点：2.9 做完的代码　硬件：1×H100，Qwen3-8B　预计改动：300–500 行　轴：7 采样与确定性

## 1. 发现问题

**关注什么**：采样的可复现性和耗时。

```python
# 同一 prompt、同一 seed、temperature=1.0，跑两次；再把它放进不同大小的 batch 里跑
```

```bash
python -m bench.run --scenario steady_decode    # 看 gpu_sample 占 wall 的比例
```

**先预测**：nano-vllm 的 `Sampler` 用 `torch.empty_like(probs).exponential_()` 做 gumbel 采样，seed 从哪来？两次运行会一样吗？同一请求在 batch 位置不同时会一样吗？加上 top-p 后采样要几个 kernel？

**现象**：

- 没有 per-request seed：`exponential_()` 用全局 RNG，结果取决于本步之前调用了多少次 RNG、这个请求在 batch 里排第几。同一请求换一个 batch 位置输出就变。2.7 的 ZOS 让调度顺序更不可预测，2.8 的投机解码又在同一步里采多个位置。
- 没有 top-p / top-k：加上之后是 `sort → cumsum → mask → softmax → sample` 四五个 kernel，`[B, 152k]` 的 sort 在 B=256 时几毫秒，`gpu_sample` 开始和 `gpu_forward` 一个量级。
- `logits.float()` 在 bf16 → fp32 转换上多一次 `[B, V]` 的读写；`compute_logits` 本身是 `[B, H] × [V, H]^T` 的 GEMM，在 nano-vllm 里由 `ParallelLMHead` 用 `F.linear` 做，没问题，但它的输出是 bf16，精度在 top-p 边界上不够。

## 2. 分析问题

- **追问链**：不可复现 → RNG 状态是全局的、和调用顺序绑定 → 要可复现，随机数必须是**位置的函数**：`f(seq_seed, position)`，和它在哪个 batch、哪一步被采无关。慢 → 采样是一串小 kernel，每个都读写一遍 `[B, V]` → 融合成一个。
- **本质**：可复现性是训推一致和回放调试的前提（4.10 的 DFlash、5.7 的 PPL 对拍都依赖它）；采样耗时在 ZOS 之后直接暴露在关键路径上。
- **理论**：counter-based RNG（Philox / hash）：随机数 = hash(key, counter)，没有状态。`reference/gpu-perf-engineering-resources/` §2 "Reduction, scan, online softmax, top-k" 是融合采样 kernel 要用的算子。
- **DeepInfer 怎么做**（`deepinfer/model_executor/layers/sampler.py:115-299`）：
  - logits 用 `bf16_gemm_nt` 对 LM head 权重做 **fp32** 输出（`sampler_utils.py:20-28`）。
  - `DEEPINFER_SAMPLER_FORCE_TOPK`（`environ.py:150`）：先用 DeepSelect 的 `topk` 把 `[total_q, V]` 压到 `[total_q, K]`（K 如 4096），后面所有工作在 top-K 空间做，MTP pool 也只存 top-K 的 logprob；`map_lookup / remap_draft_topk` 做 id 映射。
  - `fused_sample`（`tilelang_ops/fused_sample.py:18`）：温度、top-p、top-k、log-softmax、采样，一个 kernel；decode 时还融合了对 draft 的拒绝采样。
  - 随机数：`random_sampling.py` 的 hash RNG，seed 由 `(seq_seed, sample_position, tag)` 算（`_seeds`，`:41`；`_MTP_SEED_OFFSET` 区分 draft 和 target），同一请求同一位置永远同一个随机数。`SamplingParams.seq_seed` 每请求 64 位。
  - `sum_smaller_probs`：采样 token 之下的概率质量，用于置信度 / 调试。
  - 黑名单和 EOS 抑制（`first_n_token_no_eos`）在 logits 上做。

## 3. 要做什么

### 3.1 per-request seed 和位置哈希 RNG

**改哪里**：`nanovllm/sampling_params.py`、`nanovllm/layers/sampler.py`。

- `SamplingParams` 加 `seed: int | None`（None 时引擎分配一个随机 64 位）；`Sequence` 持有它。
- 采样 kernel 的随机数由 `hash(seq_seed, position, tag)` 生成（Philox 或 splitmix64 风格，Triton 里几行），`position` 是 token 在序列里的绝对位置，`tag` 区分 target 采样和 2.8 的 draft 采样。
- 验证：同一请求无论 batch 位置、无论是否 ZOS、无论和谁一起跑，固定 seed 输出一致。

### 3.2 fp32 logits 和强制 top-K

- `compute_logits` 输出 fp32（GEMM 的 epilogue 直接出 fp32，不要 bf16 再 `.float()`）。
- `Config.sampler_force_topk: int = 0`：非 0 时先 `torch.topk`（或 Triton）压到 `[total_q, K]`，后续在 K 空间；2.8 的 pool 存 K 空间的 logprob 和对应的原 id。

### 3.3 融合采样 kernel

**新建** `nanovllm/layers/fused_sample.py`（Triton）。

- 一个 kernel：温度缩放 → top-k 截断 → top-p 截断（在 K 空间排序很便宜）→ log-softmax → 用 3.1 的随机数采样 → 输出 `token_id`、`logprob`、可选 `sum_smaller_probs`。
- 2.8 的拒绝采样并进来：draft 位置的 accept / reject 和修正分布采样在同一个 kernel。
- 先写 PyTorch 参考实现 `apply_top_p_top_k_ref`，kernel 对拍。

### 3.4 `SamplingParams` 补全

- `top_p`、`top_k`、`seed`、`stop_token_ids`、`first_n_token_no_eos`（前 N 个 token 禁 EOS）。`temperature < 1e-5` 视为贪心（DeepInfer 的约定），去掉 nano-vllm 的"禁止 greedy"断言。

## 4. 验收

1. 固定 seed：同一请求单独跑、和 255 个其他请求一起跑、开关 ZOS、开关投机，输出 token 完全一致。
2. `gpu_sample` 下降（`[B, V]` 的多 kernel 变成 `[B, K]` 的一个 kernel），写进报告。
3. 分布正确性：temperature=1、top-p=0.9 下采 10 万次，频率和参考实现的概率分布 KL < 1e-3。
4. 黄金文件：近贪心改成真贪心（`temperature=0`），重新生成 `tests/golden/qwen3_8b.json`，`greedy_match` 应该变成满分或接近满分。
5. `tests/test_2_10.py`：(a) hash RNG 的确定性和均匀性；(b) kernel 和参考实现对拍（随机 logits、各种 top-p/top-k 组合、含 draft 的拒绝采样）；(c) `first_n_token_no_eos`；(d) 2.1–2.9 全过。

**新浮现的问题**：混进带 JSON schema 约束的请求，所有请求的 TBT 都被拖高。这是 2.11。

## 常见坑

- top-p 在 fp32 下做，bf16 的累积和会让边界 token 翻转。
- 强制 top-K 后，2.8 的 draft token 可能不在 target 的 top-K 里，要按 DeepInfer 的约定处理（`draft_token_ids_pool` 为 -1 视为拒绝）。
- 随机数的 `position` 是**绝对位置**，抢占重算后同一位置要给同样的数，否则重算改变输出。
- `torch.compile` 的 sampler（nano 原来的）和自定义 Triton kernel 不要混用，graph 捕获会出问题。
