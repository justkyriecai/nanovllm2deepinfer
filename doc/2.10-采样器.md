## 发现问题

**关注什么**：采样的可复现性和耗时。

```python
# 同一 prompt、同一 seed、temperature=1.0，跑两次；再把它放进不同大小的 batch 里跑
```

```bash
python -m bench.run --scenario steady_decode    # 看 gpu_sample 占 wall 的比例
```

**先预测**：nano-vllm 的 `Sampler` 用 `torch.empty_like(probs).exponential_()` 做 gumbel 采样，seed 从哪来？两次运行会一样吗？同一请求在 batch 位置不同时会一样吗？加上 top-p 后采样要几个 kernel？

**现象**：

- 没有 per-request seed：`exponential_()` 用全局 RNG，结果取决于本步之前调用了多少次 RNG、这个请求在 batch 里排第几。同一请求换一个 batch 位置输出就变。2.7 的 ZOS 让调度顺序更不可预测，2.8 的投机解码又在同一步里采多个位置。
- 没有 top-p / top-k：加上之后是 `sort → cumsum → mask → softmax → sample` 四五个 kernel，`[B, 152k]` 的 sort 在 B=256 时几毫秒，`gpu_sample` 开始和 `gpu_forward` 一个量级。
- `logits.float()` 在 bf16 → fp32 转换上多一次 `[B, V]` 的读写；`compute_logits` 本身是 `[B, H] × [V, H]^T` 的 GEMM，在 nano-vllm 里由 `ParallelLMHead` 用 `F.linear` 做，没问题，但它的输出是 bf16，精度在 top-p 边界上不够。

## 分析问题

- **追问链**：不可复现 → RNG 状态是全局的、和调用顺序绑定 → 要可复现，随机数必须是**位置的函数**：`f(seq_seed, position)`，和它在哪个 batch、哪一步被采无关。慢 → 采样是一串小 kernel，每个都读写一遍 `[B, V]` → 融合成一个。
- **本质**：可复现性是训推一致和回放调试的前提（4.10 的 DFlash、5.7 的 PPL 对拍都依赖它）；采样耗时在 ZOS 之后直接暴露在关键路径上。
- **理论**：counter-based RNG（Philox / hash）：随机数 = hash(key, counter)，没有状态。`reference/gpu-perf-engineering-resources/` §2 "Reduction, scan, online softmax, top-k" 是融合采样 kernel 要用的算子。
- **DeepInfer 怎么做**（`deepinfer/model_executor/layers/sampler.py:115-299`）：
  - logits 用 `bf16_gemm_nt` 对 LM head 权重做 **fp32** 输出（`sampler_utils.py:20-28`）。
  - `DEEPINFER_SAMPLER_FORCE_TOPK`（`environ.py:150`）：先用 DeepSelect 的 `topk` 把 `[total_q, V]` 压到 `[total_q, K]`（K 如 4096），后面所有工作在 top-K 空间做，MTP pool 也只存 top-K 的 logprob；`map_lookup / remap_draft_topk` 做 id 映射。
  - `fused_sample`（`tilelang_ops/fused_sample.py:18`）：温度、top-p、top-k、log-softmax、采样，一个 kernel；decode 时还融合了对 draft 的拒绝采样。
  - 随机数：`random_sampling.py` 的 hash RNG，seed 由 `(seq_seed, sample_position, tag)` 算（`_seeds`，`:41`；`_MTP_SEED_OFFSET` 区分 draft 和 target），同一请求同一位置永远同一个随机数。`SamplingParams.seq_seed` 每请求 64 位。
  - `sum_smaller_probs`：采样 token 之下的概率质量，用于置信度 / 调试。
  - 黑名单和 EOS 抑制（`first_n_token_no_eos`）在 logits 上做。

**思考题**：top-p 要先 sort。`[B, V]` 直接 sort 和先压到 top-K 再 sort，B=256、V=152k、K=4096 时各读写多少字节？这个比值就是任务 B 和 C 能省下多少 `gpu_sample` 的上限。

## 解决问题

三个任务，照 DeepInfer 的 sampler 管线拆：先把随机数变成位置的函数，再把 logits 变成 fp32 的 top-K 空间，最后把管线融成一个 kernel。

### 任务 A：per-request seed 和位置哈希 RNG（约 20 分钟，你写约 40 行）

- **目标**：`SamplingParams` 有 `seed`，同一请求无论 batch 位置、无论是否 ZOS、无论和谁一起跑，固定 seed 输出一致；`temperature=0` 可以用了。
- **思路**：对回分析里"随机数必须是位置的函数"。`SamplingParams` 加 `seed: int | None`（None 时引擎分配一个随机 64 位），`Sequence` 持有它。采样 kernel 的随机数由 `hash(seq_seed, position, tag)` 生成（Philox 或 splitmix64 风格，Triton 里几行），`position` 是 token 在序列里的绝对位置，`tag` 区分 target 采样和 2.8 的 draft 采样。`temperature < 1e-5` 视为贪心（DeepInfer 的约定），去掉 nano-vllm 的"禁止 greedy"断言。
- **已备好**：`SamplingParams` 补全的字段：`top_p`、`top_k`、`seed`、`stop_token_ids`、`first_n_token_no_eos`（前 N 个 token 禁 EOS）；`seed` 到 `Sequence` 和采样 kernel 参数的传递；`tests/test_2_10.py` 的 (a)。
- **你写什么**：hash RNG 那几行；None 时分配 64 位 seed；去掉禁止 greedy 的断言、`temperature < 1e-5` 走贪心。最容易写错的一处：`position` 是**绝对位置**，抢占重算后同一位置要给同样的数，用 batch 内的下标或本步的偏移都会让重算改变输出。
- **改哪里**：

  | 文件 | 函数 | 做什么 |
  |---|---|---|
  | `nanovllm/sampling_params.py` | `SamplingParams` | `seed` 等字段（已备好）；贪心约定 |
  | `nanovllm/engine/sequence.py` | `__init__` | 持有 `seed` |
  | `nanovllm/layers/sampler.py` | 随机数 | `hash(seq_seed, position, tag)` |

### 任务 B：fp32 logits 和强制 top-K（约 20 分钟，你写约 40 行）

- **目标**：`compute_logits` 直接出 fp32；`Config.sampler_force_topk: int = 0` 非 0 时 logits 压到 `[total_q, K]`，后续全在 K 空间，2.8 的 pool 存 K 空间的 logprob 和对应的原 id。
- **思路**：对回发现问题里的第三条：bf16 的 logits 在 top-p 边界上精度不够，`.float()` 又多一次 `[B, V]` 读写。GEMM 的 epilogue 直接出 fp32，不要 bf16 再 `.float()`；非 0 的 `sampler_force_topk` 先 `torch.topk`（或 Triton）压到 `[total_q, K]`，后面所有工作在 K 空间做，这是任务 C 的 kernel 便宜的前提。
- **已备好**：`Config.sampler_force_topk` 字段和传递；2.8 pool 的 K 空间布局（logprob + 原 id 两份）。
- **你写什么**：`ParallelLMHead` 的 fp32 输出；top-K 压缩和 id 映射；pool 写 K 空间。最容易写错的一处：强制 top-K 后 2.8 的 draft token 可能不在 target 的 top-K 里，要按 DeepInfer 的约定处理：`draft_token_ids_pool` 为 -1 视为拒绝。
- **改哪里**：

  | 文件 | 函数 | 做什么 |
  |---|---|---|
  | `nanovllm/layers/sampler.py` / LM head | `compute_logits` | fp32 epilogue |
  | `nanovllm/layers/sampler.py` | top-K 压缩 | `[total_q, V]` → `[total_q, K]`，id 映射 |
  | 2.8 任务 B 的 `mtp_pool.py` | pool | 存 K 空间的 logprob 和原 id |

### 任务 C：融合采样 kernel（约 40 分钟，你写约 120 行）

- **目标**：一个 Triton kernel 完成温度缩放 → top-k 截断 → top-p 截断 → log-softmax → 采样，输出 `token_id`、`logprob`、可选 `sum_smaller_probs`；2.8 的拒绝采样并进来，draft 位置的 accept / reject 和修正分布采样在同一个 kernel；`gpu_sample` 明显下降。
- **思路**：对回分析里"采样是一串小 kernel，融合成一个"。在任务 B 的 K 空间里排序很便宜，整条管线一次读进来一次写出去；随机数用任务 A 的 `hash(seq_seed, position, tag)`。先写 PyTorch 参考实现 `apply_top_p_top_k_ref`，kernel 和它对拍。
- **已备好**：`nanovllm/layers/fused_sample.py` 的 kernel 签名、启动代码；`apply_top_p_top_k_ref` 的函数壳；`tests/test_2_10.py` 的 (b)(c)。

## 常见坑

- top-p 在 fp32 下做，bf16 的累积和会让边界 token 翻转。
- 强制 top-K 后，2.8 的 draft token 可能不在 target 的 top-K 里，要按 DeepInfer 的约定处理（`draft_token_ids_pool` 为 -1 视为拒绝）。
- 随机数的 `position` 是**绝对位置**，抢占重算后同一位置要给同样的数，否则重算改变输出。
- `torch.compile` 的 sampler（nano 原来的）和自定义 Triton kernel 不要混用，graph 捕获会出问题。
