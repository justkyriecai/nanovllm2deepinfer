# 5.6：prefill 和 decode 要的资源不同，却挤在同一批卡上

> 起点：5.5 做完的代码　硬件：8×H100（4 卡做 P，4 卡做 D），DeepSeek-V2-Lite　预计改动：600–900 行　轴：6 分布式 / 1 调度

## 1. 发现问题

**关注什么**：同一组卡既做 prefill 又做 decode 时，两者互相的影响。回到 2.2 的实验，但在 8 卡 DP + EP 上看。

```bash
python -m bench.launch_dp --dp 8 --ep 8 -- bench.run --scenario mixed_long_short --per-rank-seed --report tbt-ttft
```

**先预测**：有长 prompt 进来的那些步，所有 rank 的 TBT 怎么变？prefill 步需要的是算力（大 batch GEMM），decode 步需要的是显存容量和带宽（KV、专家权重），同一张卡上两种需求谁迁就谁？

**现象**：

- 5.3 的投票让 prefill 步全组同型：一个 rank 的长 prompt 让所有 rank 的 decode 停一步，TBT p99 被 prefill 步撑大（2.2 的现象在分布式下被放大 8 倍）。
- KV 预算在两种步之间拉扯：prefill 想要大的 `max_num_batched_tokens`（profile 时按它占显存），decode 想要更多 block。
- CUDA graph、MTP、ZOS 这些 decode 的优化在 prefill 步里全关着（prefill 是 eager），一张卡同时背两套路径。
- DeepInfer 的 `EngineType` 有三种：`NORMAL / PROMPT / COMPLETION`（`engine_type.py`），README 说生产上是 EPD 分离部署（`doc/inference_deployment_qa.md:31`）。

## 2. 分析问题

- **追问链**：两种步互相干扰 → 把它们放到不同的卡上：P 引擎只 prefill，D 引擎只 decode → 请求在 P 上算完 prompt，KV 和状态要搬到 D → 搬什么：paged block（主 KV + index-K）和每序列的 state（SWA 环、压缩状态）→ 搬的时机：P 的最后一个 chunk 算完、采出第一个 token 之后 → D 怎么接：请求带着 `hit_tokens`（已经算好的 token 数）和搬来的块进 `prompted` 队列，decode 调度直接把它转 RUNNING → D 引擎没有 prefill 通道，被抢占的请求不能重算，只能结束（`stop_preempted_request`）→ 边界还要考虑：state 的哪一段值得落盘（stored），哪一段只在 P→D 之间传（dropped）。
- **本质**：PD 分离是把引擎按步型拆成两种，中间用"已算完的 KV + 状态 + hit_tokens"作为接口。DeepInfer 开源的部分是这个接口的两端（引擎类型、`prompted` 队列、状态的拷贝和落盘布局），传输本身是空钩子（内部版本接 3FS / kvcache-store / RDMA）。这一节做机内传输的最小实现，把接口两端做完整。
- **量化**：V2-Lite 一个 4k prompt 的 KV：27 层 × 4096 × 576 × 2 B ≈ 128 MB（bf16），NVLink 下几毫秒；V4.1 的 state 每序列 `StateBlock.total_bytes`（4.1）。P→D 的传输时间要藏在 D 的 decode 步后面。
- **理论**：`reference/gpu-perf-engineering-resources/` §5 "Prefill and decode disaggregation"：DistServe（按 goodput 分别优化 P 和 D）、Splitwise（按阶段配卡）、Mooncake（KV 为中心的分离架构，DeepInfer 的 kvcache-store 是同一思路）、NIXL / Dynamo（传输层和路由）。DeepInfer 的部署 QA（`doc/inference_deployment_qa.md:131-160`）讲了 3FS 上的 KV 存储和 GDR swap-in。
- **DeepInfer 怎么做**：
  - **类型**：`EngineType`（`engine/engine_type.py`，和 `scheduler.hpp:39` 的 enum 对应）。`_schedule`（`scheduler.hpp:288-294`）：PROMPT 只 `_schedule_prefill`（没活也返回空的 prefill 结果），COMPLETION 只 `_schedule_decode`，NORMAL 投票。PROMPT 引擎：无 CUDA graph、无 MTP、ZOS 关（`arg_utils.py:53-58`、`llm_engine.py:705-707`）；COMPLETION 必须 `stop_preempted_request`（`scheduler.hpp:101-104`，启动时断言）。
  - **`prompted` 队列**（`scheduler.hpp:1125`）：COMPLETION 的入口。`_schedule_decode`（`:556-610`）先把 `prompted` 队头依次转 RUNNING（`admit`），forked 的要先 `_clone_state` 和 clone 最后一个块；进 CE 之前就 abort 的直接 finished。2.4 的 fork 在 prompt 已算完时也进 `prompted`（`:1116-1120`）。
  - **带着已算好的东西进来**：`Sequence.cache.hit_tokens`（`sequence.hpp:204`，Python 侧 `cached_hit_tokens`）、`swa_valid_start`（`:205`，SWA 环里从哪个位置开始有效）；`try_allocate_seq`（`block_manager.hpp:217`）同时分块和 state 槽，失败返回 false（不 assert，调用方等）。调度器的 pybind 暴露 `try_allocate_seq`（`pybind_scheduler.cpp:86`）给引擎子类用。
  - **状态拷贝**：`do_copy_state`（`llm_engine.py:787`）把序列的 GPU state 拷进 `copy_state` buffer（4.1 profile 时留的第二份 state），记 `copy_state_event`，`last_copy_state_token_idx`；`should_copy_state`（`:811`）是虚函数默认 False；decode 步末尾挑要拷的序列（`:930-937`），`pre_sampler_sync` 时等 event 再 `do_save_kvcache`（`:833-837`）。
  - **落盘布局**：`StateBlock`（4.1）分 stored / dropped；`state_size_to_disk`（`cache_engine.py:306`）只含 producer 层的 SWA 环；`select_state_slice_to_store`（`:763`）按 `KVSTORE_GRAIN = 128`（`:32`）对齐的 `last_hit_position` 读出环里的一段（`select_state_slice` kernel），`TO_CE=True` 时连 dropped 段一起给 D；`load_state_from_store_to_prefill_cache`（`:821`）反向写回。`DEEPINFER_PREFILL_STORE_EXTRA_STATE` 让 P 多存 128 个 token 的 state 保证落盘粒度对齐（`:101-110`）。
  - **空钩子**（`llm_engine.py:801-857`）：`init_pd_split / finalize_seq / post_schedule / should_copy_state / do_save_kvcache / pe_prepare_save_kvcache / pe_do_save_kvcache / process_output / send_processed_prompts / post_process_model_outputs`。PROMPT 引擎每步末尾调 `send_processed_prompts`（`:1010`）。这些是内部版本的接口，开源版留空。
  - **只在文档里的**：3FS、kvcache-store、GDR swap-in、负载均衡器、自动扩缩容（QA 文档）。

## 3. 要做什么

### 3.1 引擎类型

**改哪里**：`csrc/scheduler.hpp`、`nanovllm/engine/llm_engine.py`、`Config`。

- `EngineType` 三值；`_schedule` 按类型分支（5.3 的投票只在 NORMAL）；PROMPT 关 graph / MTP / ZOS；COMPLETION 断言 `stop_preempted_request`（2.3）。
- `prompted` 队列：`_schedule_decode` 开头 `admit`；fork 在 prompt 算完时进 `prompted`。

### 3.2 接口两端

- `Sequence` 加 `hit_tokens`、`swa_valid_start`；`try_allocate_seq`。
- `StateBlock` 的 stored / dropped 已在 4.1；`select_state_slice(state_id, last_hit_position, TO_CE)` 和 `load_state(state_id, last_hit_position, tensor)` 两个 kernel（环的重排）。
- `copy_state` buffer + event；`should_copy_state` 等钩子按 DeepInfer 的名字留出来。

### 3.3 机内最小传输

**新建** `nanovllm/engine/pd_local.py`（这一节自己的实现，DeepInfer 没有）。

- 1 P + 1 D（各一张卡，或 4 + 4）在同一台机器：P 引擎 `send_processed_prompts` 时把序列的 block 内容和 state（`TO_CE=True`）通过 NCCL P2P（或 CUDA IPC）发给 D；D 引擎收到后 `try_allocate_seq`（失败就排队重试）、把块和 state 写进自己的 cache、设 `hit_tokens = prompt_len`、进 `prompted`。
- D 的 decode 调度照常；传输在 D 的侧 stream 上，不阻塞当前 decode 步。
- 请求的入口：一个最简单的路由（prompt 先发 P，拿到第一个 token 后转 D）。

### 3.4 观测

- `StepRecord` 加 `engine_type`；报告按 P / D 分别给 TTFT 和 TBT；加 `transfer_ms`。

## 4. 验收

1. 同一个实验重跑（4P + 4D vs 8 NORMAL）：D 侧的 TBT p99 不再被 prefill 步撑大（和 `steady_decode` 下的 p99 一致）；P 侧的 TTFT 不受 decode 影响；报告给两种部署的 TTFT / TBT 分布。
2. 正确性：P→D 之后的输出和同一请求在 NORMAL 引擎上 `greedy_match` 一致；带 SWA 环和压缩状态的层（V4.1 的层，用第 4 章的 harness 在 B200 上也验一次）传输后 decode 第一步一致。
3. 传输时间藏在 decode 步后面：D 侧 `cpu_*` 和 `gpu_*` 段里没有新增等待。
4. `tests/test_5_6.py`：(a) PROMPT 引擎永远不 decode、COMPLETION 永远不 prefill（`step_kind` 统计）；(b) `prompted → RUNNING` 的 admit，含 abort 在入队前、forked 需要 clone 的情况；(c) `select_state_slice → load_state` 往返恒等，`last_hit_position` 各种对齐；(d) `try_allocate_seq` 失败不抛、成功时块和槽都分了；(e) COMPLETION 下抢占直接结束请求（2.3 的 `stop_preempted_request`）；(f) 5.5 全过。

**新浮现的问题**：第 5 章前六节都是在 V2-Lite 上做机制。V4.1-Flash 的全模型还没有端到端跑过，和 DeepInfer 的数字没有对过。这是 5.7，期末考试。

## 常见坑

- COMPLETION 引擎没有 prefill 通道，任何会触发"重算"的路径（抢占、长度截断后的续写）都必须变成结束请求。
- `prompted` 里的 forked 序列要先 clone state 和最后一个块（COW），否则两个分支写同一个槽。
- state 落盘只能在 `KVSTORE_GRAIN` 的倍数处，P 要多存 128 个 token 的 state 才能保证对齐；传给 D 时用 `TO_CE=True` 不受这个限制。
- D 侧收到块之后 `hit_tokens = prompt_len`，但 `num_cached_tokens` 和 2.7 的 inflight 计数要按"已经采了第一个 token"初始化，否则第一步 decode 的位置错一位。
- 两种引擎的 `profile` 不一样：PROMPT 按 `max_num_batched_tokens` 占显存，COMPLETION 按 `max_num_seqs × (nextn + 1)`，不要共用一套数字。
