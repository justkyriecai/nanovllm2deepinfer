# 4.11：大 kernel 之间夹着的小算子

> 起点：4.10 做完的代码　轴：5 kernel

| | |
|---|---|
| **问题** | 一层 V4.1 的 decode 时间线按时间排大头是 FlashMLA、mega MoE、mega mHC，按个数排却有几十个我们自己用 Triton 和 torch 拼的小 kernel（norm / rope / cast / scatter 分开的四个、`torch.cat` 拼索引、`index_select` 拼的三段、engram 的 gather），每个几微秒、launch 和尾效应占大半，加起来一层百分之几到十几，kernel 数是 DeepInfer 的两倍多。本质是这些逐元素 / gather 胶水之间的数据没必要落 HBM：读一次、做完所有变换、写一次 |
| **实验** | `nsys profile -t cuda,nvtx,osrt --sample=none --cpuctxsw=none -o out/v4-layer python -m tests.v4.harness --layers 0..K --decode --batch 256 --num-steps 20` 然后 `nsys stats --report cuda_gpu_kern_sum`，盯一层的 kernel 个数和前十个里自己拼的占比 |
| **硬件 / 费用** | 1×B200 + V4.1-Flash 前几层权重，Modal 约 $6.25/h；nsys、对拍、benchmark 反复跑约 2.5 小时，约 $15 |
| **学到** | 胶水也是 kernel：DeepInfer 每个 kernel 配 `_ref`（PyTorch 参考）、`test_`（对拍）、`test_*_benchmark`（带宽利用率），放在同一个文件里，先把 `_ref` 写对再写 kernel；这类 kernel 的逻辑都不复杂，难点全在布局，paged cache 的 slot、FP8 / FP4 的 scale 打包、`stride(0) % 16 == 0` 这类向量化读写的前提，少一条断言就会在某个形状下静默错；小 kernel 的性能标尺是访存下限（输入字节 + 输出字节）占峰值带宽的比例，不是 FLOPs |
| **时长** | 发现 + 分析约 1.5 小时；任务 A 约 30 分钟、任务 B 约 1 小时、任务 C 约 20 分钟；验收约 1 小时。改动约 300–600 行（一个 kernel + 参考实现 + 测试 + benchmark） |

## 发现问题

**关注什么**：一层 V4.1 的 decode 时间线里，vendor kernel（FlashMLA、DeepGEMM、DeepSelect）之间是什么。

```bash
nsys profile -t cuda,nvtx,osrt --sample=none --cpuctxsw=none -o out/v4-layer python -m tests.v4.harness --layers 0..K --decode --batch 256 --num-steps 20
nsys stats --report cuda_gpu_kern_sum out/v4-layer.nsys-rep | head -40
```

**先预测**：一层有多少个 kernel？按时间排序，前十个里有几个是我们自己用 torch 拼的？它们加起来占一层的百分之几？

**现象**：按时间排序，大头是 FlashMLA、mega MoE、mega mHC；但按**个数**排序，一层里有几十个 Triton 和 torch 的小 kernel：4.2 的 norm / rope / cast / scatter 分开的四个、4.4 的 `torch.cat` 拼索引、2.7 的 `gather_input_ids` 用 `index_select` 拼的三段、4.8 的 gather。每个几微秒，launch 和尾效应占了大半，加起来一层百分之几到十几。DeepInfer 这一层的 kernel 数是我们的一半不到。

## 分析问题

- **追问链**：小 kernel 多 → 每个都是"读一遍、做一点、写一遍"的逐元素或 gather 操作 → 它们之间的数据没必要落 HBM → 融合成一个：读一次、做完所有变换、写一次 → 这些 kernel 的逻辑都不复杂，难点在布局（paged cache 的 slot、FP8 / FP4 的 scale 打包、对齐）→ 自己写一个，和 DeepInfer 的同名 kernel 对拍和对 benchmark。
- **本质**：第 4 章前面都在用 vendor kernel 和 Triton 胶水；这一节的目的是把"胶水也是 kernel"这件事做一遍，学会 DeepInfer 的 kernel 工程方法：每个 kernel 配 `_ref`（PyTorch 参考）、`test_`（对拍）、`test_*_benchmark`（带宽利用率），放在同一个文件里。
- **量化**：目标 kernel 的访存下限 = 输入字节 + 输出字节；benchmark 报告"达到带宽的百分之几"（B200 8 TB/s）。`fused_transform.py:1054` 的 `_benchmark_io_bytes` 就是这么算的。
- **理论**：`reference/gpu-perf-engineering-resources/` §2 "Foundational kernel exercises"（逐元素、归约、gather / scatter 的带宽分析）；§3 "Triton"（Triton 教程：fused softmax、persistent kernel）；§3 "CUTLASS, CuTe, and CUDA Tile"（tile 级编程模型，TileLang 是同一类抽象）；§Frontier "AI-generated kernels"（KernelBench 等：对拍 + benchmark 的评估方法，和这一节的验收一样）。TileLang 本身的文档不在清单里。
- **DeepInfer 怎么做**（`layers/tilelang_ops/`）：
  - 每个文件一个 kernel 族：`xxx(...)`（Python 入口，做形状和对齐检查，调 `ops.xxx_tl(...)` 的 JIT kernel）、`xxx_ref(...)`（PyTorch 参考）、`test_xxx`（pytest，随机输入对拍）、`test_xxx_benchmark`（`tile_kernels.testing` 的计时，报带宽）。
  - 三个候选（路线图点名的）：
    1. `fused_norm_rope_hadamard_cast_store_kvcache`（`fused_transform.py:189`，参考 `:389`）：输入 `[n, heads, head_dim]` bf16，可选 norm、RoPE（只转尾部 `rotary_dim`）、Hadamard、FP8 / FP4 cast（scale 格式 `ue8m0 / e4m3 / fp32`），输出到连续张量或按 `slot_mapping` 散到 paged cache（`KVCacheOutArgs`），还能顺便留一份某个阶段（`out_stage="norm"`）的 bf16。4.2、4.3、4.4、4.10 都在用它，是 V4 路径上调用最多的胶水 kernel。
    2. `gather_input_ids_zos`（`gather_input_ids_zos.py:10`，参考 `:35`）：2.7 的 GPU 侧输入拼装，按 `remap` 从上一步的 `sampled / predict` 或 fresh token 取，变长 `seqlens_q`。
    3. `kv_index_cat`（`kv_index_cat.py:10`，参考 `:54`）：拼 SWA 和 top-k 索引，加偏移，-1 保留，行 stride 对齐到 4。
  - 所有 kernel 的 JIT 实现在 `tilelang_ops/ops.py`（TileLang）和 `tilelang_ops/cuda/`。

**思考题**：按 config 的 SWA 窗口和 top-k 数，batch 256 时 `kv_index_cat` 的输入加输出是多少字节？B200 8 TB/s 下的理论时间是多少微秒？和一次 kernel launch 的几微秒比，这个 kernel 还有没有可能达到峰值带宽的一半，不能的话它的性能标尺应该换成什么？

## 解决问题

三个候选里**至少做一个**，建议顺序：`kv_index_cat`（最简单，纯 gather + 加法）→ `gather_input_ids_zos`（变长 + 两源分支）→ `fused_norm_rope_hadamard_cast_store_kvcache`（最有价值，也最难：FP4 打包、scale 布局、paged scatter）。下面三个任务对选定的那一个走一遍 DeepInfer 的工程方法：先参考和测试，再 kernel，最后 benchmark。时长按 `kv_index_cat` 估；做第三个的话任务 B 翻倍。

### 任务 A：参考实现和测试（约 30 分钟，你写约 80 行）

## DeepInfer 对照

| 这一节 | DeepInfer | 差异和原因 |

| `入口 + _ref + test + benchmark` 一个文件 | `tilelang_ops/*.py` 的统一结构 | 一致 |

## 常见坑

- 先把 `_ref` 写对、和 DeepInfer 的 `_ref` 对上，再写 kernel；`_ref` 错了后面全白搭。
- FP4 的 e2m1 打包是两个元素一个字节，低位在前；scale 的 UE8M0 是 2 的幂，`round_sf` 决定向上还是最近取整，和 DeepInfer 不一致会有 1 ulp 的系统性偏差。
- paged scatter 的 `slot_mapping = -1` 要跳过，而且不能影响同一个 program 里其它行的向量化写。
- benchmark 要 warmup 并用 CUDA event 计时（1.1 的方法），小 kernel 的 CPU 计时全是噪声。
- 形状不是 tile 整数倍的尾部处理是最常见的错：测试里专门放 `n = tile + 1` 和 `n = tile − 1`。
