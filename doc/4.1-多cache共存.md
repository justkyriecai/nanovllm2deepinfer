# 4.1：一个大张量放不下 V4 的 cache

> 起点：3.3 做完的代码　硬件：1×B200，`deepseek-ai/DeepSeek-V4.1-Flash-1017` 的前几层权重　预计改动：600–900 行（其中 200 行是对拍脚手架）　轴：2 显存 / 4 模型结构

## 第 4 章在做什么

第 3 章之后，引擎控制面（第 2 章）和 MLA + MoE + FP8 的骨架（第 3 章）都和 DeepInfer 对上了。但 DeepInfer 只跑一个模型：V4.1-Flash。它的每一层都比 V2 多出东西，这些东西决定了 DeepInfer 的 cache 布局、metadata、kernel 选择。第 4 章一层一层把它们加进来，**每加一样就和 DeepInfer 的同一个模块对拍**。做完达到 P2（模型对齐）。

V4.1-Flash 的一层长什么样，全部由 HF `config.json` 决定（DeepInfer 的翻译在 `deepinfer/hugging_face/config.py`）：

| 字段 | 决定什么 | 哪一节 |
|---|---|---|
| `compress_ratios[l]` | 0 = 纯 SWA 层；1 / 2 = MLA 压缩 KV + 稀疏 indexer + SWA（`_build_attn_module_list`，`config.py:146`） | 4.2、4.3、4.4 |
| 第一个 `ratio == 1` 的层 | YoCo 边界 `n_prefill_layer`（`:158`）：之前是 producer，之后是 consumer | 4.5 |
| `kv_source_layer_ids` / `index_source_layer_ids` / `index_k_source_layer_ids` / `candidate_source_layer_id` | 跨层共享拓扑（`_shared_layer_cfg`，`:68`） | 4.6、4.4 |
| `hc_mult`、`hc_shifted`、`hc_sinkhorn_iters` | mHC 四路残差 | 4.7 |
| `engram_layer_ids`、`engram_max_ngram_size`、`engram_vocab_size` | engram 层 | 4.8 |
| `quantization_config`：FP8 权重、`expert_dtype = fp4`、`weight_block_size = [32, 32]`、`scale_fmt = ue8m0` | Mega MoE 和 FP4 专家 | 4.9 |
| `num_nextn_predict_layers`、`dspark_*` | DFlash draft 头 | 4.10 |

为什么要换到 B200：FP4 专家、FP4 index-K、Mega MoE、Mega mHC 这些 kernel 只有 SM100 版本。V4.1-Flash 的完整权重一张卡放不下，整章只加载**前几层**的真实权重；端到端的数字留给 5.7。

### 对拍脚手架（这一节先搭）

**新建** `tests/v4/harness.py`。整章的验收都靠它。

- 从 HF checkpoint 只读前 `K` 层（`K` 按显存定，建议从 4 开始）的 safetensors，写一个截断的 `config.json`（`num_hidden_layers = K`，`compress_ratios[:K]`，`dspark_target_layer_ids`、`engram_layer_ids` 等按 `< K` 过滤）。
- 参考实现直接用 DeepInfer 的模块：`PG` 以 world size 1 初始化（EP = CP = DP = 1），`V41Builder.build_model`（`v4_modules/builder.py:93`）建出前 `K` 层的参数容器，用 DeepInfer 自己的 `hugging_face/loading.py` 装权重，再按 `decoder_layer.py:48` 的方式构造 `DeepseekDecoderLayer` / `V4Attention` / `DeepseekMoE`。
- 对拍粒度：同一份输入（hidden、`InputMetadataV4`、cache），DeepInfer 的模块跑一遍，我们的跑一遍，用 `deepinfer/testing.py:15` 的 `assert_close` 和 `:4` 的 `cal_diff` 比。4.1–4.6 比 attention 模块，4.7 比整层，4.9 比 MoE，4.10 比 DFlash。
- 构造 DeepInfer 的 `InputMetadataV4` 比较繁琐（它是 C++ `prepare_prompt_v4 / prepare_decode_v4` 的产物）；走不通就退一步：在 DeepInfer 的层上挂 forward hook，把同一 prompt 下每层的输入输出 dump 到磁盘，我们对 dump 比。先把这条路跑通，再决定要不要直接调用模块。

## 1. 发现问题

**关注什么**：nano-vllm 的 KV cache 是一个张量 `[2, L, num_blocks, block_size, kv_heads, head_dim]`，所有层同构。V4.1-Flash 的层不同构，这个张量放不放得下。

先不写代码，按 `config.json` 填一张表：每一层需要哪些 cache，每个 token 各占几个字节。

| 层类型（`compress_ratios[l]`） | 需要什么 | 按什么单位分配 |
|---|---|---|
| 0（纯 SWA） | 最近 `window_size` 个 token 的 KV | 每序列固定大小，和上下文长度无关 |
| 1（压缩比 1 + 稀疏） | 压缩 KV（每 token 1 个 latent）+ indexer 的 K（每 token 68 B） | 随长度线性增长，paged |
| 2（压缩比 2 + 稀疏） | 压缩 KV（每 2 个 token 1 个 latent）+ indexer K + **fp32 累加状态**（跨 chunk 用） | KV paged，但每层每块只有一半的 token；状态每序列固定 |
| 所有带 SWA 的层 | SWA 环 | 每序列固定 |

然后做实验：把 3.1 的 `allocate_kv_cache` 硬套到这个配置上（每种 cache 一个张量，每层一份），跑启动流程，看显存和 block 数。

**先预测**：block 数怎么算？压缩比 2 的层每块放多少 token？纯 SWA 层需要 block 吗？fp32 状态按什么释放？

**现象**：

- 块表是**每序列一张**，一个 block id 要在所有层都有意义，但每层每块的字节数不一样（纯 SWA 层 0 字节，压缩比 2 的层是压缩比 1 的一半）。按层各开张量算不出一个统一的 `num_blocks`。
- 纯 SWA 层的 KV 如果也 paged，每序列要占 `上下文长度 × 528 B` 而不是 `134 × 528 B`，长上下文下差几百倍。
- fp32 状态和 SWA 环跟着序列走，抢占时要释放，恢复时要重建，它们不是"块"。
- 3.1 的 profile（按峰值算剩余显存）把这些固定开销也算进了 KV 预算。

## 2. 分析问题

- **追问链**：张量放不下 → 层不同构 → 两类内存在用同一种分配器：一类随上下文长度增长（压缩 KV、index-K），一类每序列有界（SWA 环、压缩状态）→ 增长的用 paged block，有界的用固定槽位 → paged block 要让**一个 block 覆盖所有层**，每层在块内有自己的偏移和长度 → 槽位要有自己的分配器、自己的生命周期（跟着序列的 RUNNING 状态走）。
- **本质**：cache 的"形状"不该由 attention 类型决定，而该由**容量是否有界**决定。有界的（窗口、状态）用槽位，无界的（随长度）用页。DeepInfer 用同一个 `BlockManager` 类开了两个实例。
- **量化**：把表里的数字乘起来，V4.1-Flash 前 `K` 层每块（128 token）多少字节、每序列槽位多少字节。槽位总量 = `(1.2 × max_num_seqs + 1) × 每序列字节`，这是启动时就固定下来、要从 KV 预算里扣掉的。
- **理论**：`reference/gpu-perf-engineering-resources/` §4 "KV cache systems"：Jenga（混合 attention 类型模型的 KV 分配，每层不同 cache 的统一管理）、PagedAttention（页的起点）。
- **DeepInfer 怎么做**（`deepinfer/worker/cache_engine.py`）：
  - **格式**：`KVCacheFormat`（`tilelang_ops/cache_common.py:44`）描述每 token 的字节：量化元素数、每多少元素一个 scale、scale 格式、bf16 元素数；`bytes_per_token`（`:100`）。V4.1 的三种：`V41_FORMAT` 528 B（`:109`，512 个 e4m3 + 16 B 的 UE8M0 scale），`V41_FP4_FORMAT` 288 B（`:119`，256 B 的 e2m1 + 32 B 的 e4m3 scale），`FP4_INDEX_KV_FORMAT` 68 B（`:129`）。每 token `[data | scale]` 交错存。
  - **一个 block 覆盖所有层**：`KVCacheManager.process`（`:376`）按层顺序给每层分配：有 indexer 的层先放 `ica_cache`（`token_per_block × 68 B`，`:433-441`），再放 `ca_cache`（`token_per_block = block_size / ratio`，`:451-461`），每段 32 B 对齐，返回 `(layer_id, kv_offset, kv_length)`；纯 SWA 层 `kv_length == 0`。整个 block 是一个 uint8 张量 `[num_blocks, bytes_per_block]`，每层用 `as_strided` 切出 `[num_blocks, token_per_block, 1, bytes_per_token]` 的视图。
  - **槽位**：`StateBlock`（`:221`）算每序列的布局：`[stored: producer 层的 SWA 环 | dropped: consumer 层的 SWA 环 | 压缩状态]`，分成 stored / dropped 是为了 PD 分离和落盘只传前半（5.6）；SWA 每层 32 B 对齐，整块按 `lcm(32, 528)` 对齐（`:300-306`）。槽位数 `get_num_state_slots`（`:201`）= `max_num_seqs × 1.2 + 1`，slot 0 是 CUDA graph padding 用的 placeholder。`state_manager` 是第二个 `BlockManager`（`llm_engine.py:266`），序列进 RUNNING 时拿 `state_id`，终态释放。
  - **分配**：`CacheEngine.allocate_gpu_cache`（`:918`）用 `cuda_utils.alloc_tensor` 在 torch 分配器之外分配两块大内存（KV 和 state）。
  - **预算**：`profile_num_available_blocks`（`worker/base.py:212`）：`available = total × utilization − peak − 2 × state_size`（state 开两份，一份给 `copy_state` 用，5.6），再除以 `get_cache_block_size`。5.3 时会跨 rank 取平均。
  - **元数据**：每层的 `(layer_id, kv_offset, kv_length)` 列表由 `get_kvcache_layout`（`:896`）给出，`get_state_shape`（`:902`）给槽位形状。这两个函数是纯配置计算，**可以直接当验收的 oracle 调用**。

## 3. 要做什么

### 3.1 格式和布局

**新建** `nanovllm/engine/cache_engine.py`。

- `KVCacheFormat`：照 DeepInfer 的字段，`bytes_per_token`、`stride_alignment`。先注册 V4.1 的三种。
- `KVCache` dataclass：`ica_cache`、`ica_state`、`ca_cache`、`ca_state`、`swa_cache`，都可为 None。这一节只分配、不写入，内容由 4.2–4.4 填。
- `KVCacheManager.process(layer_id, layer_cfg, block_size) -> (KVCache, (layer_id, kv_offset, kv_length))`：按层切 uint8 block，32 B 对齐；纯 SWA 层不占 block。
- `StateBlock`：按 `n_prefill_layer`、`window_size`、`compress_ratios` 算 stored / dropped 两段的偏移；`swa_block_size = window_size + max_backtracking`（4.2 解释为什么），压缩状态的 ring 长度 `ratio + max_backtracking − 1`（4.3）。
- 分配：两块大 uint8 内存，在 torch 分配器之外（`torch.cuda.caching_allocator_alloc` 或 `cudaMalloc` 绑定），避免 profile 时被算成峰值。

### 3.2 第二个分配器

**改哪里**：`csrc/scheduler.hpp`、`sequence.hpp`、`model_runner.py`。

- `Scheduler` 加 `state_manager`（2.1 的 C++ `BlockManager` 第二个实例，槽位数 `1.2 × max_num_seqs + 1`，slot 0 保留）；进 RUNNING 时分配 `state_id`，终态和抢占释放；`SequenceMetadata` 带 `state_id`。
- 2.4 的 fork：子序列拿新槽位，内容拷贝（4.2 之后才有内容）。
- 2.7 的 ZOS：`state_id` 和 `block_table` 一样走 pinned 输入。

### 3.3 预算

**改哪里**：`model_runner.py` 的 profile。

- `available = total × util − peak − 2 × state_size`，`num_blocks = available // bytes_per_block`。`bytes_per_block` 来自 3.1 的 layout。
- 把 1.1 的 KV 容量报告改成按层列：每层每块字节、槽位每序列字节、最终 block 数。

### 3.4 模型骨架

**新建** `nanovllm/models/deepseek_v4.py`（这一节只做空壳）。

- 按 `config.json` 建层列表：每层一个 `V4Attention`（4.2–4.6 填）、一个 MoE（先用 3.3 的实现）、残差先按普通单路（4.7 换 mHC）。
- `load_weights` 只装前 `K` 层。权重名以 HF 为准（DeepInfer 的 `hugging_face/names.py` 列了映射）。

## 常见坑

- 每层的 `token_per_block = block_size / ratio`，压缩比 2 的层一块只有 64 个压缩 token；block table 的 id 不变，但每层按自己的 `token_per_block` 换算 slot（4.3 的 `prepare_tensor_input_v4.cpp:60`）。
- 槽位 0 是 placeholder，2.8 的 CUDA graph padding 行和 2.7 的空 prompt 步都要指向它；分配器从 1 开始发。
- `as_strided` 切出来的视图 `stride(0)` 是整块的字节数，不是本层的；写 kernel 时要用 `stride(0)` 而不是按形状算。
- 在 torch 分配器之外分配的内存，`torch.cuda.memory_stats` 看不见；1.1 的显存报告要单独加上。
- 截断的 `config.json` 里所有"按层 id 列表"的字段（engram、dflash target、各种 source_layer_ids）都要过滤到 `< K`，否则 DeepInfer 的 builder 会在第一次 forward 时断言。
