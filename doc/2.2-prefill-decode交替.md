# 2.2：长 prompt 一进来，所有人都卡一下

> 起点：2.1 做完的代码　轴：1 调度

## 发现问题

**关注什么**：稳态 decode 的请求，在有新请求到达时，TBT 会怎样。

```bash
python -m bench.run --scenario mixed_long_short --trace out/mixed.jsonl
```

**先预测**：128 个短请求在 decode，每 20 步进来一个 3072 token 的长 prompt。短请求的 TBT p50 和 p99 会差多少？长 prompt 的 TTFT 呢？

**现象**（L4，Qwen3-0.6B）：短请求 TBT p50 46 ms，p99 145 ms，是 p50 的 3.1 倍；prefill 步的 `wall` p50 94 ms，正好约等于 p99 − p50。打开 trace，每个长 prompt 到达之后的下一步是 `is_prefill=true, num_tokens=3072`；那一步里 128 个 decode 请求一个 token 都没拿到。更糟的是：如果同时到达两个长 prompt，`max_num_batched_tokens=16384` 放得下，它们会被塞进同一步。

再看 `steady_decode`：256 个请求一次性到达，开头连续 9 步全是 prefill，把 KV 塞满；之后 decode 每长出一个 block 都可能要抢占，整轮抢占 131 次、43 个请求，prefill 步一共 94 个（大部分是被抢占的请求回来重新 prefill）。

## 分析问题

- **追问链**：p99 尖刺 → trace 里对应 prefill 步 → `scheduler.schedule()` 的结构是"只要 `waiting` 非空就先 prefill，prefill 了就不 decode"（`nanovllm/engine/scheduler.py` 的 `if scheduled_seqs: return scheduled_seqs, True`）→ 任何新请求都会让所有 decode 请求停一步，停的时长等于 prefill 的时长。
- **本质**：prefill 是计算瓶颈（几千 token 把 GPU 算满，耗时随 token 数线性涨），decode 是访存瓶颈（每步读一遍权重，几十毫秒）。两者串行时，decode 的 TBT 被 prefill 的长度劫持。
- **量化**：Qwen3-8B 在 H100 上 prefill 大约每 token 几十微秒，3072 token 约 50–100 ms；decode 一步约 20–30 ms。一个长 prompt 让所有人 TBT 翻三到五倍。
- **理论**：`reference/gpu-perf-engineering-resources/` §4 Sarathi-Serve，它把这个现象命名为 **generation stall**，并指出 prefill 和 decode 的取舍是吞吐和延迟的取舍。Sarathi 的解法是把 prefill 切块混进 decode 步。
- **DeepInfer 怎么做**（和 Sarathi 不一样）：一步要么全 prefill 要么全 decode，**不混**，因为 DP 内所有 rank 每步必须同型（EP 的 all-to-all 对不上就卡死，5.3）。代价用两个机制控制：
  - `decode_step` 计数器，每 `DEEPINFER_PREFILL_ATTEMPT_INTERVAL`（70）个 decode 步才尝试一次 prefill（`csrc/engine/scheduler.hpp:308-311`），而且要 KV 用量 ≤ 90% 水位线才做（`:313`，`GPU_CACHE_PREFILL_WATERMARK`）。
  - prefill 一旦开始就连着做：prompt 步把 `decode_step` 清零（`:677`），下一步 `0 % 70 == 0` 又落在尝试点上，直到 `waiting` 清空、running 满或者 KV 超过水位线。
  - 被切的请求保持 `WAITING`、放回队头（`:1019`），每步最多切一个且排最后（`:542`）。

**思考题**：`interval = 70`、decode 一步 25 ms，一个长 prompt 最坏要等多久才开始 prefill？把这个数和它原来造成的 50–100 ms generation stall 放在一起：这一节是在用谁的时间换谁的时间？

## 解决问题

两个任务，都改 `nanovllm/engine/scheduler.py` 的 `schedule()`。任务 A 决定"这一步要不要尝试 prefill"，任务 B 决定"prefill 分支排不出、排出一半时怎么办"。`Config` 的参数和测试由 `start-step` 先写好。

### 任务 A：`_want_prefill()`：尝试间隔、水位线、空闲例外（约 20 分钟，你写约 40 行）

- **目标**：`waiting` 非空时不再每步都 prefill。只有 `decode_step % interval == 0` 且 `kv_usage <= watermark` 才尝试；`running` 为空时例外。水位线让 prefill 不再把 KV 塞满，decode 要新 block 时就不用抢占。
- **思路**：对回"任何新请求都让所有 decode 停一步"。DeepInfer 不混合，而是限制 prefill 出现的频率和时机。把"要不要 prefill"写成一个独立方法 `_want_prefill()`，给未来留接口（架构种子）：5.3 要在它外面套 DP 投票。`schedule()` 的逻辑改成：

  ```
  _want_prefill():
      waiting 为空                → 否
      running 为空                → 是（空闲例外：没有 decode 要保护）
      decode_step % interval != 0 → 否
      否则看 kv_usage <= watermark

  schedule():
      if _want_prefill() 且 prefill 分支排出了请求:
          decode_step = 0，返回 prefill 步
      走 decode 分支，decode_step += 1
  ```

- **已备好**：`Config.prefill_attempt_interval: int = 70`、`prefill_watermark: float = 0.9` 和它们到 `Scheduler` 的传递；`Scheduler.decode_step` 字段；`tests/test_2_2.py` 的 (a)(b)。
- **你写什么**：`_want_prefill()` 的函数体和 `schedule()` 的分支结构。`kv_usage = 1 - len(free_block_ids) / num_blocks`。空闲时的行为：`running` 为空、`waiting` 非空但不在尝试点，不能空转 70 步，`decode` 分支没有东西可调度时直接允许 prefill。最容易写错的两处：一是 prefill 排出请求之后忘了 `decode_step = 0`。在尝试点上触发的 prefill 看不出问题：prefill 步不加 `decode_step`，它本来就停在尝试点上，照样连着做；但空闲例外触发的 prefill，`decode_step` 可能不在尝试点上，`running` 一变成非空就连不上了。更要紧的是 `decode_step` 不再是"上一次 prefill 之后的 decode 步数"，5.3 的 ANY 点（`decode_step != 0`）就靠这个含义。二是水位线用 block 用量算，不是 token 数。
- **改哪里**：

  | 文件 | 函数 | 做什么 |
  |---|---|---|
  | `nanovllm/config.py` | `Config` | 两个参数（已备好） |
  | `nanovllm/engine/scheduler.py` | `_want_prefill` | 间隔、水位线、空闲例外 |
  | `nanovllm/engine/scheduler.py` | `schedule` | 按 `_want_prefill()` 分支，维护 `decode_step` |

### 任务 B：prefill 分支：排不出就转 decode，被切的排最后（约 20 分钟，你写约 30 行）

- **目标**：prefill 分支排不出任何请求时返回 decode 步，不返回空步；每步最多一个被切的请求，而且它在 batch 末尾。
- **思路**：对回 DeepInfer 的两个细节。排不出时（放不下、或者 `waiting` 里全是死请求）必须转 decode，DeepInfer 为此做了第二轮投票（`:327-335`），单卡没有投票，但"排不出就转 decode"这条逻辑要有。nano-vllm 已经只允许第一个请求被切，改成和 DeepInfer 一致：被切的请求排在**最后**，切了就 `break`，这样每步最多一个被切的、而且它在 batch 末尾，后面 2.7 的 ZOS 簿记会简单很多。
- **已备好**：`tests/test_2_2.py` 的 (c)。
- **你写什么**：prefill 循环里切请求之后的 `break`，和"排出 0 个"之后落到 decode 分支的那条路。最容易写错的一处：`waiting` 里全是 2.1 abort 掉、还没被清理的死请求时也算"排不出"，这种情况返回空步会让 `assert scheduled_seqs` 又炸一次。
- **改哪里**：

  | 文件 | 函数 | 做什么 |
  |---|---|---|
  | `nanovllm/engine/scheduler.py` | `schedule` 的 prefill 分支 | 被切的排最后并 `break`；排不出转 decode |

写完用 `check-step 2.2` 验收。

## 验收

同一个实验重跑：

```bash
python -m bench.run --scenario mixed_long_short --trace out/mixed-2.2.jsonl
```

1. 短请求的 TBT p99 下降（目标：不超过 p50 的 2 倍，长 prompt 到达那一步除外）。
2. 长 prompt 的 TTFT 上升，上升量不超过 `interval × decode 步时长`。把这两个数写进报告，这就是取舍的代价。
3. trace 里两个长 prompt 之间至少隔 `interval` 个 decode 步，除非 running 为空。
4. `steady_decode`：抢占次数明显下降，原因是水位线：prefill 不再把 KV 塞满。开头仍然是连续的 prefill，这一节不让 decode 提前（空闲例外 + 清零，prefill 一直连着做到超过水位线）。
5. `tests/test_2_2.py`：用假 Config 跑调度器，验证 (a) 不在尝试点时 waiting 非空也走 decode；(b) 水位线之上不 prefill；(c) prefill 排不出时转 decode 而不是返回空；(d) 2.1 的测试全过。

**解释**（由你说）：为什么短请求的 TBT p99 降了，长 prompt 的 TTFT 却升了？上升量为什么刚好被 `interval × decode 步时长` 封顶？`steady_decode` 开头仍然连着做了 8 步 prefill，为什么停在第 8 步，而不是把 256 个请求全排完？

**实测**（L4，Qwen3-0.6B，数字因机器而异）。`mixed_long_short`：

| | before（2.1） | interval=70 | 20 | 140 |
|---|---|---|---|---|
| 短请求 TBT p50 / p99 / max ms | 46 / 145 / 284 | 46 / 61 / 458 | 46 / 153 / 262 | 44 / 63 / 818 |
| 长 prompt TTFT p50 / max ms | 94 / 98 | 1618 / 3696 | 503 / 1100 | 3207 / 7401 |
| prefill 步数 | 22 | 8 | 22 | 8 |
| 吞吐 tok/s | 2424 | 2425 | 2409 | 2412 |

- interval=70：长 prompt 在尝试点之间攒着，3–4 个合成一步做完。卡顿从 20 次降到 6 次，p99 落回普通 decode 步。代价是 max 变大（4 个长 prompt 合成一步约 400 ms），TTFT 涨到秒级。
- interval=20：没有改善，原因见常见坑。interval=140：TTFT 翻倍，max 到 818 ms，p99 不再变好。

`steady_decode`（interval=70）：

| | before | after |
|---|---|---|
| 开头连续的 prefill 步 | 9 | 8 |
| prefill 总步数 | 94 | 10 |
| 抢占次数 / 被抢占请求数 | 131 / 43 | 25 / 25 |
| TBT p99 ms | 195 | 78 |
| 吞吐 tok/s | 1712 | 1768 |

**新浮现的问题**：水位线把 `steady_decode` 的抢占从 131 次压到 25 次，但没压到 0：decode 长到后面，KV 照样不够，只能抢占、整段重算。`kv_pressure` 里更明显，抢占次数和重算的 token 数很高，吞吐抖动。这是 2.3。

## DeepInfer 对照

| 这一节 | DeepInfer | 差异和原因 |
|---|---|---|
| `decode_step % interval` | `scheduler.hpp:308-311`，ALL 点 70 / ANY 点 100 | 单卡没有 ANY 点，它是给 DP 下孤立 rank 兜底的（5.3） |
| 90% 水位线 | `:313`、`GPU_CACHE_PREFILL_WATERMARK = 0.9f`（`:80`） | 一致 |
| 排不出就转 decode | 第二轮投票（`:327-335`） | 单卡退化成一个 if |
| 被切的排最后 | `:542` | 一致 |
| 混合 prefill/decode | 不混 | 和 Sarathi 的根本区别，原因是 DP 步型一致 |

## 常见坑

- `interval` 太大，新请求的 TTFT 会不可接受；太小又回到 generation stall。`mixed_long_short` 的长 prompt 每 20 步来一个，interval=20 时每个尝试点只赶上一个，等于没有合并，p99 153 ms，和不改一样。interval 要比到达间隔大好几倍，才攒得起来。70 是 DeepInfer 生产值，但它的 decode 步比你的快得多（MTP + Wide-EP），在 H100 单卡上可能要调小。把它做成参数，在报告里扫几个值。
- 水位线用 block 用量算，不是 token 数。
- 1.1 的 trace 里 `is_prefill` 现在有了实际意义，验收靠它。
