# 2.2：长 prompt 一进来，所有人都卡一下

> 起点：2.1 做完的代码　硬件：1×H100，Qwen3-8B　预计改动：60–120 行　轴：1 调度

## 1. 发现问题

**关注什么**：稳态 decode 的请求，在有新请求到达时，TBT 会怎样。

```bash
python -m bench.run --scenario mixed_long_short --trace out/mixed.jsonl
```

**先预测**：128 个短请求在 decode，每 20 步进来一个 3072 token 的长 prompt。短请求的 TBT p50 和 p99 会差多少？长 prompt 的 TTFT 呢？

**现象**：TBT p99 比 p50 大一个数量级以上。打开 trace，每个长 prompt 到达之后的下一步是 `is_prefill=true, num_tokens=3072`，`wall` 几十毫秒；那一步里 128 个 decode 请求一个 token 都没拿到。更糟的是：如果同时到达两个长 prompt，`max_num_batched_tokens=16384` 放得下，它们会被塞进同一步。

再看 `steady_decode`：256 个请求一次性到达，前面连续十几步全是 prefill，第一个 decode token 要等它们全做完。

## 2. 分析问题

- **追问链**：p99 尖刺 → trace 里对应 prefill 步 → `scheduler.schedule()` 的结构是"只要 `waiting` 非空就先 prefill，prefill 了就不 decode"（`nanovllm/engine/scheduler.py` 的 `if scheduled_seqs: return scheduled_seqs, True`）→ 任何新请求都会让所有 decode 请求停一步，停的时长等于 prefill 的时长。
- **本质**：prefill 是计算瓶颈（几千 token 把 GPU 算满，耗时随 token 数线性涨），decode 是访存瓶颈（每步读一遍权重，几十毫秒）。两者串行时，decode 的 TBT 被 prefill 的长度劫持。
- **量化**：Qwen3-8B 在 H100 上 prefill 大约每 token 几十微秒，3072 token 约 50–100 ms；decode 一步约 20–30 ms。一个长 prompt 让所有人 TBT 翻三到五倍。
- **理论**：`reference/gpu-perf-engineering-resources/` §4 Sarathi-Serve，它把这个现象命名为 **generation stall**，并指出 prefill 和 decode 的取舍是吞吐和延迟的取舍。Sarathi 的解法是把 prefill 切块混进 decode 步。
- **DeepInfer 怎么做**（和 Sarathi 不一样）：一步要么全 prefill 要么全 decode，**不混**，因为 DP 内所有 rank 每步必须同型（EP 的 all-to-all 对不上就卡死，5.3）。代价用两个机制控制：
  - `decode_step` 计数器，每 `DEEPINFER_PREFILL_ATTEMPT_INTERVAL`（70）个 decode 步才尝试一次 prefill（`csrc/engine/scheduler.hpp:308-311`），而且要 KV 用量 ≤ 90% 水位线才做（`:313`，`GPU_CACHE_PREFILL_WATERMARK`）。
  - prefill 一旦开始就连着做：prompt 步把 `decode_step` 清零（`:677`），下一步 `0 % 70 == 0` 又落在尝试点上，直到 running 满或者水位线超过。
  - 被切的请求保持 `WAITING`、放回队头（`:1019`），每步最多切一个且排最后（`:542`）。

## 3. 要做什么

**改哪里**：`nanovllm/engine/scheduler.py` 的 `schedule()`，`nanovllm/config.py` 加两个参数。

### 3.1 尝试间隔和水位线

- `Config` 加 `prefill_attempt_interval: int = 70`、`prefill_watermark: float = 0.9`。
- `Scheduler` 加 `decode_step` 计数。`schedule()` 的逻辑改成：

```
if waiting 非空 and (decode_step % interval == 0) and kv_usage <= watermark:
    走 prefill 分支；如果排出了请求，返回 prefill，decode_step = 0
走 decode 分支，decode_step += 1
```

- `kv_usage = 1 - len(free_block_ids) / num_blocks`。
- prefill 分支排不出任何请求时（放不下、或者 waiting 里全是死请求）必须转 decode，不能返回空步。DeepInfer 为此做了第二轮投票（`:327-335`），单卡没有投票，但"排不出就转 decode"这条逻辑要有。
- 给未来留接口（架构种子）：把"要不要 prefill"的判断写成一个独立方法 `_want_prefill()`，5.3 要在它外面套 DP 投票。

### 3.2 被切请求的位置

nano-vllm 已经只允许第一个请求被切。改成和 DeepInfer 一致：被切的请求排在**最后**，切了就 `break`。这样每步最多一个被切的、而且它在 batch 末尾，后面 2.7 的 ZOS 簿记会简单很多。

### 3.3 空闲时的行为

`running` 为空、`waiting` 非空但不在尝试点：不能空转 70 步。`decode` 分支没有东西可调度时，直接允许 prefill。

## 4. 验收

同一个实验重跑：

```bash
python -m bench.run --scenario mixed_long_short --trace out/mixed-2.2.jsonl
```

1. 短请求的 TBT p99 下降（目标：不超过 p50 的 2 倍，长 prompt 到达那一步除外）。
2. 长 prompt 的 TTFT 上升，上升量不超过 `interval × decode 步时长`。把这两个数写进报告，这就是取舍的代价。
3. trace 里两个长 prompt 之间至少隔 `interval` 个 decode 步，除非 running 为空。
4. `steady_decode`：第一个 decode token 不用再等全部 prefill 做完。
5. `tests/test_2_2.py`：用假 Config 跑调度器，验证 (a) 不在尝试点时 waiting 非空也走 decode；(b) 水位线之上不 prefill；(c) prefill 排不出时转 decode 而不是返回空；(d) 2.1 的测试全过。

**新浮现的问题**：`kv_pressure` 场景里抢占次数和重算的 token 数很高，吞吐抖动。这是 2.3。

## DeepInfer 对照

| 这一节 | DeepInfer | 差异和原因 |
|---|---|---|
| `decode_step % interval` | `scheduler.hpp:308-311`，ALL 点 70 / ANY 点 100 | 单卡没有 ANY 点，它是给 DP 下孤立 rank 兜底的（5.3） |
| 90% 水位线 | `:313`、`GPU_CACHE_PREFILL_WATERMARK = 0.9f`（`:80`） | 一致 |
| 排不出就转 decode | 第二轮投票（`:327-335`） | 单卡退化成一个 if |
| 被切的排最后 | `:542` | 一致 |
| 混合 prefill/decode | 不混 | 和 Sarathi 的根本区别，原因是 DP 步型一致 |

## 常见坑

- `interval` 太大，新请求的 TTFT 会不可接受；太小又回到 generation stall。70 是 DeepInfer 生产值，但它的 decode 步比你的快得多（MTP + Wide-EP），在 H100 单卡上可能要调小。把它做成参数，在报告里扫几个值。
- 水位线用 block 用量算，不是 token 数。
- 1.1 的 trace 里 `is_prefill` 现在有了实际意义，验收靠它。
