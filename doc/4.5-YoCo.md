# 4.5：后 20 层的 prefill 白算了

> 起点：4.4 做完的代码　轴：3 计算 / 4 模型结构

| | |
|---|---|
| **问题** | 16k prompt 进来，20 个 consumer 层每层都对全部 16384 个 query 做 attention 和 MoE，和 producer 层一样贵；可它们在 prefill 结束时真正要留下的只有写进 cache 的 KV（`shared_hidden` 一次投影就够）和最后几个 token 的 hidden。本质是 YoCo 下 consumer 层的 KV 是边界层 hidden 的函数，prefill 时 consumer 层的 query 维可以截到"未来会被当成 query 的那 140 行" |
| **实验** | `python -m tests.v4.harness --layers 0..K --prompt-len 16384 --report time-per-layer`，盯 consumer 层和 producer 层的每层 prefill 时间之比 |
| **硬件 / 费用** | 1×B200 + V4.1-Flash 前几层权重，Modal 约 $6.25/h；发现实验加三种模式反复对拍约 3 小时，约 $20 |
| **学到** | consumer 层的压缩 KV、index-K、SWA KV 全是 `shared_hidden` 的投影，和本层 hidden 无关，所以 prefill 时 KV 投影必须全量、attention 和 MoE 只要尾部；`keep_tokens = 134 + 6` 保的是 SWA 窗口加投机回退余量里的**残差流**，不是 KV；收缩的不只是 hidden，残差、mHC lazy 数据、top-k、候选块要一起按 `query_indices` gather，后面的层按 `total_q_c` 算、metadata 换成 consumer view |
| **时长** | 发现 + 分析约 2 小时；任务 A 约 20 分钟、任务 B 约 40 分钟、任务 C 约 40 分钟；验收约 1 小时。改动约 600–900 行 |

## 发现问题

**关注什么**：V4.1 的 config 里第一个 `ratio == 1` 的层是 `n_prefill_layer`（`config.py:158`）。它之前的层叫 producer，它和之后的层叫 consumer。consumer 层的 KV **不是从本层的 hidden 算的**。先看 DeepInfer 的 `V4Attention.__init__`（`attn.py:247-251`）和 `_resolve_shared_hidden`（`:465`）：第一个 consumer 层把自己 attn-norm 之后的 hidden 存成 `shared_hidden`，后面所有 consumer 层的 KV（压缩 KV、index-K、SWA KV）都从这一份 `shared_hidden` 投影。

实验：

```bash
python -m tests.v4.harness --layers 0..K --prompt-len 16384 --report time-per-layer
```

**先预测**：如果 consumer 层的 KV 只依赖边界层的 hidden，那 prefill 时 consumer 层的 attention 还需要对所有 16384 个 query 算吗？decode 时呢？

**现象**：

- 每层 prefill 时间差不多，consumer 层没有更便宜。
- 但 consumer 层在 prefill 结束时真正需要的产出只有两样：写进 cache 的 KV（它只依赖 `shared_hidden`，一次投影就够），和**最后几个 token** 的 hidden（下一步 decode 要用的残差流）。中间 16000 多个 query 的 attention、MoE 全是为了算出一个之后再也不用的 hidden。
- 对拍发现一个细节：consumer 层的 SWA KV 也从 `shared_hidden` 来（`yoco_swa_share_hidden`），decode 时每层的 SWA 环里存的是 `shared_hidden` 的投影，不是本层 hidden 的。

## 分析问题

- **追问链**：consumer 层 prefill 全量计算 → 产出里只有 KV 和尾部 hidden 有用 → KV 可以从 `shared_hidden` 对全部 token 一次投影得到（这一步必须全量）→ 只有尾部的 query 需要走完整的 attention + MoE → 尾部要多长：下一步 decode 的 SWA 窗口要看最近 128 个 token 的**本层** hidden 投影吗？不，SWA KV 也从 `shared_hidden` 来，所以尾部只需要覆盖"接下来会被当成 query 的位置"，再加投机解码回退的余量 → `keep_tokens = 134 + 6 = 140`（README 给的默认值）→ 在边界层把 hidden、残差、mHC 的 lazy 数据、top-k 索引都**按 `query_indices` 收缩**成 `[total_q_c, …]`，后面的层按收缩后的行数算，metadata 换成 consumer view。
- **本质**：YoCo（You Only Cache Once）的推理含义是：consumer 层的 KV 是边界层 hidden 的函数，prefill 时 consumer 层的 query 维度可以截断到"未来会用到的那几行"。这是 V4.1 prefill 省一半算力的来源。
- **量化**：16k prompt，20 个 consumer 层从 16384 行降到每序列 140 行，consumer 层的 attention 和 MoE 计算量降到 1%；整个 prefill 接近减半。KV 投影（全量）还在，但它是一个 GEMM，便宜。
- **理论**：YOCO（Sun et al. 2024，"You Only Cache Once"，不在清单里）：decoder-decoder 结构，self-decoder 产 KV，cross-decoder 复用。`reference/gpu-perf-engineering-resources/` §4 KV cache systems 里的 DeepSeek-V2 和 GQA 是"共享 KV"思路的前两步，YoCo 是把共享推到跨层。
- **DeepInfer 怎么做**：
  - **shared hidden**：`decoder_layer.py:146-152`：第一个 consumer 层 attn-norm 之后 `cross_layer_runtime.shared_hidden = hidden_bf16.clone()`；`yoco_shared_hidden_required`（`yoco.py:24`）决定要不要捕获。consumer kv-source 层用 `shared_hidden_kv_proj` 投影（`attn.py:775-781`），SWA 层用 `kv_swa_proj(shared_hidden)`（`:386-397`）。
  - **三种模式**：`DEEPINFER_YOCO_PREFILL_TRUNCATION_MODE`（`environ.py:188`）`off / mask / compact`。`mask` 不收缩行，只把矩形之外的可见域置空（`get_mask_view`，`input_metadata/yoco.py:86`），结果和 `compact` 等价，用来测试；`compact` 真正收缩。
  - **C++ 算截断**：`fill_yoco_truncation_metadata`（`prepare_tensor_input_v4.cpp:203`）：每序列 `clip_prefix = clamp(data_len − keep_tokens − q_start, 0, q_len − 1)`，`keep_len = q_len − clip_prefix`，整个 chunk 都在保留区间之前时仍保留最后 1 个 token 占位；输出 `query_indices [total_q_c]`、`cu_c`、compact 布局下的 `positions_yc`、`slot_store_swa_c`、SWA 的 `pivots_c`。
  - **边界处收缩**：`deepseek.py:191-209`：`i == yoco_boundary_layer_idx` 时 `input_metadata = get_consumer_view()`（`input_metadata/yoco.py:94`），原来的 full metadata 存进 `cross_layer_runtime.consumer_full_metadata`。层内 `decoder_layer.py:134-142`：`compact_yoco_boundary`（`yoco.py:93`）用 `gather` 按 `query_indices` 收缩 hidden、残差（含 mHC 的 `HCLazyPostData` 四个张量，`gather_hc_lazy :79`）、`topk_indices`、`block_candidate_idxs`；full 的 hidden 过一次 attn-norm 存成 `consumer_full_hidden`。
  - **full KV 仍然要写**：`_store_yoco_full_kv`（`attn.py:672`）：consumer kv-source 层用 `consumer_full_hidden` 投影全量 KV 写 cache（压缩 + index-K），走的是 `shared_hidden_kv_proj`（不算 index weights）；之后主路径 `_compute_kv_ca_index` 看到 `yoco_full_kv_stored` 就跳过存，只对 compact 的 query 算 top-k（`:540-553`）。
  - **DFlash 的 target 特征**也跟着切成 compact（`deepseek.py:199-206`，4.10）。
  - **decode 不受影响**：每层 1 个 query，没有可截的。
  - **CP 下**（5.5）：收缩还要经过一次 all-gather 重排（`yoco.py:62-78`）。

**思考题**：chunk 大小 4096、prompt 16384、`keep_tokens = 140`：按 `fill_yoco_truncation_metadata` 的公式，四个 chunk 各保留几行？为什么中间的 chunk 不能保留 0 行？

## 解决问题

三个任务按三种模式走：先换 KV 的来源（`off`），再算出截断区间并用 `mask` 验证截掉的行确实不影响结果，最后真正收缩（`compact`）。每一步都在 harness 上和前一步对拍。

### 任务 A：shared hidden 和 consumer 投影（约 20 分钟，你写约 60 行）

- **目标**：`off` 模式下 consumer 层的压缩 KV、index-K 和 SWA KV 都从 `shared_hidden` 投影，harness 上 decode 和 prefill 对拍通过。
- **思路**：第一个 consumer 层在 attn-norm 之后把 hidden 放进跨层的 runtime 对象（4.6 正式化），后面的 consumer kv-source 层用 `shared_hidden_kv_proj(shared_hidden)` 代替从本层 hidden 投影，SWA 层用 `kv_swa_proj(shared_hidden)`。对应分析里的第一个结论：consumer 的 KV 是边界层 hidden 的函数。这一步不截任何行，先把"KV 来源换掉"单独对拍。
- **已备好**：层对象的 `is_yoco_consumer`、`is_first_yoco_consumer`（从 config 的 `n_prefill_layer` 算）；跨层 runtime 对象的占位（`shared_hidden` 一个槽）；`Config.yoco_prefill_truncation_mode` 默认 `off`；`tests/test_4_5.py` 的测试壳。
- **你写什么**：第一个 consumer 层的捕获，以及 consumer 层 KV / SWA 投影的来源切换。最容易写错的一处：SWA 层也要从 `shared_hidden` 投影（`yoco_swa_share_hidden`），decode 时每层 SWA 环里存的是 `shared_hidden` 的投影，不是本层 hidden 的，漏掉这一处 decode 对拍从边界层之后的第一个 SWA 层开始错。`shared_hidden` 是 attn-norm **之后**的量。
- **改哪里**：

  | 文件 | 函数 | 做什么 |
  |---|---|---|
  | `nanovllm/models/deepseek_v4.py` | 层的 `forward` | 第一个 consumer 层捕获 `shared_hidden` |
  | `nanovllm/models/deepseek_v4.py` | `V4Attention` 的 KV / SWA 投影 | consumer 层从 `shared_hidden` 投影 |

### 任务 B：截断元数据和 mask 模式（约 40 分钟，你写约 120 行）

- **目标**：C++ 算出每序列的 `clip_prefix / keep_len / query_indices / cu_seqlens_q_c / positions_c / slot_mapping_store_swa_c / swa_pivots_c`；`mask` 模式下 consumer 层的输出和 `off` 一致。
- **思路**：`clip_prefix = clamp(data_len − keep_tokens − q_start, 0, q_len − 1)`，`keep_len = q_len − clip_prefix`，照 DeepInfer 的 `fill_yoco_truncation_metadata`。`mask` 模式不收缩行，只把 `[data_len − keep_tokens, data_len)` 之外的 query 行的可见域置空（attention 索引全 -1，MoE 照算），用来验证"截掉的行确实不影响结果"；它和 `compact` 的结果等价，是任务 C 的参考答案。对应分析里"只有尾部的 query 需要走完整的 attention + MoE"。
- **已备好**：`Config.yoco_prefill_truncation_mode`（`off / mask / compact`）和 `yoco_prefill_keep_tokens`（默认 140，校验 ≥ `window + max_backtracking`）的传递；`InputMetadata` 上新增字段的声明和张量分配；C++ 侧的 pybind；测试 (a) 里 `clip_prefix / query_indices` 的 Python 参考实现壳。
- **你写什么**：`csrc/prepare_input.cpp` 里的截断元数据计算，`InputMetadata.get_mask_view()`。最容易写错的两处：`clip_prefix` 的上界是 `q_len − 1`，每个序列至少留 1 行，否则 varlen 布局里出现 0 长度序列，很多 kernel 不支持；2.2 的 chunked prefill 下 `clip_prefix` 按序列的 `data_len` 算，不按本 chunk 的长度，中间 chunk 可能整个被截到只剩 1 行占位，测试 (a) 的"整个 chunk 在保留区之前"和"保留区跨两个 chunk"就是抓这个。
- **改哪里**：

  | 文件 | 函数 | 做什么 |
  |---|---|---|
  | `csrc/prepare_input.cpp` | 截断元数据 | `clip_prefix / keep_len / query_indices / cu_seqlens_q_c / positions_c / slot_mapping_store_swa_c / swa_pivots_c` |
  | `InputMetadata` | `get_mask_view` | query 行不变，保留区之外的行 attention 索引全 -1 |

### 任务 C：compact 模式（约 40 分钟，你写约 150 行）

- **目标**：`compact` 模式下边界层把行数从 `total_q` 收缩到 `total_q_c`，后面所有层按收缩后的行数算，输出和 `off / mask` 一致；16k prompt 下 consumer 层的时间降到 producer 层的几个百分点。
- **思路**：边界层把 metadata 换成 consumer view，full metadata 存进跨层 runtime；层内用 `gather` 按 `query_indices` 收缩 hidden、残差（4.7 之后含 mHC 的四个 lazy 张量）、top-k、候选块；full 的 hidden 过一次 attn-norm 存成 `consumer_full_hidden`。consumer kv-source 层先用 `consumer_full_hidden` 写全量 KV（压缩 + index-K，用 full metadata），再对 compact 的 query 做 top-k 和 attention；采样只看每序列最后一行，位置不变。对应分析里"KV 投影必须全量，attention 和 MoE 只要尾部"。
- **已备好**：`InputMetadata.get_consumer_view()` 的字段搬运；跨层 runtime 的 `consumer_full_metadata / consumer_full_hidden / yoco_full_kv_stored` 槽；4.4 缓存的调度元数据的清理钩子（候选块和 top-k 的行布局变了，`yoco.py:121-122`）。和前面各节的接缝已经查过：2.7 的 ZOS 不受影响（`query_indices` 依赖 `data_len`，prefill 不在 ZOS 的乐观路径上）；4.3 的压缩状态用 full metadata 写入，状态环照常推进。
- **你写什么**：边界层的收缩（照 `compact_yoco_boundary`），consumer kv-source 层的 full KV 写入（照 `_store_yoco_full_kv`）和主路径跳过存 KV 的分支，后续层的 `total_q_c`。最容易写错的两处：收缩漏项，残差、mHC lazy 数据、top-k、候选块漏一个就错，而且错在后面几层才显出来；`consumer_full_hidden` 是 attn-norm **之后**的（和 `shared_hidden` 同一个量），不是 norm 之前的。
- **改哪里**：

  | 文件 | 函数 | 做什么 |
  |---|---|---|
  | `nanovllm/models/deepseek_v4.py` | 模型 `forward` 的边界层分支 | 换 consumer view，存 full metadata |
  | `nanovllm/models/deepseek_v4.py` | 边界层的收缩 | `gather` 收缩 hidden / 残差 / top-k / 候选块，存 `consumer_full_hidden` |
  | `nanovllm/models/deepseek_v4.py` | `V4Attention` 的 full KV 写入 | 用 `consumer_full_hidden` 写全量 KV，主路径跳过存 |
  | `InputMetadata` | `get_consumer_view` | compact 布局的 metadata |

## 验收

1. `mask` 和 `compact` 两种模式下，整个 prefill 的输出（最后一个 token 的 logits、写进 cache 的 KV、SWA 环、压缩状态）和 `off` 模式完全一致（bf16 容差）；三种模式和 DeepInfer 的同样模式一致。
2. 同一个实验重跑：16k prompt 下 consumer 层的时间降到 producer 层的几个百分点，整个 prefill 时间接近减半；报告里给 per-layer 的 before / after。
3. decode 吞吐不变（这一节不该影响 decode）。
4. `tests/test_4_5.py`：(a) `clip_prefix / query_indices` 的 C++ 计算和一个 Python 参考一致，含"整个 chunk 在保留区之前"和"保留区跨两个 chunk"；(b) 收缩 gather 对 hidden / 残差 / top-k 的行一致；(c) 三种模式输出一致；(d) 前面全过。
5. **解释**（由你说）：`mask` 和 `off` 输出相同、`compact` 和 `mask` 输出相同，这两个事实分别证明了什么？consumer 层的时间为什么是降到"几个百分点"而不是 1%，剩下的那部分是什么？decode 吞吐为什么一点都不该变？

**新浮现的问题**：consumer 层有 20 层，每层都在写自己的压缩 KV 和 index-K，但它们都是同一个 `shared_hidden` 的投影。config 里的 `kv_source_layer_ids` 说明很多层的 KV 是**同一份**。这是 4.6。

## 常见坑

- `keep_tokens` 必须覆盖 SWA 窗口 + 回退余量（`134 + 6`），否则 decode 的第一步 SWA 窗口里缺 query 行的 hidden 残差。注意缺的不是 KV（KV 全量写了），是残差流。
- `clip_prefix` 的上界是 `q_len − 1`：每个序列至少留 1 行，否则 varlen 布局里出现 0 长度序列，很多 kernel 不支持。
- 收缩的不只是 hidden：残差、mHC 的四个 lazy 张量、top-k、候选块，漏一个就错。
- `consumer_full_hidden` 是 attn-norm **之后**的（和 `shared_hidden` 同一个量），不是 norm 之前的。
- 候选块和 top-k 的行布局变了，4.4 缓存的调度元数据要清掉（`yoco.py:121-122`）。
