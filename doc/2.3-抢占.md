# 2.3：KV 一满，白算的 token 占了产出的三成

> 起点：2.2 做完的代码　轴：1 调度 / 4 显存

| | |
|---|---|
| **问题** | `kv_pressure` 上 KV 一满就不停抢占：L4 实测抢占 154 次，白算的 token 13.4 万，占产出的 29%；被踢的请求流式输出最长卡住 41 s。抢占是用计算换显存，nano-vllm 只有一种做法：`running.pop()` 踢队尾，也就是最近才进来的那个，然后整段重算。这一节回答两件事：踢谁，踢了之后怎么办 |
| **实验** | `python -m bench.run --scenario kv_pressure --trace out/kv.jsonl --gpu-memory-utilization 0.5`，盯 `preemptions`、`recomputed_tokens`（每次抢占时 `seq.num_tokens` 之和）和 TBT 最大值 |
| **硬件 / 费用** | L4 + Qwen3-0.6B 即可（$0.80/h），文档数字都是 L4 实测；H100 + Qwen3-8B（$3.95/h）抢占更重。发现、before / after、stop 开关三组对照约 2 小时，L4 约 $2 |
| **学到** | 每腾出一个 block 大约要重算 `block_size` 个 token，踢谁这笔账都差不多，"踢一个长的顶好几个短的"按 token 算不成立；踢谁真正的差别在于有没有把"跑完、还 block"这个来源堵上，所以在输出长度集中的负载上，照 DeepInfer 踢输出最长的反而抢占更多；两条出路都要当场释放 block，同一步的 `can_append` 才看得见；DeepInfer 只重算不 swap，`stop_preempted_request` 是没有 prefill 通道的 decode 机器（5.6）唯一能走的路 |
| **时长** | 发现 + 分析约 1 小时；任务 A / B 各约 20 分钟；验收约 30 分钟。你写约 35 行 |

## 发现问题

**关注什么**：KV cache 被占满时，引擎在做什么。

```bash
python -m bench.run --scenario kv_pressure --trace out/kv.jsonl --gpu-memory-utilization 0.5
```

（`--gpu-memory-utilization 0.5` 是为了更快把 KV 压满。）

**先预测**：512 个请求同时到，每个输出 768–1024 token（`ignore_eos`），KV 放不下全部。会抢占多少次？白算的 token 占产出的几成？被踢的请求，TTFT 和 TBT 哪个会变？

**现象**（L4 + Qwen3-0.6B）：抢占 154 次、涉及 143 个请求，白算的 token 13.4 万，占产出的 29%，平均每次扔掉 873 个 token。trace 里 `preempted_ids` 频繁出现，每次抢占之后跟着一个 prefill 步把它重算一遍。

被抢占的请求变的是 **TBT 最大值**，41 s：它在被踢之前早就吐过第一个 token，`token_times[0]` 不会再变，卡住的是中间那一段。TTFT 中位数 124 s 是排队造成的，和抢占无关：512 个请求同时到，只装得下约 60 个。

再看被踢的是谁：`running.pop()` 取队尾，是最近一批进来的请求。victim 被踢时的输出中位数 214，同一步 batch 的中位数 355。

## 分析问题

- **追问链**：抢占多 → victim 被整段重算 → 看 `scheduler.preempt`：释放全部 block、放回 `waiting` 队头，以后 prompt 加已有输出全部重新 prefill → 再看 victim 怎么选：`running.pop()`，队尾，没有任何策略 → 那应该按什么选？
- **卡在哪种资源上**：HBM 容量。抢占是拿计算去换它。
- **量化**：踢掉一个请求，腾出的 block 约等于 `num_tokens / 256`，以后要重算的是 `num_tokens`。所以每腾出一个 block，大约要重算 256 个 token，**踢谁都差不多**。"踢一个长的顶好几个短的"按 token 算并不成立：踢一个 1000 token 的和踢四个 250 token 的，腾出的 block 和要重算的 token 都一样多。
- **那差别在哪**：KV 满了以后，空闲 block 只有两个来源：有请求跑完，或者有请求被踢。踢一个快跑完的请求，就是把"马上要永久还回来的 block"换成"现在借出、以后还要拿回去，外加重算一遍"，把"跑完还 block"这个来源堵上了。`kv_pressure` 用的是 `ignore_eos`，`max_tokens` 只在 768–1024 之间，**输出最长的请求正好离跑完最近**。
- **理论**：`reference/gpu-perf-engineering-resources/` §4 vLLM 论文 4.5 节：FCFS、后到先踢、all-or-nothing；recompute vs swap 的取舍（block 小的时候 recompute 更划算，因为 swap 的 PCIe 拷贝是许多次小块）。
- **DeepInfer 怎么做**：
  - `_schedule_decode` 先把 `running` 按 `get_output_len()` **降序**排（`csrc/engine/scheduler.hpp:622-643`），从尾部（输出最短）开始分配 block，放不下时从头部踢，也就是踢**输出最长**的；只剩自己还放不下，就踢自己。注释写的是 `// LCFS`，代码踢的却是最长的，以代码为准。
  - 为什么选最长的，源码和 `doc/` 都没有说明。几种可能的解释，**都未验证**：真实流量的输出长度是长尾分布，已经跑得越长，预期剩下的越长，这时候踢最长的才是保住"跑完还 block"的来源；生产环境的 decode 机器必须开 `stop_preempted_request`（`:102`），被踢的请求不回来，踢最大的能让失败的请求最少；长上下文下，踢掉最长的，attention 每步读的 KV 少得最多。
  - `_preempt`（`:766`）分两条路：`stop_preempted_request` 开着就直接 `FINISHED_PREEMPTED` 不重算（COMPLETION 引擎必须开，因为它没有 prefill 通道，5.6）；否则 `reset_for_recompute`（`sequence.hpp:134`、`:223`）清掉 cache 计数、inflight 计数、MTP 计数，回 `waiting` 队头。**两条路都立刻 `free_seq_nolock`**（`:779`、`:787`）。
  - 没有 swap。`SWAPPED` 状态在枚举里但没用。

**思考题**：每腾出一个 block 的重算代价对谁都一样，那踢谁的差别到底在哪里？在 `kv_pressure` 上，输出最长的请求离跑完还有多远？换成输出长度是长尾分布的负载，答案会不会反过来？

## 解决问题

两个任务：任务 A 改"踢谁"，任务 B 改"踢了之后怎么办"。照 DeepInfer 的做法改完，在这个负载上抢占会**变多**，这是这一节验收时要解释的核心。

### 改动全景

| 逻辑上的一步 | 文件:函数 | 谁实现 | 目标 |
|---|---|---|---|
| 按输出长度排序，双指针调度和踢 | `scheduler.py`：`_decode` | 你（任务 A） | 降序排，从尾部分配 block，从头部踢；只剩自己放不下就踢自己；没轮到的留在 `running` |
| 抢占分两条出路 | `sequence.py`：`reset_for_recompute`；`scheduler.py`：`preempt` | 你（任务 B） | 重算：清计数、回 `waiting` 队头；stop：`FINISHED_PREEMPTED` 进 `finished`；两条都当场释放 block |
| 观测 | `stats.py`：`StepRecord.recomputed_tokens`；`bench/metrics.py`：报告里占产出的百分比；`preempt` 开头记 `preempted` / `recomputed_tokens` / `num_preemptions` | 脚手架 | 验收指标 |
| 开关 | `config.py`：`stop_preempted_request = False` 和它到 `Scheduler` 的传递；`bench/run.py`：`--stop-preempted-request` | 脚手架 | 和 why 无关的配置透传 |
| 测试 | `tests/test_2_3.py`；2.1、2.2 测试的假 config 补上新字段 | 脚手架 | A 做完 `test_victim_is_the_longest_output` 变绿，B 做完另外三条变绿，2.1、2.2 的测试全过 |

### 任务 A：按输出长度踢（约 20 分钟，你写约 25 行）

- **目标**：放不下时踢的是输出最长的请求；`test_victim_is_the_longest_output` 变绿。
- **思路**：照 DeepInfer `scheduler.hpp:622-643`：`_decode` 开头把 `running` 按 `num_completion_tokens` 降序排成一个 list，`l` 指头、`r` 指尾。每次取 `running[r-1]` 来调度：放不下就踢 `running[l]`、`l += 1`，直到放得下或者只剩它自己；只剩自己还放不下，就踢自己。策略就是排序的 key，不用单独抽一个 `_pick_victim()`，抽出来和双指针配合反而别扭。
- **你写什么**：`_decode` 的函数体。最容易写错的三处：
  - 降序排之后尾部是输出最短的，**分配从尾部、踢从头部**，两个方向别反，否则刚分配完的请求转头就被踢掉。
  - 踢一个可能还不够，要循环踢；内层循环的条件是 `r - l > 1`，否则会把当前这个请求也当成别人踢一遍。
  - 受 `max_num_seqs` 限制，循环可能在 `l < r` 时停下。没轮到的 `running[l:r]` 要留在 `running` 里：`self.running = deque(running[l:r] + scheduled)`。DeepInfer 是 `TORCH_CHECK(l == r)`，因为它的 `max_seqs` 保证每个请求都轮得到。
- **改哪里**：

  | 文件 | 函数 | 做什么 |
  |---|---|---|
  | `nanovllm/engine/scheduler.py` | `_decode` | 降序排、双指针、循环踢、踢自己 |

### 任务 B：重算或者直接结束（约 20 分钟，你写约 10 行）

- **目标**：`preempt` 只有两条路：重算（清计数、回 `waiting` 队头）或直接结束（`FINISHED_PREEMPTED`，进 `finished`，`step()` 以 `insufficient_system_resource` 返回）。两条路都在 `preempt` 里当场 `deallocate`。`test_reset_for_recompute`、`test_recompute_goes_back_to_the_head_of_waiting`、`test_stop_preempted_request` 变绿。
- **思路**：对回 DeepInfer 的 `_preempt`（`:766`）。清计数的工作收进 `Sequence.reset_for_recompute()`，`preempt` 调它，不散落在调度器里。直接结束这条路走 2.1 的出口：进 `self.finished`，由 `step()` 记录和返回。但释放**不能**等 2.1 那样在这一步跑完之后才做：`_decode` 踢完人，同一步就要检查 `can_append(seq)`，block 不当场还回去，当前这个请求还是放不下，只好把自己也踢掉，白踢了一个人。DeepInfer 两条路都调用了 `free_seq_nolock`（`:779`、`:787`）。
- **你写什么**：
  - `Sequence.reset_for_recompute()`：清 4 个计数，`num_cached_tokens = 0`、`num_scheduled_tokens = 0`、`is_prefill = True`、`total_inflight_tokens = 0`（2.7 用）。`token_ids` 和 `num_prompt_tokens` 不动，`max_tokens` 照原来的进度继续算。
  - `preempt`：`deallocate` 放在分支之前；开关开了标 `FINISHED_PREEMPTED`、`self.finished.append(seq)`、返回；否则 `reset_for_recompute()`、`WAITING`、`waiting.appendleft(seq)`。

  最容易写错的两处：stop 这一路以为"走 2.1 的出口就会释放"，没有当场 `deallocate`，`test_stop_preempted_request` 会抓到同一步 block 没回来；重算这一路回到 `waiting` **队头**，不是队尾，否则它已经付过一次 prefill，又被新请求饿死。直接结束的请求会在 `step()` 里再被 `deallocate` 一次，`block_table` 已经空了，等于什么都不做。
- **改哪里**：

  | 文件 | 函数 | 做什么 |
  |---|---|---|
  | `nanovllm/engine/sequence.py` | `reset_for_recompute` | 清 4 个计数 |
  | `nanovllm/engine/scheduler.py` | `preempt` | 当场释放，两条出路 |

写完用 `check-step 2.3` 验收。

## 验收

同一个实验重跑，再开一次 stop 开关：

```bash
python -m bench.run --scenario kv_pressure --trace out/kv-2.3.jsonl --gpu-memory-utilization 0.5
python -m bench.run --scenario kv_pressure --trace out/kv-2.3-stop.jsonl --gpu-memory-utilization 0.5 --stop-preempted-request true
```

L4 + Qwen3-0.6B 实测：

| | before：踢队尾 | after：踢输出最长的 | stop：直接结束 |
|---|---|---|---|
| 抢占次数 / 被抢占的请求 | 154 / 143 | 167 / 148 | 182 / 182（全部失败） |
| recomputed_tokens | 13.4 万（29%） | 20.0 万（44%） | 20.3 万（54%，全部丢弃） |
| 每次抢占扔掉的 token | 873 | 1198 | 1116 |
| victim 被踢时的输出中位数 / 同一步 batch 的中位数 | 214 / 355 | 540 / 400 | — |
| 吞吐 tok/s | 1497 | 1473 | 1555 |
| TBT 最大值 | 41.3 s | 37.8 s | 1.5 s |
| TTFT 中位数 | 124 s | 130 s | 84 s |

1. victim 被踢时的输出中位数从 214 变成 540，高过同一步 batch 的中位数：踢的确实是输出最长的。抢占次数和白算的 token **反而上升**。这不是写错了，是这一节要解释的东西。
2. stop 开关：没有重算，被抢占的请求以 `insufficient_system_resource` 结束，TBT 最大值降到 1.5 s，吞吐只高 4%，代价是 182 个请求失败，它们已经算过的 token 也一起扔掉。这是 PD 分离下 decode 机器的行为，5.6 会用到。
3. `pytest tests/test_2_3.py`：victim 是输出最长的；`reset_for_recompute` 清干净；重算回到 `waiting` 队头并能跑完；stop 模式在同一步就释放 block。2.1、2.2 的测试全过。

**映射回顾**（由你说，三五句话，写进卡片）：`git diff` 对着改动全景走一遍。大致是：`_decode` 从"取队头调度、`pop` 队尾踢"改成先按输出长度降序排，两个指针一个从尾部分配、一个从头部踢，相遇或者 batch 满了就停，没轮到的留在 `running`。`preempt` 先当场释放，再分两条路：重算交给 `Sequence.reset_for_recompute()` 清计数、回 `waiting` 队头；直接结束标 `FINISHED_PREEMPTED`，走 2.1 的出口。

**解释**（由你说）：每腾出一个 block 要重算多少 token？既然踢谁都差不多，为什么踢最长的在这个负载上抢占反而更多？DeepInfer 为什么还是选最长的，哪种负载下它会赢？`stop_preempted_request=True` 的 TBT 最大值为什么从 41 s 降到 1.5 s，它少付了哪一笔、又扔掉了什么？

**延伸实验**（可选，文档还没有实测数字）：要让 DeepInfer 的选择有一个能复现的收益，可以加一个长尾负载（`max_tokens` 按长尾分布抽，去掉 `ignore_eos`），或者在 stop 模式下对照"踢最长"和"踢最短"的失败请求数。

**新浮现的问题**：试一下 `n=4` 采样（同一个 prompt 要 4 个不同的输出）。现在只能发 4 个一样的请求，prefill 算 4 遍。这是 2.4。

## DeepInfer 对照

| 这一节 | DeepInfer | 差异和原因 |
|---|---|---|
| 按输出长度降序、从头部踢最长的 | `scheduler.hpp:622-643` | 做法一致。DeepInfer 注释写 `LCFS`，也没说为什么选最长的 |
| 没轮到的 `running[l:r]` 留在 `running` | `TORCH_CHECK(l == r)`（`:645`） | DeepInfer 的 `max_seqs` 保证每个请求都轮得到，我们可能中途停下 |
| `reset_for_recompute` 清 4 个计数 | `sequence.hpp:134`、`:223` | DeepInfer 还要清 MTP 状态（2.8）、SWA 起点（4.2） |
| `stop_preempted_request`，两条路都当场释放 | `:766-787` | DeepInfer 还有一条：结构化输出的请求不能重算，直接结束（2.11） |
| `recomputed_tokens` 观测 | 只有 `num_preempted` 计数 | 为了教学加的验收指标 |
| 没有 swap | 没有 swap | 一致。vLLM 论文里的 swap 在 DeepInfer 里被 PD 分离和 KV 分层存储取代 |
| decode 按需追加 block | `_append_slot`（`:817`） | nano-vllm 的 `may_append` 已经是这样 |

## 常见坑

- 以为踢最长的一定更省。每腾出一个 block 的重算代价对谁都一样，差别在有没有堵上"跑完还 block"的来源；在 `ignore_eos`、输出长度集中的负载上，最长的就是最快跑完的。
- 看 TTFT 找抢占的代价。被踢的请求第一个 token 早就出过了，代价在 TBT 最大值上；`kv_pressure` 的 TTFT 主要是排队。
- stop 这一路等到这一步跑完才释放：同一步的 `can_append` 看不到这些 block，当前请求只好把自己也踢掉。
- 被抢占后回到 `waiting` **队头**，不是队尾，否则它会被新请求饿死。
- 排序是 O(n log n)，每步做一次。2.5 会算这笔账，现在先不优化。
- 2.2 的水位线和这一节互相影响：水位线越低，抢占越少，但 batch 越小。报告里可以扫一下。
