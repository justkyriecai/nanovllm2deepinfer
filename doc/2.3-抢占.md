# 2.3：KV 一满，白算的 token 比产出的还多

> 起点：2.2 做完的代码　轴：1 调度 / 4 显存

| | |
|---|---|
| **问题** | `kv_pressure` 里被抢占的请求重算的 token 和产出的 token 一个量级，吞吐锯齿，被抢占的请求 TTFT 极大。根因是 victim 用 `running.pop()` 取队尾，也就是最新进来、输出最短的请求：它释放的 block 最少，重算成本却和别人一样，这笔"用计算换显存"的交换做得最亏 |
| **实验** | `python -m bench.run --scenario kv_pressure --trace out/kv.jsonl --gpu-memory-utilization 0.5`，盯 `preempted` 次数和"白算的 token 总数"（每次抢占时 `seq.num_tokens` 之和） |
| **硬件 / 费用** | 1×H100 + Qwen3-8B（$3.95/h）；调度逻辑 L4 即可（$0.80/h），H100 更接近文档数字。发现加 before / after 和开关对比约 2 小时，约 $8 |
| **学到** | 抢占是用计算换显存容量，victim 要选释放 block 最多的（输出最长），因为 prompt 重算成本大家一样、踢一个长的顶踢好几个短的；DeepInfer 只 recompute 不 swap，vLLM 论文里的 swap 被 PD 分离和 KV 分层存储取代；`stop_preempted_request` 是没有 prefill 通道的 decode 机器（5.6）唯一能走的路，吞吐最高但有请求失败 |
| **时长** | 发现 + 分析约 1 小时；任务 A / B 各约 20 分钟；验收约 30 分钟。改动约 60–120 行 |

## 发现问题

**关注什么**：KV cache 被占满时，引擎在做什么。

```bash
python -m bench.run --scenario kv_pressure --trace out/kv.jsonl --gpu-memory-utilization 0.5
```

（`--gpu-memory-utilization 0.5` 是为了在 80GB 的卡上更快把 KV 压满。）

**先预测**：512 个请求、每个输出 768–1024 token，KV 放不下全部。被抢占的请求有多少？每次抢占浪费多少 token？吞吐曲线是平的还是锯齿？

**现象**：报告里 `preempted` 一列非零，而且往往不止一次；被抢占的请求 TTFT 极大。trace 里 `preempted_ids` 频繁出现，每次抢占后紧跟一个 prefill 步把它重算一遍。把每次抢占时 `seq.num_tokens` 加起来，就是白算的 token 总数，和产出 token 数一个量级。再看被抢占的是谁：`running.pop()` 取队尾，也就是**最近才进来、输出最短**的请求。

## 分析问题

- **追问链**：抢占多 → victim 被重算 → 看 `scheduler.preempt`：recompute 方式，释放全部 block，放回 `waiting` 队头 → 再看 victim 怎么选：`running.pop()`，队尾 → 队尾是最新进来的，它的 prompt 刚算完、输出还很短 → 重算它的成本（prompt + 输出）和它马上要释放的收益（block 数）不成比例。
- **本质**：抢占是用**计算**换**显存容量**。要让这笔交换划算，要么踢掉重算代价最小的，要么踢掉释放显存最多的；nano-vllm 两样都没算。
- **理论**：`reference/gpu-perf-engineering-resources/` §4 vLLM 论文 4.5 节：FCFS、后到先踢、all-or-nothing；recompute vs swap 的取舍（block 小的时候 recompute 更划算，因为 swap 的 PCIe 拷贝是小块的）。
- **DeepInfer 怎么做**：
  - `_schedule_decode` 先把 `running` 按 `get_output_len()` **降序**排（`csrc/engine/scheduler.hpp:622-646`），从尾部（输出最短）开始调度；放不下时从头部踢，也就是踢**输出最长**的。注意源码注释写的是"抢占最短"，代码踢的是最长的，以代码为准。原因：输出最长的请求占 block 最多，踢一个顶踢好几个短的；而它的 prompt 重算成本和别人一样。
  - `_preempt`（`:766`）有一个开关 `stop_preempted_request`：开了就直接 `FINISHED_PREEMPTED` 不重算（COMPLETION 引擎必须开，因为它没有 prefill 通道，5.6）；否则 `reset_for_recompute`（`sequence.hpp:134`、`:223`）清掉 cache 计数、inflight 计数、MTP 计数，回 waiting 队头。
  - 没有 swap。`SWAPPED` 状态在枚举里但没用。
  - `_append_slot`（`:817`）按 `get_num_blocks()` 增减，decode 阶段一块一块按需加，这才是 paged KV 省显存的地方。

**思考题**：改成踢输出最长的之后，**每一次**抢占白算的 token 数会比原来多还是少？"白算的 token 总数"却应该下降，这两件事怎么同时成立？

## 解决问题

两个任务：任务 A 改"踢谁"，任务 B 改"踢了之后怎么办"。`_pick_victim()` 的签名、`Config` 开关、观测字段和测试由 `start-step` 先写好。

### 任务 A：victim 选择（约 20 分钟，你写约 30 行）

- **目标**：放不下时踢的是输出最长的请求；`kv_pressure` 的抢占次数和白算的 token 总数都下降。
- **思路**：对回"重算成本和释放收益不成比例"。照 DeepInfer `scheduler.hpp:622-646`：decode 分支调度前，把 `running` 按 `num_completion_tokens` 降序排；从尾部开始逐个 `can_append`；放不下时从头部取 victim 抢占，直到放得下。和 2.2 一样把这个策略写成一个独立方法 `_pick_victim()`，便于在报告里比较不同策略。
- **已备好**：`_pick_victim()` 的签名；观测：1.1 的 `StepRecord.preempted_ids` 已经有了，再加一个 `recomputed_tokens`（本步被抢占请求的 `num_tokens` 之和），`summarize_steps` 汇总成"白算的 token 总数"，这是本节的验收指标；`tests/test_2_3.py` 的 (a)。
- **你写什么**：排序、从尾部调度、从头部循环踢、`_pick_victim()` 的函数体。最容易写错的两处：抢占一个请求后它释放的 block 可能还是不够当前这个，要循环踢，不是踢一个就 `break`；降序排之后尾部是输出最短的，调度从尾部开始、踢从头部开始，两个方向别反。
- **改哪里**：

  | 文件 | 函数 | 做什么 |
  |---|---|---|
  | `nanovllm/engine/scheduler.py` | `schedule` 的 decode 分支 | 按 `num_completion_tokens` 降序排，尾部调度、头部踢 |
  | `nanovllm/engine/scheduler.py` | `_pick_victim` | 策略独立成方法 |

### 任务 B：`reset_for_recompute` 和 `stop_preempted_request`（约 20 分钟，你写约 30 行）

- **目标**：`preempt` 只有两条路：重算（清计数、回 `waiting` 队头）或直接结束（`FINISHED_PREEMPTED`，`finish_reason = "insufficient_system_resource"`）。
- **思路**：对回 DeepInfer 的 `_preempt`（`:766`）。清计数的工作收进 `Sequence.reset_for_recompute()`，`preempt` 调它，不要散落在调度器里；开关打开时走 2.1 的出队和释放路径，一行新的释放代码都不用写。
- **已备好**：`Config.stop_preempted_request: bool = False` 和它到 `Scheduler` 的传递；`tests/test_2_3.py` 的 (b)(c)。
- **你写什么**：
  - `Sequence.reset_for_recompute()`：`num_cached_tokens = 0`、`num_scheduled_tokens = 0`、`is_prefill = True`、`total_inflight_tokens = 0`（2.7 用）、`num_preemptions += 1`。
  - `preempt`：开关开了直接标 `FINISHED_PREEMPTED`、`finish_reason = "insufficient_system_resource"`；否则释放全部 block、`reset_for_recompute()`、回 `waiting` **队头**。

  最容易写错的一处：被抢占后回到 `waiting` 队头，不是队尾，否则它会被新请求饿死。
- **改哪里**：

  | 文件 | 函数 | 做什么 |
  |---|---|---|
  | `nanovllm/engine/sequence.py` | `reset_for_recompute` | 清五个计数 |
  | `nanovllm/engine/scheduler.py` | `preempt` | 两个分支 |

写完用 `check-step 2.3` 验收。

## 验收

同一个实验重跑：

```bash
python -m bench.run --scenario kv_pressure --trace out/kv-2.3.jsonl --gpu-memory-utilization 0.5
```

1. 抢占次数和"白算的 token 总数"都下降；吞吐上升、抖动变小。把 before / after 写进报告。
2. 换成 `stop_preempted_request=True`：没有重算，被抢占的请求以 `insufficient_system_resource` 结束，吞吐最高但有请求失败。这是 PD 分离下 decode 机器的行为，5.6 会用到。
3. `tests/test_2_3.py`：假 Config、小 `num_blocks`，构造 3 个输出长度不同的请求，验证 (a) 放不下时踢的是输出最长的；(b) 被踢的请求 `num_cached_tokens == 0`、`block_table` 为空、回到 waiting 队头；(c) `stop_preempted_request` 下状态正确；(d) 2.1、2.2 的测试全过。

**解释**（由你说）：抢占次数为什么降了？白算的 token 总数为什么跟着降，尽管每次踢的是最长的那个？`stop_preempted_request=True` 的吞吐为什么反而最高，它少付了哪一笔？

**新浮现的问题**：试一下 `n=4` 采样（同一个 prompt 要 4 个不同的输出）。现在只能发 4 个一样的请求，prefill 算 4 遍。这是 2.4。

## DeepInfer 对照

## 常见坑

- 排序是 O(n log n)，每步做一次。2.5 会算这笔账，现在先不优化。
- 抢占一个请求后，它释放的 block 可能还是不够当前这个，要循环踢。
- 被抢占后回到 waiting **队头**，不是队尾，否则它会被新请求饿死。
- 2.2 的水位线和这一节互相影响：水位线越低，抢占越少，但 batch 越小。报告里可以扫一下。
