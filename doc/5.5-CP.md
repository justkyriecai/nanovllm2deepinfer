# 5.5：一个 64k 的 prompt，七张卡陪跑

> 起点：5.4 做完的代码　轴：6 分布式 / 3 计算

## 发现问题

**关注什么**：长 prompt 的 prefill 在 DP 下的代价。

```bash
python -m bench.launch_dp --dp 8 --ep 8 -- bench.run --scenario mixed_long_short --prompt-len 65536 --per-rank-seed
```

**先预测**：rank 0 收到一个 64k 的 prompt，它一步 prefill 要多久？这一步里其它 rank 在做什么？TTFT 是多少？

**现象**：

- 64k prompt 单卡 prefill 几秒（attention 是二次的，MoE 是线性的）。这几秒里其它 7 个 rank 要么陪跑空 prompt 步（5.3 投了 ANY），要么它们自己的 decode 全部停住（5.3 投了 ALL 之后大家一起做）。
- TTFT 由单卡算力决定，8 张卡对它没帮助。
- 2.2 的 chunked prefill 把它切成 2k 的块交替做，TTFT 更长，只是 decode 不被饿死。

## 分析问题

- **追问链**：长 prompt 单卡算 → 把一个 prompt 的 token 切给多张卡算（CP）→ attention 需要全部 K / V：每张卡算自己那段 query，K / V 要 all-gather → 因果 attention 下后面的 token 要看前面全部，均匀切分前面的卡轻后面的卡重 → zigzag：序列切成 `2 × cp` 块，rank r 拿块 r 和 `2cp − 1 − r`，每张卡的工作量相等 → all-gather 用拷贝引擎（不占 SM），发出后立刻算 q 投影，等到要用时才 wait → MoE 不受影响（每张卡的 token 各自路由，EP 照常）→ decode 不用 CP（每序列只有 1 个 token，没东西可切）→ 调度器要让每个序列的 chunk 长度对齐到 `2 × cp`。
- **本质**：CP 是 prefill 专用的并行：按 token 切 query，K / V all-gather。它不改变总算力，但把一个请求的延迟分到 `cp` 张卡上。和 TP 的区别：TP 每层两次 allreduce（输出），CP 每层一次 all-gather（输入 KV），而且 all-gather 可以用拷贝引擎、可以提前发。
- **量化**：64k prompt、cp = 8：每卡 8k 个 query，attention 计算 1/8（zigzag 下均衡），KV all-gather 每层 `64k × 576 × 2 B ≈ 75 MB`，NVLink 下 200 µs 量级，和 q 投影重叠。TTFT 接近 1/8。
- **理论**：`reference/gpu-perf-engineering-resources/` §4 "Long context and multimodal inference"：Ring Attention（分布式精确 attention，CP 的起点；DeepInfer 用 all-gather 而不是环传递，因为 MLA 的 KV 只有一个头、很小）；§5 "Parallelism, collectives, and topology"。
- **DeepInfer 怎么做**：
  - **进程**：CP > 1 时引擎 spawn `cp_size − 1` 个 follower 进程（`llm_engine.py:377-395`），它们跑 `start_slave_worker_loop`（`base.py:129`）：阻塞在 `cp_broadcast_object`，收到 `(method, kwargs)` 就调。driver 的 `run_workers`（`base.py:290`）先在 cp 的 gloo 组上广播方法名再自己执行。广播用 `MessageQueue`（`distributed/shm_broadcast.py:162`）：POSIX shm 无锁环 + ZMQ 溢出通道。调度器只在 cp0。
  - **输入广播**：`model_runner.py:200-215`：driver 把 `input_metadata` 和采样输入广播给 follower（`broadcast_tensor_dict`）。
  - **zigzag 镜像** `prepare_cp_mirror`（`tilelang_ops/prepare_cp_mirror.py:11`，参考实现 `:126`）：序列切成 `2cp` 块，rank r 拿块 `r` 和 `2cp − 1 − r`；输出 `mirror_cp_index [cp_mirror_len]`（本 rank 的 token 在原 varlen 布局里的下标，-1 是 pad）、`mirror_cp_reverse_index [total_q]`（反向）、每个 token 的 `ks / ke`（它能看到的压缩 KV 范围）。`InputMetadata.prepare_for_mirror_cp`（`input_metadata.py:170`）在模型开头调一次，把 `positions`、`ngram_token_ids`、`gate_force_random` 按镜像重排，`valid_token_mask = mirror_cp_index != -1`。
  - **调度对齐**：`cp_align = 2 × cp_size`（`scheduler.hpp:90`），chunk 的 token 数向上对齐到它（`:470-471`、`:515`），保证每个序列能被均匀切成 `2cp` 块。
  - **all-gather**：`CPManager`（`parallel_utils/cp.py:9`）包 DeepEP 的 `BucketBuffer`（README "Bucket collectives"，all-gather 由拷贝引擎驱动，`num_sms = 0`）；`allocate_cp`（`userbuffer.py:97`）按 `max_num_tokens × max_ag_bytes_per_token × cp` 算 buffer；`cp_session()` 内 `all_gather(x)` 返回一个**可调用**（`:42`），调用时才 `wait()` 并拼成 `[cp × n, …]`；`get_inplace_tensor`（`:36`）让 producer 直接写进 buffer 省一次拷贝。
  - **在 attention 里**（`attn.py:783-830`）：`cp_session` 内先发 `projected_kv` 的 all-gather（`_make_cp_gather_getter`，`:54`），然后算 q 投影、SWA KV（也 all-gather），再 `wait_projected_kv()` 做压缩和存储；gather 回来的 KV 用 `mirror_cp_reverse_index` 恢复原序（`gather(wait_kv_swa(), reverse_index)`，`:828`）。每层每张卡的 `get_max_ag_bytes_per_token`（`:375`）决定 buffer 大小。
  - **YoCo 下的 CP**：4.5 的边界收缩要先 all-gather 再按 `yoco_cp_boundary_index` 选（`yoco.py:62-78`，`yoco_cp_boundary_fused`，`prepare_cp_mirror.py:79`）。
  - **DFlash 的 follower**：decode 时 CP 组的 follower 只跑 forward 不采样（`dflash.py:359-364`，`cp_broadcast_multi_tensor`）。
  - **decode 不切**：`world = dp × cp`，decode 时 CP 组内每个 rank 跑同样的 batch（follower 是 driver 的镜像），只有 prefill 的 query 被切。

**思考题**：cp = 8、64k prompt，如果不 zigzag、按顺序均匀切成 8 段，rank 0 和 rank 7 的因果 attention 工作量差多少倍？zigzag 之后每张卡拿块 r 和 `2cp − 1 − r`，为什么两块加起来刚好相等？

## 解决问题

### 任务 A：follower 进程和输入广播（约 40 分钟，你写约 100 行）

- **目标**：`Config.context_parallel_size > 1` 时引擎 spawn `cp_size − 1` 个 follower，driver 每步先广播 `(method, kwargs)` 再自己执行；follower 收到 driver 的 `input_metadata` 和采样输入跑同样的 forward，不采样、不 post-process；decode 吞吐不受 CP 影响。
- **思路**：对回"调度器只在 cp0"和"decode 不切，follower 是 driver 的镜像"。follower 跑 slave loop：阻塞在广播上，收到方法名就调；driver 的 `run_workers(method, kwargs)` 先广播再执行。广播先用 `torch.distributed.broadcast_object_list`（gloo），验收过了再换 shm 环（照 `shm_broadcast.py`）。decode 时 follower 跑和 driver 一样的 batch（输入广播），输出丢弃；DFlash 的 draft forward 同样。
- **已备好**：`Config.context_parallel_size`；`world = dp × cp`、`rank = engine_rank × cp_size + cp_rank` 在 5.1 分组里的位置；follower 的 spawn 骨架和 `start_slave_worker_loop` 的壳；`tests/test_5_5.py` (e) 5.4 全过。
- **你写什么**：`run_workers` 的广播 + 执行；slave loop 的接收 + 分发；`model_runner` 里 driver 广播 `input_metadata` 和采样输入、follower 跳过采样和 post-process 的分支。最容易写错的一处：follower 收到的 `input_metadata` 是 driver 的，但 `cp_rank` 不同，任务 B 的 `prepare_for_mirror_cp` 必须在每个 rank 上各自算，不能在 driver 上算完再广播。
- **改哪里**：

  | 文件 | 函数 | 做什么 |
  |---|---|---|
  | `nanovllm/engine/llm_engine.py` | `__init__` | spawn `cp_size − 1` 个 follower |
  | `nanovllm/engine/worker.py` | `run_workers`、`start_slave_worker_loop` | 先广播 `(method, kwargs)` 再执行；follower 阻塞接收 |
  | `nanovllm/engine/model_runner.py` | `run` | driver 广播输入；follower 不采样、不 post-process；DFlash draft forward 同样 |

### 任务 B：zigzag 镜像和调度对齐（约 40 分钟，你写约 100 行）

- **目标**：`prepare_cp_mirror` 给出 `mirror_index / reverse_index / ks / ke`，和参考实现一致（含 pad 和多序列）；zigzag 下各 rank 的因果 attention FLOPs 相等；调度器的 chunk 长度都是 `2cp` 的倍数。
- **思路**：对回"均匀切分前面的卡轻后面的卡重，zigzag 让每张卡的工作量相等"。序列切成 `2cp` 块，rank r 拿块 r 和 `2cp − 1 − r`；`mirror_cp_index` 是本 rank 的 token 在原 varlen 布局里的下标（-1 是 pad），`reverse_index` 反向，`ks / ke` 是每个 token 能看到的压缩 KV 范围。要让每个序列能被均匀切成 `2cp` 块，调度器的 chunk 要向上对齐到 `cp_align = 2 × cp`。`InputMetadata.prepare_for_mirror_cp` 在模型开头调一次，把 `positions` 等按镜像重排，`valid_token_mask = mirror_cp_index != -1`。先照 `prepare_cp_mirror_ref` 写 Python 版，再 Triton。
- **已备好**：`nanovllm/layers/cp_mirror.py` 的函数签名和 `prepare_cp_mirror_ref` 的测试对拍；`scheduler.hpp` 里 `cp_align` 的字段；`tests/test_5_5.py` (a) `prepare_cp_mirror` 和 `prepare_cp_mirror_ref` 一致，含 pad 和多序列、(b) zigzag 下各 rank 的因果 attention FLOPs 相等（按 `ke − ks` 求和）、(d) `cp_align` 下 chunk 长度都是 `2cp` 的倍数。
- **你写什么**：`prepare_cp_mirror` 的 Python 版和 Triton 版；`_schedule_prefill` 里 chunk 长度对齐到 `cp_align`；`prepare_for_mirror_cp` 的重排。最容易写错的两处：zigzag 的两块在原序列里不相邻，`positions` 必须按 `mirror_index` 重排，RoPE 才对；`cp_align` 让短 prompt 也被 pad 到 `2cp` 的倍数，`valid_token_mask` 要传给 MoE 的 gate，pad 行不参与路由统计（`mlp.py:382`）。
- **改哪里**：

  | 文件 | 函数 | 做什么 |
  |---|---|---|
  | `nanovllm/layers/cp_mirror.py`（新建） | `prepare_cp_mirror` | `mirror_index / reverse_index / ks / ke`，先 Python 后 Triton |
  | `csrc/scheduler.hpp` | `_schedule_prefill` | `cp_align = 2 × cp`，chunk 长度对齐 |
  | `nanovllm/engine/input_metadata.py` | `prepare_for_mirror_cp` | 重排 `positions` 等，`valid_token_mask` |
  | `nanovllm/layers/moe.py` | gate | pad 行不参与路由统计 |

### 任务 C：KV all-gather 和 attention 里的延迟 wait（约 40 分钟，你写约 120 行）

- **目标**：`cp.all_gather(x) -> callable`，`cp_session()` 内发出、调用时才 wait；attention 里先发 KV 的 all-gather → 算 q → wait → 压缩 / 存储 / attention；cp = 8 和 cp = 1 在同样 prompt 上 `greedy_match` 一致，YoCo compact + CP 的输出和 `off` 一致。
- **思路**：对回"all-gather 用拷贝引擎，发出后立刻算 q 投影，等到要用时才 wait"。先用 `dist.all_gather_into_tensor`（NCCL，占 SM）做对，再换 DeepEP `BucketBuffer`（拷贝引擎，`num_sms = 0`）；buffer 按 `max_num_tokens × max_ag_bytes_per_token × cp` 算。attention 里 SWA KV 同样 all-gather；gather 回来的顺序是 `[rank0 的块 | rank1 的块 | …]`，要按 `reverse_index` 恢复原序。4.5 的 YoCo 边界在 CP 下要先 all-gather 再按 `yoco_cp_boundary_index` 选。
- **已备好**：`nanovllm/distributed/cp.py` 的 `CPManager` 骨架、`cp_session()` 上下文、`allocate_cp` 的 buffer 计算（照 `userbuffer.py:97`）；`get_max_ag_bytes_per_token` 每层的值；`tests/test_5_5.py` (c) all-gather + reverse_index 恢复原序是恒等。
- **你写什么**：`all_gather(x)` 返回可调用的那段（先 NCCL 版，再 `BucketBuffer` 版）；attention forward 里发 / 算 q / wait / `reverse_index` 恢复的顺序；YoCo 边界收缩在 CP 下的分支。最容易写错的两处：任何按位置用 KV 的地方（压缩状态、存 cache）都要先过 `reverse_index`，直接用 gather 回来的顺序会把 KV 存错位置；`cp_session` 内 all-gather 的结果是 buffer 的视图，下一个 session 会复用，要用的话在 session 结束前拷走。
- **改哪里**：

  | 文件 | 函数 | 做什么 |
  |---|---|---|
  | `nanovllm/distributed/cp.py`（新建） | `CPManager.all_gather`、`cp_session` | 返回可调用，调用时才 wait；NCCL → `BucketBuffer` |
  | `nanovllm/distributed/userbuffer.py` | `allocate_cp` | buffer 大小 |
  | `nanovllm/layers/attention.py` | `forward` | 发 KV all-gather → q 投影 → wait → `reverse_index` → 压缩 / 存储；SWA KV 同样 |
  | `nanovllm/layers/yoco.py` | 边界收缩 | 先 all-gather 再按 `yoco_cp_boundary_index` 选 |

## 验收

同一个实验重跑（cp = 8，dp = 1，ep = 8，或 cp = 2 × dp = 4）：

1. 64k prompt 的 TTFT 接近单卡的 1/cp；报告里给 cp = 1 / 2 / 4 / 8 的曲线。
2. Nsight：KV all-gather 和 q 投影重叠；换成拷贝引擎后 all-gather 不占 SM。
3. 正确性：cp = 8 和 cp = 1 在同样 prompt 上 `greedy_match` 一致，KL 通过；YoCo compact + CP 的输出和 `off` 一致。
4. decode 吞吐不受 CP 影响（follower 是镜像）。
5. `tests/test_5_5.py`：(a) `prepare_cp_mirror` 和 `prepare_cp_mirror_ref` 一致，含 pad 和多序列；(b) zigzag 下各 rank 的因果 attention FLOPs 相等（按 `ke − ks` 求和）；(c) all-gather + reverse_index 恢复原序是恒等；(d) `cp_align` 下 chunk 长度都是 `2cp` 的倍数；(e) 5.4 全过。
6. **解释**（由你说）：TTFT 为什么接近 1/cp 而不是正好 1/cp，差的那部分是什么？decode 吞吐为什么不变？cp = 8 时 all-gather 的量是 cp = 2 的多少倍，它为什么没有体现在 TTFT 曲线上？

**新浮现的问题**：prefill 和 decode 的资源需求不同（算力 vs 显存和带宽），却挤在同一批卡上互相干扰；DeepInfer 有 PROMPT / COMPLETION 两种引擎类型和 `prompted` 队列。这是 5.6。

## 常见坑

- zigzag 的两块在原序列里不相邻，`positions` 必须按 `mirror_index` 重排，RoPE 才对。
- all-gather 回来的顺序是 `[rank0 的块 | rank1 的块 | …]`，不是原序；任何按位置用 KV 的地方（压缩状态、存 cache）都要先过 `reverse_index`。
- `cp_session` 内 all-gather 的结果是 buffer 的视图，下一个 session 会复用；要用的话在 session 结束前拷走。
- follower 收到的 `input_metadata` 是 driver 的，但 `cp_rank` 不同，`prepare_for_mirror_cp` 在每个 rank 上各自算。
- `cp_align` 让短 prompt 也被 pad 到 `2cp` 的倍数，`valid_token_mask` 要传给 MoE 的 gate（pad 行不参与路由统计，`mlp.py:382`）。
