# 5.2：all-to-all 占满 SM，和计算串行

> 起点：5.1 做完的代码　硬件：8×H100，DeepSeek-V2-Lite　预计改动：400–600 行　轴：6 分布式 / 3 通信与计算重叠

## 1. 发现问题

**关注什么**：5.1 的 all-to-all 在时间线上长什么样。

```bash
nsys profile -o out/ep8 python -m bench.launch_dp --dp 8 --ep 8 -- bench.run --scenario steady_decode --max-num-seqs 256 --num-steps 20
```

**先预测**：一层 MoE 里 dispatch、专家 GEMM、combine 各占多少时间？它们之间有没有重叠？通信 kernel 用了多少个 SM？

**现象**：

- NCCL 的 all-to-all kernel 占满所有 SM，前后的 GEMM 只能等它结束；一层 MoE 的时间 = 通信 + 计算，没有任何重叠。
- shared expert 的 GEMM 和 routed expert 的 combine 互不依赖，却也在串行。
- 2.7 的 CUDA graph 捕获不了 NCCL 的 all-to-all（split sizes 每步变），decode 只能 `enforce_eager`，2.5 省下来的 launch 开销又回来了。
- split sizes 的交换本身是一次同步的小通信，CPU 要等它回来才能发大的 all-to-all，ZOS 的"每步一次同步"被打破。

## 2. 分析问题

- **追问链**：通信和计算串行 → 通信 kernel 独占 SM → 把通信限制在少量 SM 上，剩下的 SM 跑和它无关的计算（shared expert）→ 通信 kernel 要知道每个 token 去哪个 rank，不需要 CPU 先交换计数（kernel 内部算）→ buffer 固定大小、地址固定，才能进 CUDA graph → 发送的是 FP8 + scale，接收端直接是 grouped GEMM 要的连续布局（按专家分段、对齐到 GEMM 的 tile）→ combine 把 shared expert 的输出当 bias 顺便加上 → 这就是 DeepEP 的 `EPBuffer`。
- **本质**：EP 的通信和计算要重叠，必须满足三件事：通信只用一部分 SM、通信的元数据在 GPU 上算、通信的 buffer 在 graph 里地址固定。NCCL 的通用 all-to-all 三件都不满足。
- **量化**：H100 132 个 SM，DeepEP 按拓扑和通信量估算通信 SM 数（`get_theoretical_num_sms`），DeepInfer 再保证计算至少有 `min(32, SM/4)` 个（`userbuffer.py:87-89`）。shared expert 的 GEMM 在剩下的 SM 上跑，时间和 combine 重叠。
- **理论**：`reference/gpu-perf-engineering-resources/` §5 "Mixture-of-experts serving"：DeepEP（dispatch / combine kernel 的设计）、MegaScale-Infer（通信计算重叠的系统视角）；§5 "Parallelism, collectives, and topology"：NCCL 设备侧通信 API（DeepEP 的 NCCL Gin 后端就是它）。DeepEP 的 README（`reference/DeepInfer/vendor/DeepEP/README.md:103-290`）是直接的接口文档。
- **DeepInfer 怎么做**：
  - **buffer 单例** `userbuffer`（`parallel_utils/userbuffer.py:54`，`_UserBufferManager`）：进程级持有 `ep / cp / engram / sym_buffers`。`allocate_ep`（`:63`）建一个 `EPBuffer(group, num_max_tokens_per_rank, hidden, num_topk, use_fp8_dispatch, allow_hybrid_mode, allow_multiple_reduction)`；`num_max_tokens_per_rank` 取 prefill / decode 的最大值，一个 buffer 两种步都用；已经有且够大就复用。`allow_multiple_reduction` 在 batch-invariant + EPLB 时关掉（2.12）。
  - **SM 数**：`DEEPINFER_USERBUFFER_COMM_SMS`（`environ.py:109`）为 0 时自动算：`min(buffer 的理论值, 总 SM − min(32, 总 SM/4))`（`:87-89`）。
  - **dispatch**（`mlp.py:461`）：`ep_buffer.dispatch(x, num_sms, topk_idx, topk_weights, cumulative_local_expert_recv_stats=eplb.expert_count, num_experts, num_max_tokens_per_rank, expert_alignment=deep_gemm 的对齐, previous_event, async_with_compute_stream=True, allocate_on_comm_stream, do_handle_copy=False, do_cpu_sync=…, do_expand=True, use_tma_aligned_col_major_sf=True, defer_epilogue=True)`，返回 `EventOverlap`；`.current_stream_wait()` 给 `(recv_x, recv_topk_idx, recv_topk_weights, handle)`，`handle.psum_num_recv_tokens_per_expert` 直接给 grouped GEMM。`do_cpu_sync` 只在 YoCo compact 的 prefill 之外开（`:482-486`）。`expert_count` 由 dispatch kernel **免费**写（5.4）。
  - **combine**（`:493`）：`ep_buffer.combine(x, handle, num_sms, bias=shared_out, previous_event, async_with_compute_stream, allocate_on_comm_stream, defer_epilogue)`。
  - **重叠**（`:565-616`）：dispatch → wait → routed GEMM → `combine_pre_evt = ep_buffer.capture()` → `with limit_num_sms(COMM_SMS)`（`userbuffer.py:40`，把 DeepGEMM 和 TileKernels 的 SM 上限调低）跑 `shared_forward` → combine 以 `previous_event = combine_pre_evt` 发出、`bias = shared_out` → wait。shared expert 的 GEMM 和 combine 真正并行。
  - **FP8 dispatch**：`use_fp8_dispatch = use_fp8_act`，发的是 3.3 的 `(fp8, sf)`，scale 按 TMA 列主序布局，接收端直接喂 `m_grouped_fp8_fp4_gemm_nt_contiguous`。
  - **有序销毁** `close`（`:227`）：`ep / cp / engram` 先 destroy，再逆序 destroy sym buffers；`WorkerBase.stop`（`base.py:135`）把它夹在两个 `dist.barrier()` 之间，否则 `os._exit` 跳过析构会让对端卡在析构的 barrier 上。
  - **Mega MoE 在 B200 上不走这条路**（4.9，通信在 kernel 内），H100 上走。

## 3. 要做什么

### 3.1 buffer 单例

**新建** `nanovllm/distributed/userbuffer.py`。

- `userbuffer.allocate_ep(group, max_num_tokens, hidden, num_topk, num_experts, use_fp8_dispatch)`：`max_num_tokens = max(max_num_batched_tokens, max_num_seqs × (nextn + 1))`；自动算通信 SM 数；`close()` 有序销毁，`Worker.stop` 两个 barrier 之间调。
- `limit_num_sms(n)` 上下文：DeepGEMM `set_num_sms`，自己的 Triton kernel 也按这个数设 grid 上限。

### 3.2 换 dispatch / combine

**改哪里**：`nanovllm/layers/moe.py`。

- 5.1 的 `dispatch / combine` 接口不变，实现换成 `EPBuffer`：`defer_epilogue=True` + `async_with_compute_stream=True`，用 `EventOverlap.current_stream_wait()`。
- `expert_alignment` 传 DeepGEMM 的 `get_mk_alignment_for_contiguous_layout()`；`handle.psum_num_recv_tokens_per_expert` 直接给 3.2 的 grouped GEMM，去掉 5.1 的计数交换。
- FP8：dispatch 发 `(fp8, sf)`，`use_tma_aligned_col_major_sf=True`。

### 3.3 重叠 shared expert

- `combine_pre_evt = ep_buffer.capture()` → `limit_num_sms` 下跑 shared expert → combine 带 `bias=shared_out`、`previous_event=combine_pre_evt`。
- 2.12 的 batch-invariant：`allow_multiple_reduction=False` 时 combine 的归约顺序固定。

### 3.4 CUDA graph

- buffer 地址固定，dispatch / combine 可以捕进 2.8 的按 `total_q` 分桶的 graph；`do_cpu_sync=False` 的 decode 路径不同步。prefill 保持 eager。

## 4. 验收

1. 同一个实验重跑：Nsight 里 shared expert 的 GEMM 和 combine 重叠；一层 MoE 的时间低于"通信 + 计算"之和；通信 kernel 只占设定的 SM 数。报告给前后对比。
2. decode 回到 CUDA graph：`gpu_forward` 的 launch 空隙回到 2.8 的水平。
3. ZOS：每步仍然只有一次同步（1.1 的 `cpu_*` 段里没有新的等待）。
4. 正确性：`greedy_match` 和 KL 与 5.1 一致；batch-invariant 模式下 8 卡输出逐 token 稳定。
5. `tests/test_5_2.py`：(a) `EPBuffer` dispatch → combine 恒等；(b) FP8 dispatch 后接收端的 `(fp8, sf)` 和本地 cast 一致；(c) combine 的 `bias` 路径和"先 combine 再加"一致；(d) `close` 在多进程下不挂；(e) 5.1 全过。

**新浮现的问题**：把 `bench` 的负载改成各 rank 不同（一个 rank 来了长 prompt，其它在 decode），引擎卡死：一个 rank 在 prefill 的 all-to-all 里等，其它 rank 在 decode 的 all-to-all 里等，两边永远凑不齐。这是 5.3。

## 常见坑

- `num_max_tokens_per_rank` 所有 rank 必须一致（DeepEP README），而且要覆盖 prefill 的 `max_num_batched_tokens`；小了是静默越界。
- `previous_event` 和 `allocate_on_comm_stream=True` 必须成对，否则通信 stream 上分配的 buffer 和计算 stream 的生命周期对不上。
- `limit_num_sms` 只对 DeepGEMM / TileKernels 生效，自己的 Triton kernel 要自己限 grid，否则 shared expert 还是把 SM 抢光。
- `EventOverlap` 的结果由第一次 `wait()` 产生，之后要自己保留引用；在 graph 里 wait 的位置要固定。
- 关机顺序：先 barrier、再 `close`、再 barrier、再 destroy graph、再 `destroy_process_group`；顺序错了会挂在 NCCL 的析构上（`base.py:135-152` 的注释给了 PyTorch issue 链接）。
