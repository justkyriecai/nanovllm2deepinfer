> 起点：2.12 做完的代码　轴：4 模型结构

第 3 章换模型。Qwen3-8B 是标准的 GQA + dense MLP，第 2 章把它的控制面做到了和 DeepInfer 一样。接下来三节把模型本身换成 DeepSeek 家族的结构：MLA（本节）、MoE（3.2）、FP8（3.3）。V2-Lite 是 Qwen3 和 V4 之间最近的中间站：有 MLA 和 MoE，单卡放得下，HF 上有 bf16 权重。

第 3 章开始，验收多了一把尺子：**KL**。新模型第一次接入，先用 HF `transformers` 做外部背书：同一个 prompt，我们的 logprob 和 HF 的 logprob 之间的 KL 要小于阈值（1.1 的 `teacher_forced_nll` 是它的前身）。接上之后，2.12 做好的两道检查为新模型重做一遍：逐位相等的黄金文件，和 `tests/kl.py` 的 decode / prefill 自洽（DeepInfer 的 `tests/models/test_kl.py` 验的就是后者，不是对 HF；`deepinfer/testing.py:4` 的 `cal_diff` 算 KL）。

## 发现问题

**关注什么**：每个 token 的 KV cache 占多少字节，它决定了同样显存下能开多大的 batch。

先不改任何代码，做一道算术题。1.1 做过一次 KV 容量分析，现在把它换算到更大的模型：

| 模型 | 层数 | KV 头 | head_dim | 每 token KV（bf16） | H100 80 GB 扣掉权重后能放的 token 数 |
|---|---|---|---|---|---|
| Qwen3-8B | 36 | 8 | 128 | 2 × 36 × 8 × 128 × 2 B = 147 KB | ~60 GB / 147 KB ≈ 40 万 |
| Qwen3-32B | 64 | 8 | 128 | 262 KB | ~15 GB / 262 KB ≈ 6 万 |
| Llama-3-70B | 80 | 8 | 128 | 327 KB | 单卡放不下权重 |
| DeepSeek-V2-Lite，**按 MHA 存** | 27 | 16 | 128（nope）+ 64（rope） | 2 × 27 × 16 × 192 × 2 B = 332 KB | ~45 GB / 332 KB ≈ 13 万 |

**先预测**：V2-Lite 只有 2.4B 激活参数，算力和访存都比 Qwen3-8B 便宜，但如果 KV 按 MHA 存，同样显存下并发只有 Qwen3-8B 的三分之一。2.3 的抢占实验在它上面会怎样？

然后做第一个实验：把 V2-Lite 的 attention 按"展开成 MHA"的方式接进来（把 `kv_b_proj` 应用到 latent 上得到完整的 K 和 V，然后走 2.12 之前的 flash-attn 路径，KV cache 存展开后的 K、V）。MoE 部分先用最朴素的 for 循环（3.2 再改）。跑：

```bash
python -m bench.run --scenario kv_pressure --model deepseek-ai/DeepSeek-V2-Lite
```

**现象**：`kv_pressure` 场景下抢占次数比 Qwen3-8B 高几倍，`max_num_seqs` 实际能跑到的上限只有一百多，吞吐被 KV 容量卡住。但看 HF 的 `config.json`：`kv_lora_rank = 512`，`qk_rope_head_dim = 64`。模型本身只需要每 token 存 **576 个数**（512 + 64），不是 16 × 192 × 2 = 6144 个。展开后存了 10 倍多的东西。

## 分析问题

- **追问链**：batch 开不大 → KV 太大 → 每个 head 都存一份 K 和 V → GQA 已经把 KV 头从 32 压到 8，还能不能再压 → 把所有头的 K、V 压到一个低秩的 latent 向量 c（512 维），需要时再用 `W_UK`、`W_UV` 投影回去 → 但"投影回去"在 decode 时每步都要做，算力花在哪里 → 把 `W_UK` 吸收进 query 一侧，`W_UV` 吸收进 output 一侧，attention 直接在 latent 空间做，**KV cache 只存 latent，decode 时不展开**。
- **本质**：MLA 把 KV cache 从 `num_kv_heads × head_dim` 压到 `kv_lora_rank + rope_dim`，代价是 attention 的 head_dim 变成 576（decode 时 q 要投到 latent 空间），attention 本身的计算和访存变成 MQA 形状：一个 KV 头，16（V4 是 64 / 128）个 query 头共享。这正是 FlashMLA 的目标形状。
- **量化**：V2-Lite 每 token KV 从 332 KB 降到 27 × 576 × 2 B = 31 KB，**10.7 倍**。同样 45 GB 能放 140 万 token。decode 时每步 attention 的访存从读 332 KB/token 变成读 31 KB/token。
- **理论**：`reference/gpu-perf-engineering-resources/` §4 "KV cache systems"：DeepSeek-V2 论文（MLA 的推导和权重吸收，附录里有 RoPE 为什么要单独分一条 64 维的路）；GQA 论文（为什么共享 KV 头精度损失小）。§2 Attention 里的 FlashAttention-3 解释了 Hopper 上 attention kernel 的结构，FlashMLA 是它的 MLA 特化。
- **RoPE 的麻烦**：权重吸收要求 `q·k = (x_q W_Q)(c W_UK)^T = x_q (W_Q W_UK^T) c^T`，RoPE 是位置相关的旋转，夹在 `W_Q` 和 `W_UK` 之间就吸收不了。所以 MLA 把 head_dim 分成两段：`qk_nope_head_dim = 128` 走吸收，`qk_rope_head_dim = 64` 单独投影、单独 RoPE、所有头共享一份 k_rope（存在 latent 旁边）。
- **DeepInfer 怎么做**（V4 的 MLA 和 V2 同构，多了压缩和稀疏，这里只看 MLA 的骨架）：
  - **参数容器** `LoraRopeCompressFlashMHAAutoRecomp`（`models/v4_modules/mla_attn.py:156`）：`Wq = ColumnParallelLora`（`:198`，`x → A → norm → B`，V4 有 q_lora，V2-Lite 没有，`q_lora_rank = None` 直接一个 `q_proj`）；`Wkv = ColumnParallelLora`（`:232`，只有 A，输出 `kv_lora_rank + rope_head_dim = 576`，后接 `DropoutAddRMSNorm`）；`Wv`（`:228`）是吸收后的 value 侧权重，`einsum_info = (n_wv_group, o_head_dim, wv_in_features)`。
  - **Q 侧吸收**：`_project_q_b`（`v4_modules/attn.py:453`）把 q 投到 `[num_heads, qk_head_dim]`，这里的 `qk_head_dim` 已经是 latent 维度 + rope 维度（V4 的 `q_b_proj` 直接出这个形状，权重是离线把 `W_Q` 和 `W_UK` 乘好的）。
  - **KV 只存 latent**：cache 的每 token 字节数是 `kv_lora_rank + rope` 的量化字节（`tilelang_ops/cache_common.py:100` `bytes_per_token`），V4 FP8 是 528 B/token（512 latent FP8 + 64 rope bf16 的 128 B 减去共享的 scale 布局，具体见 4.3）。
  - **attention kernel 是 MQA 形状**：decode 走 `flash_mla_with_kvcache`（`layers/attention_backend.py:125`，`head_dim_v = kv_lora_rank`，`is_fp8_kvcache`）；prefill 走 `flash_mla_sparse_fwd`（`:64`）。两者的 KV 输入都是 `[total_k, 1, head_dim]`：**一个 KV 头**。
  - **V 侧吸收**：`_wv_and_o_proj`（`attn.py:191`）在 attention 之后做 `deep_gemm.fp8_einsum("bhr,hdr->bhd")`（`:215`）：把每个头在 latent 空间的输出用 `W_UV` 投回 `v_head_dim`，再过 `out_proj`。V4 把 `n_head` 个头分成 `n_wv_group` 组共享 `W_UV`（`o_groups`），V2-Lite 是每头一份。
  - **prefill 不吸收**：prefill 时 q 和 k 的数量一样多，把 latent 展开成 `[total_k, num_heads, 192]` 再做标准 attention 更省算力（吸收后的 q·k 是 576 维，展开是 192 维，prefill 时 KV 是现算的，不用从 cache 读）。DeepInfer V4 的 prefill 因为有稀疏索引走的是 `flash_mla_sparse_fwd`，V2 时代（FlashMLA 的 dense prefill 和 vLLM/SGLang 的做法）是展开。这一节**prefill 展开、decode 吸收**。
  - **RoPE**：`rope.py:42` `build_rotary_emb`，V2-Lite 用 yarn（`:19` `RotaryEmbeddingYarn`，`mscale_all_dim`）。rope 只作用在 64 维那一段。

**思考题**：吸收后 decode 每个 query 头的点积从 192 维变成 576 维，算力是原来的 3 倍，为什么 decode 还是吸收更快？按 1.1 的算法，并发 256、上下文 4k 时，展开存法和 latent 存法 decode 一步 attention 各要读多少字节？

### 任务 B：KV cache 只存 latent（约 20 分钟，你写约 60 行）

- **目标**：cache 形状从 `[2, L, blocks, block_size, kv_heads, head_dim]` 变成 `[L, blocks, block_size, 1, 576]`，没有 V；V2-Lite 每 token KV 从 332 KB 变成 31 KB，`block_bytes` 按 576 算。**这是 1.1 的 KV 容量分析数字要重新算的地方。**
- **思路**：对回分析里的"KV 只存 latent"：cache 里存 `[c_kv (512) | k_rope (64)]`，k_rope 是 RoPE 之后的、所有头共享一份（MQA）。读的时候再展开：从 cache 读 latent（prefix cache 命中时）或用现算的 latent，乘 `kv_b_proj` 展开成 K、V。prefix cache（nano-vllm 的 xxhash 块复用）照常工作，因为 latent 位置无关、k_rope 已经 RoPE 过，命中后不用重算。
- **已备好**：`MLAAttention` 的类壳和它与 GQA 的 `Attention` 并存的分发（Qwen3 还要能跑）；`allocate_kv_cache` 的新形状和 `block_bytes` 的报告格式。
- **你写什么**：`allocate_kv_cache` 按 576 算；`store_kvcache` 存 `[c_kv | k_rope]`；`MLAAttention` 的展开路径：乘 `kv_b_proj` 展开后走 `flash_attn_varlen_func`，`head_dim = 192`（q 和 k）、`v_head_dim = 128`（flash-attn 要求 qk 和 v 同维，V 补零到 192 或用支持不等维的版本）。这一步 prefill 和 decode 都走展开，任务 C 把 decode 换成吸收。最容易错的一处：k_rope 存 cache 时只存一份，展开时要 broadcast 到每个头。
- **改哪里**：

  | 文件 | 函数 | 做什么 |
  |---|---|---|
  | `nanovllm/engine/model_runner.py` | `allocate_kv_cache` | `[L, blocks, block_size, 1, 576]`，`block_bytes` 按 576 |
  | `nanovllm/layers/attention.py` | `store_kvcache`、`MLAAttention` | 存 latent + k_rope；读时展开 |

### 任务 C：decode 权重吸收 + FlashMLA（约 40 分钟，你写约 120 行）

- **目标**：decode 走 `flash_mla_with_kvcache`，q 投到 576 维 latent 空间，KV 不展开；展开路径和吸收路径在同一组输入上输出一致（`atol` 按 bf16 定）。
- **思路**：对回分析里的"Q 侧吸收 / V 侧吸收"。启动时（权重装完后）做一次吸收：把 `kv_b_proj` 拆成 `W_UK [heads, 128, 512]` 和 `W_UV [heads, 128, 512]`。decode 时 `q_nope [heads, 128]` 先乘 `W_UK` 得到 `q_latent [heads, 512]`，拼上 `q_rope [heads, 64]`，变成 `[heads, 576]`；FlashMLA 输出 `[heads, 512]` 乘 `W_UV` 得到 `[heads, 128]`，再 `o_proj`。这一步就是 DeepInfer 的 `fp8_einsum("bhr,hdr->bhd")`，我们先用 `torch.einsum` 或 `bmm`。prefill 仍然走任务 B 的展开路径（KV 是现算的，不用从 cache 读，192 维比 576 维省算力）。
- **已备好**：FlashMLA 的安装和调用壳；block_size 改成 64（nano-vllm 的 block 是 256，FlashMLA 要求 64 的倍数，block table 要能表达：把 256 的块当 4 个 64 的子块，或者把 block_size 改成 64，后者简单）；CUDA graph 下按最大 batch 准备 metadata 的固定 buffer（2.9 的 `get_mla_metadata` 和 CUDA graph：metadata 依赖 `cache_seqlens`，graph 里要用固定 buffer 的版本，FlashMLA 提供按最大值准备的接口，这和 2.7 的"GPU 上准备元数据"是同一类问题）；2.12 的 batch-invariant 开关到 FlashMLA `enable_batch_invariant` 的传递（V4 的用法在 `attention_backend.py:141`）。
- **你写什么**：吸收（权重拆分、q 投影、输出投回）；decode 分支：`flash_mla.get_mla_metadata(cache_seqlens, num_heads_q, num_heads_k=1)` 得到 `tile_scheduler_metadata, num_splits`，`flash_mla_with_kvcache(q[B,1,heads,576], kv_cache[blocks, block_size, 1, 576], block_table, cache_seqlens, head_dim_v=512, ...)`。FlashMLA 的 Hopper 版本原生支持 bf16 latent cache。最容易错的两处：吸收后 `q_latent` 的 softmax scale 仍然是 `1/sqrt(128 + 64)`（原始 qk head_dim），不是 `1/sqrt(576)`，yarn 的 `mscale` 还要再乘上去；`num_splits` 和 `tile_scheduler_metadata` 在 batch 变化时要重新算。
- **改哪里**：

  | `nanovllm/layers/attention.py` | `MLAAttention` decode 分支 | q 投 latent、FlashMLA、`W_UV` 投回 |
  | `nanovllm/engine/model_runner.py` | block_size、CUDA graph 的 metadata buffer | 已备好，核对 |

## 验收

1. 同一个实验重跑：V2-Lite 的每 token KV 从 332 KB 变成 31 KB，`kv_pressure` 场景下抢占次数归零（或和 Qwen3-8B 相当），`max_num_seqs` 能开到几百。写进报告，附 1.1 的容量算式。
2. KL：`tests/kl.py` 对 HF 的 KL 和任务 A 的基线相当（不能因为吸收变差；吸收后多了一次 bf16 的矩阵乘，KL 允许略增但在 1e-3 量级）。`greedy_match` 和黄金文件一致。
3. decode 吞吐：并发 256 时 `gpu_forward` 的 attention 部分比展开版本快（Nsight 看 attention kernel 的时间）；报告里给数字。
4. Qwen3-8B 的全部回归通过（两种 attention 并存）。
5. `tests/test_3_1.py`：(a) 展开路径和吸收路径在同一组随机输入上输出一致（`atol` 按 bf16 定）；(b) FlashMLA 的输出和 PyTorch 参考实现（latent 展开后做 softmax attention）一致；(c) 同一请求 prefill 结束后第一个 decode token 和 HF 一致；(d) yarn RoPE 和 HF 实现数值一致；(e) 2.1–2.12 的测试在 Qwen3 上仍然全过。
6. **解释**（由你说）：每 token KV 降 10 倍为什么抢占归零；decode 的 q·k 从 192 维变成 576 维，attention kernel 为什么反而更快；吸收多了一次 bf16 矩阵乘，为什么 KL 允许略增、上限却仍是 1e-3 量级。

**新浮现的问题**：V2-Lite 只有 2.4B 激活参数，但 decode 每步的 `gpu_forward` 比 Qwen3-8B 没快多少，Nsight 里 MoE 的 for 循环是几十个小 GEMM 串在一起，每个专家只分到几个 token。这是 3.2。

| yarn RoPE | `RotaryEmbeddingYarn`（`rope.py:19`） | 一致 |
| 一种 cache | 7 种 cache（4.1） | |

## 常见坑

- `kv_b_proj` 的输出排布是 `[heads, nope + v]` 交错的，拆 `W_UK` / `W_UV` 时按头拆，不是前一半后一半。
- 吸收后 `q_latent` 的 scale：softmax scale 仍然是 `1/sqrt(128 + 64)`（原始 qk head_dim），不是 `1/sqrt(576)`；yarn 的 `mscale` 还要再乘上去。
- k_rope 是所有头共享的一份（MQA），存 cache 时只存一份；展开时要 broadcast 到每个头。
- prefix cache（nano-vllm 的 xxhash 块复用）在 latent cache 上照常工作，因为 cache 里存的是位置无关的 latent + 已经 RoPE 过的 k_rope，命中后不用重算。
- FlashMLA 的 `num_splits` 和 `tile_scheduler_metadata` 在 batch 变化时要重新算，CUDA graph 下按最大 batch 准备。2.12 的 batch-invariant 开关要传给 FlashMLA 的 `enable_batch_invariant`（V4 的用法在 `attention_backend.py:141`）。
- HF 的 `DeepseekV2` 实现要用 `trust_remote_code`，算 KL 时注意它默认的 attention 实现和 dtype，对拍要同为 bf16。
