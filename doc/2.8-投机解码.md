# 2.8：低并发时算力闲着

> 起点：2.7 做完的代码　轴：3 解码加速

| | |
|---|---|
| **问题** | 并发从 1 到 64，`gpu_forward` 都在 15–25 ms 不变；并发 1 时一步只产 1 个 token，算力用了千分之一，时间全花在从 HBM 读一遍 16 GB 权重上。根因是 decode 是访存瓶颈，算力有富余；投机解码用一个便宜的 draft 先猜几个 token，大模型一步验证，用富余的算力换 token |
| **实验** | `for n in 1 4 16 64 256; do python -m bench.run --scenario steady_decode --max-num-seqs $n; done`，盯 `gpu_forward` 随并发的变化和并发 1 时的吞吐 |
| **硬件 / 费用** | 1×H100 + Qwen3-8B + `RedHatAI/Qwen3-8B-speculator.eagle3`。H100 $3.95/h，五档并发反复扫加验证 kernel 对拍约 5 小时，约 $20 |
| **学到** | 一步 decode 的时间由读权重决定、和 token 数几乎无关，所以多验证几个 token 近乎免费；拒绝采样让输出分布和不投机时精确一致，接受率只影响速度不影响正确性；ZOS 下 CPU 不知道上一步接受了几个，`seqlen_k` 要在 GPU 上修、inflight 上界每步加 `nextn+1` |
| **时长** | 发现 + 分析约 2 小时；任务 A 约 60 分钟、B 约 40 分钟、C 约 50 分钟；验收约 1.5 小时。改动约 500–800 行 |

## 发现问题

**关注什么**：并发很低时，一步 decode 的 GPU 时间和它产出的 token 数。

```bash
for n in 1 4 16 64 256; do python -m bench.run --scenario steady_decode --max-num-seqs $n; done
```

**先预测**：并发从 1 到 256，`gpu_forward` 怎么变？吞吐怎么变？并发 1 时 H100 的算力用了百分之几？

**现象**：`gpu_forward` 从并发 1 到 64 几乎不变（都在 15–25 ms），吞吐随并发线性涨。并发 1 时每步只产 1 个 token，算一下 FLOPs：8B 参数 × 2 × 1 token ≈ 16 GFLOP，20 ms，不到 1 TFLOPS，H100 有 1000 TFLOPS。**算力用了千分之一**；这一步的时间全花在从 HBM 读一遍 16 GB 权重上。

## 分析问题

- **追问链**：低并发吞吐低 → 每步只产 1 token → 每步时间由读权重决定（访存瓶颈），和 token 数无关 → 如果一步能验证多个 token，几乎不多花时间 → 需要一个便宜的方法先猜出几个 token，再用大模型一次验证。
- **本质**：decode 是访存瓶颈时算力有富余，投机解码用富余的算力换 token。
- **量化**：draft 5 个 token、平均接受 3 个，一步产 ~4 个 token，低并发吞吐接近 4 倍。代价：每步多算 5 倍的 token（算力有富余时免费），draft 模型本身的时间，接受率低时白算。
- **理论**：`reference/gpu-perf-engineering-resources/` §4 Speculative decoding：Leviathan 等（精确采样的拒绝采样证明）、EAGLE-3（draft 层吃 target 的特征）。DeepInfer 的 DFlash 和 EAGLE-3 同构。
- **draft 来源**：`RedHatAI/Qwen3-8B-speculator.eagle3`（HF 上下载最多的 Qwen3-8B EAGLE-3 头），结构上和 DeepInfer 的 DFlash 一样：draft 层吃 target 中间层特征和上一个 token，自回归地产 `nextn` 个 draft token。4.10 换成 V4 的 DFlash 头和置信度头。
- **DeepInfer 怎么做**：
  - **槽位**：调度器持有 `free_mtp_info_slots`（`csrc/engine/scheduler.hpp:124`），请求进 RUNNING 时分配（`:792`），结束/抢占时释放；slot 0 是 padding。`MTPInfoPool`（`deepinfer/model_executor/layers/mtp_info_pool.py:14`）在 GPU 上按槽位存 draft token、draft logprob、置信度。
  - **输入**：`[last committed token, draft_0 … draft_{q-2}]`（`prepare_tensor_input_base.cpp:104-119`），`seqlen_q = 1 + len(draft_tokens)`；CUDA graph 按 **total_q**（不是 batch 数）分桶（`cuda_graph_runner.py:41`），padding 行用 placeholder 元数据。
  - **验证**：在 GPU 上一个融合 kernel 里做拒绝采样（`layers/sampler_utils.py:113` `process_sampling`，`fused_sample.py:18`）：对每个 draft 位置，用 target 概率和 pool 里的 draft 概率做 accept / reject，第一个 reject 处从修正分布重采一个，输出 `sampled_token_ids[req]`、`verified_token_ids[total_q]`（-1 = 拒绝）、`last_valid_offset[req]`（接受数）。
  - **draft 生成**：`DFlash.decode_forward`（`models/mtp/dflash.py`）吃 target 特征跑 draft 层，逐步采 `nextn` 个 token，写进 pool 的 write slot；独立的 CUDA graph（`dflash_cuda_graph_runner.py`）。
  - **CPU 簿记**：`process_MTPInfo`（`scheduler.hpp:1196`）把 draft 拷进 `mtp.draft_tokens`、算接受率；`process_outputs` 追加接受的 token，每个都过 `_check_stop`。
  - **ZOS 下**：`seqlen_k` 依赖上一步接受了几个，CPU 不知道，GPU 上 `compute_seqlens_k_zos` 修正；inflight 每步加 `nextn+1`。
  - **回滚**：`MAX_BACKTRACKING = nextn+1`（`environ.py:132`），拒绝的 token 对应的 KV 位置下一步被覆盖；SWA 环和压缩状态要能退回（4.2、4.3），SO matcher 也要 `rollback`（2.11）。

**思考题**：并发 64、`nextn=5` 时一步要验证 6 × 64 = 384 个 token。按发现问题里的算式（8B × 2 FLOP / 参数 / token）这一步要多少 FLOP，按 H100 的 1000 TFLOPS 要几毫秒？和 15–25 ms 的读权重时间比一比，算力从哪个并发开始不再免费？这就是 2.9 的交叉点。

## 解决问题

三个任务，照 DeepInfer 的槽位 + pool + 融合验证拆。这一节量比前面几节大，时长按实际写。

### 任务 A：draft 模型（约 60 分钟，你写约 150 行）

- **目标**：`drafter.propose(metadata, model_output) -> draft_tokens[req, nextn], draft_probs`，对每个 decode 请求自回归地产 `nextn` 个 draft token 和它们的概率。
- **思路**：对回分析里"需要一个便宜的方法先猜出几个 token"。EAGLE-3 的 draft 层吃 target 中间层特征（三层拼接）和上一个 token，结构上和 DeepInfer 的 DFlash 一样。target 模型 forward 时把它需要的中间层 hidden 留下来放进 `model_output`，drafter 拿着它跑 `nextn` 步，每步一个小 forward。draft 的 KV 自己管一份小的 paged cache，slot 和主模型对齐。先不做 CUDA graph，验收通过后再加（和主模型分开捕获，按 `num_seqs` 分桶）。
- **已备好**：`nanovllm/models/eagle3.py` 的权重加载和模块骨架；`nanovllm/engine/drafter.py` 的类和 `propose` 签名；draft paged cache 的分配。
- **你写什么**：target forward 里抽取固定几层 hidden 并放进 `model_output`；EAGLE-3 draft 层的 forward；`propose` 的自回归循环和 draft KV 的写入。最容易写错的两处：EAGLE-3 要的 target 特征是**固定几层**的 hidden，主模型 forward 要把它们留下来，CUDA graph 的输出 buffer 也要包含它们，否则 graph 回放时拿到的是上一次的；draft 的 KV cache 也要按请求管理，抢占时和主模型的一起释放。
- **改哪里**：

  | 文件 | 函数 | 做什么 |
  |---|---|---|
  | `nanovllm/models/eagle3.py`（新建） | draft 层 forward | 吃三层特征 + 上一个 token |
  | `nanovllm/engine/drafter.py`（新建） | `propose` | 自回归 `nextn` 步，返回 token 和概率 |
  | 主模型 forward | 中间层 hidden | 留下 EAGLE-3 要的那几层，放进 `model_output` |
  | `nanovllm/engine/model_runner.py` | graph 捕获 | 输出 buffer 含中间层 hidden |

### 任务 B：槽位、pool 和多 token 输入（约 40 分钟，你写约 100 行）

- **目标**：每个 RUNNING 请求有一个 MTP 槽位，draft token 和 logprob 按槽位存在 GPU 上的 pool 里；一步 decode 的输入变成每请求 `[last, drafts…]`、`seqlen_q = 1 + len(draft_tokens)`；CUDA graph 按 `total_q` 分桶；ZOS 下输入仍在 GPU 上拼。
- **思路**：对回分析里"一步验证多个 token"。draft 在 GPU 上产、验证也在 GPU 上做，中间不该经 CPU，所以 draft 按槽位存在 GPU pool 里：`MTPInfoPool` 是 `[max_num_seqs+1, nextn]` 的 token 和 logprob（先存 top-K 后的，K 可配），slot 0 保留，填 pad / -inf。`Scheduler` 加 `free_mtp_slots`，RUNNING 时分配、终态时释放；`Sequence.mtp` 子结构：`slot`、`draft_tokens`、`accept_rates`。输入侧 `positions / slot_mapping` 按 `seqlen_q` 展开；graph 按 `total_q` 分桶，`1,2,4,8` 之后每 8 一桶，padding 行指向 block 0、slot 0。ZOS 下 2.7 任务 C 的 `gather_input_ids` 改成按 remap 从 pool 和 sampled 里取：`[prev_sampled[remap], pool[slot, :]]`。
- **已备好**：`nanovllm/engine/mtp_pool.py` 的 `MTPInfoPool` 类和 buffer 分配；`Sequence.mtp` 字段；graph 桶表；`tests/test_2_8.py` 的 (b)(d)。
- **你写什么**：槽位的分配 / 释放和它们在 RUNNING / 终态 / 抢占路径上的调用点；`prepare_input.cpp` 里按 `seqlen_q` 展开 `positions / slot_mapping`；`gather_input_ids` 的多 token 版本。最容易写错的一处：抢占后 `mtp` 状态要清零、槽位要还回去，不然槽位泄漏，或者新请求读到旧 draft。
- **改哪里**：

  | 文件 | 函数 | 做什么 |
  |---|---|---|
  | `csrc/scheduler.hpp` | `free_mtp_slots`、schedule / finish / preempt 路径 | 槽位分配释放，slot 0 保留 |
  | `csrc/sequence.hpp` | `mtp` 子结构 | `slot`、`draft_tokens`、`accept_rates` |
  | `nanovllm/engine/mtp_pool.py`（新建） | `MTPInfoPool` | GPU 上 `[max_num_seqs+1, nextn]` 的 token 和 logprob |
  | `csrc/prepare_input.cpp` | prepare | `[last, drafts…]`，按 `seqlen_q` 展开 |
  | `nanovllm/engine/model_runner.py` | graph 分桶 | 按 `total_q`，padding 行 placeholder |

### 任务 C：验证 kernel 和 CPU 簿记（约 50 分钟，你写约 120 行）

- **目标**：一个 Triton kernel 做拒绝采样：输入 target logits `[total_q, V]`、pool 里的 draft token 和 draft prob、每请求的 `seqlen_q` 和温度；输出 `sampled[req]`、`verified[total_q]`、`num_accepted[req]`。post-process 按 `num_accepted` 把接受的 token 追加进序列；`StepRecord` 有 `num_drafted / num_accepted`，报告里有接受率和"每步产出 token 数"。
- **思路**：对回分析里"用大模型一次验证"。对每个 draft 位置，用 target 概率和 pool 里的 draft 概率做 accept / reject，第一个 reject 处从修正分布 `max(0, p - q)` 归一化后采样；温度为 0 时退化成贪心比较。先用 PyTorch 写一版参考实现（逐请求循环）做对拍，再写 Triton。CPU 侧：post-process 按 `num_accepted` 追加 token，每个都过 `_check_stop`（EOS 可能在 draft 中间）；把本步新 draft 写进 `Sequence.mtp.draft_tokens`，算累积接受率。ZOS 下 CPU 不知道上一步接受了几个：2.7 任务 B 的 inflight 每步加 `1 + nextn`；`compute_seqlens_k` kernel 在 GPU 上修 `seqlen_k = base + num_accepted_prev[remap] + 1`。被拒绝的 draft 占过的 KV slot 下一步被覆盖。
- **已备好**：`nanovllm/layers/verify.py` 的 kernel 签名和启动代码；`tests/test_2_8.py` 的 (a)(c) 测试壳；`StepRecord` 的 `num_drafted / num_accepted` 字段和报告里接受率、每步产出 token 数两列。
- **你写什么**：PyTorch 参考实现和 Triton kernel 体；post-process 的追加和 `_check_stop` 循环；接受率统计；`compute_seqlens_k` 的修正。最容易写错的两处：拒绝采样对 draft 概率的精度敏感，pool 里存的 logprob 要和采样时用的一致（都在 top-K 空间或都在全词表）；`slot_mapping` 的计算要用 committed 长度而不是 inflight 上界，用错了被拒绝的 draft 写过的 KV 位置就不会被下一步覆盖。
- **改哪里**：

  | `csrc/sequence.hpp` | inflight | 每步加 `1 + nextn` |
  | 2.7 任务 C 的 GPU 侧准备 | `compute_seqlens_k` | `base + num_accepted_prev[remap] + 1`；`slot_mapping` 用 committed 长度 |

## 验收

同一个实验重跑：

```bash
for n in 1 4 16 64 256; do python -m bench.run --scenario steady_decode --max-num-seqs $n; done
```

1. 并发 1–16 时吞吐提升 2–3 倍；接受率曲线（每个 draft 位置的接受概率）写进报告。
2. 并发 256 时吞吐**可能反而下降**，把这个数记下来，这是 2.9 的现象。
3. 正确性：固定 seed 下，开/关投机解码的输出分布一致（拒绝采样是精确的）；近贪心下 `greedy_match` 和黄金文件一致。
4. 关掉投机（`nextn=0`）数字回到 2.7。
5. `tests/test_2_8.py`：(a) 验证 kernel 和 PyTorch 参考实现在随机输入上一致；(b) 槽位分配释放配对；(c) EOS 出现在 draft 中间时后面的 token 被丢弃；(d) 抢占后 `mtp` 状态清零；(e) 2.1–2.7 全过。
6. **解释**（由你说）：为什么并发 1 时 `gpu_forward` 从 1 个 token 变成 6 个几乎没变、吞吐却翻了 2–3 倍？接受率 0.6 的 draft 每步期望产几个 token，和实测对得上吗？为什么并发 256 时提升消失甚至倒退？

**新浮现的问题**：高并发下开投机解码反而变慢。这是 2.9。

## 常见坑

- EAGLE-3 要的 target 特征是**固定几层**的 hidden，主模型 forward 要把它们留下来，CUDA graph 的输出 buffer 要包含它们。
- draft 的 KV cache 也要按请求管理，抢占时一起释放。
- `seqlen_q` 变了之后，1.1 任务 B 的 `num_tokens` 统计要分清"验证的 token 数"和"产出的 token 数"。
- 拒绝采样对 draft 概率的精度敏感；pool 里存的 logprob 要和采样时用的一致（都在 top-K 空间或都在全词表）。
- 温度 1e-3 的近贪心下，draft 和 target 的 argmax 不一致就全拒，接受率会比真实采样低，别拿它当性能指标。
