# 2.5：GPU 时间线上一半是空隙

> 起点：2.4 做完的代码　轴：2 每步执行模型

| | |
|---|---|
| **问题** | Qwen3-0.6B 跑 `many_small` 512 并发，`gpu_busy` 掉到 30–50%，nsys 上 kernel 之间大片空隙，空隙里 CPU 在跑 Python。根因是 CPU 每步的工作（list 拼输入、调度扫描和排序、逐请求 postprocess、对象分配和 GC）随 batch 线性涨，而 decode 是访存瓶颈，GPU 时间几乎不随 batch 涨；batch 越大、模型越小、GPU 越快，CPU 占比越高 |
| **实验** | `python -m bench.run --model ~/huggingface/Qwen3-0.6B --scenario many_small --max-num-seqs 512`，再 `bash bench/nsys.sh many_small ...`，盯 `gpu_busy` 和 `cpu_prepare` 相对 `gpu_forward` 的比例 |
| **硬件 / 费用** | 1×H100（$3.95/h）+ Qwen3-0.6B（放大 CPU 占比），再用 Qwen3-8B 验证不退化。这一节的现象靠 GPU 快才显出来，L4 上一步 60 多 ms 会把 CPU 开销遮住，要用 H100。发现、cProfile、before / after 和 8B 回归约 3 小时，约 $12 |
| **学到** | CPU 开销是固定的，GPU 一步越短它越显眼，所以 DeepInfer（FP4、MLA、Wide-EP 之后 GPU 每步只剩几毫秒）把整个热路径搬进 C++；输入准备不建 Python list，往预分配的 pinned buffer 里写、一次 `non_blocking` H2D，`non_blocking` 对非 pinned 源会静默退化成同步；对象池、延迟释放、手动 GC 三件事都放在 GPU 忙的时候做，调度元数据是带指针的池对象而不是快照，2.7 要在采样前改它的 `seqlen` |
| **时长** | 发现 + 分析约 1.5 小时；任务 A 约 40 分钟，任务 B 约 30 分钟，任务 C 约 20 分钟；验收约 1 小时（含 cProfile 和 8B 回归）。改动约 300–500 行 |

## 发现问题

**关注什么**：一步里 CPU 花了多久，GPU 在这段时间干什么。

```bash
python -m bench.run --model ~/huggingface/Qwen3-0.6B --scenario many_small --max-num-seqs 512
bash bench/nsys.sh many_small --model ~/huggingface/Qwen3-0.6B --max-num-seqs 512
```

**先预测**：0.6B 模型 decode 一步 GPU 大概几毫秒？`cpu_prepare + cpu_schedule + cpu_postprocess` 加起来呢？`gpu_busy` 是多少？

**现象**：`gpu_busy` 掉到 30–50%。`cpu_prepare` 和 `gpu_forward` 同量级甚至更大。nsys 的 CUDA 行上 kernel 之间有大片空隙，空隙里 CPU 在跑 Python。按 `cpu_*` 各段拆：`cpu_prepare` 最大（512 个请求的 `input_ids / positions / slot_mapping / block_tables` 全是 Python list 拼出来再 `torch.tensor`），`cpu_schedule` 其次（2.3 的排序、2.1 的两次队列扫描、`deque.remove`），`cpu_postprocess`（逐请求 `hash_blocks`、`append_token`）。再用 `py-spy` 或 `cProfile` 看一眼，对象分配和 GC 也占一块。

换 8B 跑同样场景，GPU 一步变长，`gpu_busy` 回到 70% 以上。**这说明 CPU 开销是固定的，GPU 越快它越显眼。** DeepInfer 的 GPU 每步只剩几毫秒（FP4、MLA、Wide-EP），所以它把整个热路径搬到了 C++。

## 分析问题

- **追问链**：空隙 → CPU 在准备下一步 → 每步做了多少 Python 工作：O(num_seqs) 次 list append、O(num_seqs) 个 `Sequence` 属性访问、几次 `torch.tensor(list)`（每次都要走 Python → C++ 的转换和 pinned 分配）、调度器的排序和扫描、postprocess 的 hash、每步新建的各种临时对象 → 这些都和 batch 大小线性相关，GPU 时间却因为访存瓶颈几乎不随 batch 涨。
- **本质**：decode 是访存瓶颈，batch 从 64 到 512 GPU 时间差不多；CPU 工作却从 64 份涨到 512 份。batch 越大、模型越小、GPU 越快，CPU 占比越高。
- **量化**：`cpu 总时间 / wall` 就是 GPU 空闲比例的下界。用 1.1 的报告算一下 0.6B 和 8B 各是多少。
- **理论**：没有专门的论文，这是工程常识，但 DeepInfer QA 文档 "Asynchronous scheduling" 一节的第一句就是这个问题的描述。`reference/gpu-perf-engineering-resources/` §3 Nsight Systems 是看这个问题的工具。
- **DeepInfer 怎么做**（这一节先做 Python 能做的部分，C++ 留给 2.6）：
  - 输入准备不建 Python list：C++ 直接往**预分配的 pinned tensor** 里写（`csrc/engine/input_metadata/prepare_tensor_input_base.cpp`），然后一次 `non_blocking` H2D。
  - 对象池：`SequenceMetadataPool` 复用每步的元数据对象（`csrc/utils/object_pool.hpp`）；`RequestOutputPool` 预分配 10000 个输出对象，`build_request_outputs` 返回 **uint64 裸指针数组**，Python 读字段用静态函数，要保留就 `clone`（`csrc/engine/outputs.hpp:45`）。
  - 延迟释放：`DeferredRelease`（`llm_engine.py:67`）把上一步的元数据、输出、克隆 unpin 收集起来，下一步 `pre_sampler_sync` 时（GPU 正忙）归还。
  - GC：worker 初始化 `gc.disable()`（`base.py:102`），每 `DEEPINFER_GC_INTERVAL_STEP`（1000）步在 `pre_sampler_sync` 里手动 `gc.collect()`（`worker.py:165`），同样放在 GPU 忙的时候。
  - 调度元数据是**带指针的池对象**（`SequenceMetadata` 指向 `Sequence`，`sequence.hpp:333`），不是快照。2.7 的 ZOS 要在采样前改它的 `seqlen`，2.8 的 MTP 槽位也挂在它上面。

**思考题**：用 1.1 的报告算出 0.6B 和 8B 各自的 `cpu 总时间 / wall`。如果换一张比 H100 快一倍的卡，0.6B 的 `gpu_busy` 会掉到多少？8B 呢？这一节做完之后这两个数会怎么变？

## 解决问题

三个任务，顺着一步的数据流拆：任务 A 管进 GPU 的输入，任务 B 管出 GPU 的输出和对象的归还，任务 C 管调度器自己的循环。开工之前先用 `cProfile` 跑 `many_small` 100 步、按函数排序，把前 10 项写进报告，这是本节的 before（验收第 3 条要和它比）。buffer 分配、池的骨架、`Config` 参数、观测字段和测试由 `start-step` 先写好。

### 任务 A：输入侧：pinned buffer 和 `SequenceMetadata`（约 40 分钟，你写约 120 行）

- **目标**：runner 每步不再 `torch.tensor(list)`，输入从预分配的 pinned buffer 一次 `non_blocking` 拷到 GPU；输入准备只读 `SequenceMetadata`，不再碰 `Sequence`。`cpu_prepare` 下降一个量级。
- **思路**：对回"`cpu_prepare` 最大，全是 list 拼出来再 `torch.tensor`"。照 `prepare_tensor_input_base.cpp` 和 `SequenceMetadataPool`：启动时按 `max_num_seqs` 和 `max_num_batched_tokens` 预分配 pinned 的 `input_ids / positions / slot_mapping / context_lens / block_tables / temperatures / cu_seqlens_*`，GPU 侧也预分配对应 buffer；每步往 pinned buffer 里写（先用 numpy 数组切片赋值，比 list 快一个量级），一次 `copy_(non_blocking=True)` 到 GPU，取前 `n` 行的 view 给模型。每步每个请求要交给 runner 的字段（`seqlen_q`、`seqlen_k`、`block_table` 引用、`temperature`、`last_token`）收成 `SequenceMetadata`，它持有 `Sequence` 的引用而不是复制值，用一个简单的池（预分配 `max_num_seqs` 个，每步 `acquire / release`）。这是架构种子：2.6 的 C++ 直接写同一块 pinned buffer；2.7 的 `input_on_device` CUDA graph 直接用 GPU 侧 buffer。
- **已备好**：新建 `nanovllm/engine/metadata.py`，`SequenceMetadata` 的字段和池的 `acquire / release` 骨架；`model_runner.__init__` 里 pinned 和 GPU buffer 的分配；`tests/test_2_5.py` 的 (a)(b)。
- **你写什么**：`prepare_prefill / prepare_decode / prepare_block_tables / prepare_sample` 里往 pinned buffer 写的那段和取 view 的那段；池的 `acquire / release`；调度器把每步的 `SequenceMetadata` 填好交给 runner。最容易写错的三处：`non_blocking` H2D 要求源是 pinned 的，否则会退化成同步拷贝而且不报错；pinned 内存分配很慢、不能超量，按上限分配一次之后只切 view，超过 `max_num_seqs` 要有明确的断言；`SequenceMetadata` 存的是 `Sequence` 的引用，不要把 `block_table` 复制成新 list。
- **改哪里**：

  | 文件 | 函数 | 做什么 |
  |---|---|---|
  | `nanovllm/engine/model_runner.py` | `prepare_prefill`、`prepare_decode`、`prepare_block_tables`、`prepare_sample` | 写 pinned buffer，`copy_(non_blocking=True)`，取 view |
  | `nanovllm/engine/metadata.py` | `SequenceMetadata`、池 | 字段、`acquire / release` |
  | `nanovllm/engine/scheduler.py` | `schedule` | 填 `SequenceMetadata` 交给 runner |

### 任务 B：回收侧：输出对象池、`DeferredRelease`、GC（约 30 分钟，你写约 70 行）

- **目标**：`step()` 返回池里的 `RequestOutput`；元数据、输出对象、block 三样在下一步 `run` 发射之后统一归还；`gc.collect()` 每 N 步在同一个位置手动做。`num_allocs` 每步接近常数，不随 `num_seqs` 涨。
- **思路**：对回"对象分配和 GC 也占一块"。照 `RequestOutputPool`（`outputs.hpp:45`）、`DeferredRelease`（`llm_engine.py:67`）、`base.py:102` + `worker.py:165`：归还和回收都放在 GPU 忙的时候做。`step()` 返回的 outputs 改成从池里取的 `RequestOutput`，约定调用方下一步之前消费完，`generate()` 里要 `clone` 一份存起来。加 `DeferredRelease`：本步结束时不立刻归还元数据和输出对象，下一步 `run` 发射之后再归还；2.1 已经把 block 释放挪到了这个位置，现在把三样东西收在一起。引擎初始化 `gc.disable()`，每 N 步（`Config.gc_interval_step = 1000`）在 `run` 发射之后手动 `gc.collect()`。
- **已备好**：`RequestOutput` 池和 `clone`；`Config.gc_interval_step = 1000`；`StepRecord.num_allocs`（用 `tracemalloc` 或 `gc.get_count()` 的差）；`tests/test_2_5.py` 的 (c)。
- **你写什么**：`DeferredRelease` 的收集和归还；`step()` 里归还和 `gc.collect()` 的位置；`generate()` 里的 `clone`。最容易写错的两处：返回池对象给调用方后，调用方拿着引用不放会被下一步覆盖，`generate()` 一定要 `clone`；`gc.disable()` 之后循环引用的对象不会被回收，内存会慢慢涨，定期 `collect` 不能省。
- **改哪里**：

  | 文件 | 函数 | 做什么 |
  |---|---|---|
  | `nanovllm/engine/llm_engine.py` | `__init__` | `gc.disable()`，建 `DeferredRelease` |
  | `nanovllm/engine/llm_engine.py` | `step` | 从池取 `RequestOutput`；`run` 发射之后归还上一步的三样、定期 `gc.collect()` |
  | `nanovllm/engine/llm_engine.py` | `generate` | `clone` |

### 任务 C：调度器里的 O(n) 操作（约 20 分钟，你写约 30 行）

## 验收

同一个实验重跑：

```bash
python -m bench.run --model ~/huggingface/Qwen3-0.6B --scenario many_small --max-num-seqs 512
```

1. `cpu_prepare` 下降一个量级；`cpu_postprocess` 和 `cpu_schedule` 明显下降；`gpu_busy` 提升（目标 0.6B 上从 30–50% 到 60% 以上）。每一段的 before / after 写进报告。
2. `num_allocs` 每步接近常数，不随 `num_seqs` 涨。
3. cProfile 前 10 项里不再有 `torch.tensor(list)` 和 list 拼接。
4. 8B 上 `steady_decode` 吞吐不退化（CPU 省下的时间在 8B 上不一定变成吞吐，但不能变差）。
5. `tests/test_2_5.py`：(a) 池的 acquire / release 配对，泄漏时报错；(b) pinned buffer 超过 `max_num_seqs` 时有明确的断言；(c) `DeferredRelease` 在下一步才归还；(d) 2.1–2.4 全过。

**解释**（由你说）：`cpu_prepare` 降了一个量级，`gpu_busy` 却没有翻倍，剩下的空隙在哪？为什么 0.6B 上的改善在 8B 上几乎看不出来，这说明 CPU 开销是什么性质的？

**新浮现的问题**：cProfile 里剩下最大的一块是 `scheduler.schedule` 本身，纯 Python 循环，随 batch 线性。这是 2.6。

| 这一节 | DeepInfer | 差异和原因 |
|---|---|---|
| numpy 写 pinned buffer | C++ 写 pinned buffer（`csrc/engine/input_metadata/`） | 2.6 换成 C++ |

## 常见坑

- pinned 内存分配很慢，而且不能超量：按上限分配一次，之后只切 view。
- `non_blocking` H2D 要求源是 pinned 的，否则会退化成同步拷贝而且不报错。
- 返回池对象给调用方后，调用方拿着引用不放会被下一步覆盖；`generate()` 一定要 `clone`。
- `gc.disable()` 之后循环引用的对象不会被回收，内存会慢慢涨，定期 `collect` 不能省。
- 0.6B 上的改善在 8B 上看起来很小，这是预期的：CPU 开销是固定的，GPU 慢的时候它被遮住了。
