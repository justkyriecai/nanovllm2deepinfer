# 2.6：剩下的 CPU 时间全是解释器

> 起点：2.5 做完的代码　硬件：1×H100，Qwen3-0.6B / 8B　预计改动：800–1200 行（C++ + pybind + 构建）　轴：2 每步执行模型

## 1. 发现问题

**关注什么**：2.5 之后，CPU 时间还剩在哪。

```bash
python -c "import cProfile; ..."    # 2.5 的 profile 脚本，many_small，0.6B，512 并发
```

**先预测**：输入准备已经不建 list 了，剩下最大的一块是什么？它随并发怎么变？

**现象**：`scheduler.schedule` 和 `scheduler.postprocess` 成了前两名。`cpu_schedule` 随 `num_seqs` 线性涨：512 并发时几毫秒，和 0.6B 的 `gpu_forward` 一个量级。里面没有任何重活，就是 Python 循环、属性访问、`deque` 操作和 2.3 的排序。再加上 `SequenceMetadata` 填充（2.5 加的）也是逐请求的 Python 循环。

## 2. 分析问题

- **追问链**：调度耗时 → 每请求几十次 Python 属性访问和方法调用 → 每次都是字典查找加函数帧 → 每请求约 10–20 μs，512 个就是 5–10 ms → 0.6B 的 forward 才 3–5 ms。
- **本质**：解释器的固定开销乘以 batch 大小。这类"每请求几十次小操作"的热路径，Python 和 C++ 差 50–100 倍。
- **量化**：目标是调度 + postprocess 在 512 并发下 < 0.5 ms。
- **理论**：没有论文。DeepInfer 的选择本身就是答案：`csrc/engine/` 5.2k 行 C++，热路径上的每请求工作全在 C++，Python 只按步编排。
- **DeepInfer 怎么做**：
  - `Scheduler`、`Sequence`、`BlockManager`、`SchedulerOutputs` 都是 C++ 类，pybind 暴露（`csrc/engine/pybind_scheduler.cpp`、`pybind_sequence.cpp`）。
  - `schedule()` 持 BlockManager 锁的同时**释放 GIL**（`scheduler.hpp:276`），SO 编译线程和 profile server 不被卡。
  - `Blocks` 是侵入式双向链表 free list（`block_manager.hpp:27-117`）：`allocate` 从头取，`free` 接到尾，block 0 保留做空指针，`ref_count` 直接存在数组里。
  - `Sequence` 是结构体套结构体（`sequence.hpp:265`）：`request / input / generation / cache / mtp / structured_output / schedule`，Python 侧通过 pybind 的 property 读。
  - 返回给 Python 的东西尽量是 numpy 视图或裸指针：`SchedulerOutputs` 借用调度器内部 vector 的存储（`pybind_scheduler.cpp:31-62`），约定"下一次 schedule 前消费完"。
  - 构建：`setup.py` 一个 `deepinfer._C` 扩展，C++20，`stubgen` 生成 `.pyi`。

## 3. 要做什么

### 3.1 范围

把 2.1–2.5 积累的调度逻辑**原样**翻译成 C++，不加新功能。范围：`Sequence`（含状态机和 `reset_for_recompute`）、`BlockManager`（refcount、prefix hash、`OK/LATER/NEVER`）、`Scheduler`（三个队列、prefill/decode 交替、抢占、fork/COW、abort、finished 收集）、`SequenceMetadata` 和它的池、输入准备（2.5 的 pinned buffer 写入）。

不搬：模型、sampler、CUDA graph、1.1 的统计（它读 pybind property 就够）。

### 3.2 结构

```
csrc/
  sequence.hpp        Sequence, SequenceStatus
  block_manager.hpp   Blocks (链表 free list), BlockManager (hash 前缀缓存)
  scheduler.hpp       Scheduler, SchedulerOutputs
  prepare_input.cpp   把一步的 SequenceMetadata 写进 pinned tensor
  pybind.cpp
setup.py              torch.utils.cpp_extension，C++17 或 20
nanovllm/_C.pyi       stubgen 生成
```

- `Scheduler.schedule()` 返回 `(seq_metadata_list, scheduler_outputs)`；`SchedulerOutputs` 含 `scheduled / prompt_run / num_batched_tokens / finished / ignored / preempted / seqlens_q`，Python 侧按 property 读。
- `schedule()` 内部 `py::gil_scoped_release`。
- 输入准备接收 pinned tensor 的 `data_ptr`，直接写。

### 3.3 Python 侧

- `nanovllm/engine/scheduler.py` 变成薄包装或直接删除，`LLMEngine` 持有 `_C.Scheduler`。
- 1.1 的 `StepRecord` 从 `SchedulerOutputs` 读 `finished / preempted`。
- 保留 Python 实现一段时间做对拍：同一个请求 trace 喂两个调度器，决策必须一致。这是本节最重要的测试。

### 3.4 构建和 CI

- `pip install -e .` 触发编译；没有 CUDA 的机器要能跳过 CUDA 相关的编译单元（这一节的 C++ 不需要 CUDA，只需要 torch 头文件）。
- `tests/test_2_6.py` 在没有编译产物时 skip 而不是报错。

## 4. 验收

同一个实验重跑：

```bash
python -m bench.run --model ~/huggingface/Qwen3-0.6B --scenario many_small --max-num-seqs 512
```

1. `cpu_schedule + cpu_postprocess` 在 512 并发下 < 0.5 ms（before 是几毫秒）。
2. `gpu_busy` 在 0.6B 上继续上升；此时剩余的空隙应该主要是 `cpu_sample_wait` 之外的 `.tolist()` 同步和 launch，这是 2.7 的现象。
3. **对拍**：四个场景的 trace，Python 调度器和 C++ 调度器的 `scheduled_ids / finished_ids / preempted_ids` 逐步相同。
4. 2.1–2.5 的测试在 C++ 调度器上全过（测试通过 `Scheduler` 的接口写，两个实现都能跑）。
5. `greedy_match` / `nll` 黄金文件对比不变。

**新浮现的问题**：调度快了，但 `cpu_sample_wait` 之后 GPU 仍然要等 `postprocess` 和下一次 `schedule` 做完才有活干。nsys 上空隙缩小了但还在。这是 2.7。

## DeepInfer 对照

| 这一节 | DeepInfer | 差异和原因 |
|---|---|---|
| C++ `Scheduler / Sequence / BlockManager` | `csrc/engine/scheduler.hpp`、`sequence.hpp`、`block_manager.hpp` | DeepInfer 多了 MTP 槽位、SO、fork 的 state、CP 对齐、DP 投票 |
| 释放 GIL | `scheduler.hpp:276` | 一致 |
| 链表 free list | `block_manager.hpp:27` | 一致 |
| 一个 `BlockManager` 类 | 两个实例：block 和 state（`llm_engine.py:265`） | 4.1 加第二个实例，所以类要写成通用的 |
| `SchedulerOutputs` 借用存储 | `pybind_scheduler.cpp:31-62` | 一致 |
| 没有 | `FlopsEstimator`（MFU）、`flops_estimator.hpp` | 可以顺手加，1.1 的报告多一列 MFU |

## 常见坑

- pybind 对象的生命周期：`Sequence` 由 C++ 持有，Python 拿到的是引用；不要让 Python 侧的引用比 C++ 对象活得长。
- `deque` 和 `vector` 的语义不同：DeepInfer `running` 是 `vector`（要排序），`waiting / prompted` 是 `deque`。
- 2.5 的 `SequenceMetadata` 池如果留在 Python，这一节会被它卡住；要一起搬。
- 编译时间：一改就要重新编译，开发期用 `ccache` 或 `ninja`。
- 释放 GIL 之后，C++ 里不能碰任何 Python 对象，`SamplingParams` 这类东西要在调度前拷成 C++ 结构（DeepInfer 的 `SamplingScalars`，`sequence.hpp:92-116`）。
