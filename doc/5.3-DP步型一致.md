# 5.3：一个 rank 在 prefill，另一个在 decode，all-to-all 卡死

> 起点：5.2 做完的代码　轴：6 分布式 / 1 调度

| | |
|---|---|
| **问题** | 各 rank 的请求流不同时，rank 0 的调度器选了 prefill、其它 rank 选了 decode，DeepEP 的 dispatch 两种形状对不上，所有 rank 永远等；就算形状碰巧对上，各 rank 的 `decode_step` 也会错开、越跑越乱。本质：DP + EP 把 8 个独立引擎变成一个同步系统，每步要一次组内共识"这一步做什么"，共识的次数和时机各 rank 必须一致 |
| **实验** | `python -m bench.launch_dp --dp 8 --ep 8 -- bench.run --scenario mixed_long_short --per-rank-seed`，盯引擎是否卡死，以及每步各 rank 的步型是否一致 |
| **硬件 / 费用** | 8×H100 + DeepSeek-V2-Lite，Modal 约 $32/h；复现死锁、调试、验收约 3–5 小时，约 $100–160 |
| **学到** | 投票绑在 `decode_step` 上，因为它由上一步的结果决定、各 rank 天然一致，allreduce 的次数和时机才对得齐；投票走 gloo 在 CPU 上做，几十微秒，放到 NCCL 上会插进 CUDA stream 打掉 ZOS 的重叠；没活的 rank 不走特殊路径，而是跑一个 placeholder 步让所有集合通信照常发生；第二轮确认防止"全组空手 → `decode_step` 清零 → 再投票再空手"的死循环 |
| **时长** | 发现 + 分析约 2 小时；任务 A 约 30 分钟、B 约 30 分钟、C 约 20 分钟；验收约 1.5 小时。改动约 400–600 行 |

## 发现问题

**关注什么**：各 rank 的请求流不一样时会发生什么。5.1 把负载按 rank 复制是为了绕开这个问题，现在把它打开。

```bash
python -m bench.launch_dp --dp 8 --ep 8 -- bench.run --scenario mixed_long_short --per-rank-seed   # 每个 rank 不同的到达序列
```

**先预测**：rank 0 来了一个 16k 的 prompt、其它 rank 还在 decode，下一步各 rank 的调度器各自决定做什么？all-to-all 的双方会不会凑齐？

**现象**：

- 引擎挂死。rank 0 的调度器选了 prefill，forward 走到 MoE 的 dispatch，发的是 prefill 形状的通信；其它 rank 选了 decode，发的是 decode 形状（还在 CUDA graph 里）。DeepEP 的 dispatch 是组内集合通信，两种形状对不上，所有 rank 永远等。
- 就算形状碰巧对上（都 eager），步数也会错开：rank 0 这一步 prefill 不产 token，其它 rank 产了；下一步 rank 0 又要 decode，别人可能在 prefill。每步的 `decode_step` 各 rank 不同，2.2 的"每 70 步考虑一次 prefill"在各 rank 上触发的时机不同，越跑越乱。
- 还有一种死法：某个 rank 完全没有请求（`has_unfinished_requests` 为假），它退出了 step 循环，别的 rank 在 all-to-all 里等它。
- 8 个 rank 的 KV 块数不同（5.1 已经平均了，但如果没平均）：watermark 判断各 rank 不同，同一步有的 rank 想 prefill 有的不想。

## 分析问题

- **追问链**：卡死 → EP 的集合通信要求组内每步**同型**（都 prefill 或都 decode）→ 每个 rank 的调度器是独立的 → 需要一次组内的共识："这一步做什么" → 共识用一次小的 allreduce 投票 → 投票的次数和时机各 rank 必须一致（否则 allreduce 本身对不齐）→ 把投票绑在 `decode_step` 上，而 `decode_step` 由上一步的结果决定、各 rank 一致 → 投了"做 prefill"但有的 rank 没活可排：它跑一个空的 prompt 步陪跑 → 完全没请求的 rank：跑一个 placeholder 步（一个 dummy 序列），让所有集合通信照常发生 → `has_unfinished_requests` 也要组内 allreduce，任一 rank 有活全组都不退出 → 投票走 gloo（CPU），不碰 CUDA stream，ZOS 的重叠不受影响。
- **本质**：DP + EP 把 8 个独立引擎变成了一个**同步系统**：每步一次组内共识，共识的代价是一次 CPU allreduce（几十微秒）和偶尔的陪跑步。这是 Wide-EP 的固有税，DeepInfer 把它做到最小：投票点稀疏（70 步一次）、投票在 CPU、陪跑步用 placeholder 而不是特殊路径。
- **量化**：每步一次 gloo allreduce 约 20–50 µs，相对 decode 一步十几毫秒可以忽略；但如果放到 NCCL 上，它会插进 CUDA stream，破坏 2.7 的重叠。空 prompt 步的代价是一步 decode 的时间（该 rank 没产 token），ALL 点的"全员有活才 prefill"就是为了少付这个税。
- **理论**：`reference/gpu-perf-engineering-resources/` §4 "Scheduling and continuous batching"：Orca / Sarathi-Serve 的 iteration-level 调度，这里是它的分布式版本；§5 的 DeepSeek-V3 部署部分讲 DP attention + EP 的同步约束。
- **DeepInfer 怎么做**（`csrc/engine/scheduler.hpp:286-342`）：
  - **投票点**：`is_all_point = decode_step % prefill_attempt_interval == 0`（默认 70，`environ.py:174`），`is_any_point = decode_step != 0 && decode_step % prefill_any_attempt_interval == 0`（默认 100）；两者重合按 ANY 算。不在投票点直接 decode。
  - **想不想**：`want = gpu_cache_usage ≤ 0.9 && waiting 队头可调度`（`:313`，`_has_prefill_waiting :273`）。
  - **第一轮**：ALL 点 `allreduce(MIN(want))`，全员想才做；ANY 点 `allreduce(MIN(!want)) == 0`，任一想就做（给孤立 rank 兜底：它的 prefill 最多等 100 个 decode 步）。
  - **第二轮**（`:328-335`）：想做的 rank 跑 `_schedule_prefill`，可能空手（slot 满、块不够）；`allreduce` 确认是否有 rank 真排出了 prefill。全组空手必须转 decode：硬做空 prompt 步会把 `decode_step` 清零，下一步又投票又空手，running 满 + waiting 非空就死循环。
  - **陪跑**：组内有 rank 在 prefill、本 rank 没排出：`_make_outputs({}, true, 0, …)`（`:340`），一个空的 prompt 步。
  - **allreduce 走哪**：`_dp_allreduce`（`:170`）：`use_cpu_dp_group` 时在 CPU 张量上用 gloo 组。
  - **placeholder 步**：`scheduler_outputs.is_empty()` 时 `Worker.execute_model_step`（`worker/worker.py:116-127`）用 `_placeholder_seq_metadata`（`model_runner.py:386`）造一个 dummy 序列（block 0、state slot 0、mtp slot 0）跑完整的 forward，`post_process` 时输出置 None（`llm_engine.py:987`）。
  - **退出条件**：`has_unfinished_requests`（`llm_engine.py:665`）：ZOS 下用 `cpu_data_parallel_group` 做 `MAX` allreduce。
  - **`decode_step` 一致**：prompt 步把 `decode_step` 清零（2.2），各 rank 同步做 prompt 步所以一致；`prefill_attempt_interval` 各 rank 相同配置。
  - **块数一致**：5.1 的跨 rank 平均。

**思考题**：ALL 点每 70 步一次、ANY 点每 100 步一次，重合时按 ANY 算。一个孤立 rank（只有它有 waiting）的 prefill 最坏要等多少个 decode 步？如果把 ANY 间隔也改成 70，会多付什么税？

## 解决问题

### 任务 A：两轮投票（约 30 分钟，你写约 60 行）

- **目标**：混合负载下 8 卡不卡死；每步的步型各 rank 一致；`dp_size == 1` 时调度器行为和 5.2 完全一样。
- **思路**：对回"共识用一次小的 allreduce 投票，投票的次数和时机各 rank 必须一致"。投票点由 `decode_step` 定（ALL 每 70 步、ANY 每 100 步，重合按 ANY），不在投票点直接 decode；第一轮投"想不想"，ALL 点 `MIN(want)` 全员想才做、ANY 点任一想就做；第二轮每个 rank 都参加，想做的跑 `_schedule_prefill`，再 allreduce 确认是否真有 rank 排出了 prefill，全组空手就转 decode。allreduce 在 CPU 张量上走 gloo 组，不碰 CUDA stream。2.2 留的"要不要 prefill"方法就是为这里准备的。
- **已备好**：`dp_group`（gloo）传进调度器的通道；`Config.prefill_attempt_interval = 70`、`prefill_any_attempt_interval = 100`；`bench` 的 `--per-rank-seed`（发现问题的实验已经在用）和"rank 0 独自有请求"的场景；`tests/test_5_3.py` (a) 投票逻辑的纯函数版（给定各 rank 的 `want / scheduled`，输出每个 rank 的步型）和真实多进程一致、(b) `decode_step` 各 rank 每步一致。
- **你写什么**：`_dp_allreduce<T>(value, op)`；`_schedule` 里按 ALL / ANY 点投两轮票的逻辑，`dp_size == 1` 时短路。最容易写错的两处：第二轮投票不管本 rank 想不想都要参加，任何"只有某些 rank 才调用"的集合通信都是死锁；`decode_step` 要在 prompt 步（含空 prompt 步）清零，否则各 rank 的投票点错开。
- **改哪里**：

  | 文件 | 函数 | 做什么 |
  |---|---|---|
  | `csrc/scheduler.hpp` | `_dp_allreduce`、`_schedule` | gloo allreduce；ALL / ANY 两轮投票；全组空手转 decode |
  | `nanovllm/config.py` | `Config` | `prefill_attempt_interval`、`prefill_any_attempt_interval` |

### 任务 B：空 prompt 步和 placeholder 步（约 30 分钟，你写约 60 行）

- **目标**：投了 prefill 但本 rank 没排出的，跑一个空 prompt 步；完全没请求的 rank 跑 placeholder 步；两种步都走正常 forward，输出丢弃，不影响下一步的 `remap`。
- **思路**：对回"陪跑步用 placeholder 而不是特殊路径"。`SchedulerOutputs.is_empty()` 时造一个 dummy 序列（block 0、slot 0）跑完整的 forward，采样输出丢弃；这样 dispatch / combine 和所有集合通信照常发生，形状也和别人对得上。2.7 的 ZOS：placeholder 步没有 inflight 请求，`remap` 全 -1；上一步是 placeholder 时本步的 `gather_input_ids` 不读上一步结果（`worker.py:199` 的判断）。2.8 的 CUDA graph：placeholder decode 步走最小的桶。
- **已备好**：`SchedulerOutputs.is_empty()`；`_placeholder_seq_metadata` 的数据类（照 `model_runner.py:386`）；`tests/test_5_3.py` (c) placeholder 步的输出被丢弃且不影响下一步的 `remap`。
- **你写什么**：`Worker.execute_model_step` 里 `is_empty()` 时换成 dummy 序列的分支；`post_process` 丢弃输出；`gather_input_ids` 里"上一步是 placeholder"的判断。最容易写错的一处：placeholder 步的 `remap` 不是"跳过"，是全 -1 地走一遍，跳过的话下一步的 inflight 计数就和别的 rank 不一样。
- **改哪里**：

  | 文件 | 函数 | 做什么 |
  |---|---|---|
  | `nanovllm/engine/model_runner.py` | `_placeholder_seq_metadata` | dummy 序列：block 0、slot 0 |
  | `nanovllm/engine/worker.py` | `execute_model_step`、`gather_input_ids` | 空 / placeholder 步走正常 forward；上一步是 placeholder 时不读上一步结果 |
  | `nanovllm/engine/llm_engine.py` | `post_process` | placeholder 步输出置 None |

### 任务 C：退出条件和步型统计（约 20 分钟，你写约 30 行）

- **目标**：任一 rank 有活全组都不退出；1.1 的 `StepRecord` 多 `step_kind ∈ {prefill, decode, empty_prompt, placeholder}` 和 `vote_us`，报告里给每种步的比例。
- **思路**：对回"`has_unfinished_requests` 也要组内 allreduce"：一个 rank 退出了 step 循环，别人就在 all-to-all 里等它，所以退出也是一次 gloo `MAX` allreduce。步型和投票耗时记进 `StepRecord`，验收时把 8 份记录对齐比，就能看出各 rank 是否同型、placeholder 占了多少。
- **已备好**：`StepRecord` 的两个新字段和报告里按步型分组的统计；`tests/test_5_3.py` (d) 5.2 全过。
- **你写什么**：`has_unfinished_requests` 的 gloo `MAX` allreduce；`step()` 里给 `step_kind` 和 `vote_us` 赋值。最容易写错的一处：`has_unfinished_requests` 要算上 2.11 还在编译的 SO 请求（`llm_engine.py:674`），漏了它本 rank 会提前退出。
- **改哪里**：

  | 文件 | 函数 | 做什么 |
  |---|---|---|
  | `nanovllm/engine/llm_engine.py` | `has_unfinished_requests`、`step` | gloo `MAX` allreduce；`step_kind`、`vote_us` |
  | `nanovllm/engine/stats.py`、`bench/metrics.py` | `StepRecord`、报告 | 新字段；每种步的比例 |

写完用 `check-step 5.3` 验收。

## 验收

同一个实验重跑：

1. 混合负载下 8 卡不卡死，跑完；每步的 `step_kind` 各 rank 一致（把 8 份 `StepRecord` 对齐比）。
2. 孤立 rank（只有 rank 0 有请求）：它的 prefill 最多等 `prefill_any_attempt_interval` 个 decode 步；其它 rank 全程跑 placeholder 步；统计里 placeholder 的比例写进报告。
3. ZOS 不变：每步仍然一次 GPU 同步，投票的时间在 `cpu_schedule` 里体现为几十微秒。
4. 没有死循环：构造 running 满 + waiting 非空 + 块不够的情况，第二轮投票让全组转 decode。
5. `tests/test_5_3.py`：(a) 投票逻辑的纯函数版（给定各 rank 的 `want / scheduled`，输出每个 rank 的步型）和真实多进程一致；(b) `decode_step` 各 rank 每步一致；(c) placeholder 步的输出被丢弃且不影响下一步的 `remap`；(d) 5.2 全过。
6. **解释**（由你说）：投票为什么能绑在 `decode_step` 上而不用再同步一次？`vote_us` 几十微秒为什么不影响 ZOS，换成 NCCL 就会影响？孤立 rank 的 prefill 等的是 100 步而不是 70 步，这 30 步的差是在换什么？

**新浮现的问题**：混合负载下各 rank 的 MoE 时间不一样，最慢的 rank 决定整步；看 `moe_tokens_per_expert`，某几个专家的 token 数是平均值的几倍，它们所在的 rank 拖慢所有人。这是 5.4。

## 常见坑

- 投票的 allreduce 次数每步各 rank 必须相同：任何"只有某些 rank 才调用"的集合通信都是死锁。第二轮投票不管本 rank 想不想都要参加。
- `decode_step` 要在 prompt 步（含空 prompt 步）清零，否则各 rank 的投票点错开。
- placeholder 步也要过 EPLB 的统计和 2.9 的性能曲线更新吗：DeepInfer 不记录（`record_runtime` 排除 placeholder，`worker.py:130-137`）。
- `has_unfinished_requests` 要算上 2.11 还在编译的 SO 请求（`llm_engine.py:674`）。
- gloo 的超时默认很长（`DEEPINFER_GLOO_TIMEOUT` 4 小时）；调试死锁时先把它调短。
