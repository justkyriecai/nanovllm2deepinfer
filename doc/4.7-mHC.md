# 4.7：四条残差，每个子层读写四倍的 hidden

> 起点：4.6 做完的代码　轴：3 访存 / 4 模型结构

| | |
|---|---|
| **问题** | 把 mHC 按 HF 的数学写成 PyTorch 之后整层对拍过了，但 Nsight 里每个子层前后多出一串小 kernel，`[n, 4, H]` 的 trunk 被读三四遍，decode batch 64 时 attention 本身只占这一段的一半。本质是四路残差的系数计算、pre 混合、post 混合都是逐 token 的小矩阵运算、各自访存瓶颈，而上一个子层的 post 和下一个子层的 pre 读的是同一份 trunk，融合之后 trunk 每子层只过一遍 |
| **实验** | `nsys profile python -m tests.v4.harness --layers 0..K --decode --batch 64`，盯每个子层前后 trunk 相关 kernel 的个数和它们占一层时间的比例 |
| **硬件 / 费用** | 1×B200 + V4.1-Flash 前几层权重，Modal 约 $6.25/h；对拍加 Nsight 前后对比约 3 小时，约 $20 |
| **学到** | 一个子层 trunk 读写从 `(3 读 + 1 写) × 4H` 降到 `(1 读 + 1 写) × 4H`，靠的是把"上一子层的 post + 本子层的 pre + RMSNorm + FP8 cast"做成一个 kernel，子层拿到的直接是 `(fp8, sf)`；`fn` 是 fp32 且已经折进 norm 权重，系数 GEMM 必须用 TF32 / fp32，bf16 会让 Sinkhorn 后的 comb 矩阵差到 1e-2；`hc_shifted` 下子层 t 用的 pre 系数是子层 t−1 算出来的，第一个子层用 one-hot，模型末尾直接用最后一个 pre 把四路混成一路 |
| **时长** | 发现 + 分析约 2 小时；任务 A 约 40 分钟、任务 B 约 40 分钟、任务 C 约 20 分钟；验收约 1 小时。改动约 500–800 行 |

## 发现问题

**关注什么**：V4.1 的残差流。config 里 `hc_mult = 4`，`hc_shifted`，HF 权重里每层有 `hc_attn_fn / hc_ffn_fn [(2+4)×4, 4×H]`、`hc_attn / hc_ffn [(2+4)×4]`、`hc_attn_scale / hc_ffn_scale [3]`。这些权重在 4.6 之前都没用上，所以 harness 只能比 attention 模块，比不了整层。

先按 HF 的 `modeling` 把 mHC 的数学写成 PyTorch（每个子层：从四路残差算三组混合系数，pre 混合出子层输入，post 把子层输出混回四路），整层对拍：

```bash
python -m tests.v4.harness --layers 0..K --compare layer
nsys profile python -m tests.v4.harness --layers 0..K --decode --batch 64
```

**先预测**：一个子层（attention 或 MoE）前后，残差流要读写多少字节？和子层本身的权重读取比呢？

**现象**：

- 整层对拍过了（数学对了）。
- Nsight 里每个子层前后多了一串小 kernel：`[n, 4, H]` 的 bf16 trunk 被读了三四遍（算系数一遍、pre 混合一遍、post 混合读一遍写一遍、Sinkhorn 若干小 kernel）。decode batch 64 时 attention 本身的 kernel 只占这一段的一半，剩下是 trunk 搬运和 launch。
- 把残差流的字节数算出来：每 token 每子层 `4 × H × 2 B` 读三遍写一遍，40 层 80 个子层，对 decode 来说和读一层专家权重是一个量级。

## 分析问题

- **追问链**：子层前后多了 kernel → 四路残差要在每个子层前算系数、混合、子层后再混回去 → 这些操作是逐 token 的小矩阵运算（`[4, H]` 和 `[(2+4)×4, 4H]` 的乘法、`[4, 4]` 的 Sinkhorn），单独做每个都是访存瓶颈 → 上一个子层的 post 和下一个子层的 pre 读的是**同一份 trunk** → 把 post 延迟到下一个 pre 一起做，trunk 只过一遍 → 顺便把 RMSNorm 和 FP8 cast 也做了，子层拿到的直接是 `(fp8, sf)` → 一个 kernel（`mega_mhc`）。
- **本质**：mHC（manifold-constrained hyper-connections）用 `hc_mult` 条残差流代替一条，表达能力换访存；推理时的解法是把"post + pre + norm + cast"这条链融合，让 trunk 每子层只读写一次。
- **量化**：V4.1 `H` 按 config；一个子层 trunk 读写从 `(3 读 + 1 写) × 4H × 2 B` 降到 `(1 读 + 1 写) × 4H × 2 B`，加上 norm 和 cast 不再单独读写 hidden。
- **理论**：Hyper-Connections（Zhu et al. 2024）和 DeepSeek 的 mHC 报告（不在清单里）：多路残差 + 流形约束（comb 矩阵 Sinkhorn 归一化成双随机矩阵）。`reference/gpu-perf-engineering-resources/` §2 "Foundational kernel exercises" 里的归约和融合是这一节 kernel 的基本功。
- **DeepInfer 怎么做**（`models/v4_modules/hc.py`、`mhc_ops.py`、`hc_blocks.py`）：
  - **参数**（`hc_blocks.py:18`）：每个子层 `fn [(2+m)m, mH]` fp32（HF 已把 norm 权重折进去）、`base [(2+m)m]`（前 `m` 个是 pre，中 `m` 个是 post，后 `m²` 个是 comb 的初值）、`scale [3]`。
  - **pre**（`hc.py:317`）：`mhc_pre_norm_fn`（`mhc_ops.py:117`）对 trunk `[n, 4H]` 做一次 **TF32** GEMM 得 `[n, (2+m)m]` 的 mixes 和平方和（split-K，`:102`），RMSNorm epilogue；`mhc_pre_split_mixes`（`:60`）按 scale / base 切成 `pre_layer_mix [n, m, 1]`、`post_layer_mix [n, m, 1]`、`comb_res_mix [n, m, m]`；comb 过 `sinkhorn_normalize`（`:95`，`hc_sinkhorn_iters` 次）；`layer_input = Σ_i pre_i × trunk_i`（`mhc_pre_apply_mix`，`:40`）；然后 RMSNorm（+ FP8 cast）得子层输入。
  - **post**（`hc.py:164`）：`trunk' = comb_res_mix × trunk + post_layer_mix ⊗ out`（`mhc_post`，`mhc_ops.py:31`）。
  - **shifted**（`hc.py:343-358`）：`hc_shifted` 时子层 t 用的 pre 系数是子层 t−1 算出来的（第一个子层用 one-hot，`:45`），本子层算出的 pre 传给下一个；模型末尾不用 `HCHead`，直接用最后一个 pre 把四路混成一路（`deepseek.py:230`）。
  - **延迟 post**：`HCLazyPostData`（`hc_lazy.py:15`）把 `residual / post_layer_mix / comb_res_mix / pre_layer_mix` 带到下一个子层；`_hc_fused_post_pre`（`hc.py:174`）：有完整 lazy 数据且无干预时走 `_mega_mhc`（`:229`），一个 `deep_gemm.mega_mhc`（`:270`）做上一个 post + 本次 pre + norm + FP8 cast，输出 `new_residual`、三组新系数、`y_bf16`、`y_fp8 / sf`；FP8 的 scale 布局按下游要求直接写（Mega MoE 的 `x_sf` 和 shared 的 sf，`:258-262`；或 MXFP8 的 TMA 列主序 `:266-268`）。第一层没有 post，走 `expand_to_mhc`（`:206`）+ 单独 pre；engram 层要在 post 和 pre 之间插干预（4.8），不能融合（`:195`）。
  - **条件**：`use_mega_mhc` 要求 `hc_mult == 4` 且 `fn` 的列数是 `4 × 1024` 的倍数（`hc.py:99`）。
  - **末尾**：`HCHead`（`:367`）非 shifted 时用 `hc_head_layer_fn` 把四路混成一路。

**思考题**：按 config 的 `H`，decode batch 64 时一个子层的 trunk 读写从 4 次降到 2 次省了多少字节？40 层 80 个子层加起来，和一步 decode 读一遍专家权重比是几分之几？

## 解决问题

先用 PyTorch 把数学写对并整层对拍（任务 A），再把 post 延迟到下一个 pre 融合成一个 kernel（任务 B），最后让 norm 的输出直接是下游 GEMM 要的 FP8 布局（任务 C）。

### 任务 A：PyTorch 版 mHC（约 40 分钟，你写约 120 行）

- **目标**：整层对拍通过：harness 上前 `K` 层（含 mHC）的层输出和 DeepInfer 一致，prefill 和 decode；`hc_shifted` 的末尾混合和 DeepInfer 的最终 hidden 一致。
- **思路**：照分析里的 pre / post / shifted 语义写 PyTorch 参考：`expand`（第一层把一路扩成四路）、`pre_norm_fn`（TF32 GEMM + RMSNorm epilogue）、`split_mixes`（按 scale / base 切成三组）、`sinkhorn`、`apply_mix`、`post`。层的 forward 改成 `attn_norm_forward → attn → ffn_norm_forward → mlp`，残差是 `[n, 4, H]`。先有一个对得上的参考，任务 B 的融合 kernel 才有东西可比。
- **已备好**：**新建**的 `nanovllm/layers/mhc.py` 的函数签名；`fn / base / scale` 的装载（HF 权重名到层对象的映射，`base` 三段的切分）；harness 的 `--compare layer`；`tests/test_4_7.py` (b)(c) 的用例壳。
- **你写什么**：六个函数的函数体，层 forward 的改写。最容易写错的三处：`fn` 是 fp32 且已折进 norm 权重，系数 GEMM 要用 TF32 / fp32，bf16 会让 Sinkhorn 后的 comb 矩阵和 DeepInfer 差到 1e-2；`base` 的三段顺序是 pre、post、comb，`comb` 初值是 `eye × 2res − res` 的展开，装载时别转置；shifted 下第一个子层的 pre 是 one-hot（`layer_id % m` 那一路），不是从 trunk 算的。
- **改哪里**：

  | 文件 | 函数 | 做什么 |
  |---|---|---|
  | `nanovllm/layers/mhc.py` | `expand`、`pre_norm_fn`、`split_mixes`、`sinkhorn`、`apply_mix`、`post` | PyTorch 参考 |
  | `nanovllm/models/deepseek_v4.py` | 层的 `forward` | `attn_norm_forward → attn → ffn_norm_forward → mlp`，残差 `[n, 4, H]`；末尾按 shifted 用最后一个 pre 混成一路 |

### 任务 B：延迟 post + 融合（约 40 分钟，你写约 150 行）

- **目标**：post 不在子层后做，带到下一个子层的 pre 里，一个 Triton kernel 做"上一个 post + 本次 pre + norm + cast"；对拍过了再换成 `deep_gemm.mega_mhc`，Nsight 里每个子层前后的 trunk kernel 从一串变成一个。
- **思路**：`HCLazyPostData` 把 `residual / post_layer_mix / comb_res_mix / pre_layer_mix` 带到下一个子层；`fused_post_pre_norm` 的输入是上一子层输出 `[n, H]`、lazy 数据、本子层 `fn / scale / base`，输出新 trunk、三组系数、norm 后的 bf16 和 `(fp8, sf)`。Sinkhorn 在 kernel 内做（`4×4` 矩阵迭代 10 次，每 token 一个 program）。第一层没有 post，走 `expand + pre`；末尾按 shifted 走最后一个 pre。Triton 版对拍过了再把它换成 vendor 的 `deep_gemm.mega_mhc`，布局要求照 `hc.py:244-270`。对应分析里"post 和 pre 读的是同一份 trunk，融合后只过一遍"。
- **已备好**：`HCLazyPostData` 的 dataclass 和 `clear()`；Triton kernel 的 launch 包装和 grid 计算；`use_mega_mhc` 的条件判断（`hc_mult == 4` 且 `fn` 列数是 `4 × 1024` 的倍数）；`tests/test_4_7.py` (a) 的随机 trunk / 随机 fn 用例。
- **你写什么**：Triton kernel 的函数体（GEMM 得 mixes 和平方和 → 切分 → Sinkhorn → post 混合 → pre 混合 → RMSNorm → cast），层 forward 里 lazy 数据的传递和第一层 / 末层的特殊路径。最容易写错的两处：lazy 数据在用完后要 `clear()`，否则每层多持有 4 个 `[n, 4, H]` 的张量，prefill 显存爆；2.12 的 batch-invariant 要求 split-K 的 prenorm GEMM 归约顺序固定。
- **改哪里**：

  | 文件 | 函数 | 做什么 |
  |---|---|---|
  | `nanovllm/layers/mhc.py` | `HCLazyPostData`、`fused_post_pre_norm` | lazy 数据；Triton 融合 kernel；之后换 `deep_gemm.mega_mhc` |
  | `nanovllm/models/deepseek_v4.py` | `attn_norm_forward`、`ffn_norm_forward` | 有 lazy 数据走融合，第一层走 `expand + pre`，末尾按 shifted |

### 任务 C：FP8 输出布局（约 20 分钟，你写约 40 行）

- **目标**：norm 的输出直接是下游 GEMM 要的 `(fp8, sf)`，attention 的 `q_a_kv_swa_proj` 和 MoE 的 gate / dispatch 不再单独 cast；反量化后和 bf16 输出一致。
- **思路**：3.3 的 FP8 cast 在这里被融进 mHC kernel。4.9 会要求把 sf 直接写进 Mega MoE 的 buffer，这一节先按普通的 TMA 对齐布局输出，留一个 `cast_kwargs` 参数给 4.9 接。对应分析里"顺便把 RMSNorm 和 FP8 cast 也做了"。
- **已备好**：`cast_kwargs` 的参数透传；`tests/test_4_7.py` (d) 的反量化比较。
- **你写什么**：kernel 里 cast 和 sf 的写出，下游两处去掉单独的 cast。最容易写错的一处：sf 的布局要按下游 GEMM 的要求（TMA 对齐），和 3.3 单独 cast 时的布局不一定相同，反量化一致不代表 GEMM 读到的 scale 对。
- **改哪里**：

  | 文件 | 函数 | 做什么 |
  |---|---|---|
  | `nanovllm/layers/mhc.py` | `fused_post_pre_norm` 的 cast 段 | 输出 `(fp8, sf)`，`cast_kwargs` 控制布局 |
  | `nanovllm/models/deepseek_v4.py` | `V4Attention` 的 `q_a_kv_swa_proj`、MoE 的 gate / dispatch | 直接吃 `(fp8, sf)`，去掉单独 cast |

## 验收

1. 整层对拍：harness 上前 `K` 层（含 mHC）的层输出和 DeepInfer 一致，prefill 和 decode；`hc_shifted` 的末尾混合和 DeepInfer 的最终 hidden 一致。
2. 同一个实验重跑：每个子层前后的 trunk 相关 kernel 从一串变成一个，decode batch 64 下一层的时间下降，报告里给 Nsight 的前后对比。
3. `tests/test_4_7.py`：(a) 融合 kernel 和 PyTorch 参考一致（随机 trunk、随机 fn，fp32 容差按 TF32 定）；(b) Sinkhorn 输出行列和都接近 1；(c) 第一层（无 post）和末层（shifted 混合）路径；(d) `(fp8, sf)` 输出反量化后和 bf16 输出一致；(e) 前面全过。
4. **解释**（由你说）：一层时间降的那部分是从哪里省出来的，是 kernel 数还是字节数？按"量化"里的算式算出来的字节节省和 Nsight 里的时间节省对得上吗，对不上差在哪？

**新浮现的问题**：config 里 `engram_layer_ids` 指定的几层，在 post 和 pre 之间还要插一个 n-gram 查表的干预，而且查表的表比显存大。这是 4.8。

## 常见坑

- `fn` 是 fp32 且已经折进 norm 权重，系数 GEMM 要用 TF32 / fp32，bf16 会让 Sinkhorn 后的 comb 矩阵和 DeepInfer 差到 1e-2。
- `base` 的三段顺序是 pre、post、comb，`comb` 初值是 `eye × 2res − res` 的展开，装载时别转置。
- shifted 下第一个子层的 pre 是 one-hot（`layer_id % m` 那一路），不是从 trunk 算的。
- lazy 数据在用完后要 `clear()`，否则每层多持有 4 个 `[n, 4, H]` 的张量，prefill 显存爆。
- 2.12 的 batch-invariant：split-K 的 prenorm GEMM 归约顺序要固定。
