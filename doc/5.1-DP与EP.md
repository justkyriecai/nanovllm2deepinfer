# 5.1：一张卡上每个专家只分到几个 token

> 起点：4.11 做完的代码　轴：6 分布式

| | |
|---|---|
| **问题** | 单卡 MoE decode 并发 256 时每个专家只分到 24 个 token，一步却要读全部 64 个专家的权重，专家 GEMM 的 `M = 24`，时间全在读权重；nano-vllm 的 TP 把每个专家切成 8 份，`M` 不变，读取量也不变。本质：MoE 的访存成本取决于一步命中的专家总量，要让一个专家看到更多卡的请求，就得专家分到各卡（EP）、请求也分到各卡（DP），attention 不切 |
| **实验** | `python -m bench.run --scenario steady_decode --model ~/huggingface/DeepSeek-V2-Lite --max-num-seqs 256 --report moe`，盯每专家的 token 数：单卡 24，8 卡 DP + EP 之后应到 192 左右 |
| **硬件 / 费用** | 8×H100 + DeepSeek-V2-Lite（机制用 V2-Lite 做，5.7 才换 V4.1-Flash 和 B200），Modal 约 $32/h；单卡对照加 8 卡反复起停约 4–6 小时，约 $150–200 |
| **学到** | TP 对 MoE 没有用：切专家只是把同样的权重读取量分到 8 张卡，每专家的 `M` 一点没变；DP + EP 让每卡只读 1/8 的专家而每专家的有效 batch 乘以 8，代价是每层 MoE 前后各一次 all-to-all，所有卡每步必须同时到达；控制面的集合通信走 gloo 默认组，NCCL 子组懒初始化后用一次 dummy allreduce 建 comm，不碰 CUDA stream |
| **时长** | 发现 + 分析约 3 小时；任务 A 约 40 分钟、B 约 40 分钟、C 约 20 分钟；验收约 2 小时。改动约 800–1200 行 |

## 第 5 章在做什么

第 4 章把 V4.1-Flash 的每一层都对上了，但一张卡装不下整个模型。第 5 章做分布式，做完达到 P3（系统对齐）。5.1–5.6 在 8×H100 上用 V2-Lite 做**机制**（DeepEP、DeepGEMM 的 FP8 路径、FlashMLA 都支持 Hopper），5.7 换到 8×B200 跑 V4.1-Flash 全模型，和 DeepInfer 的 PPL 黄金基线逐样本对。

DeepInfer 的并行方式和大多数引擎不同，先把这件事说清楚：

- **没有 TP。** `model_parallel_size = context_parallel_size`（`config.py:171`）。attention 是纯 DP：每张卡一个完整的 attention 副本，处理自己的请求。
- **MoE 用 EP。** 专家分到各卡，token 通过 all-to-all 送到专家所在的卡。
- **一卡一进程**，`world_size = dp × cp`（CP 在 5.5）。每个 DP rank 是一个独立引擎，有自己的 C++ 调度器。DP rank 之间唯一的耦合是 EP 的集合通信，所以每步必须同型（5.3）。

## 发现问题

**关注什么**：3.2 的结论是单卡 MoE decode 读全部专家权重，每个专家只服务几个 token。把并发开到最大，看每个专家的有效 batch。

```bash
python -m bench.run --scenario steady_decode --model ~/huggingface/DeepSeek-V2-Lite --max-num-seqs 256 --report moe
```

**先预测**：V2-Lite 64 个专家、top-6，并发 256 时每个专家平均分到多少个 token？一步要读多少专家权重？如果有 8 张卡，每张卡只放 8 个专家、各自服务自己那 256 个请求送来的 token，每个专家分到多少？

**现象**：

- 单卡：每专家 `256 × 6 / 64 = 24` 个 token，一步读全部 64 个专家（3.2 的数字）。专家 GEMM 的 `M = 24`，算力利用率个位数，时间全在读权重。
- nano-vllm 的 TP 模式（`tensor_parallel_size = 8`）：每张卡放全部 64 个专家的 1/8 切片，每层一次 allreduce；每个专家的 `M` 还是 24，权重读取量不变，只是分到 8 张卡上各读 1/8，再加通信。并发和显存都没有变好。
- 想要的是：8 张卡各跑 256 个请求（DP），每张卡只放 8 个专家（EP），token 按路由送到专家所在的卡。每个专家分到 `8 × 256 × 6 / 64 = 192` 个 token，`M` 大 8 倍，权重读一遍服务 8 倍的 token。

## 分析问题

- **追问链**：每专家 batch 小 → 一张卡上的请求数有限（KV 容量）→ 要让一个专家看到更多卡的请求 → 专家不复制，分到各卡（EP），请求也分到各卡（DP）→ 每层 MoE 前后各一次 all-to-all（dispatch / combine）→ attention 部分不切（DP 副本），省掉 TP 的每层 allreduce → 代价：所有卡每步必须同时到达 all-to-all（5.3），专家负载不均时最慢的卡决定步时间（5.4）。
- **本质**：MoE 的访存成本取决于"一步被命中的专家总量"（3.2）。DP + EP 让每张卡只读 1/8 的专家，而每个专家的有效 batch 乘以 8。TP 对 MoE 没有这个效果。
- **量化**：V2-Lite 8 卡 EP：每卡每步读 8 个专家 `≈ 1.5 GB / 8 ≈ 190 MB`，加 shared expert 和 attention 权重；每卡并发 256，总并发 2048。all-to-all 每层每卡发送 `256 × 6 × H × 1 B（FP8）≈ 3 MB`，NVLink 下几十微秒。
- **理论**：`reference/gpu-perf-engineering-resources/` §5 "Mixture-of-experts serving"：GShard（EP 的 dispatch / combine 定义）、DeepSeek-V3（DP attention + EP MoE 的部署设计，为什么不用 TP）；§5 "Parallelism, collectives, and topology"：NCCL 和 NVLink 拓扑。
- **DeepInfer 怎么做**：
  - **分组** `ParallelProcessGroup.create_process_groups`（`parallel_utils/parallel_state.py:70`）：从一个 rank 向量用 `einops.rearrange` 切出 `world / local / dp / cp / ep / ep_in_dp / enp` 七种组，每种 NCCL 组配一个 gloo 镜像（`cpu_dp_group / cpu_cp_group / cpu_ep_in_dp`）。EP 组是连续的 `ep_size` 个 rank；`ep_size == world` 时直接复用 world 组。`_split_group_cached`（`:27`）避免同一组建两次。
  - **默认进程组是 gloo**（`worker/base.py:334`）：NCCL 子组懒初始化，`init_device_groups`（`parallel_state.py:173`）对每个 NCCL 组跑一次 dummy allreduce 强制建 comm，**单 rank 组也不跳过**（DeepEP 的 engram 要复用这个 comm 的指针）。控制面的集合通信（投票、`has_unfinished_requests`）走 gloo，不碰 CUDA stream。
  - **启动**：`_init_distributed_environment`（`base.py:315`）：`rank = engine_rank × cp_size + cp_rank`，`dist.init_process_group("gloo")`，然后 `init_parallel_groups`。每个 DP rank 一个 `LLMEngine`（`examples/_launch.py` 的 `launch_dp` 用 spawn 起 `dp_size` 个进程，每个进程跑 `main(dp_size, dp_rank)`），`CUDA_VISIBLE_DEVICES` 按 `engine_rank` 切（`examples/_config.py:55`）。
  - **MoE**：`DeepseekMoE.__init__`（`mlp.py:148`）：`num_local_physical_experts = num_physical_experts // ep_size`，每卡只装自己的专家（`FusedExperts` 的 `n_local_routed_experts`，`moe.py:70`，HF 按名字只装本 rank 的）；gate 在每卡上算全部 `num_routed_experts` 的分数，`topk_idx` 是全局专家 id；dispatch / combine 用 DeepEP（5.2），这一节先用 `torch.distributed.all_to_all_single` 的朴素版。
  - **block 数跨 rank 一致**：`profile_num_available_blocks` 末尾 `all_reduce(SUM) // world // 2 × 2`（`base.py:264-266`），所有 rank 的 KV 块数相同，否则调度决策（watermark）各 rank 不一样，5.3 的投票会乱。
  - **CUDA graph 和 EP**：all-to-all 在 graph 里要用固定 buffer，DeepEP 的 buffer 就是为此；朴素版先 `enforce_eager`。

**思考题**：EP 把每卡每步的专家权重读取量压到约 190 MB，但每卡 256 个请求的 KV 一点没少。V2-Lite 的 MLA 压缩 KV 每 token 是 27 层 × 576 × 2 B，按每个请求上下文 1000 个 token 算一算：8 卡 EP 之后，decode 一步的访存大头是专家权重还是 KV？这对 5.5 和第 4 章的压缩 KV 意味着什么？

## 解决问题

### 任务 A：去掉 TP，建分组和启动（约 40 分钟，你写约 120 行）

- **目标**：`python -m bench.launch_dp --dp 8 --ep 8 -- ...` 起 8 个进程，每个进程一个引擎；`ParallelProcessGroup` 给出 `world / local / dp / cp / ep / ep_in_dp / enp` 七种组和它们的 gloo 镜像；`tensor_parallel_size` 从代码里消失。
- **思路**：对回分析里"attention 是纯 DP、MoE 用 EP、一卡一进程"那一条。分组是从一个 rank 向量切出来的纯函数，先写它、在 CPU 上测；进程组分两层，默认组用 gloo 承载控制面，NCCL 子组只给数据面，懒初始化后每个组跑一次 dummy allreduce（单 rank 组也不跳过）。这一节 `ep == dp`、`cp = 1`。
- **已备好**：`Config` 的 `data_parallel_size / expert_parallel_size / engine_rank` 字段和它们到 `ModelRunner` 的传递；`bench/launch_dp.py` 的 spawn 骨架（`dp_size` 个进程，`CUDA_VISIBLE_DEVICES` 按 rank 切，照 `examples/_config.py:55`）；`tests/test_5_1.py` (a)：`dp / ep / cp / local / world` 的 rank 列表和 DeepInfer 的 `create_process_groups` 对给定 `(dp, ep, cp)` 的输出一致（纯函数，CPU 可测）。
- **你写什么**：`create_process_groups` 里用 `rearrange` 切七种组的那段（照 `parallel_state.py:70`，`_split_group_cached` 避免同一组建两次，`ep_size == world` 时直接复用 world 组），每个 NCCL 组配一个 gloo 镜像；`init_device_groups` 的 dummy allreduce；删掉 `tensor_parallel_size` 和所有 `ColumnParallel / RowParallel` 的切分逻辑（第 3 章的 `ReplicatedLinear` 已经够用）。最容易写错的一处：各 rank 第一次 NCCL 集合通信的组不同，懒建 comm 时会死锁，所以所有组必须在启动时统一建完，不能等到第一次 all-to-all。

### 任务 B：专家分片和朴素 all-to-all（约 40 分钟，你写约 120 行）

- **目标**：每卡只装自己的 `num_local_experts` 个专家；`dispatch(x, topk_idx, topk_weights) -> (x_recv, psum_recv, handle)` 和 `combine(y, handle) -> y_out` 在 2 进程上是恒等（权重全 1）。接口和 5.2 的 DeepEP 对齐，5.2 只换实现。
- **思路**：对回"专家不复制，分到各卡；token 按路由送到专家所在的卡"。gate 在每卡上算全部专家的分数，`topk_idx` 是全局专家 id；专家 id 整除 `num_local` 就是目标 rank，`permute` 的输出按**目标 rank**分段后 `all_to_all_single` 发出，接收端再按本地专家分组；combine 反过来。`psum` 变成"本 rank 收到的每专家 token 数"，要先交换计数（一次小的 all-to-all）。先 bf16，3.3 的 FP8 版本要连 scale 一起发。朴素版先 `enforce_eager`：all-to-all 进 graph 要固定 buffer，那是 5.2 的 DeepEP 才有的。
- **已备好**：`dispatch / combine` 的签名和 `handle` 的数据类；`loader.py` 里按名字只装本 rank 专家的过滤（照 `moe.py:70` 的 `n_local_routed_experts`）；`tests/test_5_1.py` (b) dispatch → combine 在 2 进程上恒等、(c) 专家分片后每个 rank 装的权重和全量权重对应切片一致。
- **你写什么**：3.2 的 `[E, N, K]` 打包改成 `[E_local, N, K]`；`dispatch` 里按目标 rank 分段、计数交换、`all_to_all_single`、接收端按本地专家重排；`combine` 的逆过程。最容易写错的两处：gate 权重要完整装，不能按 rank 切；`all_to_all_single` 的 split sizes 发送端按目标 rank、接收端按来源 rank，两边都要给，少一边不报错、数据静默错位。
- **改哪里**：

  | 文件 | 函数 | 做什么 |
  |---|---|---|
  | `nanovllm/layers/moe.py` | `permute`、`dispatch`、`combine` | 按目标 rank 分段；计数交换 + `all_to_all_single`；接收端按本地专家分组；逆过程 |
  | `nanovllm/layers/moe.py` | 权重打包 | `[E, N, K]` → `[E_local, N, K]`，gate 完整 |
  | `nanovllm/loader.py` | 专家权重加载 | 只装本 rank 的 `num_local_experts` 个 |

### 任务 C：让 8 个 rank 看到同一个世界（约 20 分钟，你写约 40 行）

- **目标**：所有 rank 的 KV 块数相同；每个 rank 各写一份带 `dp_rank` 的报告；这一节的负载让所有 rank 同时 prefill、同时 decode。
- **思路**：对回"DP rank 之间唯一的耦合是 EP 的集合通信，所以每步必须同型"。同型在 5.3 才靠投票保证，这一节先硬约束两件事。块数：各 rank profile 出来的数不同，watermark 判断就不同，同一步有的 rank 想 prefill 有的不想，所以 profile 之后 `all_reduce(SUM) // world // 2 × 2`（`base.py:264-266`）。负载：`bench` 的场景按 rank 复制同样的请求流（`kv_pressure` 等都是确定性的），并且先关掉 2.2 的"prefill 优先"分支外的自由度，每 rank 的 `decode_step` 一样时自然同型。真正的异构负载在 5.3 解决。
- **已备好**：`bench` 场景按 rank 复制请求流的开关；1.1 的报告加 `dp_rank` 字段、每 rank 落盘一份的路径约定；`tests/test_5_1.py` (d) block 数所有 rank 相同、(e) 第 3、4 章的单卡测试在 `dp = 1` 下全过。
- **你写什么**：`profile_num_available_blocks` 末尾的 allreduce 和取整；`StepRecord` 带 rank 落盘（每卡一个进程后，2.6 的 C++ 调度器、2.7 的 ZOS 都在各自进程里，各写各的）。最容易写错的一处：取整要在 allreduce 的结果上做，所有 rank 算出同一个数；各 rank 先取整再 allreduce，平均出来的数可能不是偶数，也可能不一致。
- **改哪里**：

  | 文件 | 函数 | 做什么 |

## 验收

1. 同一个实验重跑（8 卡 DP = EP = 8，每卡并发 256）：每专家 token 数从 24 变成 192 左右，报告里给分布；总吞吐接近单卡的 8 倍以上（专家 `M` 变大后单卡吞吐也升）。
2. 正确性：8 卡的输出和单卡（EP = 1）在同样请求上 `greedy_match` 一致；`tests/kl.py` 通过。
3. `tests/test_5_1.py`：(a) 分组：`dp / ep / cp / local / world` 的 rank 列表和 DeepInfer 的 `create_process_groups` 对给定 `(dp, ep, cp)` 的输出一致（纯函数，可以 CPU 测）；(b) `dispatch → combine` 在 2 进程上是恒等（权重全 1）；(c) 专家分片后每个 rank 装的权重和全量权重对应切片一致；(d) block 数所有 rank 相同；(e) 第 3、4 章的单卡测试在 `dp = 1` 下全过。
4. **解释**（由你说）：每专家 token 从 24 到 192 只是 8 倍，总吞吐为什么能超过单卡的 8 倍？TP 模式下同样 8 张卡，为什么每专家的 `M` 还是 24？

**新浮现的问题**：Nsight 里 all-to-all 的 kernel 占满了 SM，和前后的 GEMM 串行；通信时间没有被任何计算盖住。这是 5.2。

## 常见坑

- gloo 默认组 + NCCL 子组：第一次 NCCL 集合通信会在调用点懒建 comm，如果各 rank 第一次调用的组不同会死锁；统一在启动时 `init_device_groups`。
- `all_to_all_single` 要先交换每个 rank 要发多少（split sizes），这次小通信也在关键路径上。
- gate 在每卡算的是全部专家的分数，权重要完整装，不能按 rank 切。
- 每卡一个进程后，2.6 的 C++ 调度器、2.7 的 ZOS 都在各自进程里，1.1 的 `StepRecord` 要带 rank 落盘。
- `CUDA_VISIBLE_DEVICES` 切完之后每个进程只看得到一张卡，`torch.cuda.current_device()` 永远是 0。
