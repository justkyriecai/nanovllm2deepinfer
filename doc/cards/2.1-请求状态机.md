# 卡片 2.1：请求状态机

## 要记住的 why

1. **每种结局一个终态，`is_finished` 用序比较。** 7 个状态，所有 `FINISHED_*` 排在 `RUNNING` 之后，`is_finished = status >= FINISHED_STOPPED`。每个终态对应一个 `finish_reason` 回给调用方。
   - 不这样做（只有一个 `FINISHED`）：调用方分不清"说完了""被截断""被取消""被拒绝"。引擎内部也没有状态可以标"被取消"，只能直接动队列。
   - 代价：枚举顺序变成了约定，以后加状态时不能在终态中间插入非终态。

2. **资源判断要三态：`NEVER` 立刻拒绝，`LATER` 才等。**
   - 不这样做（`can_allocate` 只返回 -1）：一个比整个 KV cache 还大的 prompt 永远排在队头，`LATER` 的 `break` 让后面的短请求全部饿死。running 清空后走到 decode 分支，`assert scheduled_seqs` 崩掉整个引擎。
   - 代价：`NEVER` 要用 `seq.num_blocks >= 总块数` 判断（`>=` 是因为 decode 至少还要一块），不能用 `num_new_blocks`，因为命中的前缀缓存块也占 cache。

3. **长度检查提前到入队：`prompt_len > max_model_len - 1` 直接 IGNORED。**
   - 不这样做：prompt 恰好 4096 时，prefill 能过，第一次 decode 要第 17 块，CUDA graph 的 `block_tables` 列数不够，抛 `RuntimeError`。
   - 代价：至少给 decode 留 1 个位置，所以 `max_model_len` 实际上限是 prompt + 1。DeepInfer 还要再留 draft token 和 inflight 的余量（2.7、2.8）。

4. **abort 只标记，不动队列，也不释放 block。** 之后它和 EOS、截断走完全相同的出队和释放路径。
   - 不这样做（从 `running` 里硬 remove）：block 漏掉（实测 648/650）。如果它本步刚被调度，`postprocess` 还会给它 `append_token`。
   - 代价：取消要晚一步才生效；`postprocess` 必须跳过已经是终态的 seq，因为 abort 是在 `step()` 外面调用的。

5. **判定结束、移出队列、释放 block 分三处做。** 判定在各入口（`add`、prefill 分支、`postprocess`、`abort`），只改状态；出队统一在 `schedule()` 开头；释放在 `step()` 里 `run` 返回之后。
   - 不这样做（像原来那样在 `postprocess` 里一起做）：现在看不出问题。等 2.7 做 ZOS，CPU 处理第 N 步时 GPU 已经在跑第 N+1 步，提前释放的 block 会被新请求覆盖，而 GPU 还在读。
   - 代价：一个请求从结束到 block 回到空闲表要多隔一步，这一步里 KV 用量偏高。

## 和 DeepInfer 的差异

| 这一节 | DeepInfer | 原因 |
|---|---|---|
| 7 个状态 | 10 个（`sequence.hpp:30`） | 少了 `SWAPPED`（它自己也没用）、`SO_FAILED`（2.11）、`VE_FAILED`（多模态） |
| 释放在本步 `run` 返回之后 | 在下一步 forward 发射之后 | 同一个思路。ZOS 下 postprocess 本身就晚一步，所以 DeepInfer 释放得更晚（2.7） |
| 入队只查 `max_model_len - 1` | `prompt_limit` + `runtime_max_model_len` | 还要给 draft token 和 inflight 留余量（2.7、2.8） |
| 清 waiting 里的死请求只为了不漏 | 还为了 DP 投票 | 只剩死请求的 rank 会让投票卡住（5.3） |
| 没有 | `prompted` 队列、`fork` | 2.4 |

## 可以忘的细节

| 细节 | 位置 |
|---|---|
| `SequenceStatus` 改成 `IntEnum` 才能用 `>=` 比较 | `sequence.py:9` |
| `FINISH_REASONS` 表，非终态返回 `None` | `sequence.py:20` |
| 预留 `total_inflight_tokens = 0`，算进 `num_blocks`，现在行为不变 | `sequence.py` |
| running 为空时 prefill 分支即使没排出也返回 `([], True)`，`step()` 不调 `run` | `scheduler.py`、`llm_engine.py` `step()` |
| `StepRecord.finished` 记"本步结束"的请求，释放在下一步 | `llm_engine.py` `step()` |
| IGNORED 的请求没分配过 block，`deallocate` 遇到空 `block_table` 什么也不做 | `block_manager.py:104` |
| outputs 从 `(seq_id, token_ids)` 变成三元组，多了 `finish_reason` | `llm_engine.py` `step()`、`generate()` |
| 三个边界实验一个 case 一个进程，因为 before 会崩 | `bench/edge.py` |

## L4 + Qwen3-0.6B 实测（650 块 × 256）

| 实验 | before | after |
|---|---|---|
| (a) 超容量 prompt | 堵在队头，后面的短请求饿死，最后 `AssertionError` | 当场 `prompt_length_exceeded`，其余正常结束，650/650 |
| (b) 跑到一半取消 | `running.remove` 漏 2 块（648/650） | `abort_request`，下一步出队，`run` 之后释放，650/650 |
| (c) prompt = 4096，`max_tokens=2` | 第一次 decode 要第 17 块，CUDA graph `RuntimeError` | 入队即拒绝 |

1.1 回归：`steady_decode` 1676 tok/s（1.1 为 1770），抢占 131 次 / 43 个请求（1.1 为 135 / 47）。这一节不改性能，差别在 Modal 的跑间波动范围内。

## 自测题

1. abort 一个 running 请求之后，它的 block 回到了 `free_block_ids`，但 `abort` 里一行释放代码都没有。是谁、在哪一步释放的？为什么要等到 `run` 返回之后？
2. 把 `NEVER` 的条件从 `>=` 改成 `>`，一个 prompt 恰好占满全部 block 的请求会在哪一步、因为什么出问题？和实验 (c) 是同一个问题吗？
3. `postprocess` 去掉 `if seq.is_finished: continue`。用户在两次 `step()` 之间 abort 了一个本步会被调度的请求，会发生什么？它的 `finish_reason` 最后是什么？
