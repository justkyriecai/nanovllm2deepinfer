# 卡片 2.1：请求状态机

## 这一节在代码层面做了什么

1. **加了两组类型。** `SequenceStatus` 从 3 个值扩到 7 个，终态都排在 `RUNNING` 之后，每个终态对应一个 `finish_reason`；`AllocStatus` 三态 OK / LATER / NEVER。
2. **在每个入口按类型处理，只改状态。** `add` 拒绝超长 prompt；prefill 分支 NEVER 标 IGNORED 后 `continue`、LATER 才 `break`；`postprocess` 标 STOPPED / LENGTH_CAPPED；`abort` 标 ABORTED。
3. **迁移了资源释放的位置。** 原来 `postprocess` 一口气"判定 + remove + deallocate"，现在拆成三处：判定在各入口，出队统一在下一次 `schedule()` 开头，释放统一在 `step()` 里 `run` 返回之后。所有终态走同一条出口。

## 要记住的 why

1. **每种结局一个终态，不能只有一个 `FINISHED`。**
   - 不这样做：调用方分不清正常结束、被取消、被拒绝；引擎自己也不知道该对它做什么，(b) 里手动 remove 就漏了 2 个 block。
   - 代价：枚举的顺序成了约定，`is_finished` 靠 `>=`，新终态只能加在后面。

2. **资源判断要三态，NEVER 和 LATER 分开。**
   - 不这样做：永远放不下的请求被当成"等等就好"，堵在 `waiting` 队头，后面只要 1 块的请求也饿死（队头阻塞）；最后 `assert scheduled_seqs` 崩，崩的时候 cache 是空的。
   - 代价：NEVER 要按请求需要的**总**块数判，并且用 `>=`。正好占满全部 block 的请求，prefill 能过，第一次 decode 就要不到下一块。

3. **长度在入队时检查，并且生成到 `max_model_len` 就截断。**
   - 不这样做：prompt = 4096 + `max_tokens=2` 时，decode 第一步要第 17 块，CUDA graph 的 `block_tables` 只按 `max_model_len` capture 了 16 列，`RuntimeError`。
   - 代价：`max_model_len - 1` 是 prompt 的上限，给 decode 留至少一个位置；2.7、2.8 还要再给 inflight 和 draft token 留余量（DeepInfer 的 `runtime_max_model_len`）。

4. **abort 只标记，不动队列、不还 block。**
   - 不这样做：abort 是从 `step()` 外面调的，请求可能正被本步调度、正在 GPU 上跑。当场 remove，`postprocess` 会对一个不在队列里的请求 `append_token`，命中结束条件时 `running.remove` 直接 ValueError。
   - 代价：取消要晚一步才生效；`postprocess` 必须跳过已经是终态的请求，否则被取消的请求本步还会多 append 一个 token。

5. **判定、出队、释放分三处，释放放在 `run` 返回之后。**
   - 不这样做：在判定处当场 `deallocate`，block 回到空闲列表、可能立刻被分给别人，而 GPU 还在按旧 `block_table` 读写，到了 2.7 ZOS（CPU 不再等 GPU）就是两个请求踩同一块显存。
   - 代价：现在同步执行，看起来多此一举，测试也抓不出区别；但 2.7 只需要把释放再往后挪一步，不用重新设计退出路径。

6. **所有终态走同一条出口。**
   - 不这样做：abort、ignore、EOS 各写一套出队和释放，每加一种结局就多一处可能漏的地方。
   - 代价：IGNORED 的请求也要进 `waiting` 再被清出来；它从没分配过 block，`deallocate` 要能处理空 `block_table`（遍历空列表，天然成立）。

## 和 DeepInfer 的差异

| | 我们 | DeepInfer | 原因 / 哪一节补 |
|---|---|---|---|
| 状态数 | 7 | 10 | 少 `SWAPPED`（它自己也没用）、`SO_FAILED`（2.11）、`VE_FAILED`（多模态） |
| 长度检查 | `add` 时 | prefill 分支里，`prompt_limit` | 等价；DeepInfer 的 `prompt_limit` 还扣了 draft / inflight 余量（2.7、2.8） |
| 清 `waiting` 里的死请求 | `schedule()` 开头扫一遍 | decode 分支兜底再扫 | DP 下某个 rank 的 `waiting` 只剩死请求时，prefill 不会被走到，投票会被它卡住（5.3） |
| 释放时机 | 本步 `run` 返回后 | 下一步 forward 发射后 | ZOS 下 postprocess 本身就晚一步（2.7） |
| 出队 | 重建 deque，O(n) | `std::remove_if`，O(n) | 一样；每步都扫的开销 2.5 再算 |
| `fork` / `prompted` 队列 | 没有 | 有 | 2.4 |

## 可以忘的细节

| 细节 | 位置 |
|---|---|
| `SequenceStatus` 用 `IntEnum` 才能 `>=` | `sequence.py:9` |
| `finish_reason` 用 `FINISH_REASONS.get`，非终态返回 `None` | `sequence.py:64` |
| `total_inflight_tokens` 预留，`num_blocks` 已经算上它，现在恒为 0 | `sequence.py` |
| `can_allocate` 的 NEVER / LATER 第二个返回值是 0，调用方不用 | `block_manager.py:80-82` |
| `schedule()` 里 `if scheduled_seqs or not self.running` 返回空步，替代原来撞 `assert` | `scheduler.py` |
| `StepRecord.finished` 记"本步结束的"，`RequestRecord` 在下一步释放时才写 | `llm_engine.py` |
| `summarize_requests` 的 TTFT 跳过没出过 token 的请求（IGNORED、早期 abort） | `bench/metrics.py:43` |
| `queue.clear` 漏括号不报错，只是取了方法对象；队列每步翻倍 | 抄代码时踩过 |
