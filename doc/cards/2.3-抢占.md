# 卡片 2.3：抢占

## 要记住的 why

1. **抢占是拿计算换显存：把一个请求的 KV 扔掉，腾出它的 block，代价是以后把它的 `num_tokens` 全部重算一遍。** 腾出的 block 约等于 `num_tokens / 256`，要重算的是 `num_tokens`，所以每腾出一个 block 大约要重算 256 个 token，踢谁都差不多。
   - 不这样做（swap 到 CPU）：block 很小，换出去是许多次小块 PCIe 拷贝，比重算还慢（vLLM 论文 4.5 节）。DeepInfer 根本没实现 swap，`SWAPPED` 只是留在枚举里。
   - 代价：重算的 prefill 会挤占正常 prefill 的时间，被踢的请求流式输出会卡住几十秒（TBT 最大值 41 s）。
2. **踢谁，比腾出多少 block 更要紧：一定要看有没有把"跑完、还 block"这个来源堵上。** KV 满了以后，空闲 block 只有两个来源：有请求跑完，或者有请求被踢。如果踢的是快跑完的请求，就是把"马上要永久还回来的 7 个 block"换成"现在借出 7 个，以后还要拿回来，外加重算 1540 个 token"。
   - 不这样想：在 `kv_pressure` 上照 DeepInfer 改成踢输出最长的，抢占次数 154 → 167，白算的 token 13.4 万 → 20.0 万。原因是这个负载用了 `ignore_eos`，`max_tokens` 只在 768–1024 之间，输出最长的请求正好离跑完最近。
   - 代价：调度器不知道每个请求还剩多少 token，只能拿"已经输出了多少"去猜。
3. **DeepInfer 踢输出最长的（`scheduler.hpp:622-643`），源码没有给理由，注释还写着 `LCFS`。** 下面三条是推断，都还没验证：
   - 真实流量的输出长度是长尾分布，已经跑得越长，预期剩下的反而越长（平均剩余寿命随年龄增长，和操作系统的 LAS 调度同理）。这时候踢最长的，才是保住"跑完还 block"的来源。
   - 生产环境的 decode 机器必须开 `stop_preempted_request`（`:102`）。被踢的请求不会回来，腾出的 block 就是永久空出来的，踢最大的能让失败的请求最少。
   - 上下文很长时，踢掉最长的那个，attention 每步读的 KV 少得最多。
4. **踢的方向和分配的方向必须相反：降序排好以后，从尾部开始分配 block，从头部开始踢，两个指针相遇就结束。**
   - 不这样做（同一头既分配又踢）：刚分配完的请求转头就被踢掉，或者被踢的人又被拼回 `running`。
   - 代价：每一步排序一次，复杂度 O(n log n)，2.5 再算这笔账。
5. **两条路都必须立刻 `deallocate`，不能等这一步跑完再放。** 踢完以后，同一步里马上要检查 `can_append(seq)`。
   - 不这样做（照 2.1 的方式，等这一步跑完才释放）：当前这个请求还是拿不到 block，只好把自己也踢掉，白踢了一个人。
   - 代价：没有。victim 不在这一步的 batch 里，GPU 不会再读它的 KV。
6. **重算的请求回到 `waiting` 的队头；直接结束的请求进 `finished`。** 回到队头是为了不让新请求插队：它已经付过一次 prefill 了，再排到队尾会被饿死。直接结束走的是 2.1 的出口，以 `insufficient_system_resource` 返回给用户。
   - `stop_preempted_request` 不是一个划算的选项：实测吞吐只高 4%，代价是 182/512 个请求失败，这些请求已经算过的 20 万个 token 也一起扔掉。它的意义是：没有 prefill 通道的 decode 机器只能这么做（5.6）。

## 和 DeepInfer 的差异

| 这一节 | DeepInfer | 原因 |
|---|---|---|
| 最多调度 `max_num_seqs` 个，没轮到的 `running[l:r]` 留下 | `TORCH_CHECK(l == r)` | DeepInfer 的 `max_seqs` 保证每个请求都轮得到，我们可能中途停下 |
| `reset_for_recompute` 清 4 个计数 | 还要清 MTP 状态、SWA 起点 | 2.8 投机解码、4.2 SWA 才用到 |
| 只有 `stop_preempted_request` 一个开关 | 结构化输出的请求也直接结束 | 语法状态机没法倒回去，2.11 |
| `recomputed_tokens` 观测 | 只有 `num_preempted` 计数 | 为了教学而加的验收指标 |
| 测试用的假 config 都加了 `stop_preempted_request=False` | — | 2.1、2.2 的测试要能构造 `Scheduler` |

## 可以忘的细节

| 细节 | 位置 |
|---|---|
| `Config.stop_preempted_request = False`，bench 用 `--stop-preempted-request true` | `nanovllm/config.py`、`bench/run.py` |
| `StepRecord.recomputed_tokens`：这一步被踢请求的 `num_tokens` 之和，报告里给出它占产出的百分比 | `nanovllm/engine/stats.py`、`bench/metrics.py` |
| 直接结束的请求会在 `step()` 里再被 `deallocate` 一次，`block_table` 已空，等于什么都不做 | `llm_engine.py:86` |
| `token_ids` 和 `num_prompt_tokens` 都不重置，所以 `max_tokens` 照原来的进度继续算 | `sequence.py` |
| 被踢的请求不影响 TTFT（第一个 token 早就出过了），只影响 TBT 最大值 | `RequestRecord.ttft` |
| Modal 连不上时，把 `HTTPS_PROXY` 这一组代理变量去掉再跑（gRPC 过不了本地代理） | `env -u HTTPS_PROXY -u HTTP_PROXY ...` |

## L4 + Qwen3-0.6B 实测

`kv_pressure`，`--gpu-memory-utilization 0.5`：

| | before：踢队尾 | after：踢输出最长的 | stop：直接结束 |
|---|---|---|---|
| 抢占次数 / 被抢占的请求 | 154 / 143 | 167 / 148 | 182 / 182（全部失败） |
| recomputed_tokens | 13.4 万（29%） | 20.0 万（44%） | 20.3 万（54%，全部丢弃） |
| 每次抢占扔掉的 token | 873 | 1198 | 1116 |
| victim 被踢时的输出中位数 / 同一步 batch 的中位数 | 214 / 355 | 540 / 400 | — |
| 被踢过两次的请求 | 11 | 19 | — |
| 产出 token | 458266 | 458266 | 378162 |
| 吞吐 tok/s | 1497 | 1473 | 1555 |
| TBT 最大值 | 41.3 s | 37.8 s | 1.5 s |
| TTFT 中位数 | 124 s | 130 s | 84 s |

TTFT 中位数主要反映排队时间：512 个请求同时到，只装得下约 60 个。重算的 prefill 只花了约 4 s，占总时长 306 s 的 1%。在 0.6B 模型上，抢占的代价主要体现在被踢请求的卡顿上，不在吞吐上。
