# 卡片 2.2：prefill / decode 交替

## 要记住的 why

1. **prefill 卡算力，decode 卡带宽；两者串行时，decode 的 TBT 就是 prefill 的时长。** 一步的算术强度约等于这一步的 token 数（每个参数每个 token 2 FLOP，每个参数只读一次、2 字节）。L4 的平衡点约 400：decode 只有 128 个 token，在平衡点以下；prefill 有 3072 个，在平衡点以上。
   - 不这样做（来一个新请求就插一次 prefill）：每个新请求都让所有 decode 停一整步。实测 TBT p99 145 ms，是 p50 的 3.1 倍（Sarathi 说的 generation stall）。
   - 代价：只要还是一步只做一种，这种停顿就去不掉，只能控制它出现的频率。
2. **DeepInfer 一步只做一种，不像 Sarathi 那样混合。** 原因是 DP + EP 下，每个 rank 每一步必须是同一种步，否则 all-to-all 对不上，整组卡死（5.3）。
   - 不这样做（混合）：单卡没问题，多卡 DP 需要每个 rank 的混合比例也对齐，复杂度转移到通信上。
   - 代价：TBT 偶尔会有一次大尖峰，max 从 284 涨到 458 ms。
3. **每 `interval` 个 decode 步才尝试一次 prefill：把卡顿攒起来集中做，频率压到 1% 以下。** 长 prompt 在尝试点之间攒着，3–4 个合成一步做完。卡顿从 20 次降到 6 次，占 TBT 间隔的比例从 2.5% 降到 0.75%，p99 从 145 落回 61 ms。
   - 不这样做（interval 太小，比如 20）：每次尝试点只赶上一个长 prompt，等于没有合并，p99 还是 153 ms。
   - 代价：新请求的 TTFT 上限约为 `interval × decode 步 + 一次合并的 prefill`。实测 70 时长 prompt 的 TTFT 从 94 ms 涨到 1.6 s（max 3.7 s），140 时涨到 3.2 s（max 7.4 s）。
4. **KV 水位线（block 用量 ≤ 90%）才接新请求。**
   - 不这样做：prefill 会把 KV 塞满，decode 要新 block 时只能抢占。`steady_decode` 实测抢占 131 次 → 25 次，prefill 步 94 → 10。
   - 代价：留了 10% 的 KV 不给新请求用，队列里的请求要多等。
5. **prefill 排出请求就把 `decode_step` 清零，排不出就转 decode。**
   - 不清零：`decode_step` 不再是"上次 prefill 之后的 decode 步数"。空闲例外触发的 prefill 也就连不上，5.3 的 ANY 点（`decode_step != 0`）会算错。
   - 不转 decode：会返回一个空的 prefill 步，又把 `decode_step` 清零，running 满、waiting 非空时就死循环了（`scheduler.hpp:327` 的注释）。
6. **谁都可以被切，但被切的必须排最后，切完就 `break`。**
   - 不这样做（只许第一个被切）：后面放不下的请求被直接拒绝，剩下的 token 预算白白空着。
   - 代价：没有。好处是每步最多一个被切的请求，而且位置固定，2.7 ZOS 的簿记会简单很多。

## 和 DeepInfer 的差异

| 这一节 | DeepInfer | 原因 |
|---|---|---|
| 一种尝试点 | ALL 点 70 + ANY 点 100 | ANY 点给 DP 里孤立的 rank 兜底，单卡没有这种 rank（5.3） |
| 一个 `if seqs` | 两轮 allreduce 投票 | 单卡不用投票，第二轮投票退化成"排不出就转 decode" |
| 空闲例外（running 为空直接 prefill） | `_schedule` 里没有 | 我们加的。空闲时没有 decode 要保护，不必空转到下一个尝试点 |
| 被切的请求留在 `waiting[0]` | 先 `pop_front`，`process_outputs` 再 `push_front`（:1019） | 效果一样。DeepInfer 要在步与步之间清点 running 和 waiting |
| 切块长度 = 剩余预算 | `_adjust_chunk_size`、chunk checkpoint、多模态切点（:481-492） | 切完预算还会有剩余，所以要显式 `break` |
| C++ 调度器、`gil_scoped_release` | — | 2.5、2.6 讲 CPU 开销时再做 |

## L4 + Qwen3-0.6B 实测

`mixed_long_short`：

| | before（2.1） | interval=70 | 20 | 140 |
|---|---|---|---|---|
| 短请求 TBT p50 / p99 / max ms | 46 / 145 / 284 | 46 / 61 / 458 | 46 / 153 / 262 | 44 / 63 / 818 |
| 长 prompt TTFT p50 / max ms | 94 / 98 | 1618 / 3696 | 503 / 1100 | 3207 / 7401 |
| prefill 步数 | 22 | 8 | 22 | 8 |
| 吞吐 tok/s | 2424 | 2425 | 2409 | 2412 |

`steady_decode`（interval=70）：抢占 131 次 / 43 个请求 → 25 / 25，prefill 步 94 → 10，TBT p99 195 → 78 ms，吞吐 1712 → 1768 tok/s。开头连续 prefill 仍然有 8 步（空闲例外加上清零，一直做到超过水位线，见 #23）。
