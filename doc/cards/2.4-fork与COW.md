# 卡片 2.4：fork 与 copy-on-write

## 要记住的 why

1. **同一个 prompt 的 n 个输出，要由调用方明确说出来（`SamplingParams.n`），引擎不能指望 prefix cache 自己认出来。** prefix cache 的 hash 是在这一步跑完、`postprocess` 里才注册的。同一批进来的请求互相看不见，最后那个不满的 block 也永远不会被共享。
   - 不这样做：`parallel_sampling` 把 64 个请求同时发进来，prefix cache 一次都没命中。prefill 做了 8 步，共 64×2048 个 token，KV 峰值 576 个 block。
   - 代价：多了一个接口。另外只能在 prompt 算完之后再 fork，这样 child 才有 KV 可以共享。
2. **fork 只是复制 `block_table` 这个 list，再给每个 block 加一次 `ref_count`，KV 本身一个字节都不拷。** 整块的 KV 只读不写，n 个人共享同一份没有问题。
   - 不这样做（直接共用同一个 list，或者不 pin）：child 一追加 block 就改到了父请求的表；父请求结束时 `deallocate` 会把 child 还在读的 block 还回 free list。
   - 代价：每个 block 多一个计数。谁最后放手谁负责释放，所以父请求和 child 谁先结束都可以。
3. **child 要重算 prompt 的最后一个 token（`num_cached_tokens = len - 1`），所以最后那个 block 总要复制一份，哪怕 prompt 正好填满了 block。** 每个 child 要采样出自己的第一个输出 token，就需要最后一个位置的 logits；父请求那份 logits 已经被采样用掉了。重算这个 token 会把 KV 写进最后一块，所以这一块必须是 child 自己的。
   - 不这样做（child 直接从父请求的第一个输出接着往下写）：4 个输出的第一个 token 全都一样，等于只采样了 3 次。
   - 代价：每个 child 多算 1 个 token，多复制 1 个 block。peak 是 240，不是理想的 192，原因就在这里：每组 8 块共享 + 父请求 1 块 + 每个 child 2 块（复制出的一块，加上自己 decode 写的一块）× 3。
4. **child 先进 `prompted` 排队，进 running 的那一刻才做复制。** 复制要占一个新 block，这一刻不一定有空闲的，进不去就留在 `prompted` 里等，不会丢。
   - 不这样做：放进 `waiting`，会被当成新 prompt 再 prefill 一遍；fork 时直接放进 running，就得当场分配 block，分配不到也没有地方可退。
   - 代价：多一个队列。`is_finished`、abort、清理这几个地方都得记得也遍历它。5.6 的 PD 分离也走这个入口。
5. **复制在 GPU 上完成，在这一步的 forward 之前发出，和 forward 在同一个 stream 上。源 block 可以立刻 unpin。** 同一个 stream 上的 kernel 按发出顺序执行：就算 src 被还回去、马上又分配给别的请求，下一个写它的 kernel 也一定排在复制之后。
   - 不这样做（2.7 引入多 stream 以后还立刻 unpin）：复制还没执行，src 已经被别的请求的 prefill 覆盖，child 拿到的是垃圾 KV。DeepInfer 的做法是等 `clone_done_evt`（`DeferredRelease`），确认复制完成后才放。
   - 代价：现在没有。到 2.7 要换成 event。

## 和 DeepInfer 的差异

| 这一节 | DeepInfer | 原因 |
|---|---|---|
| 只在 prompt 算完之后 fork | prompt 没算完也能 fork，进 `waiting` 队头，prefill 前做 COW | 我们的 `n` 只在第一个 token 出来时触发。没有"中途分叉"的调用方（beam search、API 层的 fork） |
| src 立刻 unpin | `DeferredRelease` 等 `clone_done_evt` | 单 stream 保证了执行顺序，2.7 多 stream 以后要补 |
| `clone_blocks` 只拷 KV | 同时拷 / 清零 SSM、MTP 等状态（`state_id`） | 线性注意力、投机解码这些状态，后面的章节才有 |
| 父请求不复制，child 每人复制 1 块 | 一样 | — |
| `peak_kv_blocks`、`parallel_sampling(_fork)` 场景 | — | 为了教学而加的验收指标 |

## 可以忘的细节

| 细节 | 位置 |
|---|---|
| child 的 `arrival_time` 沿用父请求的，所以 child 的 TTFT ≈ prefill + 1 个 decode 步 | `scheduler.py:139` |
| `del seq.block_table[num_blocks:]`：父请求在 fork 之前可能已经多开了一块，child 不需要，unpin 掉 | `scheduler.py:157` |
| `clone_pairs` 由 `step()` 取走并清空，一步只调用一次 `clone_blocks`，在 run 之前 | `llm_engine.py:60` |
| `kv_cache[:, :, dst] = kv_cache[:, :, src]`：一次高级索引，把 k、v 和所有层一起拷 | `model_runner.py:216` |
| 父请求被抢占后 `num_completion_tokens` 不会归零，所以不会再 fork 一次 | `scheduler.py:184` |
| 进度条按 `sum(sp.n)` 计数 | `llm_engine.generate` |

## L4 + Qwen3-0.6B 实测

64 个输出 = 16 个 prompt × 4，prompt 长 2048，`max_tokens` 64，temperature 1.0：

| | before：`parallel_sampling`（64 个独立请求） | after：`parallel_sampling_fork`（16 个 n=4） |
|---|---|---|
| prefill 步数 × 每步耗时 | 8 × 468 ms | 2 × 470 ms |
| peak_kv_blocks | 576 | 240（理想值 192，见 why 3） |
| 吞吐 tok/s | 505 | 1285（2.5×） |
| TTFT p50 | 2099 ms | 1020 ms |
| TBT p50 / max | 69 / 3370 ms | 34 / 561 ms |
| decode 每步 wall | 68.9 ms | 34.9 ms |
| 4 个输出各不相同（prompt 长 2049，跨 block 边界） | — | 4 of 4 |

decode 一步快了一倍，但每个 seq 每步读的 KV 量和 before 一样（都是 64 × 约 2100 个 token）。不同的是 after 里 4 个 seq 读的是同一批物理 block。推测：同组的 seq 在同一时间读同一份数据，命中 L2，HBM 实际搬运的数据变少了。没有用 profiler 验证过，2.5 有了 nsys 以后可以看 attention kernel 的 DRAM 读取量。
