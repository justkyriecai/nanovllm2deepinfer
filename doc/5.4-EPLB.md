# 5.4：热点专家所在的 rank 拖慢整步

> 起点：5.3 做完的代码　硬件：8×H100，DeepSeek-V2-Lite　预计改动：500–800 行（policy 本身 150 行，可以纯 CPU 测）　轴：6 分布式

## 1. 发现问题

**关注什么**：各 rank 每步 MoE 收到的 token 数。

```bash
python -m bench.launch_dp --dp 8 --ep 8 -- bench.run --scenario steady_decode --per-rank-seed --report moe-per-rank
```

**先预测**：64 个专家的负载均匀吗？最忙的 rank 和平均比高多少？整步的时间由谁决定？

**现象**：

- 专家负载长尾：少数专家的 token 数是平均的 3–5 倍（和数据有关，代码类的请求尤其集中）。
- 每 rank 收到的 token 数（`sum(expert_count)`）最大值 / 平均值（DeepInfer 叫 `moe_lb`）在 1.3–2 之间。all-to-all 之后大家等最慢的 rank，整步时间按最大值算。
- 这个分布随时间漂移：换一批请求，热点专家换人。

## 2. 分析问题

- **追问链**：最慢 rank 决定步时间 → 热点专家在它那里 → 把热点专家**复制**到多个 rank（冗余专家），gate 选中它时在副本之间分流 → 再把所有物理专家（原始 + 副本）重新摆放，让每个 rank 的负载接近 → 负载是变的，要周期性重算、搬权重 → 统计从哪来：dispatch kernel 本来就要数每个专家收到多少 token，免费 → 搬权重走什么：单机用 symm_mem 直接读对端显存，跨机 P2P → 重算的目标是什么：每步的峰值（最慢 rank），不是平均。
- **本质**：EP 的步时间 = `max_rank(负载)`。负载均衡的杠杆是冗余副本 + 放置；统计免费、搬运低频、目标函数对准峰值。
- **量化**：`moe_lb = Σ_steps max_rank / Σ_steps mean_rank`，理想 1.0。DeepInfer 的目标是 1.05 附近。冗余专家数 `num_extra_experts`（V4.1 用 32，`examples/_config.py:79`），要让 `num_physical % ep_size == 0`（`eplb/__init__.py:21`）。
- **理论**：`reference/gpu-perf-engineering-resources/` §5 "Mixture-of-experts serving"：EPLB（DeepSeek 的专家放置和冗余）、DeepSeek-V3（冗余专家的部署策略）；DeepEP README 的 "Expert load balancing" 一节（`vendor/DeepEP/README.md:330`）列了动态冗余的相关工作。
- **DeepInfer 怎么做**（`model_executor/eplb/`）：
  - **映射**：`physical_to_logical_map [L, P]`、`logical_to_physical_map [L, E, R+1]`（-1 填）、`logical_count [L, E]`（`__init__.py:48-52`）；初始布局 `[原始 E 个, 副本按 i % E]`（`:31`）。gate 用 `logical_to_physical_map` 把逻辑专家映射到物理槽，副本之间按 token 分流（`mlp.py:392` 传给 `moe_topk_gate`）。
  - **统计**：`expert_count [L, local_P]` 由 dispatch kernel 写（`mlp.py:474` `cumulative_local_expert_recv_stats`），每步 `step()` 后清零（`:137`）；窗口 `_expert_count_window [W, L, local_P]`（`DEEPINFER_EXPERT_COUNT_WINDOW_SIZE` 默认 100）。
  - **周期**：`DEEPINFER_EXPERT_REARRANGEMENT_STEP_INTERVAL`（0 关）；首次重排提前到 1/4 周期（`:122-124`）；NORMAL 引擎默认跳过 prefill 步的统计，或者 prefill 之后立刻重排（`DEEPINFER_REARRANGE_AFTER_PREFILL_IN_NORMAL_ENGINE`，`:82-83`、`:146-165`）。
  - **policy** `rebalance_experts_global`（`policy.py:73`）：输入 `tokens_per_expert [steps, L, E]`。第一阶段逐个分配冗余副本：每轮选"加一个副本后各 step 最大每副本负载之和最小"的逻辑专家（`:109-117`，向量化，`+ arange × 1e-4` 打破平局）；第二阶段 `_batch_greedy_indices`（`:12`）把物理专家按历史负载降序逐个放到 rank 上，选使 `Σ_step max_rank 负载` 最小的 rank（`:44-71`），目标是**每步峰值**而不是均值。全部张量化，可以在 CPU 上单测。
  - **搬权重**：`_rearrange_experts`（`__init__.py:223`）：窗口统计 `scatter_add` 到逻辑专家、EP 组 allreduce；算新映射；单机 `expert_model_parallel_shuffle_inplace_intranode`（`shuffle.py:150`）：首次 `_initialize_shuffle`（`:195`）建**一层**权重的 symm_mem 镜像（`symm_mem.empty + rendezvous`），每层：barrier → 把本层权重拷进镜像 → barrier → 本地 origin→current 拷贝 → 缺的专家直接从配对 sender 的镜像 `copy_()`（`:178-217`），没有 P2P 通信；跨机用 `expert_model_parallel_shuffle_inplace`（P2P batched）。
  - **权重清单**：`_init_eplb`（`deepseek.py:324`）：`gate_up / down` 和它们的 `sf`（存的时候 `.mT` 过，通信前转回）；同构层共用一个 `ExpertLoadBalancer`。
  - **报表**：`moe_load_balance_ratio`（`:167-193`）每 `DEEPINFER_MOE_LB_STAT_INTERVAL`（128）步 all_gather 一次各 rank 的 token 数，`stats_logger` 打 `moe_lb`（`stats_logger.py:238`）。
  - **调试旋钮**：`DEEPINFER_FORCE_IMBALANCE_RATIO`（`mlp.py:367-370`）人为制造不均衡，用来测 EPLB 本身。

## 3. 要做什么

### 3.1 映射和冗余副本

**改哪里**：`nanovllm/layers/moe.py`。

- `num_extra_experts`（`Config.eplb_num_extra_experts`，按 `resolve_num_extra_experts` 对齐到 `ep_size`）；物理专家 = 逻辑 + 副本；每卡装 `num_physical / ep_size` 个物理槽；初始布局 `[原始, 副本 i % E]`。
- gate 加 `to_physical_map` / `logical_count`：选出逻辑专家后在它的副本里按 token 轮转（或 hash）分流，输出物理槽 id。
- dispatch / combine 用物理槽 id。

### 3.2 统计

- DeepEP dispatch 的 `cumulative_local_expert_recv_stats` 指向 `expert_count [L, local_P]`；每步末 `step(is_prompt)`：写进窗口、清零；每 128 步 all_gather 算 `moe_lb`，进 `StepRecord`。

### 3.3 policy

**新建** `nanovllm/engine/eplb_policy.py`（纯 PyTorch，CPU 可跑）。

- 照 `rebalance_experts_global` 的两阶段写；先写一个朴素的逐层 for 循环版本做参考，再向量化。
- 单测：和 DeepInfer 的 `policy.py` 在随机负载上输出**完全一致**（它是确定性的，平局规则一样就一致）。

### 3.4 shuffle

- 单机版：symm_mem 一层镜像 + 两个 barrier + `copy_()`；每层做。
- `_rearrange_experts` 每 `interval` 步跑一次，首次在 1/4 周期；重排期间用 `allow_cuda_sync`（2.7 的 `forbid_cuda_sync` 在这里放开）。
- `DEEPINFER_FORCE_IMBALANCE_RATIO` 的等价旋钮，用来验证。

## 4. 验收

同一个实验重跑：

1. `moe_lb` 从 1.3–2 降到 1.05 附近（写进报告，给前后的时间序列）；整步时间下降。
2. 人为不均衡（force imbalance ratio = 4）下，几个周期后 `moe_lb` 回到 1.1 以内。
3. 重排本身的耗时（每层 barrier + 拷贝）写进报告；重排前后输出不变（权重搬对了）。
4. `tests/test_5_4.py`：(a) policy 和 DeepInfer 的 `rebalance_experts_global` 在 100 组随机负载上逐元素一致（CPU）；(b) 映射的一致性：每个逻辑专家至少一个物理槽，每 rank 恰好 `local_P` 个；(c) shuffle 后每个物理槽的权重等于对应逻辑专家的原始权重；(d) gate 的副本分流覆盖所有副本；(e) 5.3 全过。

**新浮现的问题**：一个 64k 的 prompt 进来，单卡 prefill 要几秒，期间其它 7 张卡陪跑空 prompt 步（5.3）。prefill 的算力要分到多卡上。这是 5.5。

## 常见坑

- 目标函数是 `Σ_step max_rank`，不是 `max_rank(Σ_step)`：按均值优化会把两个在不同时刻热的专家放到一起。
- 平局规则决定了和 DeepInfer 能不能逐元素一致：`+ arange × 1e-4`、`argsort(stable=True)`、`argmin` 取最小 rank。
- shuffle 的镜像只有一层的量，必须两个 barrier：第一个等大家读完上一层，第二个等大家写完本层。
- sf 存的是 `.mT` 后的视图，通信前转回连续，否则 `copy_()` 搬的是错的布局。
- 重排里有 `torch.cuda.synchronize`，不能在 ZOS 的 forward 里做；放在 step 末尾，并且各 rank 同一步做（它有 allreduce 和 barrier）。
