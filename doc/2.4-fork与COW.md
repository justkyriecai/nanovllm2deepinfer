# 2.4：n=4 采样把同一个 prompt 算了 4 遍

> 起点：2.3 做完的代码　轴：1 调度 / 4 显存

| | |
|---|---|
| **问题** | 同一个 prompt 要 4 个输出，只能发 4 个独立请求。它们同时到达时 prefix cache 一次都不命中：hash 在这一步跑完、`postprocess` 里才注册，同一批 prefill 的请求互相看不见。于是 prefill 做 4 遍、prompt 的 KV 存 4 份。根因是引擎只有"请求"这一个单位，调用方没法说出"这 n 个共享同一个 prompt" |
| **实验** | `python -m bench.run --scenario parallel_sampling`（16 个 2048 token 的 prompt × 4 个输出，`max_tokens` 64，temperature 1.0），盯 prefill 步数和 `peak_kv_blocks` |
| **硬件 / 费用** | L4 + Qwen3-0.6B 即可（$0.80/h），文档数字都是 L4 实测。发现加 before / after 约 1 小时，约 $1 |
| **学到** | n 要由调用方明确说出来，prefix cache 认不出同一批里重复的 prompt；fork 只是复制 `block_table` 再给每个 block 加一次 `ref_count`，KV 一个字节都不拷；child 要重算 prompt 的最后一个 token 才能采样出自己的第一个输出，所以最后一块总要复制，哪怕 prompt 正好填满了 block；`prompted` 是"KV 已经算好、等着进 running"的入口，fork 和 PD 分离（5.6）共用；复制和 forward 在同一个 stream 上，源块可以立刻 unpin，2.7 多 stream 之后要换成 event |
| **时长** | 发现 + 分析约 1 小时；任务 A / B 各约 20 分钟；验收约 30 分钟。你写约 60 行 |

## 发现问题

**关注什么**：同一个 prompt 要多个输出时，prefill 和 KV 各花了多少。

```bash
python -m bench.run --scenario parallel_sampling --trace out/ps.jsonl
```

`parallel_sampling` 把 16 个 prompt 各发 4 遍，64 个请求同时到达，同一个 prompt 的 4 个请求 token 完全一样。

**先预测**：prefix caching 是开着的。prefill 会做几步、一共算多少 token？KV 峰值占多少 block？

**现象**（L4 + Qwen3-0.6B）：prefill 做了 8 步，一共 64 × 2048 个 token；`peak_kv_blocks` 576，正好是 64 × 9（8 块 prompt + 1 块 decode）。prefix cache **一次都没命中**：`hash_blocks` 在 `postprocess` 里、这一步跑完之后才注册，同一个 prefill batch 里的请求互相看不见。就算错开到达、能命中整块，最后那个不满的 block 也永远不会被共享，`can_allocate` 和 hash 也还是每个请求各做一遍。

## 分析问题

- **追问链**：想要 n 个输出 → nano-vllm 只有"请求"这一个单位 → 同一 prompt 的 n 个请求各自走完整流程 → 指望 prefix cache 去重？它只在请求先后到达时才命中，而 n 个输出恰恰是同时要的 → 引擎需要一个显式的接口：调用方说 `n=4`，引擎算一次 prompt，再从它分叉。
- **卡在哪种资源上**：prefill 的计算，和 HBM 容量。
- **本质**：n 个输出共享 prompt 的 KV，只在分叉点之后各写各的。这就是 copy-on-write：共享的 block 多一个引用计数，谁要往一个共享的 block 里写，谁先复制一份。
- **理论**：`reference/gpu-perf-engineering-resources/` §4 vLLM 论文 4.4 节 "parallel sampling" 和 "beam search"，refcount + copy-on-write。
- **量化**：理想情况每组 = 8 块共享的 prompt + 4 个输出各 1 块 decode = 12 块，16 组 192 块。实际会是 240：父请求不复制，用自己那一套 8 块 + 1 块 decode；每个 child 复制一块，再加自己 decode 写的一块，`8 + 1 + 3 × 2 = 15`，16 组 240。多出来的那一份复制，原因见任务 B。
- **DeepInfer 怎么做**：
  - `fork_seq`（`csrc/engine/scheduler.hpp:1061-1120`）：新 `Sequence` 共享父的 `block_table` 和 `state_id`，两者都 pin（`ref_count++`）。
  - prompt 已经算完的 fork 进 **`prompted`** 队列（`:1118`）；`_schedule_decode` 从 `prompted` 头部接进 `running`，这时只给最后一块做克隆，记 `(src, dst)` 克隆对（`:595-619`）。`prompted` 也是 PD 分离里 decode 引擎的入口（5.6）。
  - prompt 还没算完也能 fork：进 `waiting` 队头，`branch_id` 以 `_` 开头表示"prefill 前要 COW"（`:398-438`）。这条路要有"中途分叉"的调用方（beam search、API 层的 fork），`n` 接口只在第一个 token 出来之后才 fork，**这一节不做**。
  - 克隆在 GPU 上做（`clone_and_zero_states_and_blocks`，`:1264`），源 block 的 unpin 要等 `clone_done_evt`（`llm_engine.py:67-116`，`DeferredRelease`）。
  - `Blocks` 是侵入式双向链表 free list 加 `ref_count`（`block_manager.hpp:27-117`），`pin_block` 就是 `ref_count++`。

**思考题**：`block_size = 256`，prompt 恰好 2048 个 token，8 块全满。child 要采样出自己的第一个输出 token，需要哪个位置的 logits？父请求那份已经被采样用掉了，child 只能自己算一次，这次计算的 KV 写进哪一块？那它还需要复制吗？

## 解决问题

两个任务，顺着 child 的一生拆：任务 A 让 child 生出来，并和父共享 prompt 的块；任务 B 让它进 running，并在第一次写之前把最后一块复制走。

### 改动全景

| 逻辑上的一步 | 文件:函数 | 谁实现 | 目标 |
|---|---|---|---|
| fork：共享块加引用计数 | `block_manager.py`：`pin`、`unpin`；`scheduler.py`：`fork`、`postprocess` 里触发 fork | 你（任务 A） | 第一个 token 出来后 fork 出 n-1 个 child，共享父的 `block_table`，每块 `ref_count` 加 1，child 在 `prompted` 里等 |
| 进 running 时复制最后一块 | `scheduler.py`：`_admit_prompted`，以及 `schedule` / `is_finished` / `abort` 都把 `prompted` 算进去；`model_runner.py`：`clone_blocks` | 你（任务 B） | 有空闲 block 才进 running，进的那一刻复制最后一块、unpin 源块；GPU 上一次索引赋值拷完 |
| 接口和转发 | `sampling_params.py`、`sequence.py`：`n`；`Scheduler.prompted`、`Scheduler.clone_pairs` 字段；`llm_engine.py`：`step` 在 `run` 之前把 `clone_pairs` 交给 `clone_blocks`，`generate` 的进度条按 `sum(sp.n)` | 脚手架 | 和 why 无关的转发和字段 |
| 观测和场景 | `stats.py`：`StepRecord.num_used_blocks`；`bench/metrics.py`：`peak_kv_blocks`；`bench/workloads.py`：`parallel_sampling`、`parallel_sampling_fork`；`bench/run.py`：同一 `prompt_id` 用同一组 token | 脚手架 | 验收指标和对照场景 |
| 测试 | `tests/test_2_4.py` | 脚手架 | A 做完 fork 和共享相关的变绿，B 做完 COW 和 `prompted` 相关的变绿，7 条全绿，2.1–2.3 的测试全过 |

### 任务 A：fork 和 pin（约 20 分钟，你写约 30 行）

- **目标**：`SamplingParams(n=4)` 的请求 prefill 完、第一个 token 出来时，fork 出 3 个 child。child 和父共享 `block_table`，每个共享块的 `ref_count` 加 1，child 在 `prompted` 里等；父和 child 谁先结束都不会把对方的块收走。
- **思路**：对回"n 个输出共享 prompt 的 KV"。照 `fork_seq`（`scheduler.hpp:1061-1120`）。只在 prompt 算完之后 fork，child 才有 KV 可以共享。释放不用新写：`unpin` 到 `ref_count == 0` 才真正回收，`deallocate` 也是这个语义，谁最后放手谁负责还。
- **你写什么**：
  - `BlockManager.pin(block_ids)`：每块 `ref_count += 1`；`unpin(block_ids)`：每块 `ref_count -= 1`，到 0 就还回 free list。
  - `Scheduler.fork(parent)`：新建一个 `Sequence`，同样的 prompt 和采样参数，但 `n=1`；`arrival_time` 沿用父的；`block_table = parent.block_table[:]`；`num_cached_tokens = min(parent.num_cached_tokens, child.num_tokens - 1)`；`pin(child.block_table)`；进 `prompted`。
  - `postprocess`：prefill 步里 `seq.n > 1` 且 `num_completion_tokens == 1`（刚出第一个 token）时，fork `n - 1` 次。

  最容易写错的三处：`block_table[:]` 必须是一份新 list，直接赋引用的话，child 一改最后一块就把父的也改了；child 的 `n` 必须是 1，否则它自己出第一个 token 时又会 fork；`num_cached_tokens` 设成 `len - 1`，不是 `len`，让 child 重算 prompt 的最后一个 token，采样出自己的第一个输出（父那份 logits 已经用掉了），否则 4 个输出的第一个 token 全一样。父被抢占重算之后 `num_completion_tokens` 不归零，不会再 fork 一次。
- **改哪里**：

  | 文件 | 函数 | 做什么 |
  |---|---|---|
  | `nanovllm/engine/block_manager.py` | `pin`、`unpin` | 引用计数加减，到 0 回收 |
  | `nanovllm/engine/scheduler.py` | `fork` | 新 child，复制 `block_table`，pin，进 `prompted` |
  | `nanovllm/engine/scheduler.py` | `postprocess` | 第一个 token 出来后 fork `n - 1` 次 |

### 任务 B：进 running 时复制最后一块（约 20 分钟，你写约 30 行）

- **目标**：child 从 `prompted` 头部进 `running`，这一刻把最后一块复制一份：`block_table` 里换成新块，源块 `ref_count -= 1`。同一个 prompt `n=4` 只 prefill 一次，4 个输出各不相同。
- **思路**：对回"谁要往共享的 block 里写，谁先复制一份"。照 `:595-619`：`schedule()` 没有排出 prefill、走 decode 分支之前，调 `_admit_prompted()`。复制要占一个新 block，这一刻不一定有空闲的，没有就留在 `prompted` 里等，不会丢；所以 child 先进 `prompted`，不在 fork 时当场分配。复制在 GPU 上做（对应 `clone_and_zero_states_and_blocks`，`:1264`）：调度器只记 `(src, dst)` 对，`step()` 在 `run` 之前交给 `model_runner.clone_blocks`。复制和这一步的 forward 在同一个 stream 上，按发出顺序执行，所以源块可以立刻 unpin：就算它马上被还回去、分配给别人，下一个写它的 kernel 也一定排在复制之后。
- **你写什么**：
  - `_admit_prompted()`：`while prompted and len(running) < max_num_seqs`：没有空闲 block 就 `break`；`num_blocks = ceil(num_cached_tokens / block_size)`；`src = block_table[num_blocks - 1]`，`dst` 新分配，记进 `clone_pairs`；`unpin([src] + block_table[num_blocks:])`；`block_table[num_blocks - 1] = dst`，`del block_table[num_blocks:]`；状态改成 `RUNNING`，从 `prompted` 移进 `running`。
  - `schedule()` 开头的出队、`is_finished`、`abort` 都把 `prompted` 算进去。
  - `ModelRunner.clone_blocks(pairs)`：`kv_cache[:, :, dst] = kv_cache[:, :, src]`，一次高级索引，k、v 和所有层一起拷。

  最容易写错的三处：
  - prompt 正好填满 block（2048 = 8 × 256）也要复制。child 的 `num_cached_tokens` 是 2047，重算第 2048 个 token 会把 KV 写进第 8 块，这一块必须是它自己的。`test_cow_even_when_the_prompt_fills_its_blocks` 测的就是这个。
  - 父在 fork 之前可能已经为 decode 多开了一块，child 共享了它却用不上，要一起 unpin，再从 `block_table` 删掉。
  - 复制出来的块不要注册进 `hash_to_block_id`，它马上要被 child 改写。
- **改哪里**：

  | 文件 | 函数 | 做什么 |
  |---|---|---|
  | `nanovllm/engine/scheduler.py` | `_admit_prompted` | 进 running，复制最后一块，unpin 源块 |
  | `nanovllm/engine/scheduler.py` | `schedule`、`is_finished`、`abort` | 把 `prompted` 算进去 |
  | `nanovllm/engine/model_runner.py` | `clone_blocks` | GPU 上复制 k 和 v |

写完用 `check-step 2.4` 验收。

## 验收

```bash
python -m bench.run --scenario parallel_sampling_fork --trace out/ps-fork.jsonl
```

`parallel_sampling_fork` 是同样的 16 个 prompt，每个只发一次，`n=4`。L4 + Qwen3-0.6B 实测：

| | before：`parallel_sampling`（64 个独立请求） | after：`parallel_sampling_fork`（16 个 n=4） |
|---|---|---|
| prefill 步数 × 每步耗时 | 8 × 468 ms | 2 × 470 ms |
| `peak_kv_blocks` | 576 | 240（理想值 192，见"量化"） |
| 吞吐 tok/s | 505 | 1285（2.5×） |
| TTFT p50 | 2099 ms | 1020 ms |
| TBT p50 / max | 69 / 3370 ms | 34 / 561 ms |
| decode 每步 wall | 68.9 ms | 34.9 ms |

1. prefill 从 8 步降到 2 步，`peak_kv_blocks` 从 576 降到 240。
2. prompt 长 2049（跨 block 边界）、`n=4`：4 个输出各不相同。
3. `pytest tests/test_2_4.py`：fork 后共享块的 `ref_count` 正确；没有 `n` 就不 fork；只复制最后一块；prompt 正好填满 block 也复制；没有空闲 block 时 child 留在 `prompted`；父先结束或 child 先结束，block 都不丢、最后 `free_block_ids` 完整；`n=4` 只 prefill 一次。2.1–2.3 的测试全过。

**映射回顾**（由你说，三五句话，写进卡片）：`git diff` 对着改动全景走一遍。大致是：`BlockManager` 多了 `pin` / `unpin`，块可以有多个主人。`postprocess` 在第一个 token 出来后调 `fork`，child 复制一份 `block_table`、pin 所有块、进新的 `prompted` 队列。`schedule()` 在 decode 之前调 `_admit_prompted`，child 进 running 的那一刻复制最后一块、unpin 源块，`(src, dst)` 由 `step()` 在 forward 之前交给 `clone_blocks`。

**解释**（由你说）：`peak_kv_blocks` 为什么是 240 而不是 192？父自己算不算一次复制？prompt 正好 2048 时，child 为什么还要复制？decode 一步从 68.9 ms 降到 34.9 ms，可每个 seq 每步读的 KV 量和 before 一样，快在哪？（推测：4 个 seq 读的是同一批物理 block，命中 L2，HBM 实际搬运的少了；还没用 profiler 验证，2.5 有了 nsys 可以看 attention kernel 的 DRAM 读取量。）

## DeepInfer 对照

| 这一节 | DeepInfer | 差异和原因 |
|---|---|---|
| `fork` + pin | `fork_seq`（`scheduler.hpp:1061-1120`） | DeepInfer 还要 fork 结构化输出的 matcher（`copy_without_status`，2.11）和 state 槽位（4.1） |
| `prompted` 队列 | `:1118`、`:595-619` | 一致，DeepInfer 的它还是 COMPLETION 引擎的入口（5.6） |
| 只在 prompt 算完之后 fork | prompt 没算完也能 fork，进 `waiting` 队头，prefill 前做 COW（`:398-438`） | `n` 只在第一个 token 出来时触发；没有"中途分叉"的调用方，这条路这一节不做 |
| 父不复制，每个 child 复制最后一块 | 一样 | child 要重算 prompt 的最后一个 token |
| 源块立刻 unpin | GPU 克隆 + `clone_done_evt` 延迟 unpin（`llm_engine.py:67-116`，`DeferredRelease`） | 单 stream 保证了执行顺序，2.7 多 stream 以后要补 |
| `clone_blocks` 只拷 KV | 同时拷 / 清零 SSM、MTP 等状态（`state_id`） | 线性注意力、投机解码这些状态，后面的章节才有 |
| `n` 参数 | DeepInfer 的 `SamplingParams` 没有 `n`，fork 通过 pybind 由上层调 | 我们给个便利接口 |
| `peak_kv_blocks`、`parallel_sampling(_fork)` | — | 为了教学加的验收指标 |

## 常见坑

- 指望 prefix cache 替 n 个输出去重。hash 在这一步跑完之后才注册，同时到达的请求互相看不见，最后半块也永远不共享。
- 以为 prompt 正好填满 block 就不用 COW。child 要重算最后一个 prompt token，KV 会写进最后一块。
- `block_table` 直接赋引用，child 一改最后一块，父的也跟着变。
- 忘了让 `is_finished`、`abort`、出队遍历 `prompted`：child 还在等，`generate()` 却以为跑完了，或者取消不掉。
- 复制出来的块注册进 `hash_to_block_id`：它马上要被改写，别的请求命中它会读到错的 KV。
- COW 的拷贝和 forward 在同一个 stream 上，顺序天然保证；2.7 引入多 stream 后要加 event，现在别提前加。
