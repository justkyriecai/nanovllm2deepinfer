# 2.4：n=4 采样把同一个 prompt 算了 4 遍

> 起点：2.3 做完的代码　轴：1 调度 / 4 显存

| | |
|---|---|
| **问题** | 同一个 prompt 要 4 个输出，只能发 4 个独立请求：prefill 做 4 次、`can_allocate` 和 hash 做 4 次、最后一个不满的 block 存 4 份。根因是引擎只有"请求"这一个单位，没有"从这个请求分叉出 3 个"的接口；n 个输出本该共享 prompt 的 KV，只在分叉点之后各写各的 |
| **实验** | 2048 token 的 prompt，`llm.generate([prompt] * 4, SamplingParams(temperature=1.0, max_tokens=64))`，盯 trace 里 prefill 的次数和 KV 占的 block 数 |
| **硬件 / 费用** | 1×H100 + Qwen3-8B（$3.95/h）；调度逻辑 L4 即可（$0.80/h），H100 更接近文档数字。发现加 before / after 约 2 小时，约 $8 |
| **学到** | fork 就是共享 `block_table` 加引用计数，copy-on-write 只复制尾部那个半块，整块永远共享；`prompted` 是"prompt 已算完、还没 decode"的请求进 running 的入口，fork 和 PD 分离（5.6）共用它；克隆在 GPU 上做，源块要等克隆完成才能 unpin，同步做现在没问题、2.7 多 stream 之后要加 event |
| **时长** | 发现 + 分析约 1 小时；任务 A / B 各约 20 分钟，任务 C 约 30 分钟；验收约 30 分钟。改动约 150–250 行 |

## 发现问题

**关注什么**：同一个 prompt 要多个输出时，prefill 和 KV 各花了多少。

```python
prompt = [随机 2048 个 token]
llm.generate([prompt] * 4, SamplingParams(temperature=1.0, max_tokens=64))
```

**先预测**：prefill 会做几次？KV 占多少 block？4 个输出的前缀会一样吗？

**现象**：trace 里 4 个请求各做一次 prefill（prefix caching 能让后 3 个命中前面的整块，但 hash 要逐块算、最后半块不共享，而且 4 个请求是分别 `can_allocate` 的）；KV 里 prompt 部分有 4 份（prefix cache 命中的部分是共享的，但最后一个不满的 block 各一份，decode 新开的 block 各一份）。关键是没有一个"从这个请求分叉出 3 个"的接口，调用方只能发 4 个独立请求。

## 分析问题

- **追问链**：想要 n 个输出 → nano-vllm 只有"请求"这一个单位 → 同一 prompt 的 n 个请求各自走完整流程 → prefix cache 能省一部分，但省不掉最后半块、省不掉 n 次 `can_allocate` 和 hash、省不掉每个输出各自 decode 时写进不同 block（这一点是应该的）。
- **本质**：n 个输出共享 prompt 的 KV，只在分叉点之后各写各的。这就是 copy-on-write：共享的 block 多一个引用计数，谁要写最后那个半块，谁先复制一份。
- **理论**：`reference/gpu-perf-engineering-resources/` §4 vLLM 论文 4.4 节 "parallel sampling" 和 "beam search"，refcount + copy-on-write。
- **DeepInfer 怎么做**：
  - `fork_seq`（`csrc/engine/scheduler.hpp:1061-1122`）：新 `Sequence` 共享父的 `block_table` 和 `state_id`，两者都 pin（`ref_count++`）。`branch_id` 以 `_` 开头表示"prefill 前要 COW"。
  - prompt 还没算完的 fork 进 `waiting` 队头；算完的进 **`prompted`** 队列（`:1118`），`_schedule_decode` 从 `prompted` 头部接进 running（`:583-620`）。`prompted` 是 fork 和 PD 分离共用的入口（5.6）。
  - COW 只复制尾部半块：`_schedule_prefill` 里保留整块、给剩余部分分配新 block，记 `(src, dst)` 克隆对（`:398-438`）；decode 侧 `:602-618` 同样只克隆最后一块。克隆在 GPU 上做（`clone_and_zero_states_and_blocks`，`:1264`），源 block 的 unpin 要等 `clone_done_evt`（`llm_engine.py:109-116`，`DeferredRelease`）。
  - `Blocks` 是侵入式双向链表 free list 加 `ref_count`（`block_manager.hpp:27-117`），`pin_block` 就是 `ref_count++`。

**思考题**：`block_size = 256`，prompt 恰好 2048 个 token，8 块全满、没有半块。fork 之后 child 的第一个 decode token 写到哪一块？这时还需要 COW 吗？prompt 是 2049 呢？

## 解决问题

三个任务，顺着数据流拆：任务 A 让 child 存在并共享父的块，任务 B 让它进入调度，任务 C 让它在第一次写之前把半块复制走。接口、队列字段、克隆函数的签名和测试由 `start-step` 先写好。

### 任务 A：fork 接口和 pin（约 20 分钟，你写约 40 行）

- **目标**：`LLMEngine.fork(seq_id, n)` 或 `SamplingParams(n=4)` 产生 child，child 和父共享 `block_table`，共享 block 的 `ref_count` 各加 1；父和 child 谁先结束都不会把对方的块收走。
- **思路**：对回"n 个输出共享 prompt 的 KV"。照 `fork_seq`（`scheduler.hpp:1061-1122`），实现上统一走 `Scheduler.fork(parent) -> child`。释放不用新写：`deallocate` 已经是 refcount 的，`ref_count == 0` 才真正回收。
- **已备好**：`LLMEngine.fork` / `SamplingParams.n` 的便利接口和它们到 `Scheduler.fork` 的转发；`BlockManager.pin(block_ids)` 的签名；`tests/test_2_4.py` 的 (a)(c)(d)。
- **你写什么**：`Scheduler.fork`：`child.block_table = parent.block_table[:]`，所有共享 block `ref_count += 1`（`BlockManager.pin(block_ids)`），`child.branch_pending_cow = True`；`pin` 的循环。最容易写错的一处：`block_table[:]` 必须是一份新 list，直接赋引用的话任务 C 改 `child.block_table[-1]` 会把父的也改了。
- **改哪里**：

  | 文件 | 函数 | 做什么 |
  |---|---|---|
  | `nanovllm/engine/block_manager.py` | `pin` | `ref_count += 1` |
  | `nanovllm/engine/scheduler.py` | `fork` | 复制 `block_table`、pin、标 `branch_pending_cow` |
  | `nanovllm/engine/llm_engine.py` | `fork` / `SamplingParams.n` 的处理 | 转给 `Scheduler.fork`（已备好） |

### 任务 B：`prompted` 队列（约 20 分钟，你写约 30 行）

- **目标**：父的 prompt 已算完时 child 不走 prefill，从 `prompted` 直接进 `running`；没算完时进 `waiting` 队头，和父一起被 prefill。
- **思路**：对回 DeepInfer 的 `:1118`、`:583-620`。`Scheduler` 加第三个队列 `prompted: deque`；`schedule()` 的 decode 分支开头从 `prompted` 头部接请求进 `running`，直到 `max_num_seqs`。`prompted` 是 fork 和 PD 分离共用的入口（5.6），这里先为 fork 建起来。
- **已备好**：`Scheduler.prompted: deque` 字段；`tests/test_2_4.py` 里 fork 发生在 prefill 前 / 后的两种情况。
- **你写什么**：`fork` 里按父的 prompt 状态选队列；decode 分支开头从 `prompted` 接进 `running` 的循环。最容易写错的一处：`prompted` 进 `running` 时也要过 `max_num_seqs` 和 `can_append`，不能因为它"已经 prefill 过了"就跳过资源检查。
- **改哪里**：

  | 文件 | 函数 | 做什么 |
  |---|---|---|
  | `nanovllm/engine/scheduler.py` | `fork` | 进 `prompted` 还是 `waiting` 队头 |
  | `nanovllm/engine/scheduler.py` | `schedule` 的 decode 分支 | 从 `prompted` 头部接进 `running` |

### 任务 C：copy-on-write（约 30 分钟，你写约 60 行）

- **目标**：child 第一次被调度时尾部半块被复制，`block_table[-1]` 换成新块，源块 `ref_count -= 1`；同一个 prompt `n=4` 时 trace 里只有 1 次 prefill，4 个输出各不相同。
- **思路**：对回"谁要写最后那个半块，谁先复制一份"。照 `:398-438` / `:602-618` 只克隆尾部半块：child 第一次被调度（无论 prefill 还是 decode）时，如果 `branch_pending_cow`，分配一个新 block，把共享的最后那块的内容复制过去，`block_table[-1] = new`，源 block `ref_count -= 1`。复制在 GPU 上做（对应 `clone_and_zero_states_and_blocks`，`:1264`）：`model_runner` 加 `clone_blocks(pairs)`，一个简单的 `kv_cache[:, :, dst] = kv_cache[:, :, src]`（两层 index，k 和 v 一起）。现在同步做没问题；2.7 之后它要延迟到 clone 完成再 unpin 源块，接口先按 `(src, dst)` 对的列表设计。
- **已备好**：`model_runner.clone_blocks(pairs)` 的签名和 `call` 转发；`tests/test_2_4.py` 的 (b)。
- **你写什么**：调度器里 `branch_pending_cow` 的处理（分配新块、记 `(src, dst)`、改 `block_table[-1]`、unpin 源块、清标记）；`clone_blocks` 的那一行索引赋值。最容易写错的两处：复制出来的半块还没满、没有 hash，不要把它注册进 `hash_to_block_id`；COW 的拷贝和 forward 在同一个 stream 上，顺序天然保证，2.7 引入多 stream 后要加 event，现在别提前加。
- **改哪里**：

  | 文件 | 函数 | 做什么 |
  |---|---|---|
  | `nanovllm/engine/scheduler.py` | `schedule`（prefill 和 decode 两处） | 处理 `branch_pending_cow`，收 `(src, dst)` 对 |
  | `nanovllm/engine/block_manager.py` | `allocate` 相关 | 给 COW 分配新块、源块 `ref_count -= 1` |
  | `nanovllm/engine/model_runner.py` | `clone_blocks` | GPU 上复制 k 和 v |
  | `nanovllm/engine/llm_engine.py` | `step` | 把克隆对交给 runner |

写完用 `check-step 2.4` 验收。

## 验收

1. 同一个 2048 token 的 prompt，`n=4`、`max_tokens=64`：trace 里只有 1 次 prefill；KV 占用 ≈ 1 份 prompt + 4 × 半块 + 4 × decode 增量；4 个输出各不相同。
2. 和 `[prompt]*4` 的方式比：prefill 时间和 KV 占用各写进报告。
3. `tests/test_2_4.py`：假 Config，(a) fork 后共享 block 的 `ref_count` 正确；(b) child 第一步后 `block_table[-1]` 和父的不同，其余相同；(c) 父先结束、child 继续，block 不丢；child 先结束、父继续，同样；(d) 结束后 `free_block_ids` 完整；(e) 2.1–2.3 的测试全过。

**解释**（由你说）：KV 占用为什么是"1 份 prompt + 4 × 半块"而不是"1 份 prompt + 3 × 半块"？父自己那份半块算不算一次复制？4 个输出为什么各不相同，它们的 prefix cache 命中是在哪一步分开的？

## DeepInfer 对照

| 这一节 | DeepInfer | 差异和原因 |
|---|---|---|
| `fork` + pin | `fork_seq`（`scheduler.hpp:1061`） | DeepInfer 还要 fork SO matcher（`copy_without_status`）和 state 槽位 |
| `prompted` 队列 | `:1125`、`:583-620` | 一致，DeepInfer 的它还是 COMPLETION 引擎的入口（5.6） |
| 只克隆尾部半块 | `:398-438`、`:602-618` | 一致 |
| 同步克隆 | GPU 克隆 + `clone_done_evt` 延迟 unpin | 2.7 之后要改成延迟 |
| `n` 参数 | DeepInfer 的 `SamplingParams` 没有 `n`，fork 通过 pybind 由上层调 | 我们给个便利接口 |

## 常见坑

- prefix cache 的 hash 和 COW 要协调：child 的尾部半块复制后没有 hash（它还没满），不要把它注册进 `hash_to_block_id`。
- `prompted` 进 running 时也要过 `max_num_seqs` 和 `can_append`。
- COW 的拷贝和 forward 在同一个 stream 上，顺序天然保证；2.7 引入多 stream 后要加 event。
