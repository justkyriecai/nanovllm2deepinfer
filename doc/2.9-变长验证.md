# 2.9：高并发时投机解码反而更慢

> 起点：2.8 做完的代码　轴：3 解码加速

| | |
|---|---|
| **问题** | 低并发开投机快 2–3 倍，到 64–128 并发之后反而更慢：`total_q` 从 n 变成 6n，forward 开始随 `total_q` 线性涨，从访存瓶颈变成计算瓶颈，每接受 1 个 token 要验证 6 个，算力不再免费；而且接受率 0.8 和 0.3 的请求都验证 5 个 draft。根因是定长 `nextn` 在"算力还有多少富余"和"每个请求值不值得猜"两个维度上都是错的 |
| **实验** | 下面的 for 循环，开投机和 `NEXTN=0` 各扫一遍 `1 4 16 64 128 256`，盯两条吞吐曲线的交叉点和 `gpu_forward` 随 `total_q` 的斜率 |
| **硬件 / 费用** | 1×H100 + Qwen3-8B + EAGLE-3。H100 $3.95/h，六档并发 × 开关投机反复扫约 3 小时，约 $12 |
| **学到** | 投机解码的收益 = 富余算力 × 接受率，两者都随工作点变；draft 预算要按"期望产出 / 步耗时"选，步耗时只能 profile 出来、而且必须落在 graph 桶上；ZOS 下 N-1 步的接受率还在 GPU 上，所以 CPU 用 N-2 步的定总预算、GPU 用 N-1 步的做分配 |
| **时长** | 发现 + 分析约 1.5 小时；任务 A 约 20 分钟、B 约 30 分钟、C 约 30 分钟；验收约 1 小时。改动约 250–400 行 |

## 发现问题

**关注什么**：吞吐随并发的曲线，开投机和不开各一条。

```bash
for n in 1 4 16 64 128 256; do
  python -m bench.run --scenario steady_decode --max-num-seqs $n --json out/spec-$n.json
  NEXTN=0 python -m bench.run --scenario steady_decode --max-num-seqs $n --json out/nospec-$n.json
done
```

**先预测**：两条曲线会在哪个并发交叉？交叉之后差多少？接受率随并发变吗？

**现象**：低并发开投机快 2–3 倍；某个并发（H100 + 8B 大约 64–128）之后开投机反而更慢。看 `gpu_forward`：不开投机时 `total_q = n`，开了是 `6n`，高并发时 forward 时间开始随 `total_q` 线性涨，也就是**从访存瓶颈变成了计算瓶颈**。接受率没变（它只和 draft 质量有关），但每接受 1 个 token 要验证 6 个，算力不再免费。再看请求之间：有的请求接受率 0.8，有的 0.3，但每个都验证 5 个 draft。

## 分析问题

- **追问链**：高并发变慢 → forward 随 total_q 线性涨 → 算力饱和 → 每个请求固定验证 `nextn` 个 draft，接受率低的请求在浪费 → 应该按接受率给每个请求分配 draft 长度，并且总量受"这一步还有多少富余算力"约束。
- **本质**：投机解码的收益 = 富余算力 × 接受率。两者都随工作点变：并发高了算力不再富余，请求不同接受率不同。定长 `nextn` 在两个维度上都是错的。
- **量化**：目标函数是 `期望产出 token 数 / 步耗时`。步耗时 = f(total_q)，可以 profile 出来；期望产出 = Σ_req (1 + Σ_k Π_{j≤k} p_accept_j)。DeepInfer QA 文档给的数字：约 60 并发时少验证 30% 的 draft，吞吐 +4–7%。
- **理论**：`reference/gpu-perf-engineering-resources/` §4 投机解码的分析文章（speculative sampling 的并行形式分析）；Etalon 的 goodput 视角。
- **DeepInfer 怎么做**：
  - **性能曲线**：启动时 `profile_decode_perf`（`model_runner.py:561-631`）对每个 graph 桶跑几次 decode，得到 `(graph_size, forward_ms)`；`DecodePerfCache`（`decode_perf_cache.py:26`）按模型 + batch sizes + 并行配置缓存到磁盘，1 小时 TTL。
  - **运行时估计器**：`ForwardRuntimeEstimator` 用两级中位数估每个 graph 桶的斜率，`SamplerRuntimeEstimator` 按 num_seqs 估采样耗时，`update_mtp_runtime` 每步用 event 测到的 forward / sampler 时间喂它（`mtp_varlen.hpp:139-148`，`llm_engine.py:995-1002`）。
  - **分配**：`MTPVarlen::schedule`（`mtp_varlen.hpp:150-267`）把所有 `(accept_rate, seq)` 降序排，枚举 `best_bsz` 最大化 `expected_tokens / (baseline + slope × graph + sampler_ms)`，然后按接受率给每个请求 `seqlens_q = 1 + wins`。预算用 N-2 步的接受率定、分配用 N-1 步的，因为 ZOS 下 N-1 步的置信度还在 GPU 上（`:160-168`）。
  - **ZOS 下的 GPU 重分**：CPU 只定总预算 `total_q`，`compute_seqlens_q_by_confidence_rates` kernel（`schedule_mtp_varlen.py`）在 GPU 上按上一步的置信度把预算重新分给各请求（累积乘积、全局排序取 top-k、融合 remap scatter），结果 D2H 回 pinned buffer，采样前 `update_metadata_for_sampling_zos` 写回元数据。
  - 置信度来自 DFlash 的置信度头（4.10）。EAGLE-3 没有，先用每个 draft 位置的 draft 概率（或历史接受率）代替。

**思考题**：预算用 N-2 步的接受率定、分配用 N-1 步的。为什么不能两个都用 N-1 步的？如果 CPU 硬要等 N-1 步的接受率再定预算，2.7 的哪条时间线会被打断？

## 解决问题

三个任务，照 DeepInfer 的 `MTPVarlen` 拆：先有性能曲线，再有预算和分配，最后让分配在 ZOS 下也能用上最新的接受率。

### 任务 A：性能曲线（约 20 分钟，你写约 50 行）

- **目标**：启动后每个 CUDA graph 桶有一个 `forward_ms`，采样按 `num_seqs` 有一个 `sampler_ms`；缓存命中时启动不重新 profile；运行时读数持续修正它。
- **思路**：对回分析里"步耗时 = f(total_q)，可以 profile 出来"。启动后对每个 graph 桶跑 3 次 decode（placeholder 输入），记 `forward_ms` 取中位数，采样同样按 `num_seqs` 测；缓存到 `~/.cache/nanovllm/decode_perf/<hash>.json`，key 含模型路径、`max_num_seqs`、`nextn`、GPU 名；运行时用 1.1 任务 A 的 `gpu_forward / gpu_sample` 事件读数做滑动中位数更新。
- **已备好**：`nanovllm/engine/decode_perf.py` 的类和签名、缓存文件的读写和 key 的哈希、`tests/test_2_9.py` 里缓存命中那一条。
- **你写什么**：profile 循环和取中位数；滑动中位数的更新。最容易写错的一处：性能曲线不是线性的，小 batch 下 forward 时间是平的、之后才线性，按 graph 桶插值，不要拟合一条直线。
- **改哪里**：

  | 文件 | 函数 | 做什么 |
  |---|---|---|
  | `nanovllm/engine/decode_perf.py`（新建） | profile、缓存、运行时更新 | 每桶 3 次取中位数；滑动中位数 |

### 任务 B：预算和分配（约 30 分钟，你写约 80 行）

- **目标**：`schedule()` 的 decode 分支结束后，每个请求有自己的 `seqlens_q`：接受率高的分到更长的 draft，总量 `total_q` 落在"期望产出 / 步耗时"最大的那个 graph 桶上；没有性能曲线时退化成定长；`StepRecord` 有 `total_q_budget`、`mean_seqlen_q`，报告里有"每验证一个 draft 产出多少 token"。
- **思路**：对回分析里的本质：按接受率给每个请求分配 draft 长度，总量受富余算力约束。每个请求维护 `accept_rates[k]`：第 k 个 draft 位置被接受的滑动平均（或累积乘积）。`MTPVarlen::schedule(running) -> seqlens_q`：
  1. 候选 `(rate, seq, k)` 按 rate 降序；
  2. 枚举总预算 `total_q`（按 graph 桶取值），`expected = Σ 接受的期望`，`cost = perf(total_q) + sampler(num_seqs)`，取 `expected / cost` 最大的；
  3. 按排序把 `total_q - num_seqs` 个名额分下去，`seqlens_q[i] = 1 + wins_i`，上限 `nextn + 1`。
- **已备好**：`csrc/scheduler.hpp` 里 `MTPVarlen` 的类壳和它在 `schedule()` 末尾的调用点；`accept_rates[k]` 字段；`StepRecord` 的两个字段和报告的那一列；`tests/test_2_9.py` 的 (a)(b)。
- **你写什么**：候选排序、预算枚举、名额分配三步；`accept_rates[k]` 的更新。最容易写错的两处：预算必须落在 graph 桶上，否则 padding 把省下的算力又吃回去；接受率要按 draft **位置**分开统计，第 1 个位置和第 5 个位置差很多，混成一个数分配就是错的。
- **改哪里**：

  | 文件 | 函数 | 做什么 |
  |---|---|---|
  | `csrc/scheduler.hpp` | `MTPVarlen::schedule`、`schedule()` decode 分支末尾 | 排序、枚举、分配；无曲线时定长 |
  | `csrc/sequence.hpp` | `accept_rates[k]` 的更新 | 按位置的滑动平均或累积乘积 |

### 任务 C：ZOS 下的 GPU 重分（约 30 分钟，你写约 60 行）

- **目标**：CPU 只定 `total_q`，GPU 用上一步（N-1）的 draft 概率把预算重新分给各请求，修正后的 `seqlens_q` 在采样前写回 `SequenceMetadata`。
- **思路**：对回分析里"预算用 N-2 步的接受率定、分配用 N-1 步的"。CPU 算 `total_q` 用的是 N-2 步的接受率（N-1 步的还在 GPU 上）。GPU kernel：输入上一步每请求每位置的 draft 概率（EAGLE-3 的 `draft_probs`）和 remap，算累积乘积作为该位置的"价值"，全局 top-(total_q - num_seqs) 选出要验证的位置，写回 `seqlens_q_gpu`；D2H 到 pinned，记 event。采样前 `event.synchronize()`，把修正后的 `seqlens_q` 写回 `SequenceMetadata`（2.5 的带指针元数据就是为了这里）。`cu_seqlens_q`、`positions`、`slot_mapping` 要么在 GPU 上随之展开，要么按上界准备、用 mask。先用上界 + mask。
- **已备好**：kernel 的签名、pinned buffer 和 event；`tests/test_2_9.py` 的 (c) 和 PyTorch 参考实现的壳。
- **你写什么**：累积乘积 + 全局 top-k + remap scatter 的 kernel 体；采样前写回元数据的那一段。最容易写错的一处：`seqlens_q` 在 GPU 上改了之后，所有按 `cu_seqlens_q` 展开的 metadata 都要跟着变，先用上界 + mask 做对，再优化。
- **改哪里**：

  | 文件 | 函数 | 做什么 |
  |---|---|---|
  | 2.7 任务 C 的 GPU 侧准备 | 重分 kernel | 累积乘积、top-k、写 `seqlens_q_gpu`，D2H + event |
  | `nanovllm/engine/model_runner.py` | 采样前 | `event.synchronize()`，写回 `SequenceMetadata` |

## 验收

同一个实验重跑，画两条曲线：

1. 开投机的吞吐曲线在**所有**并发下不低于不开的（目标）；高并发下和 2.8 比提升，低并发下不退化。
2. 接受率高的请求分到更长的 draft；报告里给一个 `seqlen_q` 的分布。
3. 性能曲线缓存命中时启动不重新 profile。
4. `tests/test_2_9.py`：(a) 给定人工的接受率和一条线性的性能曲线，分配结果和暴力枚举一致；(b) 预算为 `num_seqs` 时退化成每请求 1 个 token；(c) GPU 重分 kernel 和 PyTorch 参考一致；(d) 2.1–2.8 全过。
5. **解释**（由你说）：为什么高并发下曲线回到了不开投机的水平之上，而低并发下 `seqlen_q` 的分布几乎还是定长？少验证了多少 draft、吞吐提了多少，和 DeepInfer QA 给的 30% / 4–7% 是什么关系？

**新浮现的问题**：固定 seed 跑两遍，结果不一样；top-p 采样是三四个 kernel 串起来的，`gpu_sample` 占比不小。这是 2.10。

## 常见坑

- 性能曲线不是线性的：小 batch 下 forward 时间平的，之后才线性。按 graph 桶插值，不要拟合一条直线。
- 预算必须落在 graph 桶上，否则 padding 把省下的算力又吃回去。
- `seqlens_q` 在 GPU 上改了之后，所有按 `cu_seqlens_q` 展开的 metadata 都要跟着变；先用上界 + mask 做对，再优化。
- 接受率统计要按 draft **位置**分开，第 1 个位置和第 5 个位置的接受率差很多。
