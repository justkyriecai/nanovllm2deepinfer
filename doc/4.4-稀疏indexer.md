# 4.4：128k 上下文，每层 attention 读完整个 cache

> 起点：4.3 做完的代码　硬件：1×B200　预计改动：700–1000 行　轴：3 访存 / 4 模型结构

## 1. 发现问题

**关注什么**：压缩层 decode 时 attention 的耗时随上下文长度怎么变。

```bash
for n in 4096 32768 131072; do python -m tests.v4.harness --layer <ratio1 层> --decode --context-len $n --report time; done
```

**先预测**：上下文 4k → 128k，一层 decode attention 的时间涨多少倍？读了多少字节？B200 的带宽是 8 TB/s，一个 batch 256 的 decode 步，所有压缩层加起来要多少毫秒？

**现象**：时间随长度线性涨。128k 下一个请求一层读 `131072 × 528 B ≈ 69 MB`，256 个请求 20 层就是 350 GB，一步 40 多毫秒，全花在读 KV 上。而 V4.1 的 config 里有 `index_topk`：每个 query 只看 top-k 个 latent。朴素的 top-k 需要先算全部 `q·k`，那一样要读一遍 K。

## 2. 分析问题

- **追问链**：时间线性 → 读了全部 latent → 只读 top-k 需要先知道哪 k 个 → 用一个**便宜得多**的 K（64 维 FP4，每 token 68 B，比主 KV 小 8 倍）打分 → 打分本身是 `relu(q·k)` 按头加权求和，一个小 kernel → 排序取 top-k（DeepSelect）→ 把 top-k 的**逻辑位置**换算成 cache 里的物理 slot → 主 attention 只按索引读这 k 个 latent。打分 kernel 读 index-K 的成本也随长度线性，但常数小 8 倍，而且可以再用"候选块"剪一刀：某一层先选出 `candidate_topk_blocks` 个块，后面几层只在这些块里打分。
- **本质**：稀疏 attention 把访存从 `O(L)` 变成 `O(L/8) + O(k)`：indexer 是一次廉价的全扫描，主 attention 是精确的稀疏读。4.2 的 SWA 和这里用的是**同一个 attention kernel**：都是"给索引，按索引取"，区别只是索引怎么来。
- **量化**：`index_topk` 按 config（V3.2 是 2048）。128k 下主 attention 读 `k × 528 B` 而不是 `L × 528 B`，64 倍；indexer 读 `L × 68 B`，是原来的 1/8。两者加起来一层 decode 的 KV 读量降到 1/7 左右。
- **理论**：`reference/gpu-perf-engineering-resources/` §4 "Long context and multimodal inference"：DeepSeek-V3.2（DSA，lightning indexer 选 top-k 的原始设计）、Native Sparse Attention（硬件对齐的稀疏层次）、MInference（动态稀疏模式）。
- **DeepInfer 怎么做**（`models/v4_modules/index_attn.py`，`MQA`）：
  - **K**：`KProject`（`compress.py:32`）从 4.3 存 kernel 吐出的 pre-rope KV 投影到 `[index_n_heads × 128]`，`store_index_kv`（`index_attn.py:133`）norm + RoPE + FP4 cast + 存到 `ica_cache`（68 B/token，`FP4_INDEX_KV_FORMAT`），位置和 slot 用压缩层的 `positions_c / slot_mapping_store_ca[ratio]`：index-K 和主 KV **一一对应**，都是按压缩后的 token 存。
  - **Q 和权重**：indexer 的 q 和主 attention 的 q 合并在一个 GEMM 里出（`q_b_proj`，`attn.py:296-303`），`index_weights [total_q, n_head]` 从 `current_hidden_proj` 出（`:481-507`，bf16），量化 `_quantize_q`（`:164`）。
  - **打分（prefill）**：`_topk_prefill`（`:327`）：K 用 `_load_prefill_kv`（`:181`）解压到 bf16，按 `compute_chunk_size` 分块（`:114-120`，`DEEPINFER_INDEX_ATTN_MEMORY_LIMIT` 控制 logits 矩阵占多少显存，再 min 8192），每块 `deep_gemm.fp8_fp4_mqa_logits` 算 `p_sum [chunk, L]`，DeepSelect `topk`（`:362`）取 `topk_tokens` 个，`end=klen` 限制有效范围，输出加 `ks` 偏移变成拼接 buffer 里的全局索引，-1 填无效。
  - **打分（decode）**：`_topk_decode`（`:456`）：`deep_gemm.fp8_fp4_paged_mqa_logits` 直接读 paged 的 `ica_cache`，调度元数据 `get_paged_mqa_logits_metadata`（`:378-396`，按 `klen` 和 block size 算，缓存在 metadata 里）；`topk` 之后 `convert_kv_index`（`:508`）用 block table 把逻辑位置原地换成物理 slot。
  - **候选块**：`candidate_source_layer_id` 指定的层是候选源：打分后 `candidate_block_max`（`candidate_blocks.py`）按块取最大分，DeepSelect 选 `candidate_topk_blocks` 个块（`_topk_candidate_block`，`:204`），写进 `cross_layer_runtime.block_candidate_idxs`；后面的层只在候选块里算 `p_sum`（稀疏 MQA，`:228-243`，`fp8_fp4_sparse_mqa_logits`），top-k 之后 `restore_candidate_indices_inplace` 换回全局位置（`:505`）。候选块不能跨 paged block（`:400`）。
  - **用索引**：prefill `kv_index_cat`（`kv_index_cat.py:10`）把 SWA 的 `[total_q, window]` 和 top-k 的 `[total_q, topk]` 拼成一个索引（`attn.py:604-607`），`flash_mla_sparse_fwd`；decode 两套索引分别传 `indices_in_kvcache`（SWA）和 `indices_in_kvcache_extra`（压缩）（`:645-652`），`index_length` 给非稀疏层用。
  - **共享**：index-K、top-k 都可以跨层共享（4.6）；`CrossLayerRuntime.topk_indices` 让后面的层直接用。

## 3. 要做什么

### 3.1 index-K

**改哪里**：`nanovllm/models/deepseek_v4.py`、`nanovllm/layers/compress.py`。

- `KProject`：`k_proj [512 → n_head × 128]` + `k_norm`；输入是 4.3 存 kernel 返回的 pre-rope KV。
- 存到 `ica_cache`：norm + RoPE（indexer 自己的 rope dim）+ FP4 cast（e2m1 + per-32 UE8M0，68 B/token）+ scatter，slot 复用 `slot_mapping_store_ca[ratio]`。

### 3.2 打分和 top-k

**新建** `nanovllm/layers/indexer.py`。

- q 投影并进 `q_b_proj`，split 出 `index_q_b`；`index_weights` 从 hidden 投影。
- prefill：`load` index-K 到 bf16，分块算 `relu(q·k) · w` 按头求和（先 PyTorch，`torch.einsum` + relu + sum），`torch.topk` 取 `index_topk`，加 `ks` 偏移；分块大小按显存限制算。
- decode：DeepGEMM 的 `fp8_fp4_paged_mqa_logits` + `get_paged_mqa_logits_metadata`（这是 vendor kernel，直接用），DeepSelect `topk`（`reference/DeepInfer/vendor/DeepSelect`），`convert_kv_index` 换成物理 slot（Triton）。
- 对拍过了再把 prefill 的打分换成 `fp8_fp4_mqa_logits`。

### 3.3 候选块

- `candidate_source_layer_id` 层：按块取最大分，选 `candidate_topk_blocks` 个块，存在跨层的 runtime 对象里（4.6 正式定义 `CrossLayerRuntime`，这里先放一个 dict）。
- 后面的层：只在候选块里打分（先用 gather 出候选块再做 dense 打分的 PyTorch 版，再换 `fp8_fp4_sparse_mqa_logits`），top-k 后换回全局位置。

### 3.4 用索引

- `kv_index_cat`（Triton）拼 SWA 和 top-k 索引；prefill `flash_mla_sparse_fwd`，decode 两套索引传 FlashMLA。
- `InputMetadata` 加 `klen[ratio]`、`ks[ratio]`、`kv_ca_index_len`。

## 4. 验收

同一个实验重跑：

1. 128k 下压缩层 decode attention 时间接近 4k 的水平（主 attention 只读 top-k），indexer 的时间随长度线性但斜率是原来的 1/8；报告里给三个长度的分解（indexer / 主 attention）。
2. harness：prefill 和 decode 的 top-k 索引集合和 DeepInfer 一致（并列分数允许顺序不同，比集合）；attention 输出一致。候选块路径同样。
3. `tests/test_4_4.py`：(a) 打分 kernel 和 PyTorch 参考一致；(b) `convert_kv_index` 和参考一致（含 -1）；(c) `kv_index_cat` 和 `kv_index_cat_ref`（`kv_index_cat.py:54`）一致；(d) 候选块限制下 top-k 是候选块内的 top-k；(e) 前面全过。

**新浮现的问题**：V4.1 的后一半层（YoCo consumer）的 KV 不是从本层 hidden 算的，而是从边界层的 hidden 投影的。现在的实现每层都从自己的 hidden 算 KV，prefill 时后 20 层的 KV 投影和 attention 全都白做了。这是 4.5。

## 常见坑

- index-K 和主 KV 都是按**压缩后**的 token 存的，位置用 `positions_c`，不是原始位置。
- top-k 的 `end=klen` 必须传，`p_sum` 越界的部分是脏数据，不传会选到不存在的 token。
- prefill 的索引是拼接 buffer 里的全局索引（含 `ks` 偏移和 SWA 段的偏移），decode 的索引是物理 slot，两种语义不要混。
- 并列分数下 top-k 的集合可能和 DeepInfer 不同，对拍比 attention 输出而不是索引本身；2.12 的 batch-invariant 要求 top-k 稳定，DeepSelect 的 `sorted_index=True` 就是为这个。
- `DEEPINFER_INDEX_ATTN_MEMORY_LIMIT` 默认 10 GiB：prefill 的 logits 矩阵 `[chunk, L]` bf16 在 128k 下很大，分块不是可选项。
