# 1.1：什么都看不见

> 起点：`main`（nano-vllm 原始代码，tag `baseline`）　硬件：任意一张 GPU（文中的数字按 1×H100 + Qwen3-8B）　预计改动：350–500 行

这一节没有要解决的性能问题。它解决的是"发现不了问题"本身：nano-vllm 跑完只打印一个吞吐数字，改了模型代码也不知道对不对。后面每一节的"发现问题"环节都要靠这里的工具，所以它是整条路线的地基。

## 1. 发现问题

**关注什么**：跑一遍 nano-vllm 自带的 `bench.py`，然后试着回答三个问题。

```bash
python bench.py        # 在 main（nano-vllm 原始代码）上
```

**先预测**：这一次运行里，GPU 有多少比例的时间在干活？最慢的那个请求等了多久才拿到第一个 token？有没有请求被抢占过？

**现象**：三个问题一个都答不了。输出只有一行 `Throughput: xxx tok/s`。`generate()` 进度条上的 Prefill / Decode 吞吐是瞬时值，跑完就没了。

再做一个实验：把 `nanovllm/layers/attention.py` 里 decode 分支的 `causal=True` 改成 `False`，重跑 `bench.py`。吞吐一个数都不变。**引擎已经坏了，但没有任何东西告诉你。**

## 2. 分析问题

- **追问链**：吞吐 → 它是总 token 数除以总时间，把一切都平均掉了 → 要回答"GPU 在不在干活"，需要每一步里 CPU 和 GPU 各花了多少时间；回答"等了多久"，需要每个请求的时间戳；回答"对不对"，需要一把和参考实现比的尺子。
- **本质**：推理引擎的每一个优化都是在某种资源上省时间（CPU、HBM 带宽、HBM 容量、通信）。看不到时间花在哪，就无从判断该优化什么，也无法证明优化有没有效。
- **理论**：性能工程的起点是测量。`reference/gpu-perf-engineering-resources/` 第 3 节 "Profiling, benchmarking, and correctness"：Nsight Systems 看 CPU/GPU 时间线；Etalon（第 5 节 Serving benchmarks）定义了 TTFT、TPOT（本仓库叫 TBT）和 goodput，这是推理服务的标准指标。
- **一个绕不开的事实**：CUDA 是异步的。CPU 调用 `model(...)` 几乎立刻返回，GPU 还在算。所以 CPU 侧的计时只能告诉你 CPU 在干什么，GPU 的真实时间必须用 CUDA event 测；而 event 的读数要等 GPU 跑完才有效。nano-vllm 的每一步只有一处同步点：`sampler(...).tolist()`。想不引入新的同步，就只能在它之后读 event。
- **DeepInfer 怎么看自己**：`deepinfer/timer.py` 的 `cpu_timer` / `cuda_timer` 在每步的每个阶段打点（`llm_engine.py:880-906` 到处是 `with cpu_timer.record(...)`）；`stats_logger.py` 每 100 步汇总一次，含 MFU（用 `csrc/engine/flops_estimator.hpp` 估 FLOPs）；正确性靠 `tests/models/offline_decode_ppl.json` 逐样本的 PPL 黄金基线和 `tests/models/test_kl.py`。

## 3. 要做什么

照 DeepInfer 的思路，保持 nano-vllm 的体量。四件事，建议按顺序做。

### 3.1 每步耗时拆分

**改哪里**：`nanovllm/engine/model_runner.py` 的 `run()`，`nanovllm/engine/llm_engine.py` 的 `step()`。新建一个纯 Python 的 `StepRecord`（放在 `nanovllm/engine/stats.py`，不要 import torch，后面 CPU 测试要用）。

一步拆成 7 段：

| 字段 | 怎么测 | 含义 |
|---|---|---|
| `cpu_schedule` | `perf_counter` 包住 `scheduler.schedule()` | 调度 |
| `cpu_prepare` | 包住 `prepare_prefill / prepare_decode` | Python 建 list、建 tensor、H2D |
| `cpu_launch` | 包住 `run_model` | 发射 forward 的 CPU 时间，不含 GPU 执行 |
| `cpu_sample_wait` | 包住 `sampler(...).tolist()` | CPU 等 GPU 的时间 |
| `cpu_postprocess` | 包住 `scheduler.postprocess()` | 后处理 |
| `gpu_forward` | 一对 CUDA event，forward 前后 | GPU 真正算 forward 的时间 |
| `gpu_sample` | 一对 CUDA event，sampler 前后 | GPU 采样的时间 |

再加 `wall`、`is_prefill`、`num_seqs`、`num_tokens`。派生一个 `gpu_busy = (gpu_forward + gpu_sample) / wall`。

要求：

- event 必须在 `.tolist()` **之后**读，不能加 `torch.cuda.synchronize()`。理由见第 2 节。
- 引擎每步生成一条 `StepRecord`，存进 `engine.step_records`；提供一个可选的 `engine.trace` 回调，每步调一次（3.3 用）。
- TP > 1 时只有 rank 0 需要读数。

### 3.2 每个请求的时间戳

**改哪里**：`nanovllm/engine/sequence.py`、`nanovllm/engine/scheduler.py`。

- `Sequence` 加 `arrival_time`（构造时记）、`token_times`（`append_token` 时追加）、`num_preemptions`（`preempt` 时加一）。
- `Scheduler` 记下每步谁结束了、谁被抢占了，引擎每步收走并清空。
- 请求结束时，引擎把它收成 `RequestRecord`（seq_id、prompt 长度、输出长度、`arrival_time`、`token_times`、抢占次数）。TTFT 和 TBT 从这里算。

注意 `Sequence.__getstate__` 决定了什么会被 pickle 到 TP worker，这些观测字段不要进去。

### 3.3 负载场景、驱动和 trace

**新建** `bench/` 包，纯 Python 的部分不要 import torch。

| 文件 | 内容 |
|---|---|
| `bench/workloads.py` | `Request(prompt_len, max_tokens, arrival_step, temperature)` 和四个场景函数，都接受 `seed`：`steady_decode`（nano 原来的 bench：256 个请求一次到达，长度 100–1024）、`mixed_long_short`（128 个短请求稳态 decode，每 20 步插一个 3072 token 的长 prompt）、`kv_pressure`（512 个请求、输出 768–1024，KV 一定不够）、`many_small`（512 个 16–32 in / 32–64 out 的小请求）。**到达时间按步数定义，不按墙钟**，这样每次跑的调度决策可以复现 |
| `bench/run.py` | 驱动循环：按 `arrival_step` 调 `engine.add_request`，逐步 `engine.step()`；引擎空闲但还有请求没到时只推进步数。跑完打印报告。`--trace` 写每步 JSONL，`--json` 存汇总 |
| `bench/metrics.py` | `percentile`；`summarize_steps`（按 prefill / decode 分组，每段耗时的 mean / p50 / p99 / max，`gpu_busy`，抢占次数）；`summarize_requests`（吞吐、TTFT 和 TBT 的分布、被抢占的请求数）；`format_report` |
| `bench/trace.py` | `TraceWriter(path)` 作为 `engine.trace` 回调，一步一行 JSON；`read_trace`。trace 里要有每步调度了哪些 seq_id、谁结束、谁被抢占，后面对照 DeepInfer 的调度决策时要用 |
| `bench/nsys.sh` | `nsys profile` 包一层，看真实的 CPU/GPU 时间线 |

### 3.4 正确性

**新建** `bench/correctness.py`。用 HF 实现当裁判，固定 8 个 prompt、32 个输出 token，每个 prompt 两个数：

- `greedy_match`：nano 近贪心（`temperature=1e-3`，nano 的 `SamplingParams` 禁止 0）的输出和 HF `generate(do_sample=False)` 前缀相同的长度。bf16 噪声会让接近平局的 token 翻转，所以是前缀长度不是布尔值。
- `nll`：nano 的输出在 HF 下 teacher-forced 的平均负对数似然。attention 或 KV 坏了，这个数会跳。

`--write` 生成黄金文件到 `tests/golden/<模型>.json`，`--golden` 对比，超出容差就非零退出。这是 DeepInfer `offline_decode_ppl.json` 的缩小版。

## 4. 验收

```bash
pytest tests/test_1_1.py
python -m bench.run --model ~/huggingface/Qwen3-8B --scenario steady_decode --trace out/steady.jsonl
python -m bench.correctness --model ~/huggingface/Qwen3-8B --write tests/golden/qwen3_8b.json
```

`tests/test_1_1.py` 要包含：场景函数同 seed 结果相同、不同 seed 不同；percentile 算得对；`summarize_*` 在手工构造的记录上算得对；trace 写了能读回来。这些不需要 GPU。再加一条需要 GPU 的：真实引擎跑一个两请求的小场景（一个第 0 步到、一个第 3 步到），每步 7 段都有值、`gpu_forward > 0`、两个请求都有 TTFT / TBT。

验收标准：

1. `bench.run` 的报告里每一步都有 7 段耗时，`gpu busy` 在 0–100% 之间；每个请求都有 TTFT 和 TBT。
2. **再做一次第 1 节的破坏实验**（`causal=False`）：`bench.correctness --golden` 必须报错，`greedy_match` 掉到个位数、`nll` 明显上升。这就是"改一行模型代码能被抓住"。
3. 四个场景各跑一遍，报告存进 `out/`。它们是后面几节的 before。

**跑完你应该能看见什么**（1×H100，Qwen3-8B，数字因机器而异，做完请把实测值填进来）：

- `steady_decode`：decode 步的 `gpu_busy` 大约 70–85%。剩下的是 `cpu_schedule + cpu_prepare + cpu_postprocess`，这段时间 GPU 空着。这是 2.5 和 2.7 的起点。
- `mixed_long_short`：TBT 的 p99 比 p50 大一个数量级，trace 里每次长 prompt 到达后紧跟一个 `num_tokens=3072` 的 prefill 步，所有 decode 请求在那一步停了几十毫秒。这是 2.2 的起点。
- `kv_pressure`：`preempted` 不为零，被抢占的请求 TTFT 极大（重新排队、重新 prefill）。这是 2.3 的起点。
- `many_small`：`cpu_prepare` 和 `gpu_forward` 同量级。换 Qwen3-0.6B 跑，CPU 会直接超过 GPU。这是 2.5 的起点。

**新浮现的问题**：工具有了，第一件事是拿边界请求试试引擎：发一个比显存总量还大的 prompt、中途 abort 一个请求。这是 2.1。

## DeepInfer 对照

| 这一节 | DeepInfer | 差异和原因 |
|---|---|---|
| `StepRecord` 7 段，`perf_counter` + CUDA event | `deepinfer/timer.py` 的 `cpu_timer.record` 上下文管理器和 `cuda_timer`；`csrc/graph_timer` 给 CUDA graph 内部计时 | DeepInfer 的 ZOS 下没有 `.tolist()` 同步点，event 要显式 `synchronize`；它还要给 graph 内部计时 |
| `bench/run.py` 按步注入请求 | `examples/benchmark.py`、`examples/sweep/` | DeepInfer 的 benchmark 会避开 EPLB 统计 all-gather 的那些步（`steps_until_lb_stat_flush`） |
| 吞吐、TTFT、TBT | `stats_logger.py` 另有 MFU、KV 用量、NCCL 显存 | MFU 要 FLOPs 估算（`flops_estimator.hpp`），2.5 做 CPU 开销时再加 |
| `greedy_match` + `nll` | `tests/models/offline_decode_ppl.json` 逐样本 PPL，`test_kl.py` | 同一思路；DeepInfer 把并行配置也钉进黄金文件，换配置数值就变 |
| 没有 | `profile_server.py`：运行中通过 HTTP 触发 profile | 离线场景不需要 |

## 常见坑

- `cpu_launch` 很小不代表 forward 快，forward 的真实时间在 `gpu_forward`，CPU 侧的等待在 `cpu_sample_wait`。
- 第一次 `generate` 包含 CUDA graph 捕获和各种懒初始化，驱动循环先跑一个 warmup 再清空统计。
- `arrival_step` 是虚拟时间：TTFT 从 `add_request` 的墙钟时间算起，不含虚拟等待。
- `nanovllm/__init__.py` 一 import 就拉 torch。想让 `stats` 和 `bench` 的纯 Python 部分在没有 torch 的机器上跑测试，把 `LLM` 改成懒加载。
- 埋点本身有开销（每步几个 `perf_counter`、每个 token 一次 list append）。2.5 做 CPU 开销时要记得它在。
