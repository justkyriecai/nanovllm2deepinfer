## 发现问题

### 实验一：三个问题

跑一遍 nano-vllm 自带的 `bench.py`：256 个随机请求一次到达，prompt 和输出长度都在 100–1024 之间。

```bash
python bench.py
# 没有本地 GPU：modal run scripts/modal_run.py --cmd "python bench.py"
```

**先预测**：跑完之后，你能不能回答：GPU 有多大比例的时间在干活？等第一个 token 最久的那个请求等了多久？有没有请求被抢占过？

**现象**（L4，Qwen3-0.6B）：

```
Total: 133966tok, Time: 79.34s, Throughput: 1688.41tok/s
```

三个问题一个都答不了。这个数是总 token 数除以总时间，把一切都平均掉了。想象两次运行吞吐都是 1688：一次 GPU 全程满载、只是每步算得慢；另一次 GPU 每步很快、但 30% 的时间空着等 CPU。这个数字分不出它们。

### 实验二：一步里 CPU 和 GPU 各花多久

要分出上面两种情况，每一步至少要知道两个时长：这一步总共多久（墙钟），GPU 真正在算的多久。先用最朴素的办法试试：`perf_counter` 包住 `ModelRunner.run()` 里的两行（`nanovllm/engine/model_runner.py`，`logits = self.run_model(...)` 和 `token_ids = self.sampler(...).tolist()`），第 100 步之后打印 5 行。

```python
# 临时实验，跑完 git checkout 还原
t0 = perf_counter()
logits = self.run_model(input_ids, positions, is_prefill)
t1 = perf_counter()
token_ids = self.sampler(logits, temperatures).tolist() if self.rank == 0 else None
t2 = perf_counter()
print(f"prefill={is_prefill} bs={len(seqs)} launch={(t1-t0)*1e3:.2f}ms sample_wait={(t2-t1)*1e3:.2f}ms")
```

**先预测**：decode 步里，`launch`（前向那一行）和 `sample_wait`（采样那一行）哪个大？估一下倍数：Qwen3-0.6B 的 bf16 权重约 1.2 GB，L4 的显存带宽约 300 GB/s，一步 decode 至少要把权重读一遍。

**现象**：

```
step=101 prefill=False bs=236 launch=0.55ms sample_wait=72.84ms
step=102 prefill=False bs=236 launch=0.52ms sample_wait=73.08ms
```

前向那一行只花 0.5 ms，采样那一行花了 72 ms，差 130 倍。前向明明是整个模型 28 层的计算，为什么计时只有半毫秒？而采样只是一次 softmax 加 argmax，为什么要 72 ms？

## 分析问题

- **追问链**：`launch` 为什么这么小 → PyTorch 调一个 CUDA kernel 时，CPU 只是把它放进 GPU 的队列就返回，**不等它算完**。`run_model` 把几百个 kernel（decode 时是一张 CUDA graph）发射出去就回来了，这时 `logits` 还没算出来 → 什么时候 CPU 才会等？只有它**需要结果**的时候：`.item()`、`.tolist()`、`.cpu()`、显式 `synchronize()`。`run()` 里唯一这样的地方是 `.tolist()`，所以前向的 72 ms 全部落在了采样那一行头上 → 结论：**CPU 侧的计时量不到 GPU 时间**。`perf_counter` 包住前向，得出的是"发射用了多久"，不是"算了多久"。
- **卡在哪种资源上**：这一节不卡资源，卡的是看不见。但顺手把 72 ms 算一遍，后面好几节都要用这个算法。
- **量化**：decode 一步要从显存读什么？权重 1.2 GB，加上每个请求的 KV cache。Qwen3-0.6B 每个 token 的 KV 是 28 层 × 8 个 KV 头 × 128 维 × K 和 V 两份 × bf16 2 字节 = 112 KB。第 101 步 `bs=236`，每个请求的上下文约 650 个 token，KV 一共 112 KB × 650 × 236 ≈ 17.5 GB。合计 18.7 GB，按 300 GB/s 要 62 ms，实测 72.5 ms，带宽利用率约 85%，剩下的是 attention 计算、采样和 kernel 之间的间隙。**这 18.7 GB 里 17.5 GB（94%）是 KV cache，权重只占 6%。** 并发一高、上下文一长，decode 的瓶颈就从读权重变成读 KV。3.1 的 MLA、4.3 的压缩 KV、4.4 的稀疏 indexer 针对的都是这一块。
- **理论**：性能工程的起点是测量。`reference/gpu-perf-engineering-resources/` 第 3 节 "Profiling, benchmarking, and correctness"：Nsight Systems 看 CPU/GPU 时间线；Etalon（第 5 节 Serving benchmarks）定义了 TTFT、TPOT（本仓库叫 TBT）和 goodput，这是推理服务的标准指标。
- **那 GPU 时间到底怎么量**：最直接的想法是在前向后面加一行 `torch.cuda.synchronize()`，强制 CPU 等前向算完再打点。这样做测量本身会改变被测对象：

  ```
  现在：  CPU [发射前向][发射采样][········等 .tolist()········]
          GPU    [==========前向==========][采样]          ← 首尾相接
  加同步：CPU [发射前向][···等前向···][发射采样][··等··]
          GPU    [==========前向==========]   空转   [采样]  ← 多出一个 bubble
  ```

  GPU 在前向和采样之间多出一段空转，这一步比不测的时候慢；更糟的是 2.7 的 ZOS 要让 CPU 在 GPU 计算时准备下一步，插一个同步就把重叠打掉了，会测出"这个优化没用"的错误结论。**正确做法是 CUDA event**：`event.record()` 往 GPU 队列里插一个书签，立刻返回；GPU 执行到书签时记下时间戳；`start.elapsed_time(end)` 读出两个书签之间 GPU 过了多久。读数只有在 GPU 跑过书签之后才有效，而 `.tolist()` 返回时 GPU 已经把采样之前的一切都做完了，所以**把读数放在 `.tolist()` 之后，就不需要新增任何同步点**。
- **DeepInfer 怎么做**：`deepinfer/timer.py:233-248` 的 `CUDATimer.record` 是一个上下文管理器，进入时插 start event、退出时插 end event，只存起来不读；`:264-270` 的 `flush_out` 过一段时间统一读，而且先用 `end_event.query()` 问一句"GPU 跑过这个书签没"，跑过才 `synchronize` 读数，没跑过留到下次。它要这么绕是因为 ZOS 下没有每步的 `.tolist()` 同步点，CPU 一直跑在 GPU 前面，没有一个天然时刻能保证 event 都完成了。`cpu_timer.record`（`:49-63`）里套了一层 `torch.profiler.record_function`，所以它的每个阶段会自动出现在 profiler 时间线上。汇总在 `deepinfer/stats_logger.py`，每 100 步一次，含 MFU（用 `csrc/engine/flops_estimator.hpp` 估 FLOPs）。正确性靠 `tests/models/offline_decode_ppl.json` 的逐样本 PPL 黄金值（`test_offline_inference.py:156-160`，`assert actual == expected`，**逐位相等**）和 `tests/models/test_kl.py`（逐步 decode 和整段 prefill 的 logprob 之间 KL 为 0）。

**思考题**：`flush_out` 里如果去掉 `query()` 判断、每次都直接 `synchronize()`，在 ZOS 下会发生什么？用上面的时间线画一画。

## 解决问题

三个任务，照 DeepInfer 的思路，保持 nano-vllm 的体量。脚手架（数据类的字段、场景、报告格式、CLI、测试）由 `start-step` 先写好，你写的是下面标出来的关键逻辑。

### 任务 A：每步耗时拆分（约 20 分钟，你写约 40 行）

- **目标**：引擎每一步生成一条 `StepRecord`，7 段耗时都有值，存进 `engine.step_records`；派生 `gpu_busy = (gpu_forward + gpu_sample) / wall`。
- **思路**：7 段在两个地方测。`ModelRunner.run()` 里用 `perf_counter` 量 `cpu_prepare / cpu_launch / cpu_sample_wait`，用 3 个 CUDA event 量 `gpu_forward / gpu_sample`（前向的结束就是采样的开始，中间那个 event 共用），结果存到 `self.last_timing`；`LLMEngine.step()` 量 `cpu_schedule / cpu_postprocess / wall`，拼成一条记录。rank 0 的 runner 和 engine 在同一个进程，直接读。
- **已备好**：`nanovllm/engine/stats.py` 的 `StepRecord` 字段（统一用秒）、`tests/test_1_1.py` 里的 `test_gpu_busy` 和 `test_step_records`、`engine.trace` 回调的约定（每步调一次，任务 B 用）。
- **你写什么**：`gpu_busy`；`run()` 里的打点和 event；`step()` 里的拼装。最容易写错的两处：**采样结束的 event 必须 `record` 在 `.tolist()` 之前**，放在后面就把 CPU 等待也算进了 `gpu_sample`；`elapsed_time` 返回毫秒，要 `/ 1000`，测试里 `gpu_forward < wall` 这一条专门抓这个。event 在 `__init__` 里建一次反复用，放在 `warmup_model()` 之前，因为 warmup 就会调 `run()`。TP > 1 时 event 每个 rank 都 record（开销可忽略），只有 rank 0 读。
- **改哪里**：

  | 文件 | 函数 | 做什么 |
  |---|---|---|
  | `nanovllm/engine/stats.py` | `StepRecord.gpu_busy` | 一行 |
  | `nanovllm/engine/model_runner.py` | `__init__`、`run` | 3 个 event；`perf_counter` 打点；`.tolist()` 之后读 event，存 `self.last_timing` |
  | `nanovllm/engine/llm_engine.py` | `__init__`、`step` | `step_records`、`trace`；量 schedule / postprocess / wall，拼 `StepRecord` |

### 任务 B：每个请求的时间戳，和按步驱动的 bench（约 20 分钟，你写约 50 行）

- **目标**：每个请求结束时收成一条 `RequestRecord`，TTFT 和 TBT 从它算；一条命令跑完一个场景、打印报告、可选地把每步写成 JSONL trace：`python -m bench.run --scenario mixed_long_short --trace out/mixed.jsonl --json out/mixed.json`。
- **思路**：时间戳只能在事件发生的地方记。`Sequence` 构造时记 `arrival_time`，`append_token` 时追加 `token_times`，`preempt` 时 `num_preemptions += 1`；`Scheduler` 每步记下谁结束、谁被抢占；`LLMEngine.step()` 收走这两个名单并清空，结束的请求打包成 `RequestRecord`，本步调度的 `seq_ids`、`finished`、`preempted` 也写进 `StepRecord`（对照 DeepInfer 调度决策时要用）。驱动循环按 `arrival_step` 塞请求：**到达时间按步数定义，不按墙钟**，这样 GPU 快慢抖动不会改变调度决策，前后两次才能比。引擎空闲但还有请求没到时只推进步数。`bench/` 里只有 `run.py` 碰 GPU，其余纯 Python，测试不花 GPU 的钱。
- **已备好**：`bench/workloads.py` 四个场景（`steady_decode`：原 bench；`mixed_long_short`：128 个短请求稳态 decode，第 100 步起每 20 步插一个 3072 token 的长 prompt；`kv_pressure`：512 个请求、输出 768–1024；`many_small`：512 个 16–32 in / 32–64 out），都接受 `seed`；`bench/metrics.py`（`percentile` 线性插值、`summarize_steps` 按 prefill / decode 分组、`summarize_requests`、`format_report`）；`bench/trace.py`（`TraceWriter` 实现 `__call__`，挂到 `engine.trace`）；`bench/run.py` 的 `main()`、`warmup()`、引擎参数透传（`--max-num-seqs`、`--gpu-memory-utilization`、`--max-num-batched-tokens`、`--max-model-len`、`--enforce-eager`，后面各节靠它调引擎）、`--num-steps`（跑 N 步就停，录 nsys 用）、测量段包在 `torch.cuda.profiler.start()/stop()` 里；`RequestRecord` 的 `ttft` / `tbt` property；测试 7 条。
- **你写什么**：`Sequence` / `Scheduler` / `step()` 里的记录和收集；`bench/run.py` 的 `drive()` 循环；`summarize_steps` 里的 `gpu_busy`（**按时间加权**：总 GPU 时间除以总墙钟，不是对每步的比例求平均，30 ms 的步和 10 ms 的步分量不一样）。最容易写错的一处：`scheduler.finished.append(seq)` 要放在判定结束的 `if` **里面**。放在外面不报错，但每步会把所有在跑的请求都当成"结束"打包一次，TTFT 和 TBT 全错；测试里 `sum(len(s.finished)) == 2` 就是抓它的。观测字段不要进 `Sequence.__getstate__`：TP > 1 时它决定什么被 pickle 到别的 rank，`token_times` 会越长越大。
- **改哪里**：

  | 文件 | 函数 | 做什么 |
  |---|---|---|
  | `nanovllm/engine/sequence.py` | `__init__`、`append_token` | `arrival_time`、`token_times`、`num_preemptions` |
  | `nanovllm/engine/scheduler.py` | `__init__`、`preempt`、`postprocess` | `finished` / `preempted` 名单，由 engine 清空 |
  | `nanovllm/engine/llm_engine.py` | `step` | 收走名单，拼 `RequestRecord`，`seq_ids / finished / preempted` 进 `StepRecord` |
  | `bench/run.py` | `drive` | 按 `arrival_step` 塞请求，空闲只推进步数，跑够 `num_steps` 个引擎步就停，每步包一个 NVTX range `step N`，返回墙钟时长 |
  | `bench/metrics.py` | `summarize_steps` | 时间加权的 `gpu_busy` |

### 任务 C：正确性（约 20 分钟，你写约 30 行）

- **目标**：一条命令判断引擎还算得对不对。`--write` 在已知正确的代码上存基线，`--golden` 比对，超出容差退出码 1。
- **思路**：拿 HF transformers 当裁判。8 个固定的真实 prompt，各生成 32 个 token，每个 prompt 两个数：`greedy_match`，nano 近贪心（`temperature=1e-3`，nano 的 `SamplingParams` 禁止 0）的输出和 HF `generate(do_sample=False)` 从开头起连续相同的 token 数；`nll`，把 nano 的输出喂给 HF 做 teacher forcing，算平均负对数似然：HF 认为这些话越正常，这个数越低。attention 或 KV 坏了，模型会说胡话，`nll` 会跳。判定按 8 个 prompt 的**均值**、带容差（`greedy_match` 均值不低于基线一半，`nll` 均值不高于基线 + 0.3），因为 bf16 下 logits 会平局，单个 prompt 偶尔第一个 token 就翻、`greedy_match` 从 32 掉到 0 是正常噪声；真坏了是 8 个一起掉。这是 DeepInfer `offline_decode_ppl.json` 的缩小版，差别见下面的对照表。
- **已备好**：`bench/correctness.py` 的 prompt、CLI、加载 nano 和 HF（nano 用 `gpu_memory_utilization=0.5` 给同一张卡上的 HF 留显存）、生成、打印、黄金文件读写；三条测试，其中 `test_teacher_forced_nll` 用一个假模型专门检查对齐。
- **你写什么**：`greedy_match`（公共前缀长度，`zip` 到短的那个就停）、`teacher_forced_nll`、`compare`。最容易写错的一处：**位置 t 的 logits 预测的是 t+1 的 token**，所以给输出第一个 token 打分的是 `logits[len(prompt) - 1]`，错一位算的就是另一回事。`log_softmax` 之前先转 `float`，bf16 的精度不够算 log-prob。
- **改哪里**：

  | 文件 | 函数 | 做什么 |
  |---|---|---|
  | `bench/correctness.py` | `greedy_match`、`teacher_forced_nll`、`compare` | 两把尺子和判卷规则 |

### 读报告

开头的三个问题现在都能答：GPU 忙碌比例（decode 97–99%）、等最久的请求（`steady_decode` TTFT max 49 s）、有没有抢占（有，135 次）。接着看三个值得追的数。

1. **decode `gpu busy` 98%，文档原来按 H100 + 8B 估的是 70–85%。** 两者都对：CPU 每步的固定开销（调度 + 准备 + 发射 + 后处理）约 1.5 ms，不随卡变；L4 慢，一步 GPU 要 60 多 ms，1.5 ms 占比很小；换 H100 一步可能只要 10 ms，同样的 1.5 ms 就显眼了。`many_small` 的 89.7% 已经在往这个方向走。硬件不同，比例就不同，这是 2.5 的入口。
2. **`steady_decode` 在 L4 上也抢占。** L4 留给 KV 的显存约 18 GB，按 112 KB/token 只放得下约 16 万个 token；256 个请求到后期平均 1100 个 token，要 28 万。文档原来预计只有 `kv_pressure` 会抢占，那是按 H100 80 GB 写的。
3. **prefill 的数字自相矛盾。** 看 `steady_decode` 的 prefill 三行：`cpu_launch p50 ≈ 61 ms`，`gpu_forward p50 ≈ 62 ms`，`cpu_sample_wait p50 ≈ 1.4 ms`。CPU 发完 kernel，GPU 几乎同时就算完了，一点都不用等；可 `gpu busy` 却写着 98%。prefill 时 GPU 真的 98% 在算吗？

第 3 个问题的答案：**不是。event 量的是 GPU 经过两个书签之间的跨度，不是忙碌时间。** 书签之间 GPU 空等 CPU 的间隙也被算了进去。decode 走 CUDA graph，CPU 一次交出整张图，跨度等于忙碌，读数准；prefill 走 eager，28 层几百个算子逐个发射，每个都要过 Python 和 dispatcher，CPU 发一个 kernel 要几十微秒，而 0.6B 的 kernel 往往算得更快。发射时间几乎是常数（28 层的 kernel 数不随 token 数变，`cpu_launch` p50 61 / p99 68 ms），GPU 时间随 token 数线性涨（`gpu_forward` p50 62 / p99 432 ms）。所以**大 prefill 步（开头那几步，上万 token）是 GPU 瓶颈；小 prefill 步（被抢占后回来重新 prefill，几百 token）是 CPU 发射瓶颈**，p50 落在后者上。读法：`cpu_launch ≈ gpu_forward` 且 `cpu_sample_wait ≈ 0`，就是 launch-bound。`gpu_busy` 是上限，CPU 领先 GPU 时准，CPU 拖住 GPU 时偏高。要看清书签之间的空隙，得看 kernel 级的时间线。

### 看时间线

```bash
python -m bench.timeline --scenario steady_decode     # 录 3 个 prefill 步 + 3 个 decode 步
# 把 out/steady_decode_prefill.json 拖进 https://ui.perfetto.dev
```

第一次看 Perfetto 会完全看不懂，按这条路线走一遍：

1. **认轨道**。`python <pid>` 是 CPU 进程：主线程是一张火焰图，上层调用下层，块的宽度是耗时。`python 0` 其实是 GPU 0（torch profiler 用设备号当进程名），`stream 7` 上每个色块是一个 kernel 真正执行的时间。`Spans` 是 CPU 发射和 GPU kernel 之间的关联箭头，先忽略。操作：搜索框搜 `prefill step 1`，回车，按 **F** 聚焦，**W / S** 缩放，**A / D** 平移。
2. **`prefill step 0`，约 2.1 秒**。CPU 那排中间一大块 `_compile.compile_inner`（约 1.1 秒），GPU 那排同一段完全空白：torch.compile 遇到 warmup 没见过的形状，当场重编译。GPU 轨道上的 `prefill step 0` 标注条横跨整整 2.1 秒，下面实际有 kernel 的只有开头一小段，这就是"跨度 ≠ 忙碌"的现场示意。报告里 prefill `wall max` 和 `gpu_sample max` 的秒级尖峰就是它，见常见坑里的 warmup。
3. **`prefill step 1`，约 400 ms**。CPU 那排分两段：前 85 ms 是密密麻麻的 `cudaLaunchKernel`，后 315 ms 是一整条 `aten::to → _to_copy → copy_ → cudaMemcpyAsync`，这就是 `.tolist()` 在等 GPU 把结果拷回来。GPU 那排从头到尾 kernel 几乎不断。所以这一步是 GPU 瓶颈：CPU 85 ms 就发完了，剩下的时间都在等。看两段谁长，就知道瓶颈在哪边。
4. **上下两排是对齐的**。同一根时间轴（CUPTI 的 GPU 时间戳换算到 CPU 时钟）。CPU 还在发射时 GPU 已经在执行，这就是异步。点一个 `cudaLaunchKernel`，Perfetto 画出它指向 kernel 的箭头：开头几个几乎垂直，越往后越斜，说明 GPU 跟不上 CPU，队列在积压。反过来 launch-bound 时队列总是空的，kernel 之间会出现白色空隙。
5. **换 decode 那份**。CPU 那排只有一个很短的 `cudaGraphLaunch`，GPU 那排是一长串紧挨着的 kernel，然后 CPU 在 `.tolist()` 等。和 prefill 对比，CUDA graph 省掉的就是那 85 ms 的发射。

**nsys**。上面用的是 `torch.profiler`，第一次看够了：能看到 PyTorch 算子名，浏览器就能开。从 2.5 起要看长一点的时间线、按步统计，用 nsys（Nsight Systems）。Modal 的镜像里已经装好：

```bash
nsys profile -t cuda,nvtx,osrt --sample=none --cpuctxsw=none \
  --capture-range=cudaProfilerApi --capture-range-end=stop \
  -o out/many_small python -m bench.run --scenario many_small --num-steps 30
nsys stats --report nvtx_sum,cuda_gpu_kern_sum out/many_small.nsys-rep
```

- `-t cuda,nvtx,osrt`：录 CUDA 调用和 kernel、NVTX 标签、系统调用。
- `--sample=none --cpuctxsw=none`：关掉 CPU 采样。Modal 的容器跑在沙箱里，CPU 采样用不了；本机有卡时可以去掉。
- `--capture-range=cudaProfilerApi`：只录 `bench.run` 用 `torch.cuda.profiler.start()/stop()` 圈出来的测量段，加载、warmup、编译都不进来，报告才 200 KB 左右。
- `--num-steps 30`：跑 30 步就停，不用把整个场景跑完。
- `nsys stats` 不开图形界面就能出表：`nvtx_sum` 里是每个 `step N` 的时长（`bench.run` 给每步打了 NVTX 标签），`cuda_gpu_kern_sum` 里是每种 kernel 一共花了多久。要看图，把 `.nsys-rep` 拉回本地，用 Nsight Systems 桌面版打开（有 macOS 版）。

在 L4 上实测：NVTX 汇总里正好是 `step 0` 到 `step 29`（1 个 prefill 步 311 ms，29 个 decode 步各 31–37 ms），warmup 没被录进来；kernel 汇总里第一名是 bf16 GEMM，占 32.7%。

每一步都把图上看到的和报告里的数字对起来：图负责看见，数字负责统计。

**新浮现的问题**：工具有了，第一件事是拿边界请求试试引擎：发一个比显存总量还大的 prompt、中途 abort 一个请求。这是 2.1。`mixed_long_short`、`kv_pressure`、`many_small` 的报告分别是 2.2、2.3、2.5 的 before，留在 `out/`。

## 常见坑

- `cpu_launch` 很小不代表 forward 快，forward 的真实时间在 `gpu_forward`，CPU 侧的等待在 `cpu_sample_wait`。
- **warmup 要覆盖真实负载会出现的形状，包括 batch=1。** 只跑一个短请求做 warmup，第一个大 prefill 进来 torch.compile 当场重编译 1 秒多，混进测量；抢占后单独回来重新 prefill 的 batch=1 又要编译一次（compile 对大小 1 的维度单独特化）。`bench/run.py` 的 `warmup()` 用场景的前 64 个请求跑一遍、再跑一个单请求，之后清空记录。补上之后 prefill 的 `gpu_sample max` 从 1300 ms 降到 0.4 ms。
- **event 量的是跨度不是忙碌**，`gpu_busy` 是上限，见"读报告"。
- `arrival_step` 是虚拟时间：TTFT 从 `add_request` 的墙钟时间算起，不含虚拟等待；按步到达也不等于真实在线流量。
- 测量代码自己也会错，而且错了不报错：`sample_wait = (t2 - t1) + 1000` 跑起来每步显示 1000.xx ms，引擎一切正常。先对一眼数量级再信数字。
- `greedy_match` 单个 prompt 掉到 0 不一定是坏了：bf16 下 logits 的最小间隔是 0.125，前两名经常被舍入成相同的值，HF 的 argmax 取下标小的，nano 的 gumbel 采样随机选一个，第一个 token 一翻后面全不一样。nano 的采样没有固定 seed，每次跑 `--write` 数字会略有不同。2.10 换真贪心后这类平局按固定规则选。
- `nll` 对重复文本不敏感：`"France in France in France"` 的 nll 只有 1.3，因为重复本身在语言模型眼里是"合理"的。`greedy_match` 和 `nll` 要一起看。
- `nanovllm/__init__.py` 一 import 就拉 torch。`bench/` 里除了 `run.py`、`timeline.py`、`correctness.py` 不要 import torch，`pyproject.toml` 的 `pythonpath = ["."]` 让测试能直接 `import bench`。
- 埋点本身有开销（每步几个 `perf_counter`、每个 token 一次 list append）。2.5 做 CPU 开销时要记得它在。
- Modal 容器里写的文件不会自动回本地：产物统一写 `out/`，跑完用 `modal volume get` 拉回；本机开了代理时要绕开（文件头有说明）。
