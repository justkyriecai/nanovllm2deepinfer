# 2.7：GPU 在等 CPU 处理上一步的结果

> 起点：2.6 做完的代码　硬件：1×H100，Qwen3-0.6B / 8B　预计改动：400–600 行　轴：2 每步执行模型

## 1. 发现问题

**关注什么**：现在每一步里，GPU 什么时候空着。

```bash
bash bench/nsys.sh many_small --model ~/huggingface/Qwen3-0.6B --max-num-seqs 512
```

**先预测**：2.5 和 2.6 之后 CPU 每段都很短了，GPU 还会空吗？空在哪两个 kernel 之间？

**现象**：nsys 上每一步的最后一个 kernel（sampler）结束后，到下一步第一个 kernel 开始之间，仍有一段固定的空隙。对着 CPU 线程看，这段时间 CPU 在做：`.tolist()` 返回 → `postprocess(N)` → `schedule(N+1)` → `prepare(N+1)` → H2D → launch。**每一段都已经很短，但它们是串行的，而且全部发生在 GPU 空闲的时候。** 1.1 的 `gpu_busy` 在 0.6B 上停在 70–80% 不再上升。

## 2. 分析问题

- **追问链**：空隙 → 第 N 步的结果要回到 CPU（`.tolist()`）才能做 postprocess，postprocess 完才能 schedule 第 N+1 步，schedule 完才能 launch → 这条链上 GPU 没活 → 根本原因是 CPU 和 GPU 串行，中间一次同步。
- **本质**：要让 GPU 不空，CPU 必须在 GPU 跑第 N 步的时候就把第 N+1 步准备好并发射出去。但第 N+1 步的输入（每个请求的下一个 token）依赖第 N 步的采样结果，CPU 还没拿到。
- **理论**：DeepInfer QA 文档 "Asynchronous scheduling (zero-overhead batch scheduler)" 一节（`reference/DeepInfer/doc/inference_deployment_qa.md`）；它引用的 SGLang v0.4 overlap scheduler 和 NanoFlow。核心思想一句话：**CPU 乐观地调度第 N+1 步，输入 token 直接在 GPU 上从第 N 步的采样结果取，post-process(N) 挪到 forward(N+1) 发射之后再做。**
- **DeepInfer 怎么做**：
  - `Worker.execute_model_step`（`deepinfer/worker/worker.py:89-189`）是所有步型的统一入口，顺序是：① forward(N) 发射 → ② `_post_process_step(prev)` 处理 N-1 步 → ③ sample(N) 发射 → ④ 记 `sample_end_evt`，把本步状态存进 `prev_step_state`。**每步只同步一次**：`_post_process_step` 里的 `sample_end_evt.synchronize()`（`:263`），而且它在 forward(N) 发射之后。
  - CPU 看到的 `Sequence` 滞后一步，调度器用上界：`start_inflight_step(nextn+1)` 在调度时加（`scheduler.hpp:726`，`sequence.hpp:244`），`finish_inflight_step` 在 post-process 时减（`:249`）；`get_num_blocks` 和 `seqlen_k` 都含 `total_inflight_tokens`（`sequence.hpp:291`），所以 block 永远够用。
  - 输入在 GPU 上拼：`prepare_zos_inputs`（`csrc/engine/zos.cpp:142`）算 `remap[i]` = 请求 i 在上一步 batch 里的下标（新请求 -1）；`gather_input_ids_zos` kernel 从上一步 GPU 上的采样结果按 remap 取 token，新请求的 token 由 CPU 填。`compute_seqlens_k_zos` 在 GPU 上修正 K 长度。
  - 采样前 `update_metadata_for_sampling_zos`（`zos.cpp:279`）把修正后的 seqlen 写回 `SequenceMetadata`，`refresh_for_sampling`（`sequence.hpp:408`）更新 last token。这就是 2.5 说的"元数据必须是带指针的池对象"。
  - 结束检测晚一步：EOS 在第 N 步产生，第 N+1 步的 post-process(N) 才看到，但第 N+1 步已经把它调度进去了，GPU 多跑一步，结果丢弃（`scheduler.hpp:906-915`）。block 在第 N+2 步才释放（2.1 埋的接缝）。
  - 队列空时 `flush_inflight_reqs`（`worker.py:274`）把挂着的一步处理掉。
  - `forbid_cuda_sync`（`deepinfer/utils.py:119`）包住 forward 和采样，任何 torch 可见的 CPU-GPU 同步直接抛异常，`Event.synchronize` 除外。
  - CUDA graph 改 `input_on_device=True`：H2D 在 graph 之外，GPU 侧准备直接写 graph 的输入 buffer。
  - 有 DP 时投票用 CPU 通信组，`has_unfinished_requests` 也在 CPU 上 allreduce（5.3）。

## 3. 要做什么

### 3.1 三段式 `execute_model_step`

**改哪里**：`nanovllm/engine/model_runner.py` 的 `run`，`llm_engine.py` 的 `step`。

- `run` 拆成：`launch_forward(metadata)`、`launch_sample(metadata)`、`post_process(prev_state)`。`step()` 的顺序改成 DeepInfer 的四步。
- `WorkerStepState` 保存：本步的 `seq_metadata_list`、采样输出 tensor（GPU 上）、D2H 到 pinned buffer 的 `token_ids`、`sample_end_evt`。
- `post_process(prev)`：`prev.sample_end_evt.synchronize()` → 读 pinned 的 token_ids → `scheduler.postprocess`。这是每步唯一的同步。
- `.tolist()` 删掉，换成 `token_ids_gpu → pinned (non_blocking) + event.record()`。
- 1.1 的 `gpu_forward / gpu_sample` 读 event 的位置要跟着挪：在 `post_process(prev)` 里读 prev 的 event。

### 3.2 inflight 计数

**改哪里**：`csrc/sequence.hpp`、`scheduler.hpp`（2.6 的 C++）。

- 2.1 预留的 `total_inflight_tokens` 启用：调度时 `+= 1`（没有 MTP 时每步 1 个 token），post-process 时 `-= 1`。
- `num_blocks`、`seqlen_k` 用 `num_tokens + total_inflight_tokens` 算；`can_append` 同样。
- 2.3 的 `reset_for_recompute` 清零它。

### 3.3 GPU 侧输入拼接

**改哪里**：`csrc/prepare_input.cpp` 加 `remap`；新建一个小 Triton kernel `gather_input_ids`。

- CPU 算 `remap[i]`（上一步 batch 里的下标，新请求 -1）和新请求的 token（pinned）。
- GPU kernel：`input_ids[i] = remap[i] >= 0 ? prev_sampled[remap[i]] : fresh[i]`。`positions / context_lens / slot_mapping` 同样可以在 GPU 上由 `seqlen` 算出来，先用 CPU 算（它们不依赖采样结果），只有 token 必须在 GPU 上取。
- 被抢占或结束的请求在 post-process 时发现，它在本步的输出丢弃。

### 3.4 延迟到位

- 2.1 的"释放放在 run 之后"现在变成"释放放在 post-process(N) 之后、forward(N+1) 已发射"，也就是晚两步。2.4 的 COW unpin 同样要等克隆的 event。
- 2.5 的 `DeferredRelease` 收集的东西在同一个位置归还。

### 3.5 守卫

- 新建 `nanovllm/utils/sync_guard.py`：`forbid_cuda_sync()` 上下文管理器，用 `torch.cuda.set_sync_debug_mode("error")` 或自己 hook `torch.cuda.synchronize / .item / .tolist / .cpu()`；`Event.synchronize` 放行。`launch_forward` 和 `launch_sample` 都包在里面。

### 3.6 flush 和开关

- `LLMEngine.flush_inflight()`：队列空时处理挂着的一步。`generate()` 结尾调用。
- `Config.zero_overhead_scheduling: bool = True`，关掉时退回同步路径（prefill 步本来就同步做，照 DeepInfer：prompt 步当场 post-process）。

## 4. 验收

同一个实验重跑：

```bash
bash bench/nsys.sh many_small --model ~/huggingface/Qwen3-0.6B --max-num-seqs 512
python -m bench.run --scenario steady_decode
```

1. nsys 上 decode 步之间的空隙消失，kernel 首尾相接；`gpu_busy` 在 0.6B 上 > 90%。
2. 吞吐提升量和 2.5 测出的 CPU 占比对得上（CPU 占 20%，吞吐就该提 20% 左右）。写进报告。
3. 关掉开关，数字回到 2.6。
4. 正确性：`greedy_match / nll` 和黄金文件一致；四个场景的 trace 和 2.6 的一致（调度决策不变，只是时序变了）。
5. `tests/test_2_7.py`：(a) 守卫在 forward 里 `.item()` 会抛；(b) 一个请求 EOS 后，它的 block 在两步之后才回到 free list；(c) 队列空时 `flush_inflight` 把最后一步的 token 取回来；(d) inflight 计数在每个请求结束时归零；(e) 2.1–2.6 全过。

**新浮现的问题**：GPU 不空了，但低并发（4–8 个请求）时吞吐很低，`gpu_forward` 几乎不随并发变。算力闲着。这是 2.8。

## 常见坑

- **最难调的一节**，bug 全是时序：block 释放早了（GPU 还在读）、结束判定早了（丢了一个 token）、pinned buffer 被下一步覆盖（CPU 还没读）。每个 buffer 都要双缓冲或者按 event 保护。
- `.tolist()` 没了之后，1.1 的 CUDA event 不再自动有效，必须在 `sample_end_evt.synchronize()` 之后读。
- prefill 步不走 ZOS（输入不依赖上一步），照 DeepInfer 当场 post-process。
- 2.4 的 COW 克隆和 forward 现在可能在不同时刻，unpin 源块要等克隆 event。
- 关掉守卫来"修"一个同步错误是作弊；找到那个同步点，把它挪走。
