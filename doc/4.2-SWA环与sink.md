# 4.2：窗口只有 128，却存了整个上下文

> 起点：4.1 做完的代码　硬件：1×B200　预计改动：400–600 行　轴：2 显存 / 4 模型结构

## 1. 发现问题

**关注什么**：纯 SWA 层（`compress_ratios[l] == 0`）每个 query 只看最近 `window_size` 个 key（V4.1 是 128），再加一个 per-head 的 sink。它的 KV 该怎么存。

先用最直接的方式实现：把 SWA 层当成普通 MLA 层，KV 按 paged 存进 4.1 的 block（给它一个 `ca_cache`），attention 用 3.1 的 FlashMLA 加一个窗口 mask。在 harness 里和 DeepInfer 的 `V4Attention` 对拍，同时看三件事：

```bash
python -m tests.v4.harness --layer 0 --prompt-len 4096 --compare attn     # 数值
python -m tests.v4.harness --layer 0 --prompt-len 131072 --report memory  # 显存
python -m tests.v4.harness --layer 0 --decode --nextn 5 --reject-all      # 投机解码回退
```

**先预测**：128k 上下文下，SWA 层按 paged 存占多少显存？按"只存最近 128 个"存占多少？投机解码一步验证 6 个位置、全部拒绝之后，下一步这 6 个位置的 KV 应该是什么？

**现象**：

- 显存：paged 存法每序列 `131072 × 528 B ≈ 69 MB` **每层**；只存窗口是 `134 × 528 B ≈ 71 KB`，差一千倍。对 V4.1 这种一半的层带 SWA 的模型，paged 存法让 KV 预算被根本用不到的数据吃掉。
- 数值：窗口 mask 版本和 DeepInfer 对得上，说明语义懂了；但 DeepInfer 的 `swa_cache` 形状是 `[num_state_slots, 134, 1, 528]`，不是 paged 的，它根本不走 block table。
- 回退：拒绝 6 个 draft 之后，环里这 6 个位置被写过了。下一步 target 从被接受的位置之后继续，必须把这些位置**重新写一遍**。如果环刚好 128 个槽，最老的 6 个有效 token 已经被 draft 覆盖掉，窗口就缺了一角。

## 2. 分析问题

- **追问链**：显存浪费 → 窗口外的 KV 永远不会被读 → 只需要保留最近 `window_size` 个 → 容量有界，用 4.1 的槽位而不是页 → 位置 `pos` 放在 `pos % ring_size`，自然覆盖 → 投机解码会把未来 `nextn` 个位置提前写进环，拒绝后要回退 → 环要比窗口多 `nextn + 1` 个槽，让被 draft 覆盖的旧 token 还在。
- **本质**：SWA 的 KV 是一个固定长度的滑动窗口，环形缓冲是它的自然数据结构；paged 是给容量无界的东西用的。sink 是 softmax 分母里一个额外的 per-head 常数项，让窗口内没有强匹配时注意力有地方"放"。
- **量化**：`ring_size = window_size + max_backtracking = 128 + 6 = 134`（`cache_engine.py:88`，`max_backtracking = max(env, nextn + 1)`，`environ.py:132`）。每序列每层 `134 × 528 B`，和上下文长度无关。
- **理论**：`reference/gpu-perf-engineering-resources/` §4 "KV cache systems"：Jenga（为不同 attention 类型分别管理内存）。sink 的来源是 StreamingLLM（attention sink，不在清单里）：softmax 需要一个"垃圾桶"位置，V4.1 把它做成可学习的 per-head logit 而不是保留第一个 token。
- **DeepInfer 怎么做**：
  - **存**：`slot_mapping_store_swa[i] = state_id × swa_block_size + pos % swa_block_size`（`prepare_tensor_input_v4.cpp:104`），只有最后 `swa_block_size` 个 query 才有 slot（更早的写了也会被覆盖，`:101-106`）。写入走 `_prepare_swa_kv`（`attn.py:402`）→ `fused_norm_rope_hadamard_cast_store_kvcache`（`fused_transform.py:189`）：norm + RoPE（只转最后 64 维）+ FP8 per-32 cast + 按 slot 存，一个 kernel。decode 直接存；prefill 先把当前 chunk 的 KV 以 bf16 形式留在 buffer 里给 attention 用（`cast_back=True`），attention 之后再 `store_kv_cache`（`attn.py:855`），因为 store 的槽可能和下面 load 的槽重叠，**先 load 再 store**。
  - **读（decode）**：不用 block table，用显式索引：`kv_swa_index [total_q, window_size]`（`attn.py:857`）是每个 query 要看的 134 环里的槽号，-1 表示空；attention 走 `decode_mla_mqa_sparse`（`attention_backend.py:125`），`key_cache = swa_cache`、`indices_in_kvcache = kv_swa_index`。也就是说 **SWA 和稀疏 attention 用的是同一个 kernel**：都是"给定 `[total_q, k]` 的索引，去 cache 里取"。
  - **读（prefill）**：窗口可能跨 chunk 边界，前一个 chunk 的尾巴在环里、当前 chunk 在刚算出来的 buffer 里。所以 prefill 把 KV 拼成一个 buffer `[swa_cached | swa_cur | compressed]`（`attn.py:812-826`），环里的部分用 `load_paged_kv_cache`（`load_paged_kv_cache.py:28`）按 `load_segments_swa` 解压成 bf16 放到开头（`:847-851`）；每个 query 的索引是两段连续区间（环里的一段 + 当前 chunk 的一段），C++ 只算 `pivots [total_q, 4]`（两个起点两个长度），GPU 上 `expand_swa_index`（`swa_index.py:10`）展开成 `[total_q, window_size]`。attention 走 `flash_mla_sparse_fwd`（`attention_backend.py:64`）。
  - **sink**：`attn_sink_params [n_head]` fp32（`mla_attn.py:289-293`，`runtime_attn_sink :295`），prefill / decode 都作为 `attn_sink` 传给 FlashMLA（`attn.py:622/:665`），kernel 把它当成一个额外的 logit 加进 softmax 分母。
  - **回退**：环比窗口多 `max_backtracking` 个槽；拒绝的 draft 位置下一步按同样的 `pos % ring` 重写，中间没有任何"撤销"操作。
  - **YoCo 之后**：consumer 层的 SWA 环在 dropped 段（4.1 的 `StateBlock`），内容由 `shared_hidden` 投影（4.5）。

## 3. 要做什么

### 3.1 存

**改哪里**：`csrc/prepare_input.cpp`（2.5 的 C++ 输入准备）、`nanovllm/models/deepseek_v4.py` 的 `V4Attention`。

- `slot_mapping_store_swa [total_q]`：按上面的公式，窗口之外填 -1。
- kv_swa 的投影：V4.1 把 `q_a` 和 `kv_swa` 的投影合成一个 GEMM（`q_a_kv_swa_proj`，`attn.py:280-289`），输出 `[q_lora_rank | qk_head_dim]` 再 split。
- 存 kernel：先用三个 Triton kernel（norm、rope、cast + scatter），4.11 融合。FP8 格式按 4.1 的 `V41_FORMAT`（per-32 UE8M0）。

### 3.2 读

- decode：C++ 算 `kv_swa_index [total_q, window_size]`（环里有效的 `min(pos+1, window)` 个槽，其余 -1），FlashMLA 的 sparse decode 接口（3.1 已经在用 `flash_mla_with_kvcache`，这次传 `indices` 而不是 `block_table`，`is_fp8_kvcache=True`）。
- prefill：拼 `[swa_cached | swa_cur]` buffer；C++ 算 `pivots`，Triton 写 `expand_swa_index`；`flash_mla_sparse_fwd`。
- 2.9 / 2.8 的投机解码下，`kv_swa_index` 对 draft 位置也要给索引（它们看的是 `pos − window .. pos − 1`，其中一部分是本步刚写的 draft）。

### 3.3 sink

- `attn_sink [n_head]` fp32 参数，从 HF 权重装载，传给两条 attention 路径。
- 先用 PyTorch 参考实现验证语义：`softmax([logits, sink])` 去掉 sink 那一列。

### 3.4 元数据

- `InputMetadata` 加 `total_k_swa`、`load_segments_swa`、`kv_swa_index`、`swa_pivots`、`slot_mapping_store_swa`。2.7 的 ZOS 下这些都要能在 GPU 上按 `remap` 修正（`seqlen_k` 变了索引也变）。

## 4. 验收

同一个实验重跑：

1. 显存：128k 上下文下 SWA 层每序列占 `134 × 528 B`，和上下文长度无关；报告里给 paged 存法的对比数字。
2. 数值：harness 上 SWA 层的 attention 输出和 DeepInfer 一致（prefill 单 chunk、prefill 跨 chunk 边界、decode、decode 带 5 个 draft）。
3. 回退：全拒绝 6 个 draft 之后，下一步的输出和"从没写过 draft"的参考一致。
4. `tests/test_4_2.py`：(a) `expand_swa_index` 和 PyTorch 参考一致（含 -1 填充）；(b) 存 kernel 和 `fused_norm_rope_hadamard_cast_store_kvcache_ref`（`fused_transform.py:389`）一致；(c) sink 的 PyTorch 参考和 FlashMLA 一致；(d) 4.1 和前面全过。

**新浮现的问题**：压缩层（`ratio == 1 / 2`）的 KV 怎么存：压缩比 2 的层每两个 token 出一个 latent，chunked prefill 的边界刚好切在中间怎么办，拒绝 draft 后半个窗口的状态怎么退。这是 4.3。

## 常见坑

- prefill 必须先 `load_paged_kv_cache` 再 `store`，槽重叠时反过来会读到本 chunk 刚写的值。
- `kv_swa_index` 的有效长度是 `min(pos + 1, window_size)`，不是 `window_size`；开头几十个 token 的行大部分是 -1。
- 环的索引是 `pos % 134` 不是 `pos % 128`：窗口是 128 个，但槽是 134 个，两者不要混。
- sink 是 fp32，不要在装载时转 bf16。
- FP8 cache 的 scale 和数据在同一个 token 的 528 B 里交错，`load_paged_kv_cache` 解压时要按 `KVCacheFormat` 拆，不要按固定偏移硬编码。
